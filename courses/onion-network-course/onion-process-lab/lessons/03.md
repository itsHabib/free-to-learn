# 3. Construct the outgoing onion

Reuse the idea from the earlier course: the client builds the deepest layer first. The exit must eventually read `{operation:'lookup', item:'luna'}`, while the entry should obtain a successor ID and an encrypted inner packet.

Implement `wrapRequest(hops, body, seq)`. Each layer encrypts `{next, body}` under the hop's forward handle and context. The context authenticates protocol label, circuit, relay, direction and sequence. The supplied crypto wrapper implements AES-GCM; do not replace it with encoding, XOR or a homemade cipher.

On paper label three forward keys `F1, F2, F3`, and draw what each relay receives and what its one successful opening reveals. Explain why construction runs opposite to delivery. Then answer: can you change the `next` field in transit without invalidating authentication?

```sh
node tools/check.mjs 3
```

The check opens your layers to verify both order and successor IDs. It also tries sealing a second message under the same handle/sequence. That must fail. A failed send still reserves its sequence; it is not permission to build another ciphertext under the same key/nonce.

**Done when:** the outer JSON contains ciphertext rather than the request, every local successor is correct, and the nonce reuse guard fires. Absence of a literal request string is a small check, not a confidentiality proof.

If stuck: write the final exit plaintext first, wrap it, then treat that whole encrypted packet as the next outer layer's body. Work with the stored `next` value rather than inventing a different topology.
