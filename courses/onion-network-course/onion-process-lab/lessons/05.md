# 5. Break a real process; choose recovery

Implement `recoveryPlan`. Use the original path length, exclude known failures, and return either a valid replacement path or an explicit stop. The lifecycle will retire the original state and create a new circuit ID and fresh keys; your plan must not secretly shorten the circuit.

```sh
node tools/check.mjs all
node tools/lab.mjs interactive
```

Before each experiment, record a prediction. Commands below are examples; substitute the middle and exit IDs from your actual `open` output.

## A. Middle process loss

Enter `open alpha`, `send alpha luna`, and note the path. If the middle is `r2`, enter:

```text
stop r2
send alpha tide
recover alpha r2
send alpha tide
start r2
directory
```

`stop` terminates that child, rather than setting a boolean in its handler. Compare the old PID to the restarted PID. Compare old and replacement circuit IDs. Why should the restarted process have none of the old circuit state? Why is restarting the sequence at zero safe only with fresh keys?

## B. The archive worked but the reply vanished

```text
open beta
lose-reply beta
send beta luna
recover beta
send beta luna
```

The fault applies after the exit handler serves the request and wraps its reply. Compare the client failure with the operator's `archive` event. The next `send` is your explicit retry. Explain why repeating a read-only lookup is safe here, but repeating a payment would require application-level safeguards. Do not generalize this lab into exactly-once delivery.

## C. Too few relays

Open a new circuit. Stop two of the four relays, then attempt recovery excluding both. Record the explicit stop. Restore the processes before another experiment. Compare availability with the three-hop policy: a two-hop answer would not meet the stated contract.

Finish with `quit`. Preserve the command sequence and relevant output in your report. The client cannot diagnose the failed hop from a generic missing reply; your `stop` command and directory are privileged controller evidence.

**Done when:** one replacement succeeds, one lost reply is correctly interpreted, and one insufficient-capacity case stops without relaxing the policy.
