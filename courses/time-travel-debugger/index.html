Build a time-travel debugger

Build a debugger for a small deterministic virtual machine, then diagnose an unfamiliar program. You own control, inspection, stopping rules, tracing, replay and reverse state search. The supplied VM is original teaching infrastructure. It has no access to native processes.

Entry skills and boundaries

This course is for a programmer comfortable editing/running JavaScript ES modules, writing functions and classes, using objects/arrays/Map, reading exceptions and passing quoted arguments in a terminal. The debugger assumes you can follow nested object mutation; the supplied VM defines its own instruction set. The storage course additionally assumes basic Node Buffer use, unsigned big-endian integers, UTF-8 byte lengths and filesystem calls; lesson01 works through cursor placement before production. This is not a first programming course. If these prerequisites are unfamiliar, use the reduced examples and completion cases, then decide whether to review JavaScript first. No extra runtime or paid account is required.

01. Control and inspect

A program emitted the wrong number. Build a tool that pauses it and shows the state that produced the number. Your first usable build is a single-step inspector for the supplied VM.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 01a, then save your answer with node lab.mjs predict project 01a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A virtual machine (VM) is a program that executes a defined instruction set. This VM is a teaching model. Its four registers are named a, b, c and d; each holds one integer. Its eight memory cells are numbered 0–7. The program counter, pc, selects the next instruction. Tick counts instructions already executed. Output holds emitted integers. None of these is a native process address or a hardware register.

Read contracts.md before coding. The supplied vm.mjs validates a program, constructs the initial state and executes an instruction. You own the Debugger class that calls it. Keep that boundary: changing VM semantics to make a check pass would produce a different machine.

A reduced example is set c=5, add c=2, halt. The example runner records the before and after states using the supplied machine. First predict what a step changes, then compare your prediction with the saved output. A step changes both the register and the instruction position. Inspection changes neither. After halt, a further step returns null and does not increase tick.

Implement inspect and step in project/solution.mjs. Inspection must return a detached copy. If changing a displayed memory array changes the running VM, a debugging observation has become a program edit. The public checker deliberately mutates a returned observation to distinguish those behaviors. Returning a shallow copy is insufficient because registers and memory are nested values.

Run the first check. An unfinished-method message is an expected starting result; use its named method and lesson pointer to choose the next edit. A syntax error is an execution error, not a failed behavioral requirement. The saved attempt contains your original code, report, question identity and actual output. Repair the code and run again; keep the first attempt.

Your intermediate product is useful now: run debug.mjs with counter.json and first-session.json to inspect a state, execute one instruction and inspect again. It should be your implementation producing those observations.

For transfer, create a program that writes a register to memory and later loads it into a different register. Predict the state after each instruction without a walkthrough, then use your inspector to investigate any difference. In your report, explain why an output alone cannot identify which earlier state was wrong.

02. Conditional breakpoints

Single stepping a loop wastes attention on states you already understand. Extend your inspector so it runs until a selected instruction is about to execute under a condition you choose.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 02a, then save your answer with node lab.mjs predict project 02a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A breakpoint is a request to pause before an instruction. Its pc refers to the next instruction, not the instruction that just finished. A conditional breakpoint additionally tests the current state. The supplied condition helper compares a named register or memory cell with an integer. A false condition means execution continues.

Consider a sibling program that decreases d through a loop and stores d on each visit. To inspect the second store's input, place a breakpoint on the store and test the register before it writes. Stopping after the store would answer a different question: what it changed. The example runner makes that boundary visible as a stop record beside a state snapshot.

Add addBreakpoint and run. Check halted state first. At every instruction boundary, test breakpoints before executing. Count only the instructions executed by this call against its limit. A tight loop must eventually return a limit stop. Reaching the limit is an ordinary result; malformed limits are invocation errors. If the last permitted instruction is halt, report halt.

An immediate rerun from a breakpoint will stop there again. This is deliberate: no instruction has run and the breakpoint still applies. An explicit step bypasses breakpoints for one instruction. That rule makes the tool predictable and avoids a hidden one-time suppression rule. Tell the user how to proceed in the command output.

Run stage 02 and read the condition case carefully if it fails. A breakpoint at the right pc but wrong loop iteration is not close enough. Check the register before the instruction rather than after executing it. Record the actual stop tick and state in your report, then revise and rerun.

The intermediate build is a loop investigator. Use break PC REG VALUE in debug.mjs to focus on one visit to a repeated instruction. Preserve the original program and enter a different condition to test whether your hypothesis depends on a particular iteration.

For transfer, write a loop with two different stores. Use the JavaScript addBreakpoint API to select one store with a memory condition; the terminal break command supports register conditions. Explain why the breakpoint belongs before that instruction and which observation would refute your hypothesis. Do not copy the counter program's breakpoint location.

Worked procedure

Use node examples.mjs 02. Its loop visits the same store with different d values. At a boundary, first check halted, then the breakpoint's pc, then its condition. Only if execution continues should the per-call executed count increase. The example's stop state is the input to the pending store. Completion: from that stop, choose whether inspect, run or step will execute an instruction and explain why. Case 02b changes the program and asks about output after bypassing a breakpoint.

03. Watchpoints

You know which memory cell becomes wrong, but you do not know which instruction writes it. Add a watchpoint that runs until that cell changes and reports the change.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 03a, then save your answer with node lab.mjs predict project 03a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A watchpoint observes a data location rather than an instruction location. Here it pauses after a store changes a watched cell. The resulting state includes the store's effect. A breakpoint pauses before an instruction; keeping these two boundaries distinct is essential when you compare snapshots.

A store can write the value that is already present. That is an executed write, so it belongs in the trace, but it is not a value change and does not trigger a watchpoint in this contract. A sibling demonstration first writes the existing value, then changes it, then repeats the new value. Predict whether the second store should stop before revealing its event sequence.

Implement watch(address) and extend run. After a step, inspect that event's writes. Test both address and before-versus-after value. Do not stop just because any memory cell changed, and do not compare the wrong states after another instruction has already run. A stop contains the write that caused it, plus the post-store tick and next pc.

The public cases distinguish a watched change, an unwatched change and a same-value write. On a failure, compare the event's executed pc with the stop's next pc. They describe different boundaries. Explain the discrepancy in report.md before changing code; that note will be saved with the next check.

Your build can now investigate a symptom without prior knowledge of the program's control flow. Run with watch ADDRESS, record the first changed value and inspect the registers that supplied the store operand. Continue by stepping once if another stopping rule applies at the new position.

For a second practice case, watch two addresses in your own program. Arrange for a store to an unwatched address before either watched address changes. The tool must continue through that unrelated write. Then make a watched store write its existing value. If it pauses, state which part of your implementation confused a write with a change.

For transfer, use dispatch.json without reading its instruction list first. Watch cell 1, collect a stop, then inspect only the nearby instructions. Form a hypothesis about how the written value was computed. This is practice in choosing evidence, not a hidden assessment or a guarantee that the program has a bug.

Worked procedure

Use node examples.mjs 03. Draw three rows for the initial same-value write, changed write and repeated new value. For each row compare the event address with the watched address, then compare before and after. Those are two separate filters. Completion: replace the watched address with a different cell and predict whether the same trace would stop. Your own run method must implement the chosen policy; the VM only supplies the event.

04. Instruction traces

A stop tells you where you are. A trace tells you how you arrived. Add a record of executed instructions so you can compare causes across a loop rather than relying on memory.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 04a, then save your answer with node lab.mjs predict project 04a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

Each event has a post-instruction tick and the pre-instruction pc. It names the instruction, its memory writes and any emitted values. An event is not a full state snapshot. The state can be reconstructed later by replaying the deterministic VM, while events provide an inexpensive index of interesting actions.

In the separate counter.json loop, the store at pc 2 executes more than once. The stage04 sibling is a straight-line sequence with event PCs 0,1,2. The counter's pc repeats while its event ticks increase. A repeated pc is not evidence that the trace duplicated an event. Conversely, two events with the same tick would violate the one-event-per-executed-instruction contract.

Extend step so it records a detached event. Implement trace so a caller cannot edit stored events through a returned array or a nested write object. Keep output emission in the event as well as in state output. Inspection, setting a breakpoint and adding a watchpoint do not execute instructions and must not create events.

Run stage 04. If the event count is correct but a write is wrong, inspect which state you used for before and after. Recording a reference to a mutable state can make every old event appear to contain the newest value. The mutation control helps expose this aliasing mistake.

The intermediate build is a trace recorder you can use on a program you did not write. Run a bounded session, save the terminal output in your evidence folder, and locate stores to the same address at different ticks. State which write changed the value and which merely wrote it again. These are different claims supported by different event fields.

For repair practice, create a program with two emits and a same-value store between them. Predict the number of events and emitted values separately, run it, and explain the difference. A trace includes instructions that produce no output.

For transfer, compare two runs from new debugger instances over the same immutable program. Their complete traces should agree. Change one original program operand in a new instance and identify the earliest event that differs. Do not mutate an existing instance's program to simulate a branch; source replacement is outside this model.

05. Checkpoints and replay

You have found a late symptom and want to inspect an earlier state. Implement seek by executing forward from genesis or an earlier checkpoint.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 05a, then save your answer with node lab.mjs predict project 05a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A checkpoint is a saved full VM state at a tick. Replay starts from a checkpoint at or before the target tick and executes the same instructions forward. This works here because the VM has no external input, random values or clock. A real process would require a much larger recording contract.

A sibling example records a checkpoint partway through a loop, runs farther, seeks to genesis and then seeks to a later recorded tick. The example runner checks both the immediate rewind state and the reconstructed state. Looking only at the final state could miss an implementation that ignored rewind altogether.

Implement checkpoint and seek. Store an internal deep copy. The returned checkpoint object is an observation, not a portable restore token; editing it must not change replay. Seek may use the nearest earlier checkpoint or recompute from genesis. Both strategies satisfy the behavior. Explain the cost difference in your report rather than treating one strategy as the only correct answer.

Keep the recorded frontier separate from the current tick. Seeking backwards changes the current state but does not erase the known trace. Re-executing a recorded tick must not append a duplicate event. Seek can only address 0 through the farthest recorded tick; it must reject requests for an unrecorded future.

Run stage 05. A replay failure may come from checkpoint mutation, incomplete state capture, starting after the target or duplicate trace events. Use the checker input and intermediate state to narrow the cause. Do not fix an event-count failure by silently deleting historical events.

Your build is now a time-travel viewer for one deterministic execution. Run node debug.mjs project/solution.mjs programs/counter.json programs/replay-session-stage05.json, inspect the checkpoint and then revisit the same tick. This command file uses only methods from lessons 01–05. The longer programs/replay-session.json also uses reverse search and is assigned after lesson 06. Include the two observed snapshots and their comparison in your report. Checkpoints are local to one debugger instance; there is no session import or source replacement API to test.

For transfer, choose a program that emits before and after the checkpoint. Seek to a tick before the first emit and then beyond the second. Verify output as well as registers and memory. Explain why saving only pc and registers would reconstruct the wrong state even if the final arithmetic looked correct.

06. Reverse state search

Rewinding one tick at a time is still slow when a symptom has a precise condition. Add a search for the nearest earlier state that matches a register or memory value.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 06a, then save your answer with node lab.mjs predict project 06a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

reverseFind searches states, not instructions or write events. Its bound is exclusive: from current tick t, it begins with t−1 and moves towards tick 0. A match returns that tick and leaves the debugger positioned there. A missing match returns null and restores the state from before the search.

A sibling example reaches the same register value on several adjacent ticks. The correct match is the nearest earlier state, even if the instruction at that tick did not write the register. This distinguishes state search from last-write search. To investigate the last write to an address, inspect trace events backwards and seek to that event's tick minus one instead.

Implement reverseFind using your existing replay operation. Validate the condition and bound before changing the current state. Store the original state so a failed search has no visible effect. Include genesis in the search. If the bound is zero, there are no earlier states to examine.

Run stage 06. After it passes, run node debug.mjs project/solution.mjs programs/counter.json programs/replay-session.json. Its final find reg b 0 command now exercises your reverse search after the lesson-05 replay steps. If the tool returns the current tick, check whether you accidentally made the bound inclusive. If a no-match search moves the debugger to genesis, the search has leaked its exploratory state. Compare inspect before and after a deliberately absent value and keep that experiment in the report.

Use the matching state and nearby trace events to decide which earlier instruction to inspect. Search for a value that preceded the symptom, inspect the nearby trace and formulate a smaller question. The returned tick alone does not prove which instruction caused a bug. Distinguish the observation from the explanation.

For practice, use a program that holds a value unchanged for several instructions. Predict the nearest matching tick, then contrast that result with the tick of the last write. State which question each operation answers.

For a return to the familiar rehearsal, run dispatch.json to completion and find an earlier matching memory value. Use a new debugger instance to confirm the same state by forward execution. Then try a value that never occurs and verify state preservation. Your report should include a refutable causal hypothesis rather than just a screenshot of a matching number.

Use node examples.mjs 06. Start one tick below the exclusive bound. Reconstruct that state, test the condition and stop at the first match; otherwise decrease the candidate. Save the caller's state before exploring and restore it when no candidate matches. Completion: explain why a matching state may occur after an unrelated emit rather than at the last write. Case 06b asks for a concrete field after a no-match search on a different program.

Original deterministic VM: frozen behavioral contract v1

Learner contract v1, adopted 2026-10-27. Implement the debugger behavior defined here over the supplied original VM. This course does not access native processes.

VM

State is {pc,tick,regs:{a,b,c,d},mem,output,halted}. Initially pc=0, tick=0, all four registers and all eight memory cells are 0, output=[], halted=false. Registers hold JavaScript safe integers; overflow raises an execution error before state changes. Memory addresses are integer 0–7. Programs have 1–256 instructions. No clock, randomness, I/O inputs or external side effects.

Operands called value are a safe integer literal or one of the register names. Instructions:

  • {op:"set",reg:"a",value:3} assigns an operand.
  • {op:"add",reg:"a",value:-1} adds an operand.
  • {op:"load",reg:"b",address:0} copies a memory cell into a register.
  • {op:"store",address:0,value:"a"} writes an operand to a memory cell.
  • {op:"jnz",value:"a",target:2} jumps if the operand is nonzero; target is an in-program instruction index.
  • {op:"emit",value:"a"} appends the operand to output.
  • {op:"halt"} sets halted=true.

Every executed instruction increments tick once. Normally pc advances by one; taken jnz replaces that next pc. Halt also advances pc and tick. Falling off a program without halt raises an error. A halted step is a no-op returning null.

Debugger interface and boundaries

Construct new Debugger(program). The program and returned observations are deep copies. inspect() returns the detached current state. step() bypasses breakpoints, executes one instruction and returns its event, or null if already halted.

addBreakpoint({pc,condition?}) adds a breakpoint. Conditions are {kind:"reg",name:"a",equals:2} or {kind:"mem",address:0,equals:2}. run(limit=1000) checks breakpoints before execution, including at the current pc. A false condition does not stop. An immediate rerun at the same breakpoint stops again; step bypasses it. Explicit run limit is integer 1–10000 and counts only instructions executed by that call.

watch(address) stops after a store changes that watched cell. Same-value stores are events but do not stop. Stops are {reason,tick,pc} where reason is breakpoint, watchpoint, halt or limit. A watchpoint additionally has write:{address,before,after}. A run executing halt reports halt even if halt was the last budgeted instruction. Already halted run reports halt without execution. Watchpoint pc is the next instruction, and tick includes the store.

Events are {tick,pc,op,writes,emitted}. Event tick is the post-instruction tick; event pc is the executed instruction's pre-state pc. A store includes one {address,before,after} even for a same-value store. Only emit populates emitted. trace() returns detached events from the farthest recorded frontier in tick order. Seeking does not shrink that frontier; re-executing known ticks does not duplicate events.

Replay, checkpoints and sessions

checkpoint(nonemptyLabel) stores an internal deep snapshot and returns {label,tick,state} detached from it. seek(tick) accepts integer 0 through recorded frontier inclusive, replays from an internal checkpoint or genesis, replaces current state and returns detached state. Seeking beyond recorded history is an error. A checkpoint is an observation, not a portable restore token. No external checkpoint/session import API exists.

reverseFind(condition,beforeTick=currentTick) searches strictly earlier ticks in descending order, including tick0. Valid explicit bound is 0 through frontier+1. It returns the nearest matching tick and positions the debugger there. With no match it returns null and preserves the state before the call. It uses the same condition forms as breakpoints.

Each debugger instance owns its program, trace and checkpoints. A new instance starts at genesis and cannot consume another instance's session. No persisted execution sessions, source replacement or branching external input are supported in v1. The supported interface cannot import an external session. Learner check receipts separately bind exact solution and assessment hashes and label changed source historical.

There is no dedicated reverse-last-write method. A debugger user can search the detached trace backwards for a write to an address and seek to the event tick minus one to inspect the cause. reverseFind is not an event/write search.
