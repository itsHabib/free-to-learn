# 03. Watchpoints

You know which memory cell becomes wrong, but you do not know which instruction writes it. Add a watchpoint that runs until that cell changes and reports the change.

## Before the worked result

This case uses the terms and interface in contracts.md. Read the input in `node lab.mjs question 03a`, then save your answer with `node lab.mjs predict project 03a YOUR_ANSWER --help-used none` before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A watchpoint observes a data location rather than an instruction location. Here it pauses after a store changes a watched cell. The resulting state includes the store's effect. A breakpoint pauses before an instruction; keeping these two boundaries distinct is essential when you compare snapshots.

A store can write the value that is already present. That is an executed write, so it belongs in the trace, but it is not a value change and does not trigger a watchpoint in this contract. A sibling demonstration first writes the existing value, then changes it, then repeats the new value. Predict whether the second store should stop before revealing its event sequence.

Implement watch(address) and extend run. After a step, inspect that event's writes. Test both address and before-versus-after value. Do not stop just because any memory cell changed, and do not compare the wrong states after another instruction has already run. A stop contains the write that caused it, plus the post-store tick and next pc.

The public cases distinguish a watched change, an unwatched change and a same-value write. On a failure, compare the event's executed pc with the stop's next pc. They describe different boundaries. Explain the discrepancy in report.md before changing code; that note will be saved with the next check.

Your build can now investigate a symptom without prior knowledge of the program's control flow. Run with watch ADDRESS, record the first changed value and inspect the registers that supplied the store operand. Continue by stepping once if another stopping rule applies at the new position.

For a second practice case, watch two addresses in your own program. Arrange for a store to an unwatched address before either watched address changes. The tool must continue through that unrelated write. Then make a watched store write its existing value. If it pauses, state which part of your implementation confused a write with a change.

For transfer, use dispatch.json without reading its instruction list first. Watch cell 1, collect a stop, then inspect only the nearby instructions. Form a hypothesis about how the written value was computed. This is practice in choosing evidence, not a hidden assessment or a guarantee that the program has a bug.
