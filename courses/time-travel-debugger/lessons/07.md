# 07. Diagnose an unfamiliar program

Use your debugger to explain a faulty result in a program you did not design. The capstone changes the investigation surface and leaves the choice of evidence to you.

## Before the worked result

This case uses the terms and interface in contracts.md. Read the input in `node lab.mjs question 07a`, then save your answer with `node lab.mjs predict project 07a YOUR_ANSWER --help-used none` before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

Read capstone.md for the user's expected behavior and the two supplied cases. Start with the reported symptom. Choose a stopping condition, inspect the state, and save the smallest trace segment that supports your first hypothesis. Do not begin by rewriting the whole program: you need an explanation of what happened in the original execution.

Your deliverable is your own debugger, its runnable checks and a diagnosis report. The reference implementation and author controls are not a capstone submission. The report must name the original program, the first state that violates the stated expectation, the instruction involved and a forward experiment that could disprove the explanation.

Use checkpoint/replay and reverse search where they answer a real question. A report that merely lists every command is harder to assess than one that connects observations to an explanation. Include enough command input for another person to reproduce the important observations from a new instance.

Keep the original program unchanged and put an experimental revision in a separate file. Compare both results. If a change fixes one supplied input but fails another, retain that evidence and revise the hypothesis. A successful patch is useful, but an unexplained changed output does not establish the cause.

Run stage 07 as a final integration check. It exercises the debugger on a changed program; it does not grade the causal reasoning in your report. Use the capstone rubric for that reasoning. An optional LLM critique is advisory and uses your own account only if you choose; no hosted service or staff response is required.

For the learner-owned extension, write a small deterministic VM program representing a problem of your choice, introduce one plausible data-flow bug and give a second person only its intended behavior and failing input. Use your debugger to produce a reproducible diagnosis. Keep that investigation separate from the supplied cases so the evidence shows you can choose a useful question on a fresh surface.

Export the complete project and attempts to a new directory. Run the exported code and commands from that directory without relying on the author worktree. State the tested runtime and the limits: this artifact diagnoses the supplied VM, not arbitrary native programs. A public checker pass is bounded conformance evidence; learning and independent acceptance remain separate questions.

## Worked procedure

Use `node examples.mjs 07` as a report procedure, not an executed diagnosis. Write expected behavior, choose one observation that could distinguish two hypotheses, run it from a fresh instance, and separate the observation from your explanation. Completion: write the result that would make you abandon your first hypothesis. The worked procedure supplies no diagnosis for transfer.json or your own program.
