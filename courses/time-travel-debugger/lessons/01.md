# 01. Control and inspect

A program emitted the wrong number. Build a tool that pauses it and shows the state that produced the number. Your first usable build is a single-step inspector for the supplied VM.

A virtual machine (VM) is a program that executes a defined instruction set. This VM is a teaching model. Its four registers are named a, b, c and d; each holds one integer. Its eight memory cells are numbered 0–7. The program counter, pc, selects the next instruction. Tick counts instructions already executed. Output holds emitted integers. None of these is a native process address or a hardware register.

Read contracts.md before coding. The supplied vm.mjs validates a program, constructs the initial state and executes an instruction. You own the Debugger class that calls it. Keep that boundary: changing VM semantics to make a check pass would produce a different machine.

A reduced example is set c=5, add c=2, halt. The example runner records the before and after states using the supplied machine. First predict what a step changes, then compare your prediction with the saved output. A step changes both the register and the instruction position. Inspection changes neither. After halt, a further step returns null and does not increase tick.

Implement inspect and step in project/solution.mjs. Inspection must return a detached copy. If changing a displayed memory array changes the running VM, a debugging observation has become a program edit. The public checker deliberately mutates a returned observation to distinguish those behaviors. Returning a shallow copy is insufficient because registers and memory are nested values.

Run the first check. An unfinished-method message is an expected starting result; use its named method and lesson pointer to choose the next edit. A syntax error is an execution error, not a failed behavioral requirement. The saved attempt contains your original code, report, question identity and actual output. Repair the code and run again; keep the first attempt.

Your intermediate product is useful now: run debug.mjs with counter.json and first-session.json to inspect a state, execute one instruction and inspect again. It should be your implementation producing those observations.

For transfer, create a program that writes a register to memory and later loads it into a different register. Predict the state after each instruction without a walkthrough, then use your inspector to investigate any difference. In your report, explain why an output alone cannot identify which earlier state was wrong.
