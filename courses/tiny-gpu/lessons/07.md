This lesson counts what a warp's memory requests cost, how many 32-byte transactions its eight lanes need, and how often a small texture cache, which keeps recently read texture bytes beside the shader, already holds what they read.

## Counting transactions

Memory doesn't move single bytes. It moves **segments** of 32 bytes, each starting at a multiple of 32, and each segment moved is one **transaction**. When a warp's lanes read or write at once, the GPU merges their requests, **coalescing** them. The warp costs one transaction for each distinct segment its lanes touch, so eight lanes reading eight neighbouring 4-byte texels, a 32-byte run that starts at a multiple of 32, cost one transaction, not eight. `SEGMENT`, supplied in `memory.mjs`, is 32.

<!-- code-example {"file":"examples/memory.txt","region":"transactions","language":"js","title":"transactions, in project/gpu/memory.mjs","change":"Write route: replace the throw line with this body."} -->
```js {"file":"examples/memory.txt","region":"transactions","title":"transactions, in project/gpu/memory.mjs","change":"Write route: replace the throw line with this body."}
// addresses[k] is lane k's byte address; bit k of mask is lane k.
export function transactions(addresses, mask) {
  const segments = new Set();
  for (let k = 0; k < addresses.length; k++) {
    if (mask & (1 << k)) {
      segments.add(Math.floor(addresses[k] / SEGMENT));
    }
  }
  return segments.size;
}
```

## Coalescing the framebuffer

The framebuffer is stored row after row too, 4 bytes a pixel, so one row of a 4 by 2 warp is 16 bytes inside one segment, and a full warp touches two segments, one per row. The depth buffer is stored the same way, 4 bytes a pixel. From stage 7 the supplied `countFramebuffer` counts three accesses for each warp: a depth read by the covered lanes, and a depth write and a colour write by the lanes that passed the depth test:

<!-- code-example {"file":"examples/pipeline.txt","region":"countFramebuffer","language":"js","title":"countFramebuffer, in project/gpu/pipeline.mjs","change":"Study: supplied."} -->
```js {"file":"examples/pipeline.txt","region":"countFramebuffer","title":"countFramebuffer, in project/gpu/pipeline.mjs","change":"Study: supplied."}
// Immediate mode, one triangle: per block, depth read by the covered
// lanes, depth and colour written by the lanes that passed.
function countFramebuffer(ctx, covered, frags) {
  const { w } = ctx.target;
  const { bytes } = ctx.target.counts;
  const blocks = new Map();
  const note = (f, field) => {
    const b = blockOf(ctx, f.x, f.y);
    if (!blocks.has(b.key)) {
      const [bw] = ctx.opts.block ?? [4, 2];
      const addr = Array.from({ length: LANES }, (_, k) =>
        ((b.y0 + Math.floor(k / bw)) * w + b.x0 + (k % bw)) * 4);
      blocks.set(b.key, { addr, cover: 0, pass: 0 });
    }
    blocks.get(b.key)[field] |= 1 << b.lane;
  };
  covered.forEach((f) => note(f, 'cover'));
  frags.forEach((f) => note(f, 'pass'));
  for (const { addr, cover, pass } of blocks.values()) {
    const read = transactions(addr, cover) * SEGMENT;
    const written = transactions(addr, pass) * SEGMENT;
    bytes.depth += read + written;
    bytes.color += written;
  }
}
```
<!-- /code-example -->

The supplied `blockOf` gives the block a pixel falls in: its bottom-left corner (`x0`, `y0`), a `key` that names the block, and the pixel's `lane`. Setting `ctx.opts.block` changes the block from 4 by 2, as the 8 by 1 comparison below does. `bytes.depth` and `bytes.color` are running totals of the bytes moved.

On the courtyard at 160 by 120, a 4 by 2 warp's colour write costs 1.738 transactions on average. An 8 by 1 warp, one row of eight pixels, costs exactly 1.000, but the courtyard then needs 3,595 warps instead of 3,053, because wide blocks fit thin triangles worse.

## A small cache

A texture read that has to go to memory costs a transaction. A **cache** keeps recently read **lines**, the same 32-byte segments that transactions move, close to the shader. A read whose line is already there is a **hit** and costs nothing more, and only a **miss** goes to memory. The course's texture cache has 8 **sets** of 8 lines each, 2 KB in all. Line n of memory may live only in set n % 8, in any of that set's 8 places, its **ways**. `CACHE` in `memory.mjs` is `{ sets: 8, ways: 8 }`, and the pipeline builds its cache with `new TextureCache(CACHE)`.

<!-- code-example {"file":"examples/memory.txt","region":"TextureCache","language":"js","title":"TextureCache, in project/gpu/memory.mjs","change":"Write route: replace the two throw lines with these bodies."} -->
```js {"file":"examples/memory.txt","region":"TextureCache","title":"TextureCache, in project/gpu/memory.mjs","change":"Write route: replace the two throw lines with these bodies."}
// Set-associative, least recently used replacement. Line n of memory
// (bytes 32n to 32n + 31) can only live in set n % sets.
export class TextureCache {
  constructor({ sets, ways }) {
    this.sets = sets;
    this.ways = ways;
    // each set lists its lines, least recently used first
    this.lines = Array.from({ length: sets }, () => []);
    this.hits = 0;
    this.misses = 0;
    this.bytes = 0;
  }

  access(addr) {
    const line = Math.floor(addr / SEGMENT);
    const set = this.lines[line % this.sets];
    const at = set.indexOf(line);
    if (at >= 0) {
      set.splice(at, 1);
      set.push(line); // now the most recently used
      this.hits += 1;
      return true;
    }
    if (set.length === this.ways) set.shift(); // evict the oldest
    set.push(line);
    this.misses += 1;
    this.bytes += SEGMENT;
    return false;
  }
}
```
<!-- /code-example -->

The pipeline sends each warp's texture reads to the cache as one access per distinct line, in the order its lanes first touch them.

## Which line leaves

When a set is full and a new line must come in, one line leaves. This cache throws out the **least recently used** line, the one whose last access, hit or miss, is oldest. Each set's list keeps its lines in that order, oldest first, and a hit moves its line to the end.

## A tiled texture layout

Stored row after row, the **row-major** layout (`'linear'` in the code and in the lab's output), a texture puts horizontal neighbours side by side and vertical neighbours a whole row apart. A **tiled** layout stores it in blocks of 4 by 2 texels, 32 bytes each, exactly one line, the blocks row after row. A 4 by 2 warp reading a 4 by 2 patch of texels lined up with the blocks then touches one line, and two when the patch is turned a quarter turn.

`texelAddress(tex, x, y, layout)` has no listing. It returns the byte address of texel (x, y) of a texture `tex.w` texels wide, 4 bytes a texel:

- `'linear'`: the texels before it, y whole rows of `tex.w` and then x more, times 4 bytes.
- `'tiled'`: a block row is two texel rows, and it holds `tex.w` / 4 blocks, rounded down. The texel's block is block row y / 2 and block column x / 4, both rounded down, so its block number is that block row times the blocks in a row, plus the block column. Inside the block, the bottom row holds places 0 to 3 and the row above places 4 to 7, so the texel's place is 4 when y is odd, 0 when it's even, plus the remainder of x / 4. The address is the block number times 32, plus the place times 4.

A worked address. In a texture 100 texels wide, texel (2, 5) row-major is (5 × 100 + 2) × 4 = 2,008. Tiled, a block row holds 25 blocks. Texel (2, 5) is in block row 2 and block column 0, so block 50, and y is odd, so its place is 4 + 2 = 6. Its address is 50 × 32 + 6 × 4 = 1,624.

The supplied `storeTexture` writes the texture's bytes in the order of the layout it is given, row after row for `'linear'` and block by block for `'tiled'`, so the memory the pipeline reads and the addresses your `texelAddress` gives agree. The texture it receives holds its texels in `tex.data` row after row, 4 bytes each:

<!-- code-example {"file":"examples/memory.txt","region":"storeTexture","language":"js","title":"storeTexture, in project/gpu/memory.mjs","change":"Study: supplied."} -->
```js {"file":"examples/memory.txt","region":"storeTexture","title":"storeTexture, in project/gpu/memory.mjs","change":"Study: supplied."}
// The texture's bytes in memory order for a layout. 'tiled' copies
// block by block: in each 4 x 2 block, the bottom row of four texels,
// then the row above.
export function storeTexture(tex, layout) {
  if (layout === 'linear') return tex.data;
  if (layout !== 'tiled') throw new Error(`unknown layout ${layout}`);
  if (tex.w % 4 || tex.h % 2) {
    throw new Error('a tiled texture needs w % 4 = 0 and h % 2 = 0');
  }
  const out = new Uint8Array(tex.data.length);
  let at = 0;
  for (let by = 0; by < tex.h; by += 2) {
    for (let bx = 0; bx < tex.w; bx += 4) {
      for (let y = by; y < by + 2; y++) {
        const row = (y * tex.w + bx) * 4;
        out.set(tex.data.subarray(row, row + 16), at);
        at += 16;
      }
    }
  }
  return out;
}
```

## A layout for any direction

Tiled, the same warp reads two lines, and a whole row of warps needs few enough lines that the next row still finds them. The tiled floor misses 2,112 times whichever way it lies, once for each line the picture needs, and the turned floor costs 3.53 times as many misses row-major. The check requires the turned floor's row-major misses to be at least 2.3 times its tiled misses. The texture is 100 texels wide on purpose. At 128, with blocks stored row after row, a whole column of blocks lands in one set of this cache, and the tiled layout would miss for that reason instead.
