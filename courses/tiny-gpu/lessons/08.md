# 8 · Tiled rendering

This lesson draws the picture one 16 by 16 tile at a time, so that colour goes to memory once per pixel and depth never does. The tile's colour and depth are held on chip, in a small fast memory inside the GPU. The course doesn't count that memory's reads and writes as memory traffic.

Before it, your GPU is an **immediate renderer**: triangle after triangle, every covered fragment reads depth in memory, and every fragment that passes writes depth and colour there. After it, triangles are first sorted into the tiles they touch, each tile is drawn on its own, and the picture is exactly the same, while a scene drawn many layers deep moves far fewer bytes.

**Code scope:** you write 43 code lines in `project/gpu/tiles.mjs`, the bodies of `bin` (18 lines) and `renderTile` (25). The lesson lists `renderTile`. For `bin` it states the rule and works one triangle, and the code is yours. The lesson tours the supplied `countBins` in `pipeline.mjs`. The new application is about 13 lines of your own.

## Binning triangles

A **tile** is a 16 by 16 square of pixels. Tile (tx, ty) covers x from 16 tx to 16 tx + 15 and y the same way, and the tiles are numbered row by row from the bottom, tile number ty × tilesX + tx, where tilesX is the number of tiles across, 10 for a 160-pixel picture. **Binning** gives every tile a list, its **bin**, of the triangles that may touch it, in draw order. `bin(tris, W, H, size = TILE)` has no listing. Write its body from this rule, with the starter's comment above it for the shapes:

- `tris[k]` is triangle k's three `[x, y]` corners in subpixels. The result is one list per tile, `tilesX` × `tilesY` of them, where `tilesX` is W / `size` and `tilesY` is H / `size`, both rounded up. Tile (tx, ty) is list number ty × `tilesX` + tx.
- For each triangle, in order, take the pixel bounding box `rasterize` walks: columns from `floor(min x / SUB)` up to, but not including, `ceil(max x / SUB)`, and rows the same way in y. Clamp it to columns 0 to W and rows 0 to H. If nothing is left, the triangle is off the screen and joins no bin.
- Otherwise push k onto the list of every tile the box overlaps: tile columns from floor(x0 / `size`), where x0 is the box's first column, while tx × `size` is less than x1, the column the box stops before, and tile rows the same way.

A worked triangle. In a 160 by 120 picture, corners at (−6.5, 4), (40, 12.75) and (30, 14) in pixels give the box columns −7 up to 40 and rows 4 up to 14. Clamped, the columns run from 0. Tile columns 0, 1 and 2 start before 40, tile column 3 starts at 48, and only tile row 0 starts before 14, so the triangle joins the bins of tiles 0, 1 and 2.

## A triangle bigger than a tile

A large triangle can cover a tile that holds none of its corners. Binning by the box, not by the corners, puts it in every tile between them. A thin diagonal triangle joins tiles its box overlaps but it never covers, and `renderTile` then finds no pixel of it there, which costs time, never pixels.

The triangles `bin` receives have already been through lesson 2's `clipNear`. A floor triangle that reaches behind the camera arrives as the pieces in front of the near plane, often with corners far off the screen, up to 12,251 pixels out over the camera stops lesson 2 measured, and the clamp keeps their boxes on the screen.

## Same picture, tile by tile

The tile's **on-chip memory**, `chip`, is the fast memory beside the shader cores. It holds 16 × 16 depths, colours and triangle ids. `renderTile` clears it, draws the tile's bin in order with the same depth test and shading as before, and then hands the tile to the supplied `store`:

<!-- code-example {"file":"examples/tiles.txt","region":"renderTile","language":"js","title":"renderTile, in project/gpu/tiles.mjs","change":"Write route: replace the throw line with this body."} -->
```js {"file":"examples/tiles.txt","region":"renderTile","title":"renderTile, in project/gpu/tiles.mjs","change":"Write route: replace the throw line with this body."}
// ctx: { W, H, size, tris: [{ id, pts, win }], chip, background,
//        shade(t, frags), store(tx, ty, parts) }
// chip is the tile's on-chip memory, reused for every tile:
// { depth, rgba, ids }, pixel (x, y) at (y - y0) * size + (x - x0).
export function renderTile(tx, ty, list, ctx) {
  const { size, chip } = ctx;
  const x0 = tx * size;
  const y0 = ty * size;
  const rect = { x0, y0, x1: Math.min(x0 + size, ctx.W),
    y1: Math.min(y0 + size, ctx.H) };
  chip.depth.fill(1); // every tile starts far away and empty
  chip.ids.fill(-1);
  chip.rgba.set(ctx.background);
  for (const k of list) {
    const t = ctx.tris[k];
    const frags = [];
    rasterize(t.pts, rect, (x, y, w0, w1, w2) => {
      const j = (y - y0) * size + (x - x0);
      const f = interpolate(t.win, [w0, w1, w2], ATTRS.length);
      if (depthTest(chip.depth, j, f.z)) {
        frags.push({ x, y, j, attrs: f.attrs });
      }
    });
    const colours = ctx.shade(t, frags); // RGBA levels per fragment
    frags.forEach((f, n) => {
      chip.rgba.set(colours[n], f.j * 4);
      chip.ids[f.j] = t.id;
    });
  }
  ctx.store(tx, ty, ['colour']); // depth never leaves the chip
}
```
<!-- /code-example -->

Each entry of `ctx.tris` holds the triangle's `id` and its corners twice. `pts` gives them as `[x, y]` in subpixels, the form `rasterize` takes. `win` gives them as the corners `{ x, y, z, invW, a }` that lesson 2's supplied `windowTris` returns, the form `interpolate` takes: through your `toWindow` for a scene with a camera, snapped straight from the scene for a 2D scene. `ctx.shade(t, frags)` shades the fragments of triangle `t` by warps, as in lesson 6, and returns one RGBA colour for each. The supplied `store(tx, ty, parts)` copies each part that `parts` names, the tile's colour or its depth, from the chip to the picture in memory, and counts 4 bytes a pixel for each part it copies.

The shader's texture reads still go through lesson 7's cache, now tile by tile, so the warps that use a line come closer together in time.

## Counting the traffic

Binning has a cost of its own. The supplied `countBins` makes two charges. Each triangle has a 64-byte record, the size this course charges for its corners and attributes, written once and read back once for every tile it was binned to. Each bin entry costs 4 bytes written and 4 bytes read:

<!-- code-example {"file":"examples/pipeline.txt","region":"countBins","language":"js","title":"countBins, in project/gpu/pipeline.mjs","change":"Study: supplied."} -->
```js {"file":"examples/pipeline.txt","region":"countBins","title":"countBins, in project/gpu/pipeline.mjs","change":"Study: supplied."}
// Binning traffic: 4 bytes per list entry and 64 per triangle record
// written; 4 per entry and 64 per record read for every entry.
function countBins(target, lists) {
  const entries = lists.reduce((n, l) => n + l.length, 0);
  const records = new Set(lists.flat()).size;
  target.counts.bytes.bins += 4 * entries + 64 * records
    + (4 + 64) * entries;
}
```

Immediate moves 14.78 times the bytes. A full 4 by 2 warp pays a depth read, a depth write and a colour write, each two transactions of 32 bytes, about 24 bytes per pixel per layer. The check requires the immediate renderer to move at least 4 times the tiled renderer's bytes on the overdraw scene. On the courtyard the gain is smaller: the immediate renderer moves 576,704 bytes and the tiled one 191,744, 112,896 of them for binning, because the courtyard's big floor triangles join many tiles. Both ratios compare against this course's immediate renderer, which has no framebuffer cache, a cache like lesson 7's texture cache for depth and colour. Real immediate-mode GPUs cache depth and colour traffic on chip, and many compress it, so on hardware the gap is smaller.
