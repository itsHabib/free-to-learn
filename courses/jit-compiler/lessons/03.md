# 03 · Switch engines halfway through a batch

A warehouse has already seen the first qualifying order when a missing quantity reaches the compiled filter. The WebAssembly function expects an integer. Your job is to finish the batch with the interpreter so the warehouse receives each qualifying order's row index exactly once.

Start with passing units 01 and 02. You will write `executeBatch` in `work/runtime.mjs`. It receives a half-open range of row indices (from `start` up to, but excluding, `end`), an optional compiled predicate and two arrays to append to. The cursor and two loops take about 20 lines. The supplied host in `lib/batches.mjs` calls this function and retains its trace for inspection.

## Find the order that was counted twice

For `[45, null, 46]` and the filter `quantity > 30`, index 0 qualifies before index 1 breaks the assumption that every input is an integer. Index 2 still needs an answer. Imagine that the interpreter restarts the scan at the beginning and appends its answers to the same list. Predict the full sequence of matching **indices**. Which index will appear twice?

The worked failure prints `{"failedAt":1,"resumeAt":0,"matches":[0,0,2]}`. This excerpt from `examples/replay-bug.mjs` intentionally restarts at zero. Find the `guard-failure` event in the output: both `at` and `resumeAt` are 3. The **guard** checks that a row is an integer before the compiled predicate reads it, and the null at row 3 fails it. The cursor points to the **first uncommitted row**. The integer prefix has been fully examined, including any integer rows that failed the predicate. The null is still pending. The interpreter can consume it and every later row in this batch.

Do not drop the null from the scan. Try the predicate `[['const', 7], ['const', 7], ['eq']]` on a null row. Its answer is true because it compares two constants, so skipping the blocked row would lose a match. Filtering duplicate **values** would be a bad repair too: two qualifying orders can have the same quantity, and the warehouse needs both row indices.

## Write the handoff

Replace the throw inside `executeBatch` in `work/runtime.mjs`. Keep the supplied function signature. Use the same cursor in the two phases.

1. Set `row = start` and `guardFailures = 0`. If `predicate` exists, walk forward while `row < end` and `values[row] !== null`. Call the predicate with the integer, append the **absolute** index to `matches` if it returns 1, then increment `row` for every processed row.
2. Still inside the compiled branch, check whether `row < end`. If so, record one guard failure and append `{kind: 'guard-failure', at: row, resumeAt: row}` to `trace`. The guard is the condition that checked whether this row met the integer assumption.
3. Save `compiledRows = row - start`. From the current cursor to `end`, run your internal `evaluate(program, values[row])` for each row. Append indices that qualify. When the host selected the interpreter, this same loop begins at `start`.
4. Return an object with `compiledRows`, `interpreted: end - start - compiledRows` and `guardFailures`. The host uses the counters to describe actual work to the next batch's decision function.

```sh
node lab.mjs check 03 --predict 'My resume row for a null at the start of batch two'
node lab.mjs demo
```

If your matches are correct but the counts fail, try a batch of one row: a null that runs under the compile decision. It should report zero compiled row evaluations, one interpreted evaluation and one guard failure. If a whole integer batch reports a guard failure, inspect why your loop exited. Reaching `end` finishes the batch.

## Read the decision boundary

In `runBatches` in `lib/batches.mjs`, find the call to `choose(observation)`. Before each batch, `runBatches` calls `choose` once. The observation holds that batch's bounds, how many rows remain, whether compiled code already exists and the **previous** batch's row, null and guard-failure counts. Returning `'compile'` requests the integer path and reuses code if this query already has it. Returning `'interpret'` processes the entire batch in the interpreter. Try changing `batchSize` in a call to `run`. A fresh choice can put a later batch back on the compiled path even though the preceding batch hit a guard. Unit 04 uses that information to learn a decision policy.
