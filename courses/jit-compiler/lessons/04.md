# 04 · Who decides when to compile?

An order importer runs the same filter on a few dozen rows at a time during the day and on thousands overnight. A guard exit in the overnight file can send hundreds of rows back to the interpreter. By the end of this chapter you’ll have two working answers to “Should I compile this batch?” and a measured reason to use one on a particular workload.

## Make a rule you can dispute

The supplied baseline in `lib/bakeoff.mjs` interprets the first batch to get some history. Once it has history, it requires 512 remaining rows to build a fresh predicate. It can reuse a cached predicate for a shorter tail. In both cases it tries Wasm only when at most one row in 32 was null in the previous batch.

```js
export function fixedRule({ remainingRows, compiled, previous }) {
  if (previous.rows === 0) return 'interpret';
  if (!compiled && remainingRows < 512) return 'interpret';
  return previous.nulls / previous.rows <= 1 / 32 ? 'compile' : 'interpret';
}
```

In your opening case, 768 rows cover the baseline’s minimum and `2 / 256` is less than `1 / 32`. The rule selects `compile`. On the next boundary the build cost has already been paid. If 32 of those 256 rows were null, the rule would still switch to `interpret` because `32 / 256` exceeds its limit. What made your prediction agree or disagree with this rule?

Try the cached-tail case yourself. Predict both action strings, then execute this from the course directory. Only the `compiled` flag changes.

for (const compiled of [false, true]) {

## Give the model one measurement

A **feature** is a number the model can use when it makes a decision. Here it is the fraction of rows that were null in the last completed batch. The engine already counted them. Before the first batch, use zero as a starting assumption. This gives a fresh query and a query following a completely clean batch the same score. Later you’ll look for situations where that loses information.

Implement `feature(observation)` in `work/policy.mjs`. For `{previous: {rows: 16, nulls: 2, guardFailures: 1}}` it should return `0.125`. A guard can fail only once before the interpreter takes the rest of this batch. To distinguish two nulls from eight, read the null count. Check the no-history branch before doing the division.

Implement `chooseLearned(score, model)` in the same file. The local trainer supplies a cutoff and two actions in `{cutoff, low, high}`. Return `low` for a score at or below the cutoff, `high` above it. For example, a fitted model with `cutoff = 0.125`, `low = 'interpret'` and `high = 'compile'` sends the example batch to the interpreter. Reversing the leaf actions must reverse the result with exactly the same feature. The engine sees an ordinary action string and keeps responsibility for the guard.

## Find out what training bought

A **decision stump** is a decision tree with a single question. This trainer searches ten candidate stumps. Four cutoffs each have two possible action orders. Two more candidates always take the same action. In `fit` in `lib/bakeoff.mjs`, find `entry.scores.push(ms)`. Each score is the time to finish all eight training queries with that candidate. Three passes through the training inputs give three scores per candidate. The trainer keeps the model with the lowest median score. This measures the downstream cost of the policy’s choices, including later reuse of a predicate built earlier in the query.

Before running the comparison, write down which contestant you expect to win on a short clean input and on a long clean input. Name a result that would reverse your recommendation. Save the output alongside your prediction. `mktemp` gives each run its own filename.

```sh
result=$(mktemp work/race.XXXXXX)
node lab.mjs race --seed 901 | tee "$result"
```

Read three things in the report.

1. **The matching IDs.** Every run checks every returned index, in order, against direct JavaScript filtering for `value > 30`. Dropping a row, duplicating a row or returning the wrong row invalidates the timing.
2. **The decisions.** `compile choices` counts batches sent down the guarded path. `builds` counts actual compilations. `exits` counts fallbacks. `Wasm rows` counts rows that reached the compiled predicate. Pick one difference in timing and see whether the decisions support your explanation.
3. **The bill.** The six paired query timings include the live feature calculation, decision, compilation, scan, trace and result collection. Both policies get a warm-up query on training data. Every timed query starts with an empty predicate cache. The first runner alternates each round. The final line comparing one pass including a fit charges the model for training once. Compare it with the line for a previously fitted model. Small differences can move around between runs. Look at the ranges and the sign of the paired difference.

The seeds `113` and `271` generate training inputs. The test seed generates fresh rows after the model is selected. Each CLI invocation fits anew, so record the actual selected leaves when comparing reports. The clock measures elapsed milliseconds in the current Node process. Host load and JavaScript or WebAssembly engine warm-up can affect the timings. [Node performance measurement API](https://nodejs.org/api/perf_hooks.html#performancenow)

## Build a challenger

Suppose the importer now receives short tail batches after a predicate has already been built. Your existing feature gives a cold, 80-row query the same score as a clean, cached 80-row tail. Both decisions have 80 rows remaining. Design a second feature that uses the `compiled` flag to separate them. The short clean workload has exactly 80 rows. The long clean workload has 8,272, so its last batch also has 80. Check the trace to see whether your policy had already built a predicate by that batch. The trainer accepts a finite score. Its available cutoffs are 0, 1/128, 1/32 and 1/8, so check where your score for each case would land. Keep `work/policy.mjs` as your first submission. Export your new `feature` from a separate `work/challenger.mjs`.

Before measuring, choose a fresh seed and write down which of the four stationary inputs you expect to gain, what you might give up, and how you would recognize a loss. Run your new feature with the same trainer, guard and fixed baseline. You can change the seed, or set `shift: true` for another run on the two importer layouts.
