05 / FROM A CLAIM TO AN OBSERVATION

A hash compares bytes. Trust chooses the reference.

A digest is a fixed-size result computed from bytes. This project uses SHA-256. A manifest lists approved file paths, digests and a release identifier. The observer reads the owned files; the policy compares those observations with the approved manifest before the launcher starts the server.

The manifest is trusted because of the workflow that supplies it, not because it contains hashes. If the same owner changes both the files and the reference, a match cannot establish that the owner is trustworthy. This lab has no remote attestation or signing authority. Its boundary is an approved local reference versus an observed owned package.

WORKED INPUTS / NOT A SUBMISSION

Validate the reference and supported-list shapes first, then check release support, compare the complete path inventory, and finally compare digests. This order determines the first refusal reason. A match establishes agreement between these two inputs. It does not establish that observations came from a trusted file reader or authenticate who approved the reference. Compare that limit with your saved prediction and append a revision if needed.

06 / REPRODUCE A DECISION
A final score leaves out the route.
A causal event is an operation needed to reproduce later state: joining, admitting an input, or taking a simulation tick. A checkpoint records the state just before a retained event window. It includes pending intent, expiry, cooldown and detector history as well as visible position and score. Omitting pending interaction can change the next tick even when two screenshots look identical.
The recorder keeps a bounded window. Before it runs out of room, it saves a new checkpoint and begins a new complete window. Absolute event indices make missing, duplicated or reordered entries visible. Replay restores the checkpoint, applies each event in order and compares the resulting state with the recorded final state.


RECORDED OWNED GAME / WORKED DEMONSTRATION


These saved inputs, verdicts and playback frames came from the owned Node game and its replay checker. This browser displays recorded results; the CLI commands below recompute them. Browser playback is an inspectable teaching aid and does not authenticate the record's author. A consistent record can still be fabricated by someone who controls its checkpoint, events and final state. A refused record establishes insufficient or inconsistent evidence, not a player's intent.

In the printed workspace, read telemetry/LEARNER.md and implement telemetry/policy.mjs. The supplied engine facade validates checkpoint shape and applies operations. Your policy checks release compatibility, completeness and contiguous event indices, then orchestrates replay and compares the final state. The source exercise's tests include complete rollover windows; rejecting every nonzero starting index is wrong.

For an actual server capture, run npm run trace:sample -- artifacts/session-window.json from the reference project. Then run npm run window:replay -- artifacts/session-window.json. The capture script owns a private test clock while its game inputs cross HTTP. No gameplay endpoint lets a client advance time or export other sessions.

Design a test that exposes a changed completion or resource balance after replay. State which data is causal and which personal data you would leave out.
Keep all first submissions, feedback and repairs. The checker grades executable behavior; the written transfer needs review. Later modules use these records to measure a detector and decide what evidence to retain.
