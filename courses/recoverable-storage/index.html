Build a recoverable single-writer store

Build a local string store with framed records, an append log, an index, atomic batches, truncated-write recovery and safe compaction. You own storage logic. The supplied disk adapter gives you local file operations and a deterministic process-interruption model.

Entry skills and boundaries

This course is for a programmer comfortable editing/running JavaScript ES modules, writing functions and classes, using objects/arrays/Map, reading exceptions and passing quoted arguments in a terminal. The storage course additionally assumes basic Node Buffer use, unsigned big-endian integers, UTF-8 byte lengths and filesystem calls; lesson01 works through cursor placement before production. This is not a first programming course. If these prerequisites are unfamiliar, use the reduced examples and completion cases, then decide whether to review JavaScript first. No extra runtime or paid account is required.

01. Binary records

A saved string needs a boundary: the next reader must know where it ends and whether its bytes are intact. Build an encoder and decoder for one explicit binary record format.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 01a, then save your answer with node lab.mjs predict project 01a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A record is one typed log entry. A frame is the byte envelope around it: magic, body length, checksum and body. Magic identifies this format. Length states how many body bytes the writer declared; available fixed field lengths must agree with it. The checksum detects selected accidental changes; it does not authenticate an attacker-controlled file.

Read contracts.md for the exact big-endian layout. All byte lengths refer to UTF-8 bytes, not JavaScript string length. A key with an accented character can occupy more bytes than its apparent character count. The supplied validator defines key, value and transaction-id bounds; you own placing those fields into bytes and reading them back.

The reduced example runner encodes one original put record and prints its header, field sizes and decoded record. Before revealing it, predict whether a missing last body byte is a valid smaller record, incomplete input or corruption. The declared outer length is what separates those cases.

Implement encodeRecord and decodeRecord in your solution module. Decode at the supplied offset and return the number of bytes consumed, so the next caller can read an adjacent frame. Return null for a consistent incomplete final frame. Once all 11 fixed body bytes are available, check that 11 plus key and value byte lengths equals the outer body length. A contradiction is malformed even if that outer length points past EOF. Do not read fixed fields that are not all present. Reject complete frames with a wrong magic, impossible lengths, invalid UTF-8 or a mismatched checksum. Never skip garbage looking for a later magic string.

Run stage 01. If round-trip succeeds but the field-layout case fails, your encoder and decoder may agree on the same wrong format. Compare the explicit header fields with the contract. The checker also changes one payload byte and tries every incomplete prefix of a valid frame. Explain why those experiments test different requirements. The length-prefix case also contrasts a genuine short suffix with an already detectable contradiction at both zero and nonzero offsets. The checksum covers the body only: a plausible damaged header may still look like an incomplete frame, so do not promise detection of every changed byte.

Your first build is a record inspector. It can encode a bounded operation, show byte lengths and reject a changed complete frame. It does not yet provide durable writes, an index or transaction atomicity.

For transfer, choose a non-ASCII key and an empty value. Predict key bytes and value bytes separately, encode the record and explain any difference from string length. Then place it after another frame and decode only from its actual offset. Keep the inputs and observed header in report.md so a later recovery investigation can rely on a format you checked.

02. Append logs and short writes

An encoded record is not a saved record until every intended byte has been appended and the persistence step has succeeded. Build appendLog over the supplied disk interface.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 02a, then save your answer with node lab.mjs predict project 02a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A short write reports that only a positive prefix of the requested bytes was accepted. The caller must continue from the first unwritten byte. Repeating the whole buffer would duplicate bytes; assuming one call wrote everything would lose a suffix. A zero-byte result makes no progress and must fail clearly rather than loop forever.

The disk adapter is supplied infrastructure. FileDisk wraps local file operations. MemoryDisk lets the checks limit each append call or interrupt it. You own the loop, the order of operations and the acknowledgement boundary. No paid service, database server or account is involved.

In the sibling worked example, the adapter accepts only a small chunk per append call. The example runner records the calls and final bytes. Predict where the next call starts before revealing that output. The loop should end with exactly the original byte sequence, followed by file synchronization.

Implement appendLog(disk,bytes,name). Validate progress on each call. Call sync only after all bytes have been accepted. A successful return is the acknowledgement that the intended bytes were written and file synchronization returned. A thrown error is not an acknowledgement, even if some bytes reached the file.

Run stage 02. The byte-preservation case distinguishes correct offset advancement from merely counting calls. If the output length is right but bytes differ, inspect which buffer slice you passed on each iteration. Keep the observed event order in the report.

This course's deterministic crash model represents process interruption. Completed file mutations remain visible, and a stopped append may leave a prefix. It does not simulate a machine losing power or storage hardware lying about flushes. FileDisk calls fsync, but the tests here do not establish universal durability under power loss. Read the assumptions in contracts.md before making any claim about persistence.

Your intermediate build is a usable append utility for framed bytes. For transfer, write two buffers with a different maximum chunk size and confirm their concatenation, then inject a zero-progress result. State which call was acknowledged and which was not. The unacknowledged call may still have left bytes, so a later reader will need recovery rules rather than a promise that failed writes leave no trace.

Worked procedure

Run node examples.mjs 02. Mark the next unwritten offset before each append. With its 9-byte sibling and 4-byte maximum, the offsets advance 0, 4, 8, then 9. A returned count advances the offset; it does not select the next record. Only after offset reaches the intended byte length should sync run. Completion: change the maximum to 2 and write the offset sequence before running your own append function.

03. Build an index

Reading a log from the start for every lookup is inconvenient. Build an index that remembers the latest value for each key as records are processed in order.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 03a, then save your answer with node lab.mjs predict project 03a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

An index maps a key to its current value. In this first index exercise, put replaces the prior value and del removes the key. A delete for a missing key leaves the map unchanged. A commit record has no direct key update. Transaction visibility is deliberately added in the next lesson; this raw index is not a safe recovered store yet.

A sibling example puts two keys, changes one and deletes the other. The example runner shows the final sorted pairs. Predict the outcome before revealing it. The order of records matters: the final operation for a key determines its raw-index state, regardless of earlier values.

Implement indexRecords(records). A Map is one possible representation; a carefully designed dictionary is another. Keys such as __proto__ must remain ordinary user data. Do not let a language object's inherited properties become store records. Return detached key/value pairs sorted by the contract's string comparison, so repeated runs have the same observable output. Use JavaScript </> string order: z precedes é; do not use locale-dependent collation.

Run stage 03. A failure on a special key is a representation error, not a reason to ban that key silently. A deletion failure may come from retaining an old entry after an operation that should remove it. Trace only the operations for the failing key to isolate the first wrong update.

The intermediate build can inspect the current logical contents of a known complete sequence of records. Combine it with the append utility to create an inspectable log and compare a full scan's result with your chosen expected entries. Do not call that combination atomic: an interrupted future batch could expose some operations unless recovery waits for a commit.

For repair practice, submit a sequence that updates and deletes the same key several times. Write the expected value after each operation in your report, then compare the final index. This makes a mistaken rule such as first value wins visible before it becomes a recovery problem.

For transfer, choose keys that sort differently from their insertion order, include an empty string value and delete a key that was never present. Explain why a missing key and a present key with an empty value are different. Revisit this distinction in the final usable-store CLI: get must use null for missing data and preserve the empty string.

Worked procedure

Run node examples.mjs 03. Maintain two columns: incoming operation and current map entry for that key. A put replaces only that key; a del removes it; an empty string remains a value. Sort a detached copy when producing entries, rather than relying on insertion order. Completion: reverse two operations for y and identify the first row where the result changes. Then use 03b to practice deletion, recreation and sorted output on a changed record sequence.

04. Atomic batches

Two related updates should become visible together. Add a commit boundary so recovery does not expose only the first half of a batch.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 04a, then save your answer with node lab.mjs predict project 04a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

A batch is a finite ordered list of puts and deletes that share one transaction id. Its physical records end with a commit record using that same id. In this model batches are contiguous and transaction ids increase. There are no concurrent writers or interleaved transactions to resolve.

Recovery accumulates a batch's operations without publishing them to the committed index. Only its complete commit applies them. A complete put without a later commit is not visible after reopen. A commit can acknowledge an empty batch. Repeated updates within a batch retain their order, so the last operation for a key wins.

The sibling example contains a committed earlier value and a later uncommitted replacement. Predict which value a reopened store may return before revealing the result. A complete operation frame answers whether the record is intact; a commit answers whether the group is visible. Those are different boundaries.

Implement encodeBatch and the committed part of recover. Build every record before starting the append, so invalid input fails without writing a half-validated transaction. Check transaction-id continuity while scanning. Interleaving or reuse is corruption under this format, rather than a request to merge operations heuristically.

Run stage 04. The final-byte truncation case is designed to leave earlier operations physically present while the commit is incomplete. If those operations enter the recovered index, the implementation confused record completeness with transaction completeness. Name that rule in report.md and record the before/after entries.

Your intermediate build can write related local changes as one logical update. The append function acknowledges only after writing the whole encoded batch and synchronizing it. A crash before acknowledgement may still leave a complete batch; recovery is allowed to show the whole batch or none of it according to the bytes that remain. It must never show only a subset.

For transfer, design a batch that deletes an old key and creates a replacement key. Test truncation before each record and just before commit. Explain why a report that checks only successful writes cannot establish atomicity. Keep both the acknowledged history and the byte prefix in the evidence; the set of allowed outcomes depends on both.

05. Recover a truncated write

A stopped writer leaves bytes that the next writer must interpret safely. Finish recovery and repair the tail before accepting another append.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 05a, then save your answer with node lab.mjs predict project 05a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

The committed boundary is the byte offset immediately after the last complete commit. It can be earlier than the last complete operation frame. recover returns that boundary, the committed entries, the number of discarded bytes and the last committed transaction id.

A reduced example appends a prefix of a new batch to a valid log. The example runner examines each cut position. Before revealing it, predict why appending a new transaction directly after the torn bytes would be unsafe. The old partial frame could consume bytes from the new transaction or hide it from the scanner.

When openStore reads a log, first run recovery without modifying the file. If a complete record is corrupt, or present fixed lengths already contradict its header, fail closed and preserve the bytes for diagnosis. A claimed end past EOF does not override an available length contradiction. If the suffix is merely incomplete or uncommitted, truncate to the committed boundary and synchronize that repair before appending a new transaction. An orphan temporary compaction file is not part of the active log.

Run stage 05. The every-cut case repeats the same recovery rule across every prefix of the second batch. It is a bounded exhaustive experiment over that batch's bytes, not a proof about all possible logs. The repair-then-append case checks a different property: the store must remain usable after the first recovery.

Your intermediate product is now a recoverable log reader and writer. Retain the original damaged bytes in a separate experiment copy, report the recovered boundary, reopen the working copy, add a new key and reopen again. Do not repair the only copy of data you wanted to inspect as evidence.

For a second practice case, leave several complete uncommitted records at the end rather than an incomplete frame. Confirm that they are still discarded. Then flip a byte inside a complete earlier record and verify an explicit corruption error. Truncating at the first bad checksum would silently erase a stronger kind of failure and is outside this contract.

For transfer, build an empty log, a log ending exactly at commit and a log containing only an uncommitted operation. Explain their different discarded-byte counts. Your report should distinguish what the bytes establish from what you assume about the environment. These tests model process interruption and known byte corruption; they do not reproduce power removal from the Mac.

06. Safe compaction and a usable store

A log retains old values after updates and deletions. Reclaim those bytes without destroying the only recoverable copy of current data.

Before the worked result

This case uses the terms and interface in contracts.md. Read the input in node lab.mjs question 06a, then save your answer with node lab.mjs predict project 06a YOUR_ANSWER --help-used none before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

Compaction writes a snapshot of the committed entries into a separate file. The temporary file is synchronized before it replaces the active log. Under the explicit atomic-rename assumption, a process interruption leaves either the old complete log or the new complete log as store.log. Both must describe the same logical entries.

The worked example updates a key repeatedly, compacts and reopens. Predict which properties must stay equal and which may change before revealing the result. Values and missing-key behavior must stay equal. File length and transaction layout may change. Byte-for-byte equality is therefore the wrong compaction criterion.

Finish openStore and its methods. get returns a string or null. put and delete are one-operation batches; batch applies several operations in order; entries returns sorted detached pairs. Once a write or compaction fails, poison that writer object and require reopen. Reusing in-memory state after uncertain persistence can build a second error on the first.

Implement compact by preparing compact.tmp, writing and synchronizing the complete snapshot, renaming it onto store.log, then synchronizing the directory. Never clear store.log to make room first. Ignore an orphan temporary file on reopen. A failed operation may leave such a file, and its existence alone is not permission to adopt it.

Run stage 06. The logical-content case checks successful use. The size case checks actual reclamation after repeated updates. The operation-order case checks that the replacement was prepared before rename. These are complementary observations; none alone establishes safe compaction.

The intermediate build is the store you can use for your own local string data. Run store.mjs to put, get, list, batch, delete and compact in a new data directory. Close the process between commands so each command really reopens the log. Keep test data separate from important personal data while you investigate faults.

For transfer, compact an empty store and a store containing only empty string values, then append new transactions to both. Explain why preserving logical entries is the invariant across those cases. State the platform assumptions in your report: one writer, atomic same-directory rename in the fault model, successful sync calls before acknowledgement, and no demonstrated claim about all filesystems or sudden power loss.

Worked procedure

Run node examples.mjs 06. Label the active log and the temporary file separately. Write the snapshot into the temporary file, sync it, rename it onto the active name, then sync the directory. Before rename, the old log must still be intact. After rename, the replacement must already describe all committed entries. Completion: put an interruption before each step and name which complete log remains under the explicit process model.

Original recoverable single-writer store: behavioral contract v1.1

Learner contract v1.1, adopted 2026-10-27. This successor clarifies malformed fixed-field prefixes; the wire format and process-interruption model are unchanged. Implement the storage behavior defined here. The byte format and fault model are original to this course, with no dependency on another course.

Scope, acknowledgement and crash model

One writer owns a local directory. Keys and values are UTF-8 strings. Reads return a string or null for a missing key. Multi-process locking, concurrent writers, replication and native database compatibility are out of scope. The intended usable artifact is a local persistent string store, callable by CLI or imported by a learner application.

The implemented deterministic fault adapter models process interruption: completed file mutations remain visible; an interrupted append can leave any prefix of that append; a rename replaces a whole file atomically. It does not simulate lost operating-system caches, reordered writes, filesystem metadata loss, power removal or faulty storage hardware. A complete checksum-corrupt frame is corruption and fails closed, rather than being treated as a torn suffix. Do not silently broaden this model to power-loss durability.

The real file adapter exposes fsync on the file and directory. Append acknowledgement occurs only after all intended bytes were written and file sync returned successfully. A crash before the caller receives acknowledgement can leave an operation either absent or committed. A failed writer object is poisoned and must be reopened. The course makes no universal power-loss claim and will report actual process/fault tests separately from platform assumptions.

Operation and record interface

Public logical operations: put(key,value), delete(key), get(key), entries() (key-sorted pairs), batch(operations), compact(), close(). Batch operations are {type:"put",key,value} or {type:"del",key}. Last operation for a repeated key wins. Entries are detached values. Single put/delete are one-operation batches.

Key order is JavaScript string comparison by UTF-16 code units: compare keys with </>, not locale-dependent localeCompare. For example, "z" sorts before "é", so these two entries are [["z","last ASCII"],["é","accented"]]. Return detached pairs; sorting must not mutate the store.

Physical records are {type:"put"|"del"|"commit",tx,key,value}. tx is integer 1 through 4294967295. A put has nonempty key and string value; del has key and value=null; commit has key=null and value=null. Key length is at most 1024 UTF-8 bytes; value length at most 65536 UTF-8 bytes. Batch records are contiguous, share tx and end with exactly one commit. Transaction ids strictly increase between committed batches. Empty batches may consist of just a commit. Interleaved/repeated transaction ids are corruption.

Only committed batches affect recovered state. A complete uncommitted operation suffix and an incomplete final frame are discarded. The recovery boundary is immediately after the last complete commit, not merely the last complete record. Recovery propagates a detectable malformed-prefix error, and opening such a log must leave its bytes untouched. Before a reopened store appends anything, it truncates the log to that committed boundary and synchronizes the repair.

Binary frame

All integers are unsigned big-endian. Header: ASCII magic IVY1 (4 bytes), body length (u32, 4 bytes), checksum (u32, 4 bytes). Body: opcode (u8: put=1, del=2, commit=3), tx (u32), key byte length (u16), value byte length (u32), key UTF-8 bytes, value UTF-8 bytes. Fixed body fields occupy 11 bytes. Body length must equal those fixed fields plus both byte strings and must be 11–70000. Commit has zero key/value lengths; del has zero value length.

Checksum is FNV-1a over body bytes: initialize uint32 2166136261; for each byte xor then multiply by 16777619 modulo 2^32. It covers no header bytes and detects selected accidental corruption; it is not authentication. It cannot detect every header change or distinguish every damaged suffix from a genuine torn write. Invalid UTF-8 is corruption.

encodeRecord(record) returns Buffer. decodeRecord(buffer,offset=0) returns {record,bytes} for a complete valid frame, null for a structurally consistent incomplete header/body at an otherwise valid offset, and throws for complete malformed/corrupt data or invalid invocation. Once all 11 fixed body bytes are present, compare their implied length (11 plus key and value byte lengths) with the outer body length before waiting for the claimed end. A disagreement is malformed and must throw even if that claimed end is past EOF. With fewer fixed bytes, do not read absent fields or infer that disagreement. This narrow prefix rule does not require earlier opcode/transaction/unused-field validation of an incomplete frame. It must not scan past garbage seeking a later magic. encodeBatch(tx,operations) returns concatenated operation frames and a final commit frame.

indexRecords(records) is an early raw-index exercise: last put/del wins and commits do nothing. It intentionally has no atomicity claim. recover(buffer) is the later committed-index operation and returns {entries,validBytes,discardedBytes,maxTx}; maxTx is the last committed transaction id (0 if none).

Supplied disk boundary and compaction

openStore(disk) uses a supplied adapter. Adapter primitives: read(name)->Buffer, append(name,bytes)->writtenCount, sync(name), truncate(name,length), rename(from,to), syncDir(). Only names store.log and compact.tmp are permitted. Append may make a positive short write; caller must loop until all bytes are written and reject zero/invalid progress.

Compaction writes the current committed snapshot as a new transaction into compact.tmp, synchronizes that file, atomically renames it onto store.log, then synchronizes the directory. It never truncates/deletes store.log before the replacement is ready. Orphan compact.tmp is ignored on reopen. Any model-level crash during compaction must retain the same logical committed entries in either old or new log. No reader is concurrent during replacement.

A fault trace may stop before/after each primitive or interrupt append after a specified byte prefix. Distinguish a complete checksum corruption from truncation. Identify which writes were acknowledged before the stop, allow an unacknowledged batch to be wholly absent or present, and reject partial batch visibility. Useful independent fixtures include repeated-key/delete batches, torn repair followed by append, empty-store compaction, short writes, failed-writer reuse and special string keys such as __proto__.

This contract freezes behavior, not correctness, independent acceptance or learning claims. Full platform/power-loss testing remains unperformed.

Capstone: a store you can use and recover

Choose a benign local string dataset you own. Build a small client on your own engine; for example, reading notes indexed by an id. Use get, put, delete and an atomic batch in a real operation such as replacing one note id with another. Include an empty string value and a repeated-key update in the workload.

State one transaction requirement for your client that differs from the lesson 04 exercise. Explain what changed and use your own workload to show that the operation meets that requirement atomically. Use the existing batch interface; the change may be in the client's rules rather than the engine API.

Keep a clean acknowledged baseline. In separate copied directories or MemoryDisk instances, interrupt the next append at several byte offsets, leave complete operations without a commit, corrupt a complete frame, and stop compaction before/after rename. Reopen each case and record the exact allowed and observed entries. After a torn-tail repair, successfully append and reopen again.

Deliver your code, runnable client/workload and recovery report. The report must state the single-writer, append-prefix, atomic-rename and synchronization assumptions; distinguish acknowledgements from attempted calls; identify the last committed byte boundary; connect each case to a requirement; retain at least one failed implementation experiment and repair; include a valid alternative strategy and one test that would reject an unsafe strategy.
