# 07. Fault injection and your recovery report

A recoverable store is useful only if you can explain which failures it handles. Use deliberate interruptions to test your own store and produce a reproducible recovery report.

## Before the worked result

This case uses the terms and interface in contracts.md. Read the input in `node lab.mjs question 07a`, then save your answer with `node lab.mjs predict project 07a YOUR_ANSWER --help-used none` before reading the worked result below. This is practice, not a mastery claim. If you need the unit's terms first, study them and label the answer assisted rather than an unaided prediction.

Fault injection means choosing a failure point rather than waiting for an accidental failure. Use MemoryDisk to stop after a primitive or leave a selected append prefix. Use copied real files for byte truncation and corruption experiments. Never apply these experiments to the only copy of data you care about.

Start with the acknowledged operation history. For each experiment record the primitive or byte offset where the writer stops, the remaining active-log bytes and the reopened entries. An unacknowledged final batch may be wholly present or absent; acknowledged earlier batches must remain visible. No allowed outcome contains half a batch.

Run stage 07. The compaction sweep stops after each primitive observed in a successful compaction and reopens the resulting log. The failed-writer case requires the interrupted object to reject reuse. These public cases are inspectable and finite. Add your own trace that distinguishes an unsafe implementation from a valid alternative; do not report only that the supplied cases passed.

Read capstone.md and choose a small real use for your string store: local reading notes, a component inventory or another benign dataset you own. Write a thin client using your engine. Keep the target storage logic in your own solution module. A supplied file adapter is infrastructure, not the capstone implementation.

Your report should connect each durability claim to its model and observation. Identify the last acknowledged operation, the permitted unacknowledged outcomes, the recovered commit boundary and the experiment that would refute your conclusion. Distinguish torn tails from complete checksum corruption. Retain failed experiments and repairs; a perfect-looking final run conceals the evidence that guided the design.

For the changed-problem capstone, use the provided workload and add a deletion plus repeated-key batch of your own. Reclaim the log, interrupt a later append and show that the client remains usable after reopen. Explain any unresolved failure rather than hiding it behind a broad durability promise.

Export your code, report, workload and complete attempt history to a new directory, then run the client from there. The optional critique prompt can help you find missing evidence if you choose your own LLM account, but deterministic checks decide their own cases and no model certifies recovery. Independent review, browser/download acceptance and human learning trials remain separate from this local engineering evidence.
