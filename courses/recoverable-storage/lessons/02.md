# 02. Append logs and short writes

An encoded record is not a saved record until every intended byte has been appended and the persistence step has succeeded. Build appendLog over the supplied disk interface.

A short write reports that only a positive prefix of the requested bytes was accepted. The caller must continue from the first unwritten byte. Repeating the whole buffer would duplicate bytes; assuming one call wrote everything would lose a suffix. A zero-byte result makes no progress and must fail clearly rather than loop forever.

The disk adapter is supplied infrastructure. FileDisk wraps local file operations. MemoryDisk lets the checks limit each append call or interrupt it. You own the loop, the order of operations and the acknowledgement boundary. No paid service, database server or account is involved.

In the sibling worked example, the adapter accepts only a small chunk per append call. The example runner records the calls and final bytes. Predict where the next call starts before revealing that output. The loop should end with exactly the original byte sequence, followed by file synchronization.

Implement appendLog(disk,bytes,name). Validate progress on each call. Call sync only after all bytes have been accepted. A successful return is the acknowledgement that the intended bytes were written and file synchronization returned. A thrown error is not an acknowledgement, even if some bytes reached the file.

Run stage 02. The byte-preservation case distinguishes correct offset advancement from merely counting calls. If the output length is right but bytes differ, inspect which buffer slice you passed on each iteration. Keep the observed event order in the report.

This course's deterministic crash model represents process interruption. Completed file mutations remain visible, and a stopped append may leave a prefix. It does not simulate a machine losing power or storage hardware lying about flushes. FileDisk calls fsync, but the tests here do not establish universal durability under power loss. Read the assumptions in contracts.md before making any claim about persistence.

Your intermediate build is a usable append utility for framed bytes. For transfer, write two buffers with a different maximum chunk size and confirm their concatenation, then inject a zero-progress result. State which call was acknowledged and which was not. The unacknowledged call may still have left bytes, so a later reader will need recovery rules rather than a promise that failed writes leave no trace.
