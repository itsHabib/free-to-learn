# 06. Safe compaction and a usable store

A log retains old values after updates and deletions. Reclaim those bytes without destroying the only recoverable copy of current data.

Compaction writes a snapshot of the committed entries into a separate file. The temporary file is synchronized before it replaces the active log. Under the explicit atomic-rename assumption, a process interruption leaves either the old complete log or the new complete log as store.log. Both must describe the same logical entries.

The worked example updates a key repeatedly, compacts and reopens. Predict which properties must stay equal and which may change before revealing the result. Values and missing-key behavior must stay equal. File length and transaction layout may change. Byte-for-byte equality is therefore the wrong compaction criterion.

Finish openStore and its methods. get returns a string or null. put and delete are one-operation batches; batch applies several operations in order; entries returns sorted detached pairs. Once a write or compaction fails, poison that writer object and require reopen. Reusing in-memory state after uncertain persistence can build a second error on the first.

Implement compact by preparing compact.tmp, writing and synchronizing the complete snapshot, renaming it onto store.log, then synchronizing the directory. Never clear store.log to make room first. Ignore an orphan temporary file on reopen. A failed operation may leave such a file, and its existence alone is not permission to adopt it.

Run stage 06. The logical-content case checks successful use. The size case checks actual reclamation after repeated updates. The operation-order case checks that the replacement was prepared before rename. These are complementary observations; none alone establishes safe compaction.

The intermediate build is the store you can use for your own local string data. Run store.mjs to put, get, list, batch, delete and compact in a new data directory. Close the process between commands so each command really reopens the log. Keep test data separate from important personal data while you investigate faults.

For transfer, compact an empty store and a store containing only empty string values, then append new transactions to both. Explain why preserving logical entries is the invariant across those cases. State the platform assumptions in your report: one writer, atomic same-directory rename in the fault model, successful sync calls before acknowledgement, and no demonstrated claim about all filesystems or sudden power loss.
