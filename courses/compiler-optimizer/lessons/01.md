# What must an optimization preserve?

## Decide what can be observed

Kernel IR returns an i8, i32 or bool value. It can also store into input arrays, append typed events, or terminate with a defined trap. All of those observations matter. Instruction identifiers, elapsed work and the arrangement of blocks do not.

Consider two runs that return i8 6. The first emits i8 2 and then i8 5; the second emits i8 5 and then i8 2. The return values agree, but the ordered event sequences differ. Comparing the event set would lose information.

For a normal return, compare the return type and value, all heap object identities/types/cells, and events in order. For a trap, compare its code and the heap/events that existed before it. Object-map key order is irrelevant; cell and event order are meaningful. Runtime observations use canonical decimal **strings** for words and booleans for bool values; no numeric coercion is needed here.

## Type along: compare one observable component

Add this helper above `compare` in `work/optimizer.mjs`. This is walked code for events, not the complete U01 solution. The exact snippet is exercised by `node --test teaching-examples.test.mjs`.

<!-- example: same-events -->
```js
function sameEvents(left, right) {
  if (left.length !== right.length) return false;
  for (let index = 0; index < left.length; index += 1) {
    const a = left[index];
    const b = right[index];
    if (a.type !== b.type || a.value !== b.value) return false;
  }
  return true;
}
```

The length check preserves duplicates: `[2, 2]` cannot equal `[2]`. Comparing the same index preserves order. Comparing both type and value distinguishes i8 `"2"` from i32 `"2"`. Empty event arrays compare equal because neither length nor an element differs. This helper assumes the well-formed event arrays produced by the supplied runtime; it is not a validator for arbitrary JSON.

Before running code, predict `sameEvents([{type:'i8', value:'2'}], [{type:'i32', value:'2'}])` and explain which line decides it. Then try a pair differing only in the second event.

## Separate program behavior from an incomplete experiment

A bounds trap is part of this IR's meaning. Running out of fuel is an incomplete observation of the program. Two loops reaching the same fuel limit have not demonstrated equivalent final behavior.

Replace only the starter's `compare` function with this bounded scaffold. Leave its imports and every later-unit function in place.

<!-- example: compare-scaffold -->
```js
export function compare(sourceResult, targetResult) {
  const completed = result =>
    result?.kind === 'return' || result?.kind === 'trap';
  if (!completed(sourceResult) || !completed(targetResult)) return false;
  if (sourceResult.kind !== targetResult.kind) return false;
  if (!sameEvents(sourceResult.events, targetResult.events)) return false;
  throw new Error('TODO U01: compare completion fields and the whole heap');
}
```

The first guard rejects unknown and invalid runs before trying to read their fields. The second separates a return from a trap. The event check can reject a discrepancy early. Equal events still do not establish equal behavior, so the scaffold deliberately throws until you finish it. Do not change that last line to `return true` and call the task done.

You own the remaining design and code:

- Compare the applicable completion fields: return type/value or trap code.
- Compare exactly the same heap object IDs regardless of object-map insertion order. For each ID, compare its element type, cell count and each cell in order. Do not sort the cells or rename the IDs.
- Return true only after all those fields agree. Exclude `steps` and `counts`.

Write a field inventory before implementing those decisions. Two heap maps can have different key insertion order and still describe the same objects. Why would comparing raw `JSON.stringify` output reject that pair? Conversely, why is comparing only return values unsafe?
