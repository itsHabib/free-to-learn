Verify exact bytes with the existing library

A digital signature relates a message, a signature and a public key. The supplied Node crypto code implements verification; you do not implement the cryptographic primitive. This lab first checks published RFC 8032 Ed25519 examples, then checks signatures over original EDUFW1 manifests.

A signature covers bytes, not an abstract JSON object. Appending a space can leave the parsed fields unchanged and invalidate the signature over the original bytes. The signed manifest names the capture digest; a separate hash comparison binds the file you received to the signed declaration. A valid signature alone does not perform that binding.

Worked case: the original manifest signature verifies, but someone hands you a different capture. Report valid signature and mismatched capture binding, then hold the classroom admission. Do not collapse these two observations into “signature invalid”.

Decide which key has authority

The local exercise pins one RFC test public key before it reads the submitted evidence. A file supplying its own key cannot grant itself authority. Verification with another key may be mathematically valid and still fail the pinned-key rule.

Everyone can obtain the RFC test seeds. A successful test-key signature therefore establishes only this classroom relationship; it does not identify a vendor, device owner or trusted distributor. No account credentials or new keys are created. This exercise teaches where authority must enter a real verification process, while leaving production roots and certificate policy outside scope.

Implement the four-axis assessEvidence function in trust.mjs. Keep manifest origin, capture binding and release policy independent; accept this one gate only when all required conditions hold. The Python config checks still have to be considered before the final investigation decision.
