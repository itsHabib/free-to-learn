# 03 · Run two desks from one order book

A shift lead is watching large orders. Dispatch is watching every open order. One cancellation can remove a row from both screens, one screen or neither. Build the loop that takes each desk from its opening snapshot to the latest committed revision.

Start with working `openView` and `classify` functions. The [store](../lib/store.mjs) supplies a retained changefeed, an ordered history of committed changes. You’ll write `poll(store, view)`, check the emitted events with a complete rescan, and run your engine across two terminals. Budget about six minutes to read and half an hour to build and experiment.

## Read one commit

Run this from the course directory. Before pressing Enter, predict which **IDs** the cursor must examine after the commit and what **events** the large-order desk should report.

```sh
node lab.mjs demo --worked
```

The demo’s initial result contains B at 42. The transaction changes A to 45 and deletes B. Scan the final rows for touched IDs. Only A still exists, so the matcher receives `[45]`. Its result `[0]` selects A. For each touched ID, look up the visible row before and after the transaction. A goes from absent to visible and B from visible to absent. The poll returns one batch.

```json
[{"revision":1,"events":[{"type":"enter","id":"A","row":{"id":"A","quantity":45}},{"type":"leave","id":"B","row":null}]}]
```

Filtering by the new rows alone loses B’s departure. Keep the entire list of touched IDs and look up each one, including a deleted ID, in your old view. Similarly, an order whose new quantity is `null` still exists. Pass this row to the matcher, since another desk may display it.

## Implement a poll

In `work/runtime.mjs`, replace the throw inside `poll`. Use the following contract to break down the implementation.

1. Call `store.changesAfter(view.revision)` once. It returns a finite list of the unread transactions in order. If a new commit arrives while scanning that list, the next poll can deliver it.
2. For each revision, collect the non-deleted final rows from `changes`. Use `selectRows(presentRows, view.matcher)` to build that revision’s visible after-rows. The matcher’s index zero refers to the first row in **this** array.
3. Walk the commit’s touched IDs in their original order. Find each ID’s prior visible row, or `null`, and look up the matching final row, or `null`. Ask `classify` for the event. Record the final visibility of that ID for the next revision.
4. Emit one object `{revision, events}` for every commit, including quiet ones. After applying the last commit, the view’s rows and revision must agree. A second call with no new writes returns `[]`.

**Try a delayed reader.** At r1, A enters with 45. At r2, before the next poll, A drops to 20. Predict the batches and the final map before reading further.

```sh
node lab.mjs check 03 --predict 'My batches and final map for the delayed reader'
```

Look for two batches containing an enter and a leave. Its final map has no A. If both comparisons use the opening view, r2 appears to have two absent versions and loses the leave.

**Make retry safe.** A matcher can throw. If you apply r1 to the live map, encounter an error on r2, and return no batches, the caller has lost the r1 notification or will see inconsistent rows when it retries. Stage the changes in a small map of touched IDs. A key present with value `null` means an earlier revision removed that ID. A missing key means you should consult the original view. Only copy the staged entries into the view and advance its cursor once the whole poll succeeds. An idle poll does no work. The worked implementation stages touched rows so an ordinary one-order update need never copy the whole board.

```sh
node lab.mjs check 03 --help-used 'describe your route'
node examples/replay.mjs
```

[The replay checker](../lib/replay.mjs) rebuilds the full result from the store at every revision. It compares visible rows, event payloads and cursor with your incremental result. In [the replay example](../examples/replay.mjs), K briefly drops below the threshold and returns to 43 inside one transaction. A classifier that emits a leave and an enter for K would end at the correct map and still send the wrong messages. The event comparison catches it. For a failure, inspect the first differing revision, write out the two committed versions, repair the local map or the batch, and replay.

## Take the shift

Use a fresh journal path for this run. In terminal one, print its path and start the board. Keep the watcher running.

```sh
orders_dir=$(mktemp -d)
echo "$orders_dir"
node lab.mjs watch --dir "$orders_dir"
```

In terminal two, change into the same course directory. Set `orders_dir` to the exact path printed by terminal one. Predict the next line on the watcher before each write.

```sh
orders_dir='/replace/with/the/printed/path'
node lab.mjs put A 45 --dir "$orders_dir"
node lab.mjs put A 45 --dir "$orders_dir"
node lab.mjs put A 30 --dir "$orders_dir"
node lab.mjs cancel B --dir "$orders_dir"
```

The second write commits a revision but leaves A at 45. Look for an empty event list **and** an advancing revision. Restart the watcher with Ctrl-C and the same command. It opens at the current revision. Its snapshot includes the final effects of these writes. This CLI rebuilds from the local journal when restarted. A separate downstream consumer would need to save its own position and outputs to resume delivery across a crash.

## Run both desks

Open a third terminal in the course directory. Set `orders_dir` to the same path and run `node lab.mjs watch --all --dir "$orders_dir"`. You now have two subscribers of the same store with different predicates. Design a sequence of writes to a **new** ID that meets all three conditions.

- Dispatch first sees an unknown quantity. The large-order desk has no visible event for that commit.
- Both desks display the ID after a later commit.
- One desk emits a leave while the other emits an update for the very same commit.

Write down both expected transcripts, run your sequence from terminal two and compare events at the same revisions. Then cancel the order and explain why the desks give different answers about its departure. Stop both watchers with Ctrl-C. The first version of your explanation and any mismatch make good notes for your next design.

## New case · The order that outranks the rest

A supervisor wants to see only the single largest order, breaking ties by the lexicographically smallest ID. In `work/largest.mjs`, open a store with A at 50 and B at 40. For this first probe the two quantities are distinct. Write a highest-quantity matcher and use it to open a view. This matcher receives only quantities, so it cannot apply the ID tie-break. Predict both the incremental result and a whole-store rescan when B rises to 45. Run them and preserve the mismatch in a test. Which row is missing from the inputs to the incremental matcher?

Build a row-aware subscriber for the full requirement in your script. Give it the IDs as well as the quantities. You can recompute the winner on each revision or keep an ordered index. Give it a second transaction that removes the current leader. Assert both the old winner’s departure and the new winner’s arrival, and verify that polling again is quiet. The existing quantity-based desks must still pass their checks. This new desk gives you an example of when scanning only touched rows stops being correct.

## Connect the JIT scan

Learners taking this course alone can run every exercise above with the supplied quantity matcher. If you built the sibling JIT and learned policy, run `node lab.mjs compare` from this directory. `node lab.mjs compare --worked` uses both author implementations for a demonstration.

The [JIT adapter](../lib/jit-scan.mjs) sends the scan a stack program for quantity greater than 30 and the batch of actual quantities. It asks the JIT for the indices that matched. Both execution modes must return the same matches. The opening board can hold thousands of rows while a single commit might touch only one. Read the decision counts and timings alongside the replay result. Record how many batches each policy chose to compile and how long its whole query run took on your machine. If the choices agree or the timings vary between runs, record that observation.

For another deployment, ask how long a changefeed retains its history and what happens to a cursor after a consumer restarts. These constraints decide whether an old view can resume or needs a fresh snapshot.
