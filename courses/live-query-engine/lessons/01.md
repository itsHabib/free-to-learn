# 01 · Catch the cancellation during startup

The packing desk opens a board of orders with more than 30 units. Order B appears with 42 units. Someone cancels B while the board is still drawing its first screen. If the desk misses the cancellation, a picker walks out with an order nobody wants.

Build the first screen and give it a place to resume. You’ll need Node 22+, a terminal, and enough JavaScript to read a `Map`. Run commands from `courses/live-query-engine`. Allow about five minutes to read and fifteen to build, an estimate.

## Watch the desk open

A **live query** returns an initial result and subsequent changes to that result. A **snapshot** captures the rows and their **revision**, the number of the last committed transaction included in those rows. We’ll keep one local map per desk, keyed by order ID.

The worked demo starts at revision 0 with A at 20 units, B at 42 and C awaiting a quantity. It then commits a single transaction that raises A to 45 and cancels B. Before you run it, write down the IDs that will appear on the first screen and which ones the transaction changes.

```sh
node lab.mjs demo --worked
```

The snapshot contains B. The next line names revision 1 and carries two events. A enters the board and B leaves. C’s `null` means its quantity is unknown. The quantity filter includes a row only when its quantity is known and strictly greater than 30.

## Take one snapshot

Open [the supplied store](../lib/store.mjs). In `snapshot()` you’ll find the complete read operation.

```js
return { revision: history.length, rows: Array.from(orders.values()) };
```

The function reads the revision and the order map in one synchronous call. It returns a new array of immutable row objects. Later commits replace the store’s rows, so this array still describes the first screen even if scanning it takes a while. This guarantee relies on the small store’s synchronous JavaScript implementation. A remote database needs an equivalent snapshot guarantee.

The **cursor** is the revision the desk has consumed. An opening cursor of 8 says “these rows already contain everything through revision 8.” Calling `store.changesAfter(8)` returns commits starting at revision 9. The store retains its whole in-memory history for this exercise.

Consider a tempting implementation. It scans `store.snapshot().rows`, spends a moment finding matching orders, then reads `store.revision` for its cursor. Put cancellation between the scan and that second read. The first screen contains B and the cursor now claims to include its cancellation. Every future poll will begin too late.

## Build the opening read

If you skipped the README setup, run `node lab.mjs init` once to create your work folder.

Edit only `openView` in `work/runtime.mjs`. Call `store.snapshot()` once. Pass its rows and the supplied matcher to `selectRows(rows, matcher)`. This helper sends quantities to the matcher, translates its zero-based indices back to orders and returns a `Map` keyed by ID. The incremental engine assumes a row qualifies solely from its own quantity. The batch API lets it evaluate many such decisions at once. A “highest quantity across all orders” filter depends on other rows and needs a different update algorithm. The returned object has three fields.

| Field | What the next poll needs |
| --- | --- |
| `revision` | The revision belonging to the rows you just scanned |
| `rows` | The map of visible orders |
| `matcher` | The same function, for future writes |

Try your code before opening the worked implementation. Record your own prediction with the check. If you used assistance, add `--help-used 'what helped'`.

```sh
node lab.mjs check 01 --predict 'replace this with the revision I expect after an in-scan write'
node examples/handoff.mjs
```

[The handoff example](../examples/handoff.mjs) cancels B inside the matcher. Its first line should still contain B at revision 0. The store is already at revision 1 with zero rows, and the unread feed contains revision 1. If B is stuck on screen and the unread feed is empty, inspect which read supplied your cursor. If the initial screen is empty, inspect which rows reached your matcher.

## Try a different arrival

Copy the runnable example into your work folder.

```sh
cp -n examples/handoff.mjs work/arrival.mjs
```

Edit the copy to insert a new matching order during the scan. Predict which screen first gets the new ID before running `node work/arrival.mjs`. Check that the snapshot omits it and the feed still holds exactly one pending commit. In lesson 03 you’ll apply that commit and retire the cursor.

PostgreSQL solves a related startup problem by exporting a snapshot aligned with a logical replication slot’s stream. Its documentation describes how a subscriber can read the snapshot and then consume the subsequent changes.
