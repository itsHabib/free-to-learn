# 08 · Your generator and cache investigation

Deliver a local generator and investigate a cache whose lengths, widths and numeric values look valid. Reproduce the discrepancy before proposing a repair.

Goal: deliver generated tokens before completion, diagnose unfamiliar cache content corruption and implement bounded beam search. Depends on all preceding modules. No project.mjs starter or completed investigation is supplied.

## Product and public interface

Create project.mjs yourself. Export async function runProject(runtime,model,spec). runtime is your implementation, and model is a validated original fixture. spec supplies prompt token IDs, a cache claimed to represent that prompt, maxNewTokens, seed and topK. Return {generation,differences}. generation must be the complete result of your runtime's local generate call under those settings.

differences is an array of numeric audit findings. Each finding identifies zero-based layer, component "keys" or "values", and maxError against a fresh replay of the stated prompt. Treat differences at or below 1e-8 as numeric agreement. A valid cache must produce no findings. Your report must go beyond naming an array: show the observed logit divergence and explain a plausible mechanism consistent with the evidence.

## Deliver the first token before completion

Also export streamGenerate(runtime,model,prompt,options={}) from your project.
Return an async iterator. It emits token events {type:'token',index,position,token},
then one {type:'complete',result} event with generate's full result. API.md
defines defaults, validation, stop precedence and failure behavior. You may use
an async generator or another iterator with the same observable behavior.

An async iterator has next(), which returns a promise for {value,done}. An
async generator is declared with async function* and pauses at each yield;
its caller resumes it with the next pull. A normal async function that returns
an array has already collected the result. A consumer can observe each event:

```js
for await (const event of streamGenerate(runtime,model,prompt,options)) {
  console.log(event);
}
```

Before implementing it, predict the calls and events for a prompt with one
context slot left, an EOS on the first draw, and a zero-token limit. Keep those
predictions and your first check result. Distinguish prompt IDs from generated
IDs; EOS is a generated event even though it adds no decoded text.

Use your existing prefill, sample, rng, decodeStep and decode. A consumer must
receive token0 before decode for token1 begins. Gathering the full result and
yielding it afterwards does not satisfy streaming. A later decode error must
reject its pull while the consumer retains the earlier prefix. It cannot be
turned into a successful result. The checks use a guarded runtime boundary to
expose buffering, then compare complete streamed results with your generate on
the original model. Repeated and interleaved streams must keep their own RNGs.

Write a small consumer in your project experiment, retain its ordered pull,
token, completion/error and runtime-call evidence in data.json and REPORT.md,
and rerun it after export. Report model/prompt/options and source identities.
Arbitrary additional script filenames are not automatically exported; preserve
their readable source in data.json or a separate explicit evidence bundle.
This baseline delivery exercise remains separate from cache diagnosis and the
distinct beam-search extension. It does not qualify pretrained language output.

## Bounded search extension

Add your own beamDecode(runtime,model,prompt,{beamWidth,maxNewTokens}) export to
project.mjs. API.md freezes the exact result, scoring, cache and stop contracts.
Width and new-token budget are both 1..4. The function uses your existing prefill,
decodeStep and tokenizer; it does not introduce another inference engine.

A greedy step chooses the best token now. A beam keeps a bounded set of prefixes,
so a different first token can later have a higher whole-sequence score. Sum
full-vocabulary log probabilities, expand the active prefixes, carry stopped
prefixes, and prune one combined pool. A carried EOS keeps its original score.
Numeric token IDs break exact ties. A log-probability tolerance is for comparing
results, not for turning unequal scores into ties.

Build in stages. First check width 1 against greedy generation. Next separate
whole-sequence scoring from last-token-only scoring on a tiny positive-weight
branching tape. Then retain multiple branches and trace each decode's parent
prefix and position. Siblings may share an unchanged parent cache; advancing one
sibling's cache and giving it to another sibling changes the conditional model.
Finally cover EOS carry, context/step bounds and the maximum 13 inference calls.
The public checks give finite score and call-ledger diagnostics for these builds.

Before running those checks, record your predicted retained prefixes and first
possible failure. Public cases disclose their expectations; passing them alone
is not an unfamiliar transfer experiment. Choose a different short branching
tape using the same 32-token model boundary, positive integer weights and no
more than two new tokens. Derive full-vocabulary conditional probabilities and
independently enumerate the complete tiny tree, including EOS stopping. State
why pruning preserves the candidates you compare; beam search is not generally
globally optimal. Explain a case where width 2 differs from greedy.

Keep a deliberately wrong accumulated-score or branch-state version, its first
observed failure, and a controlled repair with the tape/settings held fixed.
Record source identities, prompt, weights/logits, scores, retained IDs, stop
reasons, parent/child cache calls and assistance. A copied public outcome or a
claim that a shared object is always wrong cannot replace that evidence.

## Repair and export

The hint ladder is: locate the first divergent position; locate the first divergent block or component; compare a smaller explicit prefix under fixed sampling. No replacement project implementation is supplied. You may choose the optional critique prompt and your own LLM account, but its opinion remains separate from numeric results and declared assistance.

Export the runnable learner project ZIP and a REPORT.md containing your chosen prompts, original failing evidence, controlled repair and limits. Unzip into a fresh directory and rerun the checks. The artifact must include your readable runtime and project code, not just a transcript of generated letters. For CLI export, put optional tree data in work/data.json and the report in work/REPORT.md; those names are already allowlisted. Browser project export preserves code and recorded workspace history; retain a separate report or custom experiment file explicitly rather than assuming every local file is included. A passing fixture run establishes the stated numeric agreement; it establishes neither language quality nor human learning.
