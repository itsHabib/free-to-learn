# 08 · Your generator and cache investigation

Deliver a local generator and investigate a cache whose lengths, widths and numeric values look valid. Reproduce the discrepancy before proposing a repair.

Goal: deliver generated tokens before completion, diagnose unfamiliar cache content corruption and implement bounded beam search. Depends on all preceding modules. No project.mjs starter or completed investigation is supplied.

## Product and public interface

Create project.mjs yourself. Export async function runProject(runtime,model,spec). runtime is your implementation, and model is a validated original fixture. spec supplies prompt token IDs, a cache claimed to represent that prompt, maxNewTokens, seed and topK. Return {generation,differences}. generation must be the complete result of your runtime's local generate call under those settings.

differences is an array of numeric audit findings. Each finding identifies the zero-based layer (the block index from modules 04 and 05), component "keys" or "values", and maxError against a fresh replay of the stated prompt. Treat differences at or below 1e-8 as numeric agreement. A valid cache must produce no findings. Your report must go beyond naming an array: show the observed logit divergence and explain a plausible mechanism consistent with the evidence.

## Deliver the first token before completion

Also export streamGenerate(runtime,model,prompt,options={}) from your project.
Return an async iterator. It emits token events {type:'token',index,position,token},
then one {type:'complete',result} event with generate's full result. API.md
defines defaults, validation, stop precedence and failure behavior. You may use
an async generator or another iterator with the same observable behavior.

An async iterator has next(), which returns a promise for {value,done}. An
async generator is declared with async function* and pauses at each yield;
its caller resumes it with the next pull. A normal async function that returns
an array has already collected the result. A consumer can observe each event:

```js
for await (const event of streamGenerate(runtime,model,prompt,options)) {
  console.log(event);
}
```

Before implementing streamGenerate, predict the calls and events for three separate cases: a prompt with one
context slot left, a run whose first draw is EOS, and a zero-token limit. Keep those
predictions and your first check result. Distinguish prompt IDs from generated
IDs; EOS is a generated event even though it adds no decoded text.

Use your existing prefill, sample, rng, decodeStep and decode. The consumer must receive each token event before sample or decodeStep begins work for the next token; that is what lets a caller show the first token while the rest are still being computed. Gathering the full result and
yielding it afterwards does not satisfy streaming. If a later decode throws, the promise from that next() call must reject; the consumer keeps the token events it already received, and the stream must not report a successful result. The checks detect a sample or decode that starts before the consumer has received the previous token. They then compare the complete streamed result with the result from your generate on the original model. Repeated and interleaved streams must keep their own RNGs.

The author's stream, run against a recording runtime (the reference runtime with prefill, decodeStep and sample logging each call), interleaves like this for an ordinary three-token run:

Write a small consumer in your project experiment. Record, in order, each pull, token event, completion or error, and runtime call in data.json and REPORT.md. Rerun the consumer after export. Report model, prompt, options and source identities, such as each source file's SHA-256.

## Bounded search extension

Add your own beamDecode export to project.mjs. API.md freezes the exact result,
scoring, cache and stop contracts.

```js
export async function beamDecode(runtime, model, prompt, {beamWidth, maxNewTokens}) {
  // return the result API.md defines
}
```

Width and new-token budget are both 1..4. The function uses your existing prefill,
decodeStep and tokenizer; it does not introduce another inference engine.

A greedy step chooses the best token now. A beam keeps a bounded set of prefixes,
so a different first token can later have a higher whole-sequence score. Sum
full-vocabulary log probabilities, expand the active prefixes, carry stopped
prefixes, and prune one combined pool of active and stopped prefixes to beamWidth. A carried EOS keeps its original score.
Numeric token IDs break exact ties. A log-probability tolerance is for comparing
results, not for turning unequal scores into ties.

First check width 1 against greedy generation. Next separate
whole-sequence scoring from last-token-only scoring on a tiny branching tape: a table that gives, for each prefix, a positive integer weight to each next token, which the checks turn into the logit log(weight). This public tape from beam-fixture-data.mjs starts at prompt [4]; token 6 leads with weight 60, but after 7 a single EOS weight of 90 waits. `states` is keyed by the generated tokens so far, joined by commas; a prefix it does not list gets equal weights:

```js
{"id":"sequence-score-beats-greedy","prompt":[4],"maxNewTokens":2,
 "root":{"weights":{"6":60,"7":40},"defaultWeight":1},
 "states":{"6":{"weights":{"8":30,"9":29},"defaultWeight":1},
           "7":{"weights":{"0":90},"defaultWeight":1}},"fallback":"uniform32"}
```

Then retain multiple branches and trace each decode's parent
prefix and position. Siblings may share an unchanged parent cache; advancing one
sibling's cache and giving it to another sibling makes that sibling's next logits condition on the wrong prefix.
Finally cover EOS carry, context/step bounds and the call cap: one prefill plus at most beamWidth × (maxNewTokens − 1) decodeStep calls, 13 at width 4 and four tokens.
The public checks give finite score and call-ledger diagnostics for these builds.

Before running those checks, record your predicted retained prefixes and first
possible failure. Public cases disclose their expectations; passing them alone
does not show that your code works on a case whose expected result you have not seen. Choose a different short branching
tape using the same 32-token model boundary, positive integer weights and no
more than two new tokens. Derive full-vocabulary conditional probabilities and
independently enumerate the complete tiny tree, including EOS stopping. State
why pruning preserves the candidates you compare; beam search is not generally
globally optimal. Explain a case where width 2 differs from greedy.

Keep a deliberately wrong accumulated-score or branch-state version, its first
observed failure, and a controlled repair with the tape/settings held fixed.
Record source identities, prompt, weights/logits, scores, retained IDs, stop
reasons, parent/child cache calls and assistance. Copying a public expected result, or asserting that sharing a cache object is always wrong, does not replace that evidence.
