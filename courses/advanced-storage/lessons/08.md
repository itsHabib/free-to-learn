# 08 — Break and repair the concurrent database

A result is wrong only when it contradicts a specific contract under a recorded execution. Build an investigation that reproduces a snapshot defect, repairs it and survives a changed schedule.

This unit supplies the run recorder and evidence checker. You author the scenario, preserve a faulty version of your policy code, repair it, and explain the causal difference. The instructor's reference and calibration scenarios are not in this packet.

## 08.1 Record a discriminating schedule

Commit `08a`. Begin with a scenario that contains an old reader, a concurrent writer and a later read from the old transaction. Add an indexed read, cleanup while a pin remains, cleanup after all pins close, and a within-snapshot plan comparison. Use the operations and schema format in [the project contract](../PROJECTS.md).

Record your prediction before execution with `--prediction`. Run directories contain exact engine source, scenario, result, runtime identity and hashes. Put scenarios, runs and your investigation JSON inside your project directory so export carries them together. Treat one successful run as an observation rather than a general guarantee.

Your broken source must complete the scenario but violate a snapshot result. You can preserve a naturally occurring bug or deliberately evaluate a labeled wrong implementation. A syntax error, hang or missing method is not the semantic failure this project asks you to diagnose.

The supplied `minimize` command can shrink a recorded failing run before you explain it. It preserves the first snapshot mismatch, exact saved policy and input order while trying to remove whole transactions, actions and initial versions. Read its `show-witness` trace: which removals left the same observation wrong, and which changes were rejected? A smaller reproducer is useful evidence, but neither a budget-limited result nor local irreducibility proves a globally minimal cause. The project contract links the exact command and limits.

## 08.2 Connect wrong results to one violated invariant

Commit `08b`. The evidence checker builds a simple copied-map snapshot model, separate from your version selection and index code. It compares logical point reads, scans, query pulls and joined row bags against that model. It requires an actual mismatch in the broken run and none in the repaired run.

Use exactly the same scenario bytes for the broken and repaired runs. Otherwise a changed workload could explain the changed outcome. Keep the failed source and result. Describe the relevant transaction, snapshot, version and operation ordering; avoid an explanation that only says a test became green.

The repaired source must also pass all seven component milestones. A repair that avoids one scenario by aborting every writer or retaining every version is insufficient. The component controls deliberately preserve useful independent work and reclamation progress.

## 08.3 Replay the repair and its costs

Commit `08c`. Create a second scenario with a changed transaction/read/write/cleanup structure, not only different names or numbers. Run it with the exact repaired source. The checker rejects a mere added `inspect` action as structural variation.

Write your investigation descriptor and run `node lab.mjs assess work work/investigation.json --help-used none`. It reruns the saved programs and scenarios, verifies byte identities, checks the independent snapshot observations and recomputes the costs cited in your report. Include at least one predicted cost and one observed cost; the checker rejects invented numeric observations.

The resulting `engineeringPassed` value covers those explicit checks. Your diagnosis still needs to satisfy the published causal rubric: identify the violated rule, explain why the schedule exposed it, describe why the repair preserves other valid histories, and distinguish estimate error from result error. Neither a nonempty explanation nor the automated flag establishes independent course acceptance.
