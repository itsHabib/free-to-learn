01 — Decide which version exists for a reader

A booking reader pauses while another client updates the equipment table. Implement the policy that keeps the paused reader's view stable when it resumes.

Your project increment is visibleVersion. The supplied engine already stores immutable committed histories and each transaction's private writes. You decide which committed version exists for one snapshot. Read the method contract before editing.

01.1 Read time and commit time

A commit sequence number, or CSN, names a published write transaction. A snapshot is the largest published CSN included in a reader's view. These are logical counters; elapsed time is irrelevant. A row can physically have a version at CSN 7 while a reader whose snapshot is 6 must still use its earlier version.

Commit a prediction before running the example: node lab.mjs question 01a. Record it using answer work 01a 'YOUR_JSON' --help-used none.

Consider a different row with versions (CSN 3, value 14) and (CSN 8, value 22). A reader at snapshot 5 sees 14: 3 belongs to its view and 8 does not. At snapshot 8, the second version becomes visible. The equality boundary matters. A check using strictly less than the snapshot would hide a commit that was already included when the reader began.

Completion case: for versions at 1, 6 and 9, identify the qualifying prefix for snapshot 6 before choosing its final member. Then implement this decision for arbitrary ascending histories. An empty qualifying set returns null. The returned object is the version, not only its row payload.

01.2 Visibility, deletion and own writes

A tombstone is a version whose row is null. It records absence from that commit onward. Once it is the newest version in the reader's view, searching backward for a non-null row is wrong: that would resurrect an earlier value. A later reinsertion is another version with a new CSN; it does not erase the interval of absence.

Use question 01b and record your response before looking at its feedback. Explain to yourself whether the newest qualifying version or the newest qualifying *non-deleted* version is the rule you are implementing.

The shell handles a transaction's own private writes before it calls your method. If a client stages a new booking value, that client can read it immediately, while another client still sees committed history. A private deletion similarly means absence for its owner. This overlay is supplied so the exercise stays about historical visibility. Do not scan or mutate another transaction's private write map.

01.3 One query, one pinned view

A scan can pause between rows. Its next call must use the same snapshot, even if new commits now exist. The supplied query handle retains the transaction's view until exhaustion, close, abort or error. The later reclamation unit will make that lifetime important.

The query conditions are also fixed when the scan opens. The shell owns a deep copy of the predicate; changing the original object, even a nested range bound, does not change a paused scan. A different predicate requires a new scan.

Commit 01c. Then implement visibleVersion(history, snapshot, examine). Call the supplied examine(version) callback whenever you inspect a version; this produces a trace for later cost comparisons. You may traverse backward, scan forward, or use another correct strategy. Do not reorder or mutate the history.

The public checker tests exact boundaries, tombstones, absence, detached results and the supplied private overlay. 02 — Publish concurrent transactions atomically

A transaction changes two equipment records, but a reader must never see only half the change. Implement the commit ordering that turns one private write set into one acknowledged database state.

Keep your visibility method. You now own commitTransaction; the shell supplies the accepted durable batch store and the narrow helpers in the contract. This unit's tests use a declared validation-free stage with independent writes. Same-key concurrency is the next unit, so do not call this stage Snapshot Isolation yet.

02.1 Private writes and transaction states

An active transaction holds proposed writes in its own map. Staging a write is not a commit: other clients cannot read it. A successful transaction becomes committed; a rejected one becomes aborted. Once terminal, its handle cannot read or write again. Repeating a commit must not apply its operations twice.

Work through 02c: a read-only completion changes state without creating a row version. In your method, account for that case separately from a write batch. The supplied finish helper closes handles and clears private data only when you have chosen the outcome.

A query in the same transaction freezes the private overlay while it is open. The shell therefore refuses commit or new private writes until that query closes. This is a bounded API rule, not a universal property of databases.

02.2 Validate, persist and publish

There are three distinct boundaries. Preparation constructs a proposed complete update and can reject resource limits without writing. Persistence submits that update as one batch to the supplied engine. Publication makes the new logical history and CSN available to subsequent transactions. Client acknowledgement follows those effects.

Commit 02a before implementing the order. As a sibling example, imagine publishing a replacement directory listing: calculating a new list does not make it visible, writing its bytes does not mean the application has switched to it, and sending success too early can claim a state that never became durable. The database has the same need to distinguish phases, although its supplied batch operation handles the bytes.

Use this.conflicts(tx) before effects. This helper is empty in the unit-02 stage and will call your conflict policies in later stages. Obtain a prepared update once, persist that exact update, then publish that exact update. The synchronous publication section does not yield to another client. A new reader starts with either the old CSN or the fully published new CSN.

02.3 Acknowledgement and uncertain outcomes

Commit 02b. A process can stop after a batch became durable but before its client hears success. Neither “definitely committed” nor “definitely absent” follows from the lost acknowledgement alone. Reopening the supplied store can recover the whole batch. Retrying an arbitrary write as if it failed could duplicate an effect.

The shell's indeterminate helper poisons the coordinator after a persistence/publication failure. Existing state is no longer safe to serve until reopen. This preserves uncertainty rather than inventing an abort. The course inherits a process-interruption model; it does not establish power-loss safety or a distributed exactly-once protocol.

The tests also stop after durable acknowledgement, reopen a fresh engine, and check both rows. They do not ask you to rewrite the WAL or interpret its byte frames.

03 — Distinguish isolation from an application invariant

Two clients reserve the same equipment slot from the same old view. Implement write-conflict validation, then identify the kind of anomaly that it still permits.

Your increment is writeConflicts. The commit method from unit 02 calls it through the supplied validation dispatcher. Unit 03 and later turn that policy on.

03.1 Statement snapshots and transaction snapshots

A statement-snapshot reader can observe one committed state in its first query and a newer committed state in its second. A transaction-snapshot reader keeps the same committed view across its reads. Neither should read another transaction's uncommitted private values.

Our learner engine uses one transaction snapshot. The current slice does not implement a full Read Committed write mode. Treat that comparison as a distinction in allowed observations, not a promise of compatibility with another database's locking rules.

Before coding, commit 03a. Let A and B begin at snapshot 12. If both stage key 6 and A publishes at 13, B's starting view no longer includes the latest write to key 6. Publishing B unconditionally would hide A's change. A conflict is about that timeline, not whether the final row happens to equal an earlier value.

03.2 Same-key conflicts and first committer

Snapshot Isolation keeps a stable view and refuses a writer whose target key changed after its snapshot. The comparison is strict here: a latest write at the snapshot is already included; a latest write after it is a conflict. Check every distinct key in the private write map. Missing history means no previous committed write, not a special exemption from future insert races.

Deletes matter. A tombstone carries a CSN and can conflict with a stale insertion or update. A change followed by a restoration also matters. Commit 03c, then verify that your decision uses write occurrence rather than comparing endpoint row values.

The checker includes independent writers. If A writes key 1 and B writes key 2 without a dependency that this mode validates, both must be able to finish. Aborting every overlap avoids one race by destroying the intended behavior. Holding a global lock for each entire transaction would similarly evade the exercise.

03.3 Write skew without a dirty read

Now consider two equipment records whose combined availability must remain above a threshold. Each client reads both from the same valid old snapshot, then changes a different record. No same-key conflict is necessary, yet the combined result may violate the condition. This is write skew.

Commit 03b. Stable snapshots answer “what did each transaction read?” They do not by themselves answer “could all successful transactions have run one at a time with those observations?” That second question is the motivation for the next unit's dependency validation.

Implement writeConflicts and run node lab.mjs check work 03 --help-used none. Do not change the supplied private-map or disk code to make one fixture pass. Return a description for every conflicting key. Descriptions may use any clear shape and appear in any order; the checker does not require a particular witness format.

04 — Validate what a transaction depended on

A client checks that no booking exists, then another client creates one before it commits. Implement validation that includes the information in an empty result.

Your increment is readConflicts. The shell records point and predicate reads independently from how they are executed. You compare those logical dependencies with committed changes after the transaction's snapshot.

04.1 Point reads include absence

A read does not stop being information because it returns no row. An absent key can determine which branch of a transaction runs. If another transaction inserts that key, the earlier branch may no longer be compatible with placing the reader after that write.

Commit 04a. In this course's conservative Serializable mode, every point dependency includes the key identity, regardless of whether it returned a row. A later change to that key intersects the dependency. The relevant question is whether the change committed after the reader's snapshot, not whether a row happened to be returned earlier.

As a completion case, draw a timeline with a reader at 4, an insertion at 5, and the reader's validation afterward. Mark where the reader would need to be placed if its absence observation were still true. Our mode chooses commit-order validation, so it rejects the reader rather than silently choosing another serialization order.

04.2 Predicate reads include gaps

A query such as 20 <= value < 30 reads a set defined by a predicate. Recording only the returned keys misses a new matching key. It also misses the dependency of an empty result. Record the predicate domain, then test relevant changes against it.

A change contains a before-image and an after-image. An insertion can enter the set. A deletion can leave it. An update can do either, both, or neither. Commit 04b before choosing which images to test. BaseEngine.matches is the supplied typed evaluator; a null image does not match.

The recorded predicate must be the one the query actually executes. At scan creation the supplied shell captures one deep copy and uses it for both iteration and dependency recording. If a caller opens a query for A and later changes its original predicate object to B, the open query still asks for A. Recording A while executing B would make correct conflict validation miss a real dependency. That would be a shell defect, not an error you could repair by changing readConflicts.

The upper bound is exclusive. A change entirely outside the predicate should not create a conflict in the precise single-table case. This positive control matters: an implementation that always reports a conflict is safe only in the trivial sense that it prevents useful work.

04.3 Serializable validation and whole-transaction retry

At commit, first apply your same-key write policy, then the read-dependency policy when the database mode is Serializable. The current commit section is synchronous, so another client cannot slip a new published change between validation and publication. The earlier private work remains concurrent.

Ordinary Serializable transactions validate even when they happen to perform no writes. A read result used inside such a transaction is not a successful committed outcome until validation succeeds. A separate begin({readOnly:true}) declaration prohibits every staged write and can serialize at its pinned snapshot instead. That narrow route supports a long export while writers proceed; it must not be applied to a transaction that might write later. This is an explicit teaching contract, not PostgreSQL's implementation.

Commit 04c. A conflict retry needs a new transaction and snapshot, followed by repeated reads and decisions. Calling commit again on the terminal old handle cannot repair an old branch decision. This slice exposes aborts but does not yet supply an automatic retry scheduler; a client can explicitly start and recompute its transaction.

Implement readConflicts and run node lab.mjs check work 04 --help-used none. The suite compares the same disjoint-write pattern under SI and Serializable, then checks absence, an empty range, a leaving update, the upper endpoint and a value-change-then-revert. Keep the SI anomaly: eliminating it by silently making both modes identical would hide the distinction being taught.

05 — Keep index candidates correct across time

An equipment record moves from group A to B while an older reader still needs to find it in A. Implement historical index membership without changing the query's snapshot meaning.

Your increment is indexMemberships(history, field). In this slice the shell materializes candidate maps and rebuilds enabled maps before publishing changes; an incremental ordered index is not implemented. The policy you build establishes the historical coverage that such an index must preserve.

05.1 Candidate membership and visible truth

An index candidate means “this key may match,” not “return this row without checking.” The shell first finds candidate identities, then asks your visibility method for the version in the reader's view, and finally evaluates the predicate. This separates an index's search role from the database's visibility rule.

Candidate selection and the final filter use the same predicate captured when the scan opened. Otherwise a caller could change the filter after candidates were chosen and silently lose rows. The supplied shell preserves this boundary for both index and full-scan access.

Commit 05a. In a sibling example, a row has historical locations East and West. Both memberships can be necessary while two snapshots remain active. The current row alone cannot answer every old reader. A candidate that proves invisible can be discarded; a needed row omitted from the candidate set cannot be recovered by a later filter.

Use typed value keys if you deduplicate membership. JavaScript object-property coercion can conflate values, and null must remain a deliberate value for isNull. The shell supplies BaseEngine.valueKey for this bookkeeping.

05.2 Updates that move between index keys

Commit 05b. Several historical versions of one key do not become several logical rows in a single-table result. Conversely, two different keys sharing one indexed value must remain two rows. Candidate de-duplication and relational duplicate removal are different operations.

A tombstone has no indexed row fields. A reinserted row can add a new historical value without erasing an earlier one still needed by a snapshot. Uncommitted private writes are not added to shared committed history; the shell merges the owning transaction's private candidates separately. Abort must not expose them to another client.

The future retention policy will decide which committed versions can disappear. Your index membership should be based on the retained history it receives, so cleanup and index coverage remain connected.

05.3 Logical dependencies survive a faster access path

Commit 05c. Serializable validation is about what the query depended on, not which candidates a particular physical path happened to inspect. A query returning nothing can still depend on a gap. The shell records the predicate before selecting scan or index access; your membership method must not alter that record.

Implement the method and run node lab.mjs check work 05 --help-used none. The checks compare full scans and indexed scans under old and new snapshots, repeated membership, private aborts and reopen. They also insert into a predicate that an earlier index read found empty.

For a fresh test, make one key move A → B → A and give another key the same group. Keep a reader alive between the first two moves. Predict both readers' results before running either access path. A correct result must preserve the distinct keys while returning each key once.

There is no speed claim from passing this unit. Recomputing memberships scans history and can be expensive. The later planning work must measure that overhead honestly before comparing this prototype with a maintained index.

06 — Reclaim history without changing a live view

A long reader keeps an old equipment view alive while writers accumulate versions. Implement the retention boundary that permits cleanup without invalidating that reader.

Your increment is retainedVersions(history, watermark). The shell supplies the active transaction registry, persists version deletions, and records logical removals. You decide which versions must remain.

06.1 Reader lifetimes and the low-water mark

The watermark is the smallest snapshot still needed by an active transaction. Every active handle counts, including one that has not read yet. A future first read from that handle is entitled to its original view. A paused query also keeps its transaction's snapshot alive.

Commit 06b. Releasing a query handle is different from ending its transaction: the transaction can still issue another query. Exhaustion, close, cancellation and an exception release the query reference. Commit or abort ends the transaction's pin. A cleanup policy must use these explicit lifetimes rather than guessing from inactivity.

The current shell does not silently time out old readers. Under pressure it can refuse a new write. This is preferable to changing an existing reader's contract behind its back.

06.2 Retain the boundary version

Commit 06a. The watermark can lie between versions. An old reader needs the newest version at or before its snapshot, which may have been written long before the watermark. Retaining only newer versions loses that predecessor.

For a different example, use versions at 1, 5, 13 and a watermark of 9. The version at 5 is still needed; 13 is needed by newer readers or the current view. The version at 1 can disappear under this simple global-watermark policy. If the boundary at 5 is a tombstone, retain it: absence can be the correct old view.

When no transactions remain, the shell uses the current CSN as the watermark. The policy should then make progress toward one latest version per key. This slice retains even a latest tombstone rather than trying to remove its key metadata. A precise per-snapshot policy could retain fewer intermediate versions, but it must preserve all live observations.

06.3 Bounded cleanup and honest measurements

Commit 06c. Removing a version from the logical database does not prove the append-log file shrank. The accepted store records deletion as another operation; its own compaction is the separate mechanism that replaces the physical log. Process memory and physical disk size are separate measurements too.

The shell keeps a committed-change journal for Serializable validation. A row version becoming reclaimable does not automatically make every change record irrelevant. Changes after the oldest active snapshot remain available until the dependent transactions finish.

Implement retention and run node lab.mjs check work 06 --help-used none. The cumulative suite tests an idle pin, a paused iterator, a tombstone boundary, validation evidence, safe refusal at a small version limit and fresh reopen after cleanup. Keeping every version forever fails the progress control.

For a fresh investigation, hold one old transaction while repeatedly updating one key. Record retained-version count before cleanup, after cleanup with the pin, and after closing the pin and cleaning again. Explain the change using the actual boundary version. Carry this recorded investigation into the next unit: its retained history will become measured physical work in a query-plan comparison.

07 — Explain a plan in the presence of old snapshots

A query returns one matching group, but finding that group may require examining many retained versions. Implement statistics and cost estimates that separate visible rows from physical work.

Your two increments are summarizeSnapshot and planEqualityJoin. The shell supplies three physical operators and an equality-join query interface. You do not build a SQL parser, optimizer search, hash table library or distributed worker system.

07.1 Visible cardinality and stale statistics

analyze measures one declared read-only view. Its rows belong to a specific snapshot. Its metadata also identifies the current physical CSN, number of physical keys, measured version examinations, and the number of historical candidate keys under each indexed value. Your summary adds visible row count and value frequencies without changing that metadata.

Commit 07a. Two snapshots can have the same number of visible rows but require different work to find them. An old reader may pass over several newer versions before reaching its own. A frequency table describes which visible values exist; it does not by itself describe that search cost.

The current prototype collects exact bounded frequencies rather than sampling or a compact histogram. Statistics can still become stale when new versions accumulate or cleanup removes old versions. The persisted physical revision distinguishes those changes from the logical snapshot: vacuum can change physical work without publishing a new logical value. explain reports that staleness; it does not secretly change the query's snapshot. A stale estimate may choose poorly while execution remains correct.

07.2 Index probes, version checks and join alternatives

The supported query filters the left table on one value and equijoins that field to a second table. scan-loop scans the left input, then scans the right for each matching left row. scan-hash scans each input once and builds/probes a supplied hash table. index-loop uses historical candidate indexes on both sides.

The contract names every work component. Candidate visits and predicate checks are charged once per visited candidate. Estimate version examinations from each side's measured mean per physical key, rounding each side upward. Hash build/probe and emitted pairs have their own charges. Left and right visible value frequencies estimate joined-pair multiplicity. For an equality value of null, there are no matching rows.

Commit 07b. A narrow match can favor index loops; many matches can make repeated right-side probes more expensive than one hash build. The point is not that one operator is always better. It is that a declared cost assumption makes a testable prediction.

Indexes are built before a controlled comparison and maintained by rebuilding their candidate maps at publication. Setup and maintenance appear as separate index-build events. Do not describe a warm query comparison as total end-to-end savings without accounting for those events.

07.3 Predicted cost versus observed work

Commit 07c, then implement both methods using the detailed interface. planEqualityJoin returns all three estimates plus the selected candidate ID. Every candidate includes its work vector, estimated output rows and weighted cost. Any tied minimum is accepted. No candidate execution is allowed while planning.

Run node lab.mjs check work 07 --help-used none. The checks compare all plans' actual row bags, exercise selective and many-match cases, validate snapshot identities, test null and detect planning that changes measured work. They also retain logical read dependencies independently from the chosen physical operator.

For a fresh experiment, keep one read-only snapshot open while adding versions of indexed rows. Collect new statistics for that old snapshot, compare its estimates with actual counters, then close it and vacuum. Explain separately what changed in the logical view and in the physical work. Work units are not milliseconds, disk-page reads or a production-performance promise.

09 — Transfer to a protected export under churn

An archive export needs a stable old catalog while another client places a hold and a purge is being considered. Design the transactions and schedule that preserve both the export view and the hold dependency.

You receive a schema, an invariant and observable acceptance criteria in the project contract. There is no completed scenario or client for this unit. Use the same engine you built, not a second special-purpose database.

09.1 Translate the new invariant and workload

The archive has items, collections and holds. A purge reads the relevant holds predicate before staging item deletions. A concurrent hold changes the premise on which that purge depends. The invariant concerns that dependency, not whether a particular primary key had two writers.

Commit 09a. Build one scenario and run it under Snapshot Isolation and Serializable mode with identical source and actions. The SI run must expose the unsafe purge outcome; the Serializable run must reject the purge because of a holds read dependency. Do not create an incidental same-key write conflict that would mask the missing predicate validation.

An explicit readOnly:true exporter is separate from an ordinary transaction that merely happens not to write. The declaration prohibits writes and allows the exporter to serialize at its original snapshot. It must not refresh its view to make cleanup easier.

09.2 Preserve a long export while membership changes

Commit 09b. While the exporter is pinned, change an item's collection or location through another committed transaction. Read the old view through its historical index, and keep a current observer to see the newer catalog. Both can be correct while returning different rows.

Vacuum before the exporter finishes and again after all pins close. Identify the history needed by the first cleanup and why more can disappear during the second. Finish the exporter successfully through the declared read-only route. An aborted or silently refreshed export does not meet this task.

Use plan comparisons within both the old and new views. Their results need not match across views. Each comparison must itself hold one snapshot fixed while changing only the physical plan.
