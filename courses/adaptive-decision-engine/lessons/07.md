# 07 · Spend time and calls deliberately

A late correct answer can still be wrong for the current game. Build a scheduler that reserves budget before dispatch and discards results after their deadline or revision.

## One pending request

A **scheduler** records whether a request is pending, how many reservations have been spent, and when a pending request expires. It has a small state machine: idle, pending, then accepted, timed out or rejected. The deadline uses an injected monotonic clock, a clock that only moves forward during a run. Wall-clock date changes should not extend a request's allowance.

reserve takes scheduler state, episode/revision and current time. If another request is pending, return in-flight without dispatching another one. If the request limit is exhausted, return budget-exhausted. Otherwise increment used immediately, create a fresh token and store the deadline. A failed request still consumed a reservation. Counting only successful responses would permit an unlimited failure loop.

A request token distinguishes separate dispatches even at the same revision. Episode and revision distinguish game state. You need both: a later request at revision eight must not accept an earlier token that also happened to use revision eight.

## Let fallback win exactly once

Work through this timeline. Revision 8 dispatches at time 10 with timeout 5, so its deadline is 15. At time 15 the scheduler expires it and the controller chooses rules. The game commits that fallback and advances to revision 9. At time 18 the old response arrives. Its JSON is valid, but its state is old. Discard it and record a late-response event; do not resolve another round.

settle checks the current pending token and episode/revision before accepting a proposal. It also checks the deadline. At the deadline itself, the result is timed out. The tie is deliberately defined so behavior does not depend on callback ordering. Clearing pending state does not refund used reservations.

Complete the missing transition for an unavailable response before implementing the full scheduler: pending becomes idle with used unchanged. For token 3 at time 12 with deadline 15, write used, pending and accepted after the failure. Then use the same state with a valid response: it must be accepted exactly once. Rejecting every response is not a correct scheduler. Then independently solve a timeout followed by a reset to another episode that also starts at revision zero. An episode ID check must reject the original answer even though revisions match.

## Integrate without hiding failure

The supplied createController composes your observation, constraints, adapter, calibration and scheduler functions. It owns Promise racing and transport injection. Your scheduler owns reservation and acceptance policy. The controller returns a decision; the authoritative engine commits it once after validating the revision and action.

Read control.mjs alongside your implementation. A fallback records the real reason: unavailable, uncertain, timeout, stale or budget-exhausted. It also records one call for a dispatched failure. A request never begins just because a frame rendered. Decisions occur once per round, and only the controller can request evidence.

The public check runs a delayed synthetic transport, allows timeout fallback, then releases the old response. It expects one returned decision and one late-discard log. This is stronger than testing settle in isolation: it exercises the composition that could accidentally apply both answers. It is still a local deterministic failure experiment, not observed provider latency.

## Cost and cache limits

A call cap is straightforward to enforce; a monetary cap requires a verified upper bound on billing units and rates. The optional transport refuses a strict cost claim it cannot establish. A deadline controls how long the game waits, not whether a remote server has billed work already sent. Preserve unknown usage as unknown.

A cached proposal is valid only for the exact bound request. A matching action name is insufficient. If observation, question, model, host or allowed set changes, the binding changes. The default implementation performs no approximate cache reuse and no retries. If you add retries, every retry spends another reservation.

For transfer, combine a timeout with a new episode and a late response. Record the token, old and new episode/revision, used count and total committed rounds. Predict these values before running. Your successful scheduler must preserve game responsiveness and evidence of the failure at the same time.
