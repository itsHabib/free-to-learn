# 03 · Build the director you must beat

You now know what the director can observe and what it may choose. Build a deterministic rules director that lights the beacon while leaving room to recover.

## Choose a useful comparison

A **baseline** is the policy you compare another policy against. A weak baseline can make an expensive system look useful without improving the product. Always resting survives twelve rounds with full health, but earns no charge. That policy cannot satisfy the beacon goal. Your baseline must expose the player to encounters and complete at least one of the twelve published development cases.

The public check also requires encounters on at least thirty percent of the 144 possible rounds across those cases. This is a declared minimum for a meaningful demonstration, not a claim about enjoyable pacing. No policy must match the author's exact actions. Stronger rules and different lawful tie-breaking are welcome.

Begin with an ordered decision table. When health is very low, recover. When pressure is above the target band, enter recovery. When recovered sufficiently, resume challenge. During challenge, prefer an affordable encounter that respects the legal set. One reasonable starting point chooses brute at health ten or above, swarm at eight or above, then scout. Those thresholds are design choices to evaluate, not discovered truths.

## Keep a small memory

If you switch to recovery above 0.55 and immediately switch back below 0.55, small changes can alternate rest and challenge every round. **Hysteresis** uses different enter and leave boundaries. Enter recovery above the upper target; leave only below the lower target and with enough health. While pressure sits between those boundaries, preserve the previous recovery flag.

Consider pressure 0.50 with recovering true. The state has not crossed the leave boundary, so continue recovery. At pressure 0.20 and health 8, the leave condition holds, so resume challenge. The same pressure 0.50 with recovering false stays in challenge. Memory therefore changes the decision even when the current observation is identical.

The function returns an action and new memory. Do not mutate the old memory. Reusing an old object should reproduce the old decision, which is essential for replay and later checkpoint tests. Missing pressure needs a deliberate fallback: known health can trigger recovery, but null must not silently act like measured zero.

For a completion problem, start in recovery at pressure 0.30 and health 7. Fill the decision-table row: does either exit condition hold? Then independently solve the same pressure with recovering false. Preserve both predictions before calling your function.

## Play your implementation

Complete chooseRules in rules.mjs. Return {action: {kind}, memory: {recovering}}; a reason string is useful in the trace. Read the allowed set before choosing. When no action exists, stop with a terminal error instead of inventing a last rest. Use earlier-layer support only if you want an assisted workspace; the support record preserves the original source and leaves this module's target incomplete.

Select My rules director below, then New expedition. Play at least one seed with mostly Press and another with mostly Brace. Watch charge, health and remaining rounds together. Repair can save health but costs both a supply and a charge opportunity. A policy that produces a smooth pressure curve may still miss the charge deadline.

Run the terminal play command from README to exercise the same source against the fixed, cautious and aggressive bots. These bots are explicit fixtures. Their names describe their programmed rules, not measured human populations. Save a baseline manifest before tuning later candidates so that a comparison cannot secretly weaken the rules side.

## Debug and transfer

Use all-rest as a negative control. It should pass legality and fail meaningful completion. If your evaluator later declares all-rest superior based only on survival, the evaluator has changed the product goal. Retain survival and completion as separate outcomes.

For a fresh problem, switch the target from steady to the supplied pulse schedule. The target band changes every three rounds. Read target from the observation instead of hard-coding the steady limits. The public check does not require one particular response to pulse; evaluate the consequence and explain your tradeoff.

Before moving on, export the ZIP, extract it in a fresh directory, and run a check on the included work. A demonstration using supplied rules is not your implementation. The export must contain the code you edited, failed and revised attempts, and enough instructions to run without this browser. Passing this module gives you a playable baseline, which is the control for every later model experiment.
