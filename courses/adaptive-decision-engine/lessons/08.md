# 08 · Break your own explanation

A plausible story about a bad decision is not yet a diagnosis. Construct a case that changes the suspected cause while holding other inputs fixed.

## Compare explanations with an intervention

An **intervention** deliberately changes one suspected cause. A **negative control** changes something that should not affect the outcome. Consider a faulty observer that uses only health. Two states have equal health but different recent damage. If the observer returns the same pressure, the defect is in the observation. If the observer distinguishes them but the policy ignores that distinction, the defect is in policy use.

These are different explanations with different repairs. Changing a threshold while leaving the faulty observer untouched may improve one recorded run without addressing the lost information. Preserve the failing source before editing so you can distinguish a real repair from a changed test case.

The supplied exercise format uses controlled snapshots rather than pretending the counterfactual history happened naturally. Label these as constructed interventions. Replace recent damage while holding health, budget, round and last action fixed. Then change only display color as a negative control. Display color is outside the observation contract and should not change a decision.

## Create two original cases

In scenarios.json, create two cases using the schema in API.md. Each needs an ID, hypothesis, health, budget, damageA and damageB. Use three nonnegative integer damage values from zero through four. The two histories should make your rules policy choose different encounters. Choose different health or budget conditions so the second case tests a distinct boundary. Duplicate IDs, cloned conditions and reversed copies of the same history pair are rejected.

The public checker constructs the states, runs your actual observe and chooseRules functions on each intervention, and also changes display color. It requires changed decisions for the history interventions and unchanged decisions for the display control. It does not award correctness for an asserted passed flag in your JSON.

For the completion problem, take a previously recorded decision where your policy entered recovery. Hold health and budget fixed, remove only recent damage, and predict whether the policy should leave recovery. You supply the numbers. Then create the second case without copying the first case's values. If your policy legitimately ignores damage by design, revise the experiment to test the observation boundary first and explain the limitation; the current public exercise specifically asks you to implement a history-sensitive baseline.

## Preserve the reasoning record

Your REPORT.md should state the original failure, at least two possible explanations, the intervention, the negative control, actual before/after decisions and the remaining alternatives. An intervention supports a narrow claim: in this constructed case, the changed input affected the result. It does not show that the same input explains every poor episode.

Record source hashes for the original and repaired policy. The attempt store retains full code and questions before execution. Attach the original case identity to both results. A repair run against a different case is useful development but cannot by itself show that the original defect was removed.

Automated checks verify the controlled relation and execute your cases. They cannot judge whether your prose gives a sensible causal account. Use the reasoning rubric for that judgment. A complete project includes both the behavioral evidence and the explanation; a keyword-filled report with no actual intervention is insufficient.

## Distinguish a defect from missing evidence

Now change the target profile and remove the observation for one round. This is a different kind of change. A calibration table fitted on steady states does not automatically describe pulse states, and an unavailable pressure reading cannot support a precise pressure claim. The correct outcome may be abstention rather than a more elaborate threshold.

Use a fresh domain label and predict whether select will accept it. Keep the calibration table fixed for the first run. Then collect an explicitly separate calibration set if you want to support that domain. Reusing evaluation labels to fill the missing bin would hide uncertainty instead of resolving it.

For transfer, show a case where a repair helps the original intervention but the new missing-observation case still needs fallback. Explain the remaining limit. The goal is a defensible explanation with a counterexample, not a story that makes every result look like success. Keep planted faults labeled as planted; none of these cases establishes a real model's failure frequency.
