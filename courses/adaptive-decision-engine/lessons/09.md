# 09 · Resume without changing the decision

Closing a page must not erase recovery memory or replenish a spent request budget. Build a checkpoint that reproduces the next decision after a restart.

## Decide what must survive

A **checkpoint** is a serialized record of the information needed to continue. The game state alone is insufficient when the policy has memory. A policy can also update memory when it selects an encounter, before the player resolves the round. Save that completed selection with its state and memory binding; calling the policy again during resume could select a different encounter and advance memory twice. At pressure 0.30, recovery may continue or remain off depending on the previous recovery flag. Save that flag. Also save used request reservations, maximum allowance, serial token and the identities of policy source and calibration data.

The checkpoint has a version because its meaning can change. Restore must refuse an unknown version or mismatched source/calibration identity. A JSON object with similar-looking fields is not proof of compatibility. The source identity says which policy produced the memory; the calibration identity says which evidence supports selective use.

Do not restore a pending network operation. Its process and callbacks no longer exist, and restarting it silently could spend again. The saved checkpoint clears pending, records that a pending request was invalidated, and preserves the spent reservation. Restore also forces armed false. A new process requires a new explicit decision before any real provider operation.

## Prove next-step equivalence

Begin with a state and nonempty policy memory. Compute the next deterministic decision without changing the original objects. Create a checkpoint, serialize it to JSON, parse into fresh objects, restore, and compute the next decision again. Compare the full pending action and memory result. In the runtime, resume must not call the policy again when this selected result was saved. Use a counter that changes on every decision to expose double evaluation; an idempotent recovery flag alone can hide the defect.

For a worked field example, a scheduler used three of four reservations and had request token three pending. After restore, used remains three, maxRequests remains four, pending is null and armed is false. Exactly one reservation remains. The old request is not retried. The checkpoint's invalidatedPending flag records why the pending slot disappeared.

Complete that field table for a checkpoint taken after a timed-out request, where pending is already null. Then independently test a checkpoint with no history and another midway through recovery. A serialization test using empty default memory can pass while hiding the real bug.

## Export the actual work

The browser and terminal keep separate stores. Browser edits live under the local origin, including its port. Terminal work lives in the directory you created. Export is the explicit bridge: the ZIP contains the local reader, engine, public checks, your current source, attempts and session.json. Extract it before running Node commands.

Use node lab.mjs import session.json NEWDIR to restore exported browser work into a fresh terminal directory. Import refuses to overwrite an existing directory. The browser import preview asks before replacing the current workspace and retains its previous data as a local backup. Current checkpoint.json takes precedence over an older checkpoint copied into the session ledger. An older export without a saved encounter restores state and memory only, then requires you to explicitly choose a new encounter; it does not claim to reproduce an encounter that was never recorded. The exported archive includes file hashes so you can identify changes after transfer.

A historical pass belongs to the saved source and question. If you edit constraints.mjs, an earlier result remains visible but is historical. Never reinterpret the old answer under new code. A failed save prevents a new committed check from executing, leaving the existing attempt history available for export.

## Repair a broken restore

Plant a defect that resets used to zero. Demonstrate that next action equality alone fails to catch the extra allowance. Add an assertion about budget continuity. Then plant a memory reset and show that budget equality alone misses the changed decision. The two controls measure different parts of recovery.

Finally, alter only a display preference and restore into fresh objects. The next decision should remain equal because display state is outside the policy contract. Alter the source or calibration identity and expect an explicit refusal. A refused incompatible checkpoint is safer evidence than a superficially successful resume with unknown meaning.

Your transfer artifact is a ZIP reopened outside the original folder, with a successful next-step equivalence check and the original failed attempts intact. Do not claim live-request recovery: the course deliberately disarms it. Human accessibility and other operating systems still need their own observed evidence.
