# 04 · Connect a typed decision source

A response about the wrong question can look perfectly valid. Build an adapter that accepts only an encounter answer bound to the current request.

## A finite question

An **adapter** converts between your application's contract and an external interface. It contains question construction and interpretation; the supplied transport owns network mechanics. Your buildRequest function takes the observation and allowed action names. It produces a named encounter question with a description for each permitted choice. Do not offer brute when brute is illegal and hope the model remembers to avoid it.

A typed response selects one label from a finite set and supplies a distribution over that set. A **distribution** assigns a nonnegative number to every permitted label, with a total of one. Different key order is harmless. An unexpected label, missing label, negative number or nonfinite value invalidates the response. Do not repair malformed probabilities by silently dividing by their sum: that changes the evidence you received.

For comparison, imagine a weather-card selector with choices clear and rain. A valid distribution might put 0.7 on clear and 0.3 on rain. A second answer named temperature cannot stand in for weather even if it also contains two numbers. Our encounter answer uses the same principle: read answers.encounter by name, never the first object entry.

## Bind context before dispatch

A **binding** records which request an answer belongs to. Construct it before sending: episode ID, revision, hash of the observation, hash of the question, allowed action set, requested model, provider host and adapter version. The locally assigned request ID also covers the outbound body. A **hash** here is a deterministic change detector. The course's short internal hash is not a cryptographic signature; export manifests use SHA-256 for artifact identity.

When the response arrives, compare the binding with the current observation. At episode camp-2 revision 8, an answer for camp-2 revision 7 is stale. An answer for another episode at revision 8 is also stale. If the provider returns a different model from the one requested, reject it. A provider need not echo every local binding field: your transport must retain the actual request/response association instead of guessing from content.

The supplied fixtureResponse creates synthetic answers and explicit faults. It is not a language model and never contacts a service. Use its valid response for the first adapter run, then substitute wrong-question, wrong-model and invalid-sum fixtures. Keep these labels in reports. A replayed real capture would also need an exact matching request; changing a question while reusing an old answer creates a different experiment.

## Implement and repair

Complete buildRequest and parseResponse in adapter.mjs using API.md. Return either an explicit successful proposal or {ok:false,error:...}. A failure must not become a fake rest proposal from the model. The controller may execute a rules fallback afterward, but its trace must preserve the difference.

Work in stages. First construct the question with an allowed subset of rest and scout. Then complete the missing normalization checks for the selected action. Finally validate the complete distribution and every binding field. In the fresh public variant, object ordering changes. Your adapter must treat mappings by name rather than by insertion position.

Try a deliberately wrong implementation that reads Object.values(answers)[0]. Give it both a recovery answer and an encounter answer, with recovery first. Record the wrong selection, repair the named lookup, and rerun with the order reversed. That control distinguishes a repaired binding from code that merely happens to work on one fixture.

## The optional HTTP boundary

The package includes a Node-only HTTP transport for the documented Liquid endpoint. It is mock-tested, not live-qualified. Reading the course and running public checks never reads credentials. The browser does not ask for an API key. The optional terminal smoke defaults to a dry run and requires explicit arming, a named model, one-request cap, byte limit and deadline before it can dispatch.

A request cap limits count, not an invoice. The transport refuses a strict monetary cap because the package has no verified upper bound on token billing. Unknown usage remains unknown. Do not enable a provider merely to finish this lesson; the offline adapter is sufficient for every required exercise.

Before continuing, explain why a well-formed answer can still be invalid, and save one wrong-question rejection. This proves an interpretation boundary, not model quality or a useful choice.
