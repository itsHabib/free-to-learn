# 06 · The impossible par

Level 2's par is 100 frames, and by Kettle's rules as its developers meant them the level takes at least 186. In this module your search finds a route the developers' rules say cannot exist, you shrink it to the few presses that make the glitch happen, and you explain both bugs from the game's own code.

Before this module your toolkit can search for a shortest movie. After it, your toolkit can also minimise a movie while an effect still happens. Your work folder will hold a level 2 movie under par, a minimal movie of the clip that carries Kettle through a wall, and an account of both glitches.

**Before you start:** module 05 passes. A level 2 search keeps about 600,000 states and used about 450 to 550 MB of memory, depending on the Node version, so close other heavy programs first and run one search at a time.

**Code scope:** you write one function, `minimise` (15 code lines). Everything else this module runs is your module 5 search.

**Time:** about 7 minutes to read and 60 minutes to build.

## Bug two: the wall clip

`moveX`, lines 130 to 148 of `game/core.mjs`, is listed after the question below. After the horizontal move, the game tests only the edge Kettle is moving toward, at its head and its feet. If that edge is inside a solid tile, it measures how deep, and pushes Kettle out on the nearer side. Moving right from outside a wall, the front edge can end at most one frame's move deep. At walking speed that's 1.5 px, always the near half of an 8 px tile, so Kettle is pushed back the way it came. Above 4 px a frame, the front edge can end more than half a tile in, and the nearer side is then the far one.

{{practice:p06c}}

<!-- code-example {"file":"examples/06-movex-lines.txt","language":"js","title":"game/core.mjs, lines 130 to 148"} -->
```js {"file":"examples/06-movex-lines.txt","title":"game/core.mjs, lines 130 to 148"}
function moveX(st, vx) {
  const ram = st.ram;
  let x = u16(ram, ADDR.X) + vx;
  const y = u16(ram, ADDR.Y);
  if (vx !== 0) {
    // Only the edge Kettle moves toward is tested, at the head and at the feet.
    const edge = vx > 0 ? x + W - 1 : x;
    if (solid(tileAt(st, edge, y)) || solid(tileAt(st, edge, y + H - 1))) {
      const col = Math.floor(edge / TILE);
      const depth = vx > 0 ? edge - col * TILE + 1 : (col + 1) * TILE - edge;
      // Push Kettle out of the tile on the nearer side.
      const farSide = depth > TILE / 2;
      if (vx > 0) x = farSide ? (col + 1) * TILE : col * TILE - W;
      else x = farSide ? col * TILE - W : (col + 1) * TILE;
      if (!farSide) put16(ram, ADDR.VX, 0);
    }
  }
  put16(ram, ADDR.X, x);
}
```
<!-- /code-example -->

Line 136 finds the front edge, the last pixel column Kettle covers. Line 139 measures how far that edge is into the tile, and line 141 picks the far side when the depth is more than half a tile.

On frame 67 the front edge went 5 px into the 8 px tile, more than half, and Kettle came out at 280 px. Vertical moves always push Kettle back to the side it came from, so floors and ceilings can't be clipped.

## Minimise: keep only the presses that matter

The 70-frame movie holds 64 button presses, most of them there only because the search had no reason to leave them out. **Delta debugging** is the method of shrinking an input while an effect still happens, here "Kettle goes through the wall". `minimise` uses its simplest form: clear one press, replay, and keep the change only if the effect still happens.

<!-- code-example {"file":"examples/toolkit.mjs","region":"minimise","language":"js","title":"Minimise a movie","change":"Write minimise in the minimise region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"minimise","title":"Minimise a movie","change":"Write minimise in the minimise region of work/tas.mjs."}
// Clears one button press at a time and keeps the change when stillShows(inputs) is still true.
// Repeats until no single press can be cleared.
export function minimise(inputs, stillShows) {
  if (!stillShows(inputs)) throw new Error('the movie does not show the effect to begin with');
  let current = inputs.slice();
  let changed = true;
  while (changed) {
    changed = false;
    for (let i = 0; i < current.length; i++) for (const bit of [L, R, J]) {
      if (!(current[i] & bit)) continue;
      const trial = current.slice();
      trial[i] &= ~bit;
      if (!stillShows(trial)) continue;
      current = trial;
      changed = true;
    }
  }
  return current;
}
```
<!-- /code-example -->

The outer loop repeats until a whole pass clears nothing, because clearing a later press can make an earlier one unnecessary. The movie keeps its length, with empty buttons where presses were. The result is a movie in which no single press can be cleared. A smaller one that drops two presses together can still exist, which the full form of delta debugging tries by testing groups of presses.

## What real tools do

Delta debugging comes from software testing, where it shrinks a crashing input to the part that causes the crash. Test-case reducers such as C-Reduce and the fuzzer tool `afl-tmin` also shrink an input while a test stays true, as `minimise` does. Published tool-assisted runs come with an account of each glitch and the addresses that show it, like your notes file.
