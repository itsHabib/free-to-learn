# 04 · A memory watch and a model of the jump

A memory watch prints chosen values from the RAM on every frame, so you can read, frame by frame, how the game moves Kettle. In this module you use watch tables to work out how Kettle jumps and walks, then write a model that predicts its position on every frame without running the game.

Before this module your toolkit copies and compares the RAM as 32 anonymous bytes. After it, `work/tas.mjs` reads named values out of the RAM and holds a model of Kettle's motion in open space that agrees with the game to the sub-pixel. Module 5's walking bound uses the walking speed you read here.

**Before you start:** module 01's checks pass, and your work folder is `./work`.

**Code scope:** you write two functions, `peek` (5 code lines) and `predictArc` (24). The module's regions also bring `watch` (5 code lines), which this lesson tours, and `groundSpeed` (3), which `predictArc` calls.

## Reading values from the RAM

The game's RAM map, `ADDR` in `game/core.mjs`, says where each value lives. Some values fit in one byte, such as the flags at address 10. Positions don't, because Kettle's x runs to several thousand sub-pixels. A position takes two bytes, and the game stores the **low byte first**. The value is the first byte plus 256 times the second.

A speed up or to the left is stored as a negative number. A two-byte value read as **signed** treats every value from 32,768 up as negative, by subtracting 65,536. A speed of −1 is stored as 65,535, the bytes 255 and 255. `peek` names the three readings `u8` for one byte, `u16` for two and `s16` for two read as signed.

<!-- code-example {"file":"examples/toolkit.mjs","region":"peek","language":"js","title":"Read one value from the RAM","change":"Write peek in the watch region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"peek","title":"Read one value from the RAM","change":"Write peek in the watch region of work/tas.mjs."}
// Reads one value from the RAM. Two-byte values are stored low byte first; s16 values are signed.
export function peek(state, addr, type = 'u8') {
  const r = state.ram;
  if (type === 'u8') return r[addr];
  const v = r[addr] | (r[addr + 1] << 8);
  if (type === 'u16') return v;
  return v & 0x8000 ? v - 0x10000 : v;
}
```
<!-- /code-example -->

`<< 8` multiplies the second byte by 256, and `& 0x8000` tests whether the result is 32,768 or more.

## A watch table

The supplied `watch` plays a movie from a new state and calls `peek` for each field after every frame, frame 0 included, so the first row shows the state before any input.

<!-- code-example {"file":"examples/toolkit.mjs","region":"watch-table","language":"js","title":"One row of chosen values per frame","change":"Read watch in the watch region of work/tas.mjs. It arrives complete on every route."} -->
```js {"file":"examples/toolkit.mjs","region":"watch-table","title":"One row of chosen values per frame","change":"Read watch in the watch region of work/tas.mjs. It arrives complete on every route."}
// One row per frame, frame 0 (before any input) included: { frame, NAME: value, ... }.
export function watch(level, inputs, fields, version = '1.0') {
  const state = newState(level, version);
  const row = (frame) => Object.fromEntries([['frame', frame], ...fields.map((f) => [f.name, peek(state, f.addr, f.type)])]);
  const rows = [row(0)];
  inputs.forEach((input, i) => { step(state, input); rows.push(row(i + 1)); });
  return rows;
}
```

On every frame `vy` grows by 8, which is gravity. On frame 1 the speed reads −64, and y has already moved by those 64. So within one frame the game sets the speed, adds gravity, and only then moves Kettle. The jump speed is therefore 72, and the whole rise is 288 sub-pixels, 18 pixels.

Look at frame 17. Kettle is back at its starting height but `vy` is still 64, because the game lands Kettle only when a move would carry its feet below the floor. Ending a frame exactly level with the floor still counts as being in the air. On frame 18 the move would go 64 sub-pixels into the floor, so the game puts Kettle back on top and sets `vy` to 0.

On the first frame without jump, the game looks at the speed left from the frame before, −64 here. Kettle is rising faster than 16, so the speed is cut to −16, and gravity then makes it −8 on that same frame. When `vy` is −16 or greater, letting go leaves it alone. ## A model of the jump

`predictArc(start, inputs)` works out Kettle's position after each input in open space, with flat ground at the starting height and nothing to hit. `start` is `{ x, y, vx }` with Kettle standing. It never calls `step`, so every rule in it has to come from the tables.

<!-- code-example {"file":"examples/toolkit.mjs","region":"predict-arc","language":"js","title":"Predict Kettle's position frame by frame","change":"Write predictArc in the model region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"predict-arc","title":"Predict Kettle's position frame by frame","change":"Write predictArc in the model region of work/tas.mjs."}
export function predictArc(start, inputs) {
  let { x, y, vx } = start;
  let vy = 0, ground = true, held = false;
  const out = [];
  for (const input of inputs) {
    const dir = (input & R ? 1 : 0) - (input & L ? 1 : 0);
    const jump = (input & J) !== 0;
    if (ground && jump && !held) {
      vy = -72;
      if (Math.abs(vx) >= 32 && Math.sign(vx) === dir) vx += dir * 8;
    } else if (ground) {
      vx = groundSpeed(vx, dir);
    } else if (dir !== 0 && dir * vx < 24) {
      vx = dir * Math.min(dir * vx + 8, 24);
    }
    if (!jump && vy < -16) vy = -16; // letting go early cuts the rise
    vy = Math.min(vy + 8, 64);
    held = jump;
    x += vx;
    y += vy;
    ground = y > start.y; // level with the floor is still in the air: the game lands Kettle only below it
    if (ground) { y = start.y; vy = 0; }
    out.push({ x, y });
  }
  return out;
}
```
<!-- /code-example -->

<!-- code-example {"file":"examples/toolkit.mjs","region":"ground-speed","language":"js","title":"Speed on the ground","change":"Read groundSpeed in the model region of work/tas.mjs. It arrives complete on every route."} -->
```js {"file":"examples/toolkit.mjs","region":"ground-speed","title":"Speed on the ground","change":"Read groundSpeed in the model region of work/tas.mjs. It arrives complete on every route."}
function groundSpeed(vx, dir) {
  if (Math.abs(vx) > 24) vx = Math.sign(vx) * 24;
  if (dir !== 0) return Math.max(-24, Math.min(24, vx + dir * 8));
  return Math.abs(vx) <= 8 ? 0 : vx - Math.sign(vx) * 8;
}
```
<!-- /code-example -->

Each pass of the loop is one frame, in the game's order. A jump starts only on a frame when Kettle stands and jump is pressed but was not held on the frame before. `held` remembers the frame before, so holding jump through a landing doesn't jump again. On the ground `groundSpeed` applies the walking table, and in the air a held direction adds 8 up to 24. Then come the cut, gravity with the game's fastest fall of 64 (`FALL_MAX` in `game/core.mjs`, line 49; no table here falls long enough to show it), and the move. The lines after the move are the landing rule from frame 17, where a move below the floor lands and a move exactly level with it doesn't.

A jump made at a speed of 32 or more, in the direction held, gets an extra boost of 8. Walking never passes 24, so in open space that line never fires, and no table shows it. It comes from line 215 of `game/core.mjs`, and the model keeps it because the game has it. Module 6 meets the speeds that trigger it.

## What real tools do

Emulators used for speedruns have a RAM watch window that shows chosen addresses every frame, and a RAM search, which finds the address that holds a value by keeping only the bytes that change whenever that value changes in the game. Speedrunners work out a game's movement this way and publish the speeds, gravity and the order of events within a frame, so others can plan routes before trying them.
