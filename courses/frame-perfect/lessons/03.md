# 03 · Desync: the first frame two versions disagree

A movie made on one version of a game can play differently on another, and speedrunners call that a desync. In this module you find the first frame where two versions of Kettle disagree, name the bytes that differ, and then let git find the change that caused it.

Before this module your toolkit can play a movie and return to any frame of it. After it, `work/tas.mjs` can take two runs that end differently and name the frame where they parted and the values in the RAM that parted first. Each comparison halves the frames still in question.

**Code scope:** you write two functions, `firstDivergence` (7 code lines) and `diffRam` (3). The lab supplies the git repository for the last part.

**Time:** about 6 minutes to read and 40 minutes to build.

## Comparing every frame

Call the two runs agreeing after k frames when both builds, given the movie's first k inputs, hold the same 32 bytes. A function that answers that question for one k is a **probe**. Here a probe replays the movie's first k inputs on both builds and compares their hashes, so each probe costs up to two replays of the movie.

The plain way probes frame 1, then frame 2, and so on until the answer is no. This movie first disagrees after frame 97, so that scan makes 97 probes, and in the worst case it makes one per frame.

## Bisection

The runs agree after 0 frames and disagree after the last. In this movie, once they part they stay apart, so a single frame in between turns agreement into disagreement. **Bisection** finds it by keeping two frames, `lo` where the runs are known to agree and `hi` where they are known to disagree, and probing halfway between. Whatever the answer, one of the two moves to the middle, and the gap halves.

<!-- code-example {"file":"examples/toolkit.mjs","region":"first-divergence","language":"js","title":"Find the first frame two runs disagree","change":"Write firstDivergence in the desync region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"first-divergence","title":"Find the first frame two runs disagree","change":"Write firstDivergence in the desync region of work/tas.mjs."}
// probe(k) is true when the two runs agree after k frames. They agree after 0 and disagree after n.
// Returns the first frame after which they disagree.
export function firstDivergence(probe, n) {
  let lo = 0, hi = n; // agree after lo, disagree after hi
  while (hi - lo > 1) {
    const mid = Math.floor((lo + hi) / 2);
    if (probe(mid)) lo = mid;
    else hi = mid;
  }
  return hi;
}
```
<!-- /code-example -->

The loop stops when `hi` is one frame past `lo`. At that point the runs agree after `lo` frames and disagree after `hi`, so `hi` is the first frame of disagreement. Each probe halves the gap, so a gap of n frames closes in at most ceil(log2 n) probes, the smallest whole number p for which 2 to the power p is at least n. The check allows one more than that.

## Naming the bytes that differ

A frame number says when the runs parted. The addresses that differ on that frame say which values parted, and `diffRam` lists them in order.

<!-- code-example {"file":"examples/toolkit.mjs","region":"diff-ram","language":"js","title":"The addresses where two states differ","change":"Write diffRam in the desync region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"diff-ram","title":"The addresses where two states differ","change":"Write diffRam in the desync region of work/tas.mjs."}
export function diffRam(a, b) {
  const out = [];
  for (let i = 0; i < RAM_SIZE; i++) if (a.ram[i] !== b.ram[i]) out.push(i);
  return out;
}
```
<!-- /code-example -->

The game's RAM map, `ADDR` in `game/core.mjs`, names each address. Address 2 is Kettle's x, 4 is its y, 6 and 8 hold the horizontal and vertical speed, and 11 holds the random generator. Each of these is two bytes, low byte first, so a change in y can show at address 4, at address 5, or both.

## Why version 1.1 differs

Each frame, the game moves Kettle in two steps, one across and one up or down, and settles each against the tiles before the next. Version 1.0 moves across first and version 1.1 moves up or down first. That is the whole difference between the builds.

Near the end of level 1 a block two tiles wide and two tall hangs above the floor, at columns 17 and 18 of rows 5 and 6. The movie jumps under it on frame 95, and Kettle bumps its head in both versions alike. Two frames later it jumps again, with its left edge at x 2424, half a pixel short of the overhang's right end at 2432. Version 1.0 moves across first, to x 2448, clear of the overhang, and then rises freely. Version 1.1 rises first, while its head is still under the corner, bumps it, and stays on the floor.

The order matters only at a corner, where one move changes what the other move hits. On open floor, or pressed against a flat wall, both orders end the frame in the same place. This movie meets no such corner before frame 97, so both builds play its first 96 frames identically.

## Git finds the change

Someone maintaining Kettle would ask which change to the code made the movie stop working. `work/bisect/` is a git repository with eight builds of `core.mjs`, one commit each, oldest first. The first is 1.0 and the last is 1.1. It also holds `level1.movie` and `replay.mjs`, which replays the movie with whichever `core.mjs` is checked out and exits with 0 if Kettle reaches the flag and 1 if not.

`git bisect run` is bisection over commits instead of frames, with that exit code as the probe. Tell git the newest build is bad and the build seven commits back is good, then let it run:

```
git -C work/bisect bisect start
git -C work/bisect bisect bad
git -C work/bisect bisect good HEAD~7
git -C work/bisect bisect run node replay.mjs
git -C work/bisect bisect reset
```

`-C work/bisect` runs each command in that folder. `cd work/bisect` followed by plain `git bisect ...` works as well.

## What real tools do

Speedrun tools meet desyncs when a movie made on one emulator version is played on another. A movie format can also store the state's hash every so many frames, so that playback names the first stored hash that disagrees, and with it the stretch of frames where the desync began, instead of only reporting that the run failed. `git bisect run` is the same search applied to a project's history, and maintainers use it with any script that exits 0 for good and 1 for bad.
