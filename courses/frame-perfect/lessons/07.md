# 07 · Steering the random generator

The bell room's fastest route needs the bell to drop its block in one particular place, and the game picks the place at random. Kettle's randomness is a 16-bit number that changes by a fixed rule. Two things decide the place: when you ring the bell, and how often you jumped before. In this module you choose both.

Before this module your toolkit can search for a shortest movie when nothing random affects the route. After it, `work/tas.mjs` can make the bell choose the drop you want, first by waiting and then by a search that finds a faster way.

**Before you start:** modules 05 and 06 pass. You use `search` with the `withRandom` key from module 5.

**Code scope:** you write one function, `steer` (6 code lines).

**Time:** about 6 minutes to read and 40 minutes to build.

## The bell and its four drops

The bell room has a bell tile just above and to the right of Kettle's start. When Kettle's head hits it from below, a stone block appears in one of four places, numbered 0 to 3. Only drop 3 gives Kettle a shorter way up to the flag. Searching from a state with each block already in place shows what the choice is worth: 70 frames with drop 3, and 103 with any other drop or none, because Kettle must go the long way round.

The drop comes from the random state, two bytes at addresses 0x0b and 0x0c. Read `nextRandom` in `game/core.mjs`, lines 107 to 115. It mixes the 16 bits with shifts and exclusive-ors, and the same value always gives the same next value. `step` calls it once at the start of every frame (line 212) and once more on every jump (line 216). When the bell rings, `ringBell` (lines 172 to 177) advances it once more and takes the remainder after dividing by 4 as the drop. Nothing else is random. The drop depends only on how many times the generator has advanced when the bell rings.

## Steering with idle frames

The simplest way to change that count is to wait. A **plan** is a short list of inputs that walks to the bell and jumps into it. `steer` puts k idle frames before the plan, for k = 0, 1, 2 and so on, plays each, and returns the first k for which the bell rang and chose the drop you want:

<!-- code-example {"file":"examples/toolkit.mjs","region":"steer","language":"js","title":"Steer by idle frames","change":"Write steer in the steer region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"steer","title":"Steer by idle frames","change":"Write steer in the steer region of work/tas.mjs."}
// Puts k idle frames before plan, for k = 0, 1, 2, ..., and plays it. Returns the first k for which
// the bell has rung and chosen want, with the inputs that do it.
export function steer(level, plan, want, maxIdle = 30) {
  for (let idle = 0; idle <= maxIdle; idle++) {
    const inputs = [...new Array(idle).fill(0), ...plan];
    const { state } = play(level, inputs);
    if (state.ram[ADDR.BELL] && state.ram[ADDR.DROP] === want) return { idle, inputs };
  }
  return null;
}
```
<!-- /code-example -->

The drop is read after the plan has been played, never before, because before the ring the drop byte still holds 255. The plan here is 6 frames of right, then 10 frames of jump. This script asks `steer` for each drop. It then takes the start steered to drop 3, searches the rest of the route from the savestate after it, and saves the whole route as `work/movies/bell.movie` unless that file exists:

```
node examples/07-steer.mjs ./work
node lab.mjs play bell work/movies/bell.movie
```

Five idle frames give drop 3. The plan rings the bell on its 7th frame, so the bell rings on frame 12, and the route takes 83 frames, 2 under par. The five idle frames add five frames to the movie, and the route ends up 13 frames above the 70 the room takes with the block already there.

## Steering with jumps, found by search

As the bell section said, every jump advances the generator once more, even a jump that doesn't ring the bell. So the order and timing of jumps near the start can steer the drop as well. There are too many such starts to try by hand, so let a search find one.

{{practice:p07b}}

The search uses the module 5 key with `withRandom`, which keeps the random state in the key until the bell rings. Two starts that reach the same spot with different random states then stay apart, as they must, because they can get different drops. The goal is "the bell has rung and chose drop 3". Once it rings, the random state drops out of the key, so the second search, for the rest of the route, keys states as a search on a level without a bell does.

```
node examples/07-jumps.mjs ./work
```

<!-- code-example {"file":"examples/07-jumps.txt","language":"text","title":"Ringing for drop 3, then the rest"} -->
```text {"file":"examples/07-jumps.txt","title":"Ringing for drop 3, then the rest"}
bell rung with drop 3: 5 frames, 640 states expanded
  |.R.| |.R.| |..J| |...| |..J|
the rest: 66 frames, 298,900 states expanded
whole route: 71 frames
Saved it as movies/bell-jumps.movie.
```
<!-- /code-example -->

The bell rings with drop 3 on frame 5. The game rings the bell only when Kettle's middle is under it. The first jump, on frame 3, catches the bell's corner while Kettle's middle is still left of it, so Kettle just bumps its head. The bump puts the ring two frames after that first jump, and that first jump advanced the generator an extra time. The second jump rings the bell. The whole route takes 71 frames, one more than the room takes with the block in place from the start, and the script saves it as `work/movies/bell-jumps.movie`. Copy whichever route you prefer to `work/movies/bell.movie`. The check accepts any movie that finishes within par.

71 isn't proven to be the best. Splitting the work into "ring first, then the rest" commits to the earliest ring with drop 3, and a later ring could in principle lead to an earlier finish. Settling it needs one search with the random state in the key until the ring, and the author's attempt stopped at 8 million states without an answer, because most starts never ring the bell and so never merge.

## Break it and repair it

In your `steer`, put the idle frames after the plan instead of before it, `[...plan, ...new Array(idle).fill(0)]`, and run the check. Read its message, work out why no number of idle frames changes the drop now, then put them back.

## What real tools do

Changing what a game draws at random is a routine part of tool-assisted runs, usually called luck manipulation. The first step is to find the random state's address, which lesson 01's RAM map gave you and which runners find with a memory watch and a RAM search, then learn which actions advance it. Real games often advance their generator on many kinds of event, so runners search over delays and actions together, much as your two searches did.
