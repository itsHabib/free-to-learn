# 02 · Savestates, frame advance and rerecords

A savestate is a copy of the whole game at one frame, which you can return to as often as you like. In this module you write the copy and the restore, then use them to try a jump on different frames from one moment and keep the best.

Before this module your toolkit can only play a movie from frame 0. After it, `work/tas.mjs` can stop at any frame, keep that moment, try something, and go back to it, counting each return the way speedrun sites do.

## A savestate copies the RAM

Lesson 01 called the game's whole memory the RAM, 32 bytes holding Kettle's position, speed, flags, the frame counter and the random generator. A state from `newState` is an object holding `ram`, `level` and `version`. `step` changes the RAM in place on every frame and leaves the other two alone.

That difference decides what a savestate must copy. The level is frozen as soon as it's read from its file, so nothing can change it, and the version is a string that no frame touches. A savestate can share both with the live game. The RAM changes on every frame, and it is one `Uint8Array`, JavaScript's array of bytes. If the savestate held that same array, the next `step` would change the savestate as well, and loading it would give back the current bytes instead of the saved ones.

<!-- code-example {"file":"examples/toolkit.mjs","region":"save-load","language":"js","title":"Save and load","change":"Write save and load in the savestate region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"save-load","title":"Save and load","change":"Write save and load in the savestate region of work/tas.mjs."}
export function save(state) {
  return { ram: state.ram.slice(), level: state.level, version: state.version };
}

export function load(saved) {
  return { ram: saved.ram.slice(), level: saved.level, version: saved.version };
}
```
<!-- /code-example -->

`slice()` with no arguments makes a new array with the same bytes. `save` copies the RAM out of the live game, so later play can't reach it. `load` copies it again, so the game you play from a savestate can't change the savestate either. That second copy lets you load one savestate many times, and each load starts from the same bytes.

## Frame advance and rerecords

The supplied `Session` adds three things speedrun tools build on savestates: frame advance, slots and a rerecord count. **Frame advance** means playing one frame at a time, choosing the buttons, stepping once and looking at the result before the next frame. A **slot** is a numbered place to keep a savestate. A **rerecord** is one return to a savestate, after which the frames you played since it are thrown away and replaced by new ones.

<!-- code-example {"file":"examples/toolkit.mjs","region":"session","language":"js","title":"A session with slots and a rerecord count","change":"Read Session in the savestate region of work/tas.mjs. It arrives complete on every route."} -->
```js {"file":"examples/toolkit.mjs","region":"session","title":"A session with slots and a rerecord count","change":"Read Session in the savestate region of work/tas.mjs. It arrives complete on every route."}
// A TAS session: frame advance, savestates in numbered slots, and a rerecord count.
export class Session {
  constructor(level, version = '1.0') {
    this.state = newState(level, version);
    this.inputs = [];
    this.slots = new Map();
    this.rerecords = 0;
  }

  advance(input) {
    step(this.state, input);
    this.inputs.push(input);
  }

  saveSlot(n) {
    this.slots.set(n, { saved: save(this.state), inputs: this.inputs.slice() });
  }

  loadSlot(n) {
    const slot = this.slots.get(n);
    if (!slot) throw new Error(`slot ${n} is empty`);
    this.state = load(slot.saved);
    this.inputs = slot.inputs.slice(); // the movie as it was at the savestate; later frames are thrown away
    this.rerecords += 1;
  }
}
```
<!-- /code-example -->

`advance` is frame advance, one `step` and one entry in the movie. `saveSlot` keeps a savestate and its own copy of the movie at that moment. `loadSlot` restores both, so the frames played since the savestate drop out of the movie. Each slot needs its own copy of the movie, not just its length. Save in slot 1, play on, and save in slot 2; then load slot 1 and play something else. The current movie no longer holds slot 2's frames, so loading slot 2 must bring back its saved copy. The movie in `inputs` is always the one that leads to the current state, so it can be written to a file at any time.

Speedrun sites publish the rerecord count next to each run. It measures the work behind a movie rather than its quality. The recorder in the browser view from lesson 01 keeps the same count. Loading its savestate after playing on, or undoing a frame, adds one.

## Three tries at one jump

Level 1 starts with a step one tile high, past three tiles of floor to Kettle's right. Holding right walks Kettle into it and no further, so the first thing any run does is jump onto it. The question is which frame to jump on.

`examples/02-three-jumps.mjs` answers it with your `Session`. It holds right for two frames and saves in slot 1. Each try jumps on a different frame, 3, 4 or 5, holds right and jump for 12 frames, then holds right until Kettle lands. Before the second and third tries it loads slot 1, so each try starts from the same moment. At the end it loads slot 1 once more and replays the best try, so the session's movie is the one worth keeping.

## What every try costs

Without savestates you can still try every jump frame, but each try has to start from frame 0, because that is the only state `play` knows how to make. A jump on frame k first needs k − 1 frames of walking to reach it.

{{practice:p02b}}

`examples/02-every-jump.mjs` tries every jump frame from 1 to 60, once from frame 0 and once from savestates, and counts the frames it plays. Each try is the jump frame and 16 frames of flight, 17 frames in all, whichever way it starts:

```
node examples/02-every-jump.mjs ./work
```

<!-- code-example {"file":"examples/02-every-jump.txt","language":"text","title":"Sixty tries, from frame 0 and from savestates"} -->
```text {"file":"examples/02-every-jump.txt","title":"Sixty tries, from frame 0 and from savestates"}
replay from frame 0: 2790 frames played (1770 walking to the jump, 1020 jumping)
savestates:          1079 frames played (59 walking to the jump, 1020 jumping), 60 loads
57 of 60 tries end on top of the step; the earliest jump frame that does is 4
both ways give the same result for every try
```
<!-- /code-example -->

The jumping costs 1,020 frames either way. The difference is in the walking. From frame 0, try k first walks k − 1 frames, 1,770 frames over the 60 tries. With a savestate kept before each jump frame, the walk is played once, 59 frames. The walking from frame 0 grows with the square of the number of frames tried, and the walking with savestates grows only with the number itself. The script checks that both ways give the same result on every try: the savestates cut the frames played and changed no result.

Module 02 has four checks, which run in this order. One saves after 20 frames of level 1, plays 20 more frames on the live game, and tests that the savestate still holds the bytes it saved. Its random numbers come from a generator that starts from a fixed value, its seed, so every run tests the same 200 cases. One saves after 10 frames of level 1, loads that savestate twice, plays 10 frames on the first loaded game, and tests that the second still matches the saved game. The last runs `Session` on room 0: it saves in slot 1 after three frames, plays two more, loads slot 1 and plays one, then tests the inputs, the rerecord count and the state against playing those four inputs straight through. It also tests two slots on different branches.

## What real tools do

Emulators keep savestates in numbered slots and count every load as a rerecord, the same as your `Session`. Their savestates are larger, because a real console's state includes the processor's registers, video memory and sound chips, but the rule is the same one you wrote. Copy everything that changes, and record what the copy depends on. A savestate made on one version of an emulator often won't load into another, because the two versions lay that state out differently, and a tool that checks the version can refuse such a savestate rather than play on from the wrong bytes.
