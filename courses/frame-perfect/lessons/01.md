# 01 · Movies: write one, replay it

A tool-assisted speedrun is a game played from a file instead of by hand: one line of buttons for each frame. In this module you write the reader for that file and the player that feeds it to the game, then write your first movie by hand and watch it reach a flag.

Before this module your toolkit is an empty file. After it, `work/tas.mjs` can read a movie, play it on Kettle and report the frame it finished on. Every later module checks its claims by running them on the untouched game, as this one does.

**Before you start:** Node 22 or newer, and a terminal open in the course folder, the one that holds `lab.mjs`. Every command in this course runs from there.

**Code scope:** you write two functions, `readMovie` (14 code lines) and `play` (8). A code line, here and in every later lesson, is a line inside a function's body that is neither blank nor a comment. The module's region also brings three supplied functions you will read: `formatInput`, `parseInput` and `writeMovie`, 5 code lines in all.

**Time:** about 6 minutes to read and 40 minutes to build. These and every later lesson's times are estimates; nobody has timed a learner yet.

## Kettle and its frames

Kettle is the game this course plays: a small copper kettle that walks, jumps and tries to reach a flag. The game advances in **frames**, 30 to a second when you watch it. One frame is one call:

```
step(state, input)
```

`state` holds everything the game knows. `step` changes it in place and also returns it. `input` is a number whose bits are the buttons held during that frame: 1 for left, 2 for right, 4 for jump. Right and jump together is 6. The game never reads a clock or a mouse, only that number, so the same inputs from the same start give the same game every time. That property, called **determinism**, is what makes a movie possible.

The whole state is 32 bytes of memory, which the course calls the **RAM**, as on a small console. It holds Kettle's position and speed, a few flags, bytes that say whether Kettle has died or reached the flag, and a frame counter at addresses 0 and 1. A random generator at addresses 11 and 12 advances once on every frame and once more on every jump. Kettle's position is in **sub-pixels**, sixteenths of a pixel, so it can move one and a half pixels in a frame. A tile is 8 pixels square, and Kettle is 6 pixels wide and 8 tall. Module 4 reads those bytes one by one.

## A movie is one line per frame

A movie file has a short header, a line `inputs:`, and then one line per frame. Each frame line is a bar, a letter or a dot for each of the three buttons, and a bar. `|.R.|` holds right, `|.RJ|` holds right and jump, `|...|` holds nothing. A frame with nothing held is an **idle frame**.

```
# Frame Perfect movie
game: 1.0
level: room0
rerecords: 0
inputs:
|.R.|
|.R.|
|.RJ|
```

In the header, `game` names the version of Kettle the movie was made for, which lesson 03 is about, and `rerecords` is a count lesson 02 explains.

The supplied `formatInput` and `parseInput` turn one input number into one line and back. `parseInput` refuses any line that is not exactly of that shape, and names the line, because a movie with a typo in frame 300 should stop with an error naming that line, not play a different game. `readMovie`, which you write, splits the header from the frames:

<!-- code-example {"file":"examples/toolkit.mjs","region":"read-movie","language":"js","title":"Read a movie","change":"Write readMovie in the movie region of work/tas.mjs; the two line functions above it are supplied."} -->
```js {"file":"examples/toolkit.mjs","region":"read-movie","title":"Read a movie","change":"Write readMovie in the movie region of work/tas.mjs; the two line functions above it are supplied."}
export function formatInput(input) {
  return '|' + BUTTONS.map(([ch, bit]) => (input & bit ? ch : '.')).join('') + '|';
}

export function parseInput(line, n) {
  if (!/^\|[L.][R.][J.]\|$/.test(line)) throw new Error(`line ${n}: expected something like |.R.| but found "${line}"`);
  return BUTTONS.reduce((input, [ch, bit], i) => (line[i + 1] === ch ? input | bit : input), 0);
}

export function readMovie(text) {
  const lines = text.replace(/\r/g, '').split('\n');
  const start = lines.indexOf('inputs:');
  if (start < 0) throw new Error('a movie needs a line "inputs:" before its frames');
  const header = {};
  lines.slice(0, start).forEach((line) => {
    const m = line.match(/^(\w+):\s*(.*)$/);
    if (m) header[m[1]] = m[2];
  });
  const inputs = [];
  lines.slice(start + 1).forEach((line, i) => {
    if (line.trim() === '') return;
    inputs.push(parseInput(line.trim(), start + 2 + i));
  });
  return { header, inputs };
}
```
<!-- /code-example -->

The header is kept as text. Blank lines are skipped, so a movie can be read even after an editor adds a newline at the end. Line numbers count from 1, the way your editor shows them, which is why the frame lines start at `start + 2`.

## Playing a movie

`play` starts a new game and steps it once per input. It stops early in two cases: when the flag is reached, and when Kettle dies. After either, the game ignores further input, so playing on would only make the reported frame wrong.

<!-- code-example {"file":"examples/toolkit.mjs","region":"play","language":"js","title":"Play inputs on a new game","change":"Write play in the movie region of work/tas.mjs."} -->
```js {"file":"examples/toolkit.mjs","region":"play","title":"Play inputs on a new game","change":"Write play in the movie region of work/tas.mjs."}
export function play(level, inputs, version = '1.0') {
  const state = newState(level, version);
  let frame = null;
  for (let i = 0; i < inputs.length && frame === null; i++) {
    step(state, inputs[i]);
    if (state.ram[ADDR.DEAD]) break;
    if (state.ram[ADDR.DONE]) frame = i + 1;
  }
  return { finished: frame !== null, frame, dead: state.ram[ADDR.DEAD] === 1, hash: hash(state), state };
}
```
<!-- /code-example -->

The frame number counts inputs from 1: a movie whose first input reaches the flag finishes on frame 1. `hash` is a 32-bit number the game computes from all 32 bytes. Two runs with different hashes certainly differ. Two runs with the same hash almost certainly hold the same bytes, so the course treats them as the same game.

## What real tools do

BizHawk, an emulator (a program that runs a console's games on a computer) used for tool-assisted runs, keeps the same thing you just built. Its movie file is a zip archive that holds an input log, one line per frame with one character for each button held and a dot for each button not held, and a header that names the game, a hash of the game file and the emulator's version. A published run is that header and log. Anyone can check it by replaying it, and a log made on one version of a game can play differently on another. Module 3 is about that.
