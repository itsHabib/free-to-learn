# 12 · Lob behind a server

Lob is an artillery game. Each round the player sets an angle and a power and fires one shell, the wind pushes it, and a landing within 12 paces of the moving flag is a hit (README.md, "The two games", has the rest). In Sightline, a separate course you don't need for this one, Lob runs on the player's machine, and you build an engine that reads its memory and presses its keys. A game that runs on the player's machine has handed the player everything: the wind, the flag, the score. This course moves the game to a server. Each player's Lob runs there, three frames every 50 ms tick, and the player's client only draws pictures and sends requests. In each tick the server decides on the messages that have arrived, runs the game, and then sends each client a view, one message about that client's game. In this lesson it sends the full view, `public/full-view.mjs`, which holds everything the game holds, and lesson 13 replaces it.

By the end of this lesson your `server/admission.mjs` will refuse every message outside a five-field vocabulary, every old or repeated message, and every second shot in a round. Your `server/recorder.mjs` will write each session down, and its `replay` will re-run a record from its seed and refuse a record that doesn't hold up.

Part one built the same ideas for the courier arena, in its units M1, M2 and M6: a proximity guard (an interaction counts only within range of its target), admission by sequence number, and replay (re-running a session's record to check it).

## What the client may say

A client may send one kind of message:

```json
{ "v": 1, "seq": 17, "angle": 52, "power": 71, "fire": true }
```

That is the whole vocabulary: a version, a sequence number, the angle and power the player wants, and whether to fire. Everything else is the server's: where the shell flies, where it lands, whether it hit, the score, when the next round starts. `public/session.mjs` turns an admitted message into what Lob understands, presses of its own keys: one press of RIGHT per degree up, UP per point of power, then SPACE to fire.

Run a session and watch the messages go by:

```
node lab.mjs play project
```

On the type-in route it stops at your first unwritten function. Before you write anything, tour the two supplied files that call your code. They are the server's game loop, and they are short.

![The server's tick as a flow: each text that arrived goes through parseInput, which can refuse it for 10 reasons, then admit, which can refuse it as stale, flying, fired with the state unchanged; an admitted input is applied to the game, its state kept and recorded. After the last text the game runs 3 frames and the view makes the client's message.](figures/server-tick.svg)

In `public/runtime.mjs`, read `tick()`, the loop the figure draws. The facts come from the game, never from the message. Only an admitted input reaches the game, through `session.apply`. Your functions never store anything themselves: the runtime keeps `decision.next` as the session's new state and hands it back with the next text.

In `public/session.mjs`, read `apply` and `step`. `apply` presses keys until the game's angle and power equal the input's, then presses SPACE if the input fires. `step` runs the frames and starts the next round when the result has shown long enough, or when a round has gone unshot too long. Your replay will drive the game through these same two calls, which is why a replayed game runs exactly as the live one did.

## Parse strictly

Write `parseInput(text)`. API.md lists the checks in order, and the first that fails names the reason.

Refuse a message with an unknown field, even a harmless-looking one. A field the server ignores today is a field someone reads tomorrow. A client that sends `"hit": true` is asking the server to believe it, and the answer is no. A parser that drops the field silently never gives that answer and leaves the claim open.

Numbers must be JSON numbers. `"52"` is a string that a lenient parser would turn into 52, and then the server holds a value whose type its own rules never checked. Integers must be whole, because an angle of 52.5 isn't a key press Lob can make. The byte limit comes first so that a client can't make the server parse a megabyte of JSON.

Check `12.parse-accepts` gives your parser messages at every limit, and check `12.parse-refuses` one message for each reason, plus messages with several faults, which must get the first reason in API.md's order.

### Read the message before reading its fields

`parseInput` has two halves. The first decides whether the text is a message at all: a string, short enough, valid JSON, a plain object, with exactly the five keys. In `server/admission.mjs`, replace the `parse-shape` region, the first of the two regions inside `parseInput`:

<!-- code-example {"file":"examples/admission-checkpoint.mjs","region":"parse-shape","language":"js","title":"Refuse anything that is not a five-key object","change":"Replace the parse-shape region inside parseInput."} -->
```js {"file":"examples/admission-checkpoint.mjs","region":"parse-shape","title":"Refuse anything that is not a five-key object","change":"Replace the parse-shape region inside parseInput."}
  if (typeof text !== 'string') return refuse('text');
  if (Buffer.byteLength(text, 'utf8') > INPUT_MAX_BYTES)
    return refuse('too-long');
  let value;
  try {
    value = JSON.parse(text);
  } catch {
    return refuse('json');
  }
  if (value === null || typeof value !== 'object' || Array.isArray(value))
    return refuse('object');
  const keys = Object.keys(value).sort();
  if (
    keys.length !== INPUT_KEYS.length ||
    keys.some((key, i) => key !== INPUT_KEYS[i])
  )
    return refuse('keys');
```
<!-- /code-example -->

Each line refuses one way a text can fail, in API.md's order, and returns at once, so the first failing reason is the one reported. The length is measured in bytes with `Buffer.byteLength`, not in string units with `text.length`: a letter outside plain English can take two to four bytes, and the limit is about how much the server must read. The limit is tested before `JSON.parse` runs, so the server never parses a longer text. In JavaScript `typeof null` is `'object'`, and so is the type of an array, which is why the object test names both.

The key test sorts the message's own keys and compares them, one by one, with the supplied `INPUT_KEYS`, which is already in sorted order. That one comparison refuses a missing key, an extra key such as `"hit"` and a misspelt one, and it doesn't matter in which order the client wrote them. `refuse(reason)`, supplied at the bottom of the file, builds `{ ok: false, reason }`.

## Order and replays

Messages travel over a network. They can be lost, and when the network's delay varies they can arrive in a different order from the one they were sent in. Each carries `seq`, a number the client increases by one for every message it sends. The server keeps the highest `seq` it has admitted and refuses anything at or below it as `stale`. This is part one's M2 rule.

That one rule refuses a message overtaken by a later one, a message the network delivered twice, and a message an attacker recorded and sent again. A gap is fine. A lost message leaves one, and each message holds the player's whole intent (the angle and power they want now, not a change), so a later message makes up for a lost one.

A refused message changes nothing, including the highest `seq`. If a refusal moved it, a client could make the server skip its own messages.

Check `12.admit-order` tests this rule, including that a refusal leaves the state as it was.

## One shot per round

Some rules need facts that only the game has. The runtime passes them to `admit`: the tick, the round, and whether the shell is flying. While it flies, the server refuses everything. A fire in a round that already had a shot is refused as `fired`. The state, `{ lastSeq, firedRound }`, holds the highest seq admitted and the round of the last admitted fire, so a fire in the next round is admitted again.

Write `admit(state, input, facts)`. It must not change the `state` it was given, and instead returns `next`, which the runtime keeps. Check `12.admit-rounds` tests the round rules and the order of the three reasons, `stale`, then `flying`, then `fired` (API.md's table for `admit`).

### Decide, and return the next state

Replace the `admit` region of `server/admission.mjs`, the whole function:

<!-- code-example {"file":"examples/admission-checkpoint.mjs","region":"admit","language":"js","title":"Three refusals, then the next state","change":"Replace the complete admit region."} -->
```js {"file":"examples/admission-checkpoint.mjs","region":"admit","title":"Three refusals, then the next state","change":"Replace the complete admit region."}
export function admit(state, input, facts) {
  if (input.seq <= state.lastSeq)
    return { status: 'refused', reason: 'stale', next: state };
  if (facts.flying) return { status: 'refused', reason: 'flying', next: state };
  if (input.fire && state.firedRound === facts.round)
    return { status: 'refused', reason: 'fired', next: state };
  return {
    status: 'admitted',
    next: {
      lastSeq: input.seq,
      firedRound: input.fire ? facts.round : state.firedRound,
    },
  };
}
```
<!-- /code-example -->

The three refusals come in API.md's order, and each returns `next: state`, the state it was given, unchanged. That is how a refusal changes nothing. An admission builds a new object instead of assigning to `state.lastSeq`: the runtime and the checks may still hold the old object, and changing it in place would rewrite a state that should already be history.

`firedRound` moves only when the admitted input fires. An aim, an input that changes angle or power without firing, leaves it alone, so a player may aim as often as they like and still fire once in the round. The round comes from `facts`, the game's own count; nothing in the message can claim a round.

## The protocol cheats

`public/adversaries.mjs` holds four protocol cheats, clients that play like a skilled player (one of the course's legal player models) and break one rule each. `hitClaim` adds `"hit": true` to every fire, and once a session sends a message claiming `"score": 99`. `fireTwice` fires again while its shell flies, and again after it lands. `outOfRange` sends a copy of one input with power 150 every round, and once a session one with angle 4 and one with power 60.5. `replay` re-sends its previous round's fire byte for byte.

## Write it down

A server that refuses a message should be able to show what it did admit. Write `createRecorder`. The runtime calls `admitted(tick, input)` for each admitted message, and `finish(end, final)` returns the record. The format is in API.md: the session's seed, the admitted inputs numbered 1, 2, 3 with the tick each was applied in, the number of ticks run, and the final state.

The seed matters most. Lob is deterministic, so the same seed deals the same flags, winds and flag speeds, and the same inputs at the same ticks then give the same game. So a record needs no screenshots and no memory dumps, because seed and inputs are the whole session.

### Keep the inputs, hand back copies

In `server/recorder.mjs`, replace the `recorder` region, the whole of `createRecorder`:

<!-- code-example {"file":"examples/recorder-checkpoint.mjs","region":"recorder","language":"js","title":"Number each admitted input; build the record on finish","change":"Replace the complete recorder region."} -->
```js {"file":"examples/recorder-checkpoint.mjs","region":"recorder","title":"Number each admitted input; build the record on finish","change":"Replace the complete recorder region."}
export function createRecorder({ seed, mode }) {
  const inputs = [];
  return {
    admitted(tick, input) {
      inputs.push({
        n: inputs.length + 1,
        tick,
        seq: input.seq,
        angle: input.angle,
        power: input.power,
        fire: input.fire,
      });
    },
    finish(end, final) {
      return {
        v: 1,
        game: 'lob',
        mode,
        seed,
        inputs: inputs.map((input) => ({ ...input })),
        end,
        final: {
          round: final.round,
          score: final.score,
          shots: final.shots,
          angle: final.angle,
          power: final.power,
        },
      };
    },
  };
}
```
<!-- /code-example -->

The runtime makes one recorder per session, so `inputs` lives in the closure of that call and no two sessions share it. `n` comes from the list's length at the moment of the push, which numbers the inputs in the order the server applied them. Each entry copies the fields it needs by name. It drops `v`, which every admitted input has, and adds `tick`, which the input doesn't carry: the runtime passes the tick in which it decided the message.

`finish` copies again. The record goes to files and to other code, and a caller that edits the record it got must not edit the recorder's own list. `final` keeps only the five fields API.md names, which are the ones replay compares.

## Replay

### Tour the supplied shape test

`replay` first asks the supplied `wellShaped(record)`, at the bottom of `server/recorder.mjs`, whether every field is there, no other field is, and each has its type. Read it. Notice that it tests `seq`, `angle` and `power` only for being numbers: whether a number is a legal angle is your `parseInput`'s question, and the replay asks it later. A record that fails the shape test is refused with reason `shape` before any game runs.

### The order of the inputs

The next reason is `order`. Replace the `in-order` region, below `replay`:

<!-- code-example {"file":"examples/recorder-checkpoint.mjs","region":"in-order","language":"js","title":"Numbered, never back in time, seq always rising","change":"Replace the complete in-order region."} -->
```js {"file":"examples/recorder-checkpoint.mjs","region":"in-order","title":"Numbered, never back in time, seq always rising","change":"Replace the complete in-order region."}
function inOrder({ inputs, end }) {
  return inputs.every((input, i) => {
    const before = inputs[i - 1];
    return (
      input.n === i + 1 &&
      input.tick < end &&
      (!before || (input.tick >= before.tick && input.seq > before.seq))
    );
  });
}
```
<!-- /code-example -->

Each input is compared with the one before it. Ticks may stay the same, because the server can decide two messages in one tick, but never go down. `seq` must strictly rise, because the server admitted each input only above the last one. The test against `end` keeps every input inside the ticks the replay will run; an input at a later tick would otherwise never be applied and never be checked. The first input has no `before`, so only its number and tick are tested.

### Run the session again

Replace the `replay-run` region inside `replay`:

<!-- code-example {"file":"examples/recorder-checkpoint.mjs","region":"replay-run","language":"js","title":"Re-check every input at its own tick","change":"Replace the replay-run region inside replay.","focus":[12,13,14,15,16,17]} -->
```js {"file":"examples/recorder-checkpoint.mjs","region":"replay-run","title":"Re-check every input at its own tick","change":"Replace the replay-run region inside replay.","focus":[12,13,14,15,16,17]}
  if (!inOrder(record)) return { ok: false, reason: 'order' };
  const session = createLobSession({ seed: record.seed, mode: record.mode });
  let state = { lastSeq: 0, firedRound: 0 };
  let next = 0;
  for (let tick = 0; tick < record.end; tick++) {
    while (next < record.inputs.length && record.inputs[next].tick === tick) {
      const { seq, angle, power, fire } = record.inputs[next++];
      const parsed = admission.parseInput(
        JSON.stringify({ v: 1, seq, angle, power, fire }),
      );
      if (!parsed.ok) return { ok: false, reason: 'refused' };
      const { round, flying } = session.facts();
      const decision = admission.admit(state, parsed.input, {
        tick,
        round,
        flying,
      });
      if (decision.status !== 'admitted')
        return { ok: false, reason: 'refused' };
      session.apply(parsed.input);
      state = decision.next;
    }
    session.step();
  }
```
<!-- /code-example -->

This is the runtime's `tick()` again, with the record in place of the network. The loop runs exactly `end` ticks, and before each tick's frames it applies every input recorded for that tick, as the live server did. Each input goes back through your own admission. It is written out as the message a client would have sent and parsed from that text, so a field the shape test let through, such as an angle with a fraction, meets the same parser a live message meets. The marked lines ask `admit` with the facts the replayed game has at that moment, not anything the record claims. That is what refuses a forged second fire: the record can't say which round a tick fell in, and only the re-run game can.

The replay keeps its own admission state, starting where the runtime starts a session, so a record can't set it.
