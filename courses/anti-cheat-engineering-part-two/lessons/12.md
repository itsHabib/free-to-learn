# 12 · Lob behind a server

Lob is an artillery game. Each round the player sets an angle and a power and fires one shell, the wind pushes it, and a landing within 12 paces of the moving flag is a hit (README.md, "The two games", has the rest). In Sightline, a separate course you don't need for this one, Lob runs on the player's machine, and you build an engine that reads its memory and presses its keys. A game that runs on the player's machine has handed the player everything: the wind, the flag, the score. This course moves the game to a server. Each player's Lob runs there, three frames every 50 ms tick, and the player's client only draws pictures and sends requests. In each tick the server decides on the messages that have arrived, runs the game, and then sends each client a view, one message about that client's game. In this lesson it sends the full view, `public/full-view.mjs`, which holds everything the game holds, and lesson 13 replaces it.

By the end of this lesson your `server/admission.mjs` will refuse every message outside a five-field vocabulary, every old or repeated message, and every second shot in a round. Your `server/recorder.mjs` will write each session down, and its `replay` will re-run a record from its seed and refuse a record that doesn't hold up.

Part one built the same ideas for the courier arena, in its units M1, M2 and M6: a proximity guard (an interaction counts only within range of its target), admission by sequence number, and replay (re-running a session's record to check it).

## What the client may say

A client may send one kind of message:

```json
{ "v": 1, "seq": 17, "angle": 52, "power": 71, "fire": true }
```

That is the whole vocabulary: a version, a sequence number, the angle and power the player wants, and whether to fire. Everything else is the server's: where the shell flies, where it lands, whether it hit, the score, when the next round starts. `public/session.mjs` turns an admitted message into what Lob understands, presses of its own keys: one press of RIGHT per degree up, UP per point of power, then SPACE to fire.

Run a session and watch the messages go by:

```
node lab.mjs play project
```

It will stop at your first unwritten function. Read `public/session.mjs` and `public/runtime.mjs` first, because they are the server's game loop, and they are short.

## Parse strictly

Write `parseInput(text)`. API.md lists the checks in order, and the first that fails names the reason.

Refuse a message with an unknown field, even a harmless-looking one. A field the server ignores today is a field someone reads tomorrow. A client that sends `"hit": true` is asking the server to believe it, and the answer is no. A parser that drops the field silently never gives that answer and leaves the claim open.

Numbers must be JSON numbers. `"52"` is a string that a lenient parser would turn into 52, and then the server holds a value whose type its own rules never checked. Integers must be whole, because an angle of 52.5 isn't a key press Lob can make. The byte limit comes first so that a client can't make the server parse a megabyte of JSON.

Check `12.parse-accepts` gives your parser messages at every limit, and check `12.parse-refuses` one message for each reason, plus messages with several faults, which must get the first reason in API.md's order.

## Order and replays

Messages travel over a network. They can be lost, and when the network's delay varies they can arrive in a different order from the one they were sent in. Each carries `seq`, a number the client increases by one for every message it sends. The server keeps the highest `seq` it has admitted and refuses anything at or below it as `stale`. This is part one's M2 rule.

That one rule refuses a message overtaken by a later one, a message the network delivered twice, and a message an attacker recorded and sent again. A gap is fine. A lost message leaves one, and each message holds the player's whole intent (the angle and power they want now, not a change), so a later message makes up for a lost one.

A refused message changes nothing, including the highest `seq`. If a refusal moved it, a client could make the server skip its own messages.

Check `12.admit-order` tests this rule, including that a refusal leaves the state as it was.

## One shot per round

Some rules need facts that only the game has. The runtime passes them to `admit`: the tick, the round, and whether the shell is flying. While it flies, the server refuses everything. A fire in a round that already had a shot is refused as `fired`. The state, `{ lastSeq, firedRound }`, holds the highest seq admitted and the round of the last admitted fire, so a fire in the next round is admitted again.

Write `admit(state, input, facts)`. It must not change the `state` it was given, and instead returns `next`, which the runtime keeps. Check `12.admit-rounds` tests the round rules and the order of the three reasons, `stale`, then `flying`, then `fired` (API.md's table for `admit`).

## The protocol cheats

`public/adversaries.mjs` holds four protocol cheats, clients that play like a skilled player (one of the course's legal player models) and break one rule each. `hitClaim` adds `"hit": true` to every fire, and once a session sends a message claiming `"score": 99`. `fireTwice` fires again while its shell flies, and again after it lands. `outOfRange` sends a copy of one input with power 150 every round, and once a session one with angle 4 and one with power 60.5. `replay` re-sends its previous round's fire byte for byte.

```
node lab.mjs clients project
```

With a correct admission it prints, for three sessions of each client:

```
client       sent  admitted  refused  shots  rounds  refused by reason
skilled       315       315        0     36      36  -
hitClaim      513       331      182      0      36  keys 182
fireTwice     387       315       72     36      36  flying 36, fired 36
outOfRange    357       315       42     36      36  angle 3, power 39
replay        348       315       33     36      36  stale 33
```

Every cheating message is refused with its own reason, and every ordinary one admitted. `hitClaim` never fires at all, because each of its fires carries the forbidden field. Check `12.clients` plays the same clients through the server and looks at every decision.

No message can write the score, because there is no field for it, and the score is the game's, on the server. But the score follows from the game's rules, and admission is what enforces them. An admission that let `fireTwice` through would give it two chances at the flag every round, and it would score more.

## Write it down

A server that refuses a message should be able to show what it did admit. Write `createRecorder`. The runtime calls `admitted(tick, input)` for each admitted message, and `finish(end, final)` returns the record. The format is in API.md: the session's seed, the admitted inputs numbered 1, 2, 3 with the tick each was applied in, the number of ticks run, and the final state.

The seed matters most. Lob is deterministic, so the same seed deals the same flags, winds and flag speeds, and the same inputs at the same ticks then give the same game. So a record needs no screenshots and no memory dumps, because seed and inputs are the whole session.

```
node lab.mjs record project --out project/run.json
```

With no `--model` or `--seed`, `record` plays the expert player model, and this lesson calls what it saves the default record.

Check `12.recorder` feeds your recorder a session's admitted inputs and compares the record with the format.

## Replay

Write `replay(record, admission)`. It re-runs the session from the seed with `public/session.mjs`, applying each input at its tick, and compares the final state with the record's. It trusts nothing else in the record, so an input your admission would refuse makes the record `refused`, even if its final matches.

```
node lab.mjs replay project project/run.json
node lab.mjs tamper project/run.json --out project/bad.json --set inputs.7.power=70
node lab.mjs replay project project/bad.json
```

`tamper` counts inputs from 0, so `inputs.7` is the eighth input of the record, and in the default record it's the first fire. Your replay should accept `run.json` and refuse `bad.json` with reason `final`, because the edited shot lands somewhere else and at another moment, the rounds after it start at other ticks, and the session ends differently from the record.

Check `12.replay-genuine` replays records the course made, check `12.replay-tampered` replays altered copies that must be refused with the right reason, and check `12.replay-own` replays records your own recorder made, then altered copies of them. Checks `12.replay-genuine` and `12.replay-own` also watch the tick at which your replay hands each input to your `admit`, and it must be the input's own tick.

Replay shows that a record is consistent with the game, in that these inputs, from this seed, give this final. It doesn't show that the record is complete, or who wrote it. Part one's unit M5 made the same point about hashes, that a digest identifies bytes, not the hand that made them. A server that needs its records to be evidence against tampering signs them when it writes them.
