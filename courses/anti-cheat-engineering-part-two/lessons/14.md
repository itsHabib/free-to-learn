# 14 · Meet the limit, then detect

The searching client sends legal inputs: one fire a round, an angle and a power in range, in order. Your admission admits every one of them, as it should, because an honest player could send each of them too. With the drawn view it still hits about 65% of its shots. No rule about a single message can stop it, because no single message is wrong.

The session, though, is unusual. Over twelve rounds the searching client fires at nearly the same moment every round, sends one message per round where people send several, and lands closer than people do. By the end of this lesson your `detect/` files will turn a session into a handful of numbers, score it, set a threshold on development sessions (the ones you design on) for a stated budget of false flags, freeze that threshold, measure it once on held-out sessions (kept back until the end), and work out what its flags would mean in a game where one session in 100 is a cheat. A flag here is the detector's mark on a session, not the flag a shell aims at, and it's a request for a person to look. Nothing in this course bans anyone.

Part one's unit M7 built the same discipline for the courier arena: case-level counts, frozen settings, and rates with their denominators.

## Features

### Read each feature from the rounds

Tour `public/stats.mjs` first, because every feature is one of its functions applied to a list. `median` is `quantile` at one half, and `quantile` sorts the list and interpolates between the two nearest places, so the median of an even-length list is halfway between its middle two values. Both return null for an empty list. `sd` divides by the number of values, the population standard deviation API.md asks for. `correlation` returns null when either list doesn't vary or there are fewer than two pairs. Then, in `detect/features.mjs`, replace the `features` region:

<!-- code-example {"file":"examples/features-checkpoint.mjs","region":"features","language":"js","title":"Six features from the shot rounds, two from helpers","change":"Replace the complete features region."} -->
```js {"file":"examples/features-checkpoint.mjs","region":"features","title":"Six features from the shot rounds, two from helpers","change":"Replace the complete features region."}
export function features({ record, rounds }) {
  const shotRounds = rounds.filter((r) => r.shot !== null);
  const shots = shotRounds.length;
  const hits = shotRounds.filter((r) => r.result === 'hit').length;
  const fireTimes = shotRounds.map((r) => r.shot.tick - r.start);
  return {
    shots,
    hitRate: shots ? hits / shots : null,
    missMedian: median(shotRounds.map((r) => Math.abs(r.miss))),
    fireMedian: median(fireTimes),
    fireSpread: shots
      ? quantile(fireTimes, 0.75) - quantile(fireTimes, 0.25)
      : null,
    inputsMedian: median(shotRounds.map((r) => r.inputs)),
    cadenceCV: cadenceCV(record.inputs, rounds),
    missLag1: missLag1(rounds),
  };
}
```
<!-- /code-example -->

A shot round is a round whose `shot` isn't null, and five of the features are read from those rounds alone. A round without a shot has no fire time, no miss and no result, so leaving it out is what the definitions say, not a shortcut. `hitRate` and `fireSpread` are null for a session with no shots, because a share of nothing and a spread of nothing aren't numbers; `median` already gives null for an empty list. The fire time is `shot.tick - r.start`, measured on the server's clock from the start of the round, so a player far away fires later by their delay, and a client that decides at once fires early. The miss is signed, negative when short, and `missMedian` takes its size, since short and long are equally far from the flag. The other two features need more than one round at a time, so they get helpers. On the type-in route those are still holes, so the probe stops there. ```js {"file":"examples/features-checkpoint.mjs","region":"cadence-cv","title":"Gaps between inputs in the same round","change":"Replace the complete cadence-cv region."}
function cadenceCV(inputs, rounds) {
  const gaps = [];
  let previous = null;
  for (const input of inputs) {
    const round = roundAt(rounds, input.tick);
    if (previous && previous.round === round)
      gaps.push(input.tick - previous.tick);
    previous = { round, tick: input.tick };
  }
  if (gaps.length < 5) return null;
  const m = mean(gaps);
  return m > 0 ? sd(gaps) / m : null;
}

function roundAt(rounds, tick) {
  let found = null;
  for (const r of rounds) if (r.start <= tick) found = r.round;
  return found;
}
```
<!-- /code-example -->

The inputs in `record.inputs` carry the tick each was applied, not a round, so `roundAt` finds the round: the last one in the list whose start is at or before the tick, which is the latest round started by then because rounds come in order. A gap is counted only between two inputs of the same round. The gap across a round change is time spent watching the shell land and waiting for the next round, not how fast a player presses keys. `previous` moves on at every input, so each gap is between neighbours. With fewer than five gaps the spread of the gaps says little, and a client that sends one message a round has no gaps at all, so the feature is null. Then replace the `miss-lag1` region:

<!-- code-example {"file":"examples/features-checkpoint.mjs","region":"miss-lag1","language":"js","title":"Does one miss predict the next?","change":"Replace the complete miss-lag1 region."} -->
```js {"file":"examples/features-checkpoint.mjs","region":"miss-lag1","title":"Does one miss predict the next?","change":"Replace the complete miss-lag1 region."}
function missLag1(rounds) {
  const xs = [];
  const ys = [];
  for (let i = 0; i + 1 < rounds.length; i++) {
    const a = rounds[i];
    const b = rounds[i + 1];
    if (a.shot && b.shot && b.round === a.round + 1) {
      xs.push(a.miss);
      ys.push(b.miss);
    }
  }
  return xs.length < 4 ? null : correlation(xs, ys);
}
```
<!-- /code-example -->

A pair is two rounds next to each other that both had a shot, so a round lost to a reconnect breaks the chain instead of pairing two misses far apart. The signed misses go in, because a player who corrects tends to fall short after landing long, which shows as a negative correlation. Fewer than four pairs give a correlation too noisy to use, so the feature is null then.

## A score and a budget

Write `score(features, settings)`. The rule is yours. One rule that works takes, for each feature, how far the session sits from the legal median in units of a robust scale, its robust z-score, signs it so that the suspicious side is positive, caps it so that one wild feature can't decide alone, and sums them. The robust scale is 1.4826 times the median absolute deviation of the legal sessions, and the median absolute deviation is the median of their distances from the legal median. The factor makes the scale match the standard deviation when values are normally distributed, and it's robust because a few extreme sessions barely move it, where they'd drag a mean and a standard deviation with them. `node lab.mjs features project` prints the legal median and robust scale of each feature for exactly this, rounded to three decimals, which is precise enough to copy into `detect/settings.json`. Times, counts and distances are skewed (a few very slow players, a few huge misses), so compare them as `Math.log1p(value)`. Leave out a feature whose legal robust scale is 0, such as `shots`. Almost every session fires in all 12 rounds, so the median absolute deviation is 0 and dividing by it means nothing. The course's worked detector gives every feature a weight of 1 and a cap of 10. A much lower cap clips the `delay` sessions' aim scores, the part of their score that gives them away.

### One feature, worked through

The lesson works one feature through that rule, `hitRate`, so that you can see the shape of a score and run it. It is not a detector. In `detect/detector.mjs`, replace the `robust-z` region:

<!-- code-example {"file":"examples/detector-checkpoint.mjs","region":"robust-z","language":"js","title":"One feature's capped, signed robust z-score","change":"Replace the complete robust-z region."} -->
```js {"file":"examples/detector-checkpoint.mjs","region":"robust-z","title":"One feature's capped, signed robust z-score","change":"Replace the complete robust-z region."}
function robustZ(value, { transform, direction, median, scale, cap }) {
  if (value === null || value === undefined) return 0;
  const x = transform === 'log' ? Math.log1p(value) : value;
  const z = (direction * (x - median)) / scale;
  return Math.min(cap, Math.max(-cap, z));
}
```
<!-- /code-example -->

The second argument is one feature's entry in your settings, so everything the rule needs about a feature lives in `detect/settings.json`, where `freeze` will hash it. A null feature adds nothing, which is how the searching client's missing `cadenceCV` is handled: it neither helps nor hurts. With `transform` set to `log`, the value is compared as `Math.log1p(value)`, and the median and scale in the entry must then be the ones `features` prints for `log1p`. `direction` is 1 when a high value is suspicious and −1 when a low one is, so the result is positive on the suspicious side either way. The cap clips the result to between minus and plus `cap`. Then replace the `score` region:

### Choose the smallest threshold within the budget

Replace the `choose-threshold` region:

<!-- code-example {"file":"examples/detector-checkpoint.mjs","region":"choose-threshold","language":"js","title":"The smallest score that keeps false flags within the budget","change":"Replace the complete choose-threshold region."} -->
```js {"file":"examples/detector-checkpoint.mjs","region":"choose-threshold","title":"The smallest score that keeps false flags within the budget","change":"Replace the complete choose-threshold region."}
export function chooseThreshold(legalScores, budget) {
  const sorted = [...legalScores].sort((a, b) => a - b);
  const n = sorted.length;
  for (let i = 0; i < n; i++) {
    if (i > 0 && sorted[i] === sorted[i - 1]) continue;
    if ((n - i) / n <= budget) return sorted[i];
  }
  return Infinity;
}
```
<!-- /code-example -->

The scores are copied before sorting, so the caller's list keeps its order. Walking up the sorted list, at place `i` the scores at or above `sorted[i]` are the last `n - i` of them, provided `sorted[i]` is the first of its value. That is what the line that skips a repeated value is for: a threshold flags every session with that score, so the share must be counted from the first copy. The first place whose share fits the budget gives the smallest such threshold, and a smaller threshold flags more cheats, so it's the one to take. When even the highest score alone is too many, no score qualifies, and the answer is `Infinity`, which flags nothing. Check `14.threshold` tests your `chooseThreshold` on lists with ties at the cut.

## Base rates

Recall is the share of cheat sessions a detector flags, the false positive rate is the share of legal sessions it flags, and precision is the share of flagged sessions that are cheats. Recall and the false positive rate belong to the detector, but precision also depends on how many sessions are cheats. When cheats are rare, even a small false positive rate fills the flagged list with legal players.

Write `count(decisions)`, `evaluate(cases, settings)` and `precisionAt(baseRate, recall, fpr)`. `count` turns one decision per session, `{ label, flagged }`, into the counts tp (flagged cheats, true positives), fn (cheats not flagged, false negatives), fp (flagged legal sessions, false positives) and tn (legal sessions not flagged, true negatives), with the three rates. `evaluate` makes one decision per case with your score and threshold and counts them. `precisionAt` takes the base rate, the share of sessions that are cheats, with the recall and the false positive rate (fpr).

### Count sessions, then the rates

Replace the `count` region:

<!-- code-example {"file":"examples/detector-checkpoint.mjs","region":"count","language":"js","title":"One decision per session, four counts, three rates","change":"Replace the complete count region."} -->
```js {"file":"examples/detector-checkpoint.mjs","region":"count","title":"One decision per session, four counts, three rates","change":"Replace the complete count region."}
export function count(decisions) {
  let tp = 0;
  let fp = 0;
  let tn = 0;
  let fn = 0;
  for (const { label, flagged } of decisions) {
    if (label === 'cheat') {
      if (flagged) tp++;
      else fn++;
    } else if (flagged) fp++;
    else tn++;
  }
  return {
    total: decisions.length,
    tp,
    fp,
    tn,
    fn,
    recall: tp + fn ? tp / (tp + fn) : null,
    falsePositiveRate: fp + tn ? fp / (fp + tn) : null,
    precision: tp + fp ? tp / (tp + fp) : null,
  };
}
```
<!-- /code-example -->

Each decision lands in exactly one of the four counts, so they add up to `total`. Each rate is a count over the sessions it is about: recall over the cheats, the false positive rate over the legal sessions, precision over the flagged sessions. A rate whose denominator is 0 is null, not 0 and not `NaN`: a detector that flagged nothing has no precision, which is different from a precision of 0. Then replace the `evaluate` region:

<!-- code-example {"file":"examples/detector-checkpoint.mjs","region":"evaluate","language":"js","title":"Flag each case at the frozen threshold","change":"Replace the complete evaluate region."} -->
```js {"file":"examples/detector-checkpoint.mjs","region":"evaluate","title":"Flag each case at the frozen threshold","change":"Replace the complete evaluate region."}
export function evaluate(cases, settings) {
  return count(
    cases.map((c) => ({
      label: c.label,
      flagged: score(sessionFeatures(c), settings) >= settings.threshold,
    })),
  );
}
```
<!-- /code-example -->

`evaluate` is given whole cases, because counting needs the labels, but the label goes only into the decision's `label`. The flag comes from your features and score, which the checks call with a session's play alone, so a session sent twice under two labels gets the same flag both times, which check `14.heldout` tests. The comparison is at or above the threshold, the same as `chooseThreshold` assumed. Then replace the `precision-at` region:

<!-- code-example {"file":"examples/detector-checkpoint.mjs","region":"precision-at","language":"js","title":"Precision at a base rate","change":"Replace the complete precision-at region."} -->
```js {"file":"examples/detector-checkpoint.mjs","region":"precision-at","title":"Precision at a base rate","change":"Replace the complete precision-at region."}
export function precisionAt(baseRate, recall, fpr) {
  const denominator = baseRate * recall + (1 - baseRate) * fpr;
  return denominator === 0 ? null : (baseRate * recall) / denominator;
}
```
<!-- /code-example -->

Out of all sessions, a share `baseRate × recall` are flagged cheats, and the legal share of sessions times `fpr` are flagged legal sessions; precision is the first over both. When nothing is flagged there is nothing to divide by, and the answer is null, as in `count`.
