# 13 · Hide what the client doesn't draw

Lesson 12's server sends every client the full view, `public/full-view.mjs`: every field of the game, the exact wind, the flag's speed and the countdown to its next change of speed, the game's random state. Part one's courier server did the same with its `/state` endpoint, which returned the whole state. The official client, the game's own client program, draws only part of it on screen, but a client is a program on the player's machine, and any program can read the whole message.

By the end of this lesson your `server/view.mjs` will send only what the screen draws, at the precision the screen draws it (the drawn view), and your `server/leaks.mjs` will find a leak of anything hidden by changing it and watching the bytes. You will measure what hiding costs an honest player as latency grows, and what it costs a client that aims for its player.

This is often called minimizing exposed state. Riot Games has described the same idea, on a much larger scale, for the fog of war in VALORANT, its online team shooter, in which the server doesn't send a client the positions of enemies its player can't see. The server decides what each client may know, because a client can't be trusted to keep secret anything it is sent.

## What the screen draws

The official client draws the status line (angle, power, the wind's arrows, score and shots), the message (`ROUND 3`, `HIT!`, `SHORT BY 37`), the flag, the shell and its trail, the mark where the last shell landed, and the cloud, which drifts across the sky and never touches the shell. Positions are in paces, Lob's unit of distance, and the screen draws each to the nearest pace. API.md's table lists what the game holds against what is drawn. The exact wind is held by the server and never drawn, and the arrows show only its band, one of seven. The flag's speed, the frames until it picks a new one and the random state that will pick it are never drawn either.

```js {"file":"examples/view-checkpoint.mjs","region":"drawn-view","title":"Exactly what the screen draws, at its precision","change":"Replace the complete drawn-view region."}
export function drawnView(game, { tick, ack }) {
  const shell = game.shell();
  const impact = game.impact();
  return {
    v: 1,
    tick,
    ack,
    round: game.round(),
    score: game.score(),
    shots: game.shots(),
    angle: Math.round(game.angle()),
    power: game.power(),
    wind: arrows(game.windLevel()),
    flag: Math.round(game.targetX()),
    shell: shell ? [Math.round(shell.x), Math.round(shell.y)] : null,
    trail: game.trail().map(([x, y]) => [Math.round(x), Math.round(y)]),
    impact: impact ? { x: Math.round(impact.x), age: impact.age } : null,
    message: game.message(),
    cloud: Math.round(game.cloud()),
  };
}
```

## Test by changing what is hidden

How would you know a view leaks? Searching its messages for the exact wind finds the obvious leak, `"wind": 2.4375`. It doesn't find the wind multiplied by 1,000, or written as the bytes of a float in base64, or used to choose the order of the fields.

Change the hidden thing instead, and see whether the message changes. `game.clone()` makes an independent copy of the game. `copy.setHidden(name, k)` changes one hidden thing on the copy without changing anything drawn: the wind to another value inside the same arrows' band, the flag to another position inside the same whole pace, the random state to another state. If the view of the copy differs from the view of the original by even one byte, that hidden thing reaches the client, whatever the encoding. This is called a non-interference test, because nothing hidden may interfere with what the client receives.

Write `findLeaks(viewFn, game, info)`, which returns the sorted list of hidden names that reach the message. The names come from `game.hidden`, and API.md's "Hidden things" table says what each one is. The game also has getters for the hidden values, such as `game.serverWind()` for the exact wind and `game.flagSpeed()` for the flag's speed. Compare the bytes of `JSON.stringify`, not parsed objects, because a view that puts its fields in a different order depending on the wind leaks the wind, and two parsed objects with the same fields in a different order compare equal. Try all three variants `k` of each hidden thing. A leak can show for some values and not others.

Check `13.leaks-finds` runs your `findLeaks` on views with leaks planted in them, one hidden thing at a time and two at once, and on a correct view, which must give an empty list.

### Find leaks by changing one thing at a time

Tour `public/lob.mjs` before you write this: find `HIDDEN`, the list `game.hidden` returns, then `clone`, which makes an independent copy of the game in the same state, and `setHidden`, which changes one hidden thing on that copy. Notice that `setHidden` returns false, changing nothing, when the thing is absent, such as the shell's position when no shell is in the air. In `server/leaks.mjs`, replace the `find-leaks` region:

<!-- code-example {"file":"examples/leaks-checkpoint.mjs","region":"find-leaks","language":"js","title":"Change one hidden thing on a copy, compare the bytes","change":"Replace the complete find-leaks region."} -->
```js {"file":"examples/leaks-checkpoint.mjs","region":"find-leaks","title":"Change one hidden thing on a copy, compare the bytes","change":"Replace the complete find-leaks region."}
export function findLeaks(viewFn, game, info) {
  const before = JSON.stringify(viewFn(game, info));
  const leaking = [];
  for (const name of game.hidden) {
    for (let k = 1; k <= 3; k++) {
      const copy = game.clone();
      const changed = copy.setHidden(name, k);
      if (changed && JSON.stringify(viewFn(copy, info)) !== before) {
        leaking.push(name);
        break;
      }
    }
  }
  return leaking.sort();
}
```
<!-- /code-example -->

The message for the real game is turned into its bytes once, before anything changes. Each change happens on a fresh copy, so one change can't carry into the next and the real game is never touched. A copy where `setHidden` changed nothing can't show a leak, so it isn't compared. The comparison is of `JSON.stringify` text, so a different order of fields counts as a difference. The inner loop stops at the first variant that shows a leak, because one is enough to name it, and every name is tried, so the list holds each leaking name once. Sorting makes the answer the same whatever order the names are tried in.

## What hiding costs

A message is always old when it arrives, so a client has to work out where the flag is now from messages about the past. How well it can do that depends on what the messages hold, so hiding can cost an honest player something, and more as latency grows.

```
node lab.mjs cost project
```

It plays an expert (the strongest of the course's legal player models) and the searching client at five latencies, each with the full view and with your view, 200 sessions of 12 rounds per cell, the same seeds along a row. It takes from 30 to 180 seconds, depending on the machine:

```
   one-way  expert full  expert yours  searcher full  searcher yours

     50 ms        22.5%         23.1%         100.0%               ?
    100 ms        22.5%         22.0%         100.0%               ?
```

Question 13d: why does the searching client hit every shot with the full view, even at 400 ms each way? (a) the full view tells it the flag's speed, its timer and the game's random state, so it can run the flag forward past any delay (b) it fires the moment a round starts, before latency matters (c) the full view sends where the shell will land (d) the server waits for its messages

```
node lab.mjs predict project 13d YOUR_ANSWER
```

With the drawn view a client can only extrapolate from the positions it has seen, and the flag picks a new speed every two to five seconds. That costs the expert little until the delay is long. At 400 ms each way the drawn screen's guess about the flag is often wrong, and the expert hits 14.6% instead of 17.8%.

Every rate in the table has noise. A rate p measured over n shots has a standard error of about the square root of p(1 − p)/n, which for a rate near 24% over 2,400 shots is about 0.9 points. The difference between two such rates, measured on different shots, has a standard error about 1.4 times as large, here about 1.2 points. A gap of one standard error is what chance gives all the time, while a gap of three is rare. This treats every shot as independent, and they aren't quite. A player's bias (each model player aims off by its own amount for the whole session) carries from one shot to the next, so 200 sessions vary more than 2,400 independent shots would, and the true noise is somewhat larger.
