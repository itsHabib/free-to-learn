# 16 · The duplicated item

Two players agree a trade, in which Ana sells Bo her sword for 40 coins. The server has four things to write: the sword into Bo's inventory, the sword out of Ana's, 40 coins out of Bo's purse, 40 into Ana's. If the server stops between two of those writes, and the client, getting no answer, sends the request again, the world can end up in a state no trade could have produced. Players who find such a crash can make it happen on purpose, as often as they like.

By the end of this lesson your `trade/trade.mjs` will carry out a trade so that a crash after any single write, followed by recovery and the client's retry, leaves every item in exactly one inventory and the coins either where they were or where the trade put them, never between. A request sent twice will be carried out once.

The fixes in this lesson come from outside games. Payment services give each request a key chosen by the client, and answer a repeated key with the stored result instead of charging again. Databases write down what they are about to do before doing it, so that after a restart they can finish it. This is called write-ahead logging.

## Four writes and a crash

The store in this lesson stands for any game server that keeps items, and it isn't part of Lob or the courier arena. `public/store.mjs` keeps every player's belongings: `inv:ana` is a list of item ids, `coins:ana` a whole number. The operations you need are `get`, `put`, `keys`, `crashAfter` and `restart`, and API.md's unit 16 says what each does. Each `put` is durable the moment it returns, and nothing is bigger than one `put`, meaning there is no transaction across two keys. `crashAfter(n)` makes the n-th put from now apply and then throw, as if the server died the moment that write reached the disk.

## Request keys

The first fix is for the retry. Each request carries a `key` the client chose, and when the trade is carried out, the server stores its receipt, `{ key, seller, buyer, item, price }`, under the key. A trade's receipt is its answer to the client and has nothing to do with the lab's receipt (README.md, "Start"). A request whose key was already carried out with the same body gets that receipt back and writes nothing.

Question 16c: a request with key `k1` (Ana sells Bo the sword for 40) has been carried out. The client sends key `k1` again, with price 45. What should `trade` return: `ok`, or a reason from API.md's list?

```
node lab.mjs predict project 16c YOUR_ANSWER
```

A request that reuses a key with a different body is refused `conflict`, because the client has a bug, and guessing which body it meant would be worse.

Keys alone don't fix a crash. If the receipt is written last, a crash before it leaves half a trade and no receipt, and the retry runs the trade again on top of the half.

## Write what you will do first

The second fix is to write the whole trade down before touching anything. Your first write is a journal entry under a key of your own, for example `trade:<key>`, holding the request and the values the trade will change, read before any change: Ana's items, Bo's items, Ana's coins, Bo's coins. Then write the end state, computed from those values. Then mark the entry done with the receipt.

Write absolute values, not changes. "Bo has 40 coins" written twice leaves Bo with 40. "Take 40 from Bo" done twice takes 80. With absolute values computed from the journal, finishing a trade is safe to repeat.

Read each value with care, too, because a key can be missing. A player who has never held coins has no `coins:` key in the store at all, and `store.get` returns `undefined` for a key that was never written. In JavaScript, `undefined` plus or minus a number gives `NaN` ("not a number"), so arithmetic on a missing key writes a value that isn't a number. API.md therefore says to read a missing inventory as an empty list and missing coins as zero. Reading the four values once, before any change, puts that rule in one place, and every write is then computed from those values.

The order of the four writes matters too. Take before you give, removing the sword from Ana before adding it to Bo and taking Bo's coins before paying Ana. Then a crash between two writes leaves the sword or the coins in the journal for a moment, never in two places. The checks look at the world only after recovery, so they don't test this order, but it matters to anything that reads the store between a crash and its recovery.

### Finish a trade from its journal entry

The journal entry in this walkthrough is `{ state, body, before }`: `state` is `pending` until the trade is done, `body` is the request without its key, and `before` holds the four values read before any change. One function writes a trade's end state from that entry, and both `trade` and recovery call it. In `trade/trade.mjs`, replace the `finish` region:

<!-- code-example {"file":"examples/trade-checkpoint.mjs","region":"finish","language":"js","title":"The end state from the journal, then the done mark","change":"Replace the complete finish region."} -->
```js {"file":"examples/trade-checkpoint.mjs","region":"finish","title":"The end state from the journal, then the done mark","change":"Replace the complete finish region."}
function finish(store, key, entry) {
  const { seller, buyer, item, price } = entry.body;
  const { sellerItems, buyerItems, sellerCoins, buyerCoins } = entry.before;
  store.put(
    `inv:${seller}`,
    sellerItems.filter((id) => id !== item),
  );
  store.put(`inv:${buyer}`, [...buyerItems, item]);
  store.put(`coins:${buyer}`, buyerCoins - price);
  store.put(`coins:${seller}`, sellerCoins + price);
  const receipt = { key, ...entry.body };
  store.put(`trade:${key}`, { ...entry, state: 'done', receipt });
  return receipt;
}
```
<!-- /code-example -->

Every value `finish` writes comes from the entry, never from the store as it is now. Ana's items are her items before the trade without the sword, Bo's coins are his coins before the trade less the price, and so on. A crash can stop `finish` after any of its writes, and running it again from the start writes the same five values, so a write that already happened is written again unchanged. The four moves take before they give: the sword leaves Ana before it reaches Bo, and Bo pays before Ana is paid. The last write keeps the whole entry, marks it `done` and adds the receipt, and only that write makes the trade finished: a crash before it leaves the entry `pending`, so recovery will run `finish` again. The receipt is the request's key with its body, which is what a retry gets back.

## Recovery

After a crash the server restarts and calls `recover(store)` before it serves anything. Recovery reads every journal entry that isn't done and finishes it. A crash can happen during recovery as well. The server restarts and calls it again, and because every write is absolute, finishing twice is the same as finishing once.

### Roll every pending entry forward

Replace the `recover` region:

<!-- code-example {"file":"examples/trade-checkpoint.mjs","region":"recover","language":"js","title":"Finish every entry still pending","change":"Replace the complete recover region."} -->
```js {"file":"examples/trade-checkpoint.mjs","region":"recover","title":"Finish every entry still pending","change":"Replace the complete recover region."}
export function recover(store) {
  const finished = [];
  for (const name of store.keys('trade:')) {
    const entry = store.get(name);
    if (entry.state !== 'pending') continue;
    const key = name.slice('trade:'.length);
    finish(store, key, entry);
    finished.push(key);
  }
  return finished;
}
```
<!-- /code-example -->

`store.keys('trade:')` lists every journal entry, sorted, so recovery always works in the same order. An entry already `done` is skipped: its trade is finished, and writing it again would only repeat the done mark. Each pending entry is finished from its own `before`, and its request key, the store key without `trade:`, goes in the answer, so the list holds the trades this call finished and no others. A crash during `finish` stops recovery with that entry still pending, so the next call finishes it again, from the same values.

### Answer from the key, then write the journal first

Tour `wellFormed` at the top of `trade/trade.mjs` first: it is supplied, and it refuses any request whose keys aren't exactly the five, whose names aren't 1 to 40 of the allowed characters, or whose price isn't a whole number of 0 or more, the same strictness as lesson 12's admission.
```js {"file":"examples/trade-checkpoint.mjs","region":"trade-key","title":"Shape, self, then the key","change":"Replace the complete trade-key region."}
  if (!wellFormed(request)) return { ok: false, reason: 'shape' };
  if (request.seller === request.buyer) return { ok: false, reason: 'self' };
  recover(store);
  const body = {
    seller: request.seller,
    buyer: request.buyer,
    item: request.item,
    price: request.price,
  };
  const done = store.get(`trade:${request.key}`);
  if (done) {
    if (JSON.stringify(done.body) !== JSON.stringify(body))
      return { ok: false, reason: 'conflict' };
    return { ok: true, receipt: done.receipt };
  }
```
<!-- /code-example -->

The two checks that need nothing from the store come first. Then `recover(store)` finishes any trade a crash left pending, so a key whose trade was interrupted is answered from a finished entry rather than a half-made one. The key is looked up before anything about the items, which is why a retry after the trade went through gets its receipt and not `missing`: Ana no longer holds the sword, because the trade gave it away. The bodies are compared as `JSON.stringify` of objects built in the same field order, so a different price, item or player is a `conflict`, and a conflict writes nothing. Then replace the `trade-journal` region below it:

```js {"file":"examples/trade-checkpoint.mjs","region":"trade-journal","title":"Read, refuse, write the journal, finish","change":"Replace the complete trade-journal region."}
  const sellerItems = store.get(`inv:${body.seller}`) ?? [];
  const buyerItems = store.get(`inv:${body.buyer}`) ?? [];
  const sellerCoins = store.get(`coins:${body.seller}`) ?? 0;
```

## Crash at every write

Check `16.crash-trade` does what an attacker pulling the plug would do, at every place they could pull it. For each write of a trade it runs the trade with a crash after that write, restarts, recovers, sends the client's retry, and then checks the world. Every item in exactly one inventory, the total of all coins unchanged, the trade wholly done or not at all, and the retry's receipt the same as the trade's. Check `16.crash-recover` crashes recovery at each of its writes too.

With a journal entry, the four moves and the done mark, a sale is six writes:

1. `trade:<key>`: pending, with the request and the values read before any change
2. `inv:ana` without the sword
3. `inv:bo` with the sword
4. `coins:bo` less 40
5. `coins:ana` plus 40
6. `trade:<key>`: done, with the receipt

So the command tries six crash points. A crash after write 1 leaves only the journal entry, and recovery does all the rest.
