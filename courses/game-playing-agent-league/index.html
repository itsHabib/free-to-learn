1.1 Read the decision contract


A pawn reaches the far edge, yet a program reports that the other player won. Before improving the program's strategy, you need to know which part of the system owns that result. In this lesson you will identify the actor, legal actions and terminal return for a supplied game state, then implement a policy that respects that contract.


You need arrays, functions and zero-based indexing. Read time is approximately 5–7 minutes, with 20–35 minutes of practice and coding; these are targets awaiting learner trials.


A move is a request to the referee


The supplied game is a small version of Breakthrough. Player 0 begins on row 0 and moves toward row 4. Player 1 begins on row 4 and moves toward row 0. Each player starts with five pawns. A turn moves one pawn one row forward. A straight move needs an empty destination. A diagonal move may enter an empty square or capture an opposing pawn. A friendly occupied destination is illegal.


Reaching the opposite edge or removing all opposing pawns wins immediately. If the player to move has no legal action, it loses. Official terminal returns are +1 for the winner and -1 for the loser. Capturing an ordinary pawn does not itself earn a game point. A policy may prefer captures as a useful heuristic, but it cannot change the referee's objective.


For a worked position, suppose player 0 has a pawn at (1,2). The cell (2,2) is empty, (2,1) holds an opponent and (2,3) holds a friendly pawn. Moving straight is legal. Moving diagonally left is a legal capture. Moving diagonally right is illegal. The relevant facts are the actor, direction and destination occupancy; a visually attractive route has no authority over those rules.

The board is only part of the state


context.state.board is a flat array of 25 cells. An empty cell is -1; a pawn contains its player ID, 0 or 1. Cell index is row * 5 + column. The state also includes currentPlayer, ply, rule identity, terminal status and terminal returns. returns is null before the game ends. Two identical boards can allow different actions when different players are to move.


An action is an integer identifying its source and destination. For this board, the encoding is fromCell * 25 + toCell. The supplied engine already performs this conversion and validates moves. For example, source cell 6 and destination cell 11 encode as 161. An integer can have the right shape while still describing an illegal move: encoding is not validation.


The policy receives context.legalActions, an ordered list of actions the referee permits at the current state. Your first policy's job is to select from that list. It should not modify the board, invent a different action format, or turn the observation into a result record. The observation is information for making a decision; the referee remains responsible for applying the decision.

1.2 Make one policy reproducible


Your policy wins, but a rerun of the same match loses. That may reflect a different random choice, changed code or a different game—not a change in strength. In this lesson you will make a policy's decisions reproducible and identify the evidence needed to rerun them.


You need lesson 1.1 and the idea of a deterministic function. Allow approximately 5–7 minutes to read and 25–40 minutes to implement and investigate; these are unmeasured targets.


Randomness can be controlled


A deterministic game has no random state transition once its state and action are fixed. Its policies can still make random choices. A random policy is useful as a baseline because it produces varied legal behavior without pretending to understand the position. To study that policy, the runner must be able to reproduce its sequence of random decisions.


The supplied context.rng() returns the next number in a private seeded pseudorandom sequence. The same seed and same sequence of calls produce the same values. Values lie in [0,1). A policy chooses from a legal-action list using this stream, not the current time or JavaScript's ambient Math.random().


For a worked choice, take three legal actions in the order [40,42,66] and a random value of 0.62. Divide the unit interval into three equal slots. The value lies in the second slot, so this choice uses the second action. The order matters. Sorting the same actions differently after drawing the number changes the decision even though the set of legal actions is unchanged.

Freeze what “the same policy” means


A name such as challenger is a display label. The policy's behavior also depends on its source, parameters, seed handling and configuration. A source hash identifies bytes; a parameter hash identifies the associated data. The runner records both. Changing a weight while retaining the name creates a new snapshot.


The experiment also needs a game identity, starting state, side assignment and compute budget. If one program receives 256 simulated moves and another receives 1,024, a difference in results does not isolate policy logic. Similarly, repeating the same seed after changing the move order is a new experiment. Reproducibility requires the relevant conditions, not just one familiar number in the report.


Consider two archived records named runner-up. Their source hashes agree, but one uses a parameter vector from Tuesday and the other from Wednesday. It is entirely possible for both records to be genuine and for them to choose different moves. The correct repair is to retain both parameter identities. Renaming one record would make it easier to read, but would not replace that evidence.


Commit item 1.2-p2: Two runs have the same policy name and random seed. The second run has different parameter bytes and twice the simulation budget. Can their disagreement establish nondeterminism? List what would have to be held fixed for that diagnosis.


Replaying moves is weaker than rerunning a policy


A trajectory replay starts from the recorded state and applies the recorded actions. It asks whether those actions produce the recorded states and result under the stated rules. It is valuable: an edited winning score should disagree with the referee's calculation.


A policy rerun asks a further question: given the recorded policy, parameters, observations, seed and budget, does the policy choose those actions again? A person could attach the wrong policy name to a perfectly legal action trace. That trace could pass trajectory replay while failing policy rerun.


This distinction helps you localize a problem. If policy decisions differ before any state difference, inspect policy identity, random-call order and configuration. If actions agree but states differ, inspect the rule/runtime identity and transition record. Do not begin by tweaking strategic weights; that would change the object you are trying to diagnose.


Commit item 1.2-p3: Every recorded action replays to the recorded final state. The reported policy, rerun with its frozen inputs, chooses a different first action. Which reproducibility claim passed, which failed, and what should the report avoid claiming?

1.3 Separate playing strength from harness failure


A tournament says your agent won six games, but two planned matches are missing. A clean percentage would conceal whether the agent played well, returned illegal moves or never ran. In this lesson you will classify those outcomes and preserve enough evidence to make the result interpretable.


You need lessons 1.1–1.2. Allow about 5–7 minutes to read and 20–35 minutes to examine records and complete the module; these times are design targets.


A legal loss is useful evidence


A completed game has a sequence of legal actions and a terminal outcome from the referee. Your agent may lose because its evaluation was poor or it missed an adversarial reply. Those are strategic failures. They belong in the result. Deleting them would remove precisely the observations that can improve your policy.


A policy forfeit has a different cause. The program may return an illegal action or exceed the deterministic simulation quota. It did not satisfy the decision contract. The league records the forfeit and its reason instead of silently substituting another policy's move. A strong fallback would award the program competence it had not demonstrated.


For a worked record, suppose a policy is allowed 12 simulation calls but makes a thirteenth and then returns a legal move. The final action's legality does not erase the quota violation. The program used a decision process outside the agreed contract. Compare that with a policy that uses only four of the allowed 12 calls and loses legally: using less than the maximum is permitted, and its loss remains a game result.

An interrupted host has not supplied a game result


A host crash, failed write or watchdog interruption can leave the result unknown. It does not establish that either policy won. Keep the partial record and classify the planned game as incomplete. The report cannot quietly replace the unknown outcome with a draw; the default game has no draw rule that says “the computer stopped.”


An exact rerun can resolve an incomplete game when its inputs are retained. Link the retry to the same planned match, its snapshot identities and the reason for rerunning. Do not count the original partial record and the retry as two independent games. If an apparently identical completed record arrives twice, the system should recognize the duplicate. If their results conflict, it should expose the conflict rather than choosing whichever result arrived last.


Suppose a plan contains ten matches. Seven complete legally, one policy forfeits, and two are interrupted. There are eight resolved outcomes and two unresolved entries. A win rate among the seven legal games answers a narrower question than a score over all resolved outcomes. Neither denominator turns the two unknown entries into evidence. Later modules will specify the comparison before running it; for now, preserve the categories so that comparison remains possible.

Use the earliest reliable divergence to decide what to inspect. If the policy returns a forbidden action, examine the decision contract and current observation. If a legal action produces an unexpected state, inspect the rules/version and transition evidence. If a complete action trace agrees but a displayed score differs, recompute the score from the referee result. If the trace stops before completion, do not reason backward from a guessed winner.

2.1 Value a position from the correct player's perspective


A search program gives a winning position a negative score because the turn changed. It can examine many moves and still choose badly if its values switch meaning. In this lesson you will implement an evaluation whose player perspective stays explicit and whose estimates never override a known terminal result.


You need module 1, signed numbers and simple arithmetic. Plan for approximately 5–7 minutes of reading and 25–40 minutes of practice and implementation; these targets are not measured learner times.


A value needs an owner


An evaluation estimates how favorable a state is to a named player. In this course, larger values mean better outcomes for that player. The argument player in evaluate(state, player) is that owner. It is not automatically the player whose turn comes next.


Suppose player 0 has a clear advantage. An evaluator may give that state +0.4 from player 0's perspective and -0.4 from player 1's. The board did not become worse when you asked the second question. You changed whose interests the number describes. This game is zero-sum: one player's terminal gain is exactly the other's loss.


For a worked heuristic, imagine counting only a material difference in a different small position. Player 0 has four pawns and player 1 has two. A coefficient of 0.1 per extra pawn gives +0.2 for player 0 and -0.2 for player 1. That is an estimate, not a proof. Two advanced enemy pawns might be more dangerous than four poorly placed pawns. The feature is useful only to the extent that it guides decisions toward winning.

Known outcomes outrank estimates


A terminal state is no longer a prediction problem. The referee's returns array contains the outcome for both players. If player 0 won, returns[0] is +1 and returns[1] is -1. Asking from player 1's perspective must not retrieve the first entry merely because player 0 started the game.


Terminal handling comes before any depth limit or heuristic. A search that reaches a terminal win on its final allowed edge should return the known win, not call a rough material estimator because its depth counter reached zero at the same moment. The order of those decisions changes what the number means.


Nonterminal heuristic scores in this course lie between -0.99 and +0.99. Terminal outcomes remain exactly -1 and +1. The separation prevents an overconfident estimate such as 1.4 from outranking an actual win. Later learned values will retain their raw predictions for analysis, but the search boundary will keep this score contract.


Commit item 2.1-p2: A search reaches a terminal state with returns=[-1,+1] exactly at its depth limit. The requested perspective is player 1, and the material heuristic would give -0.2. Which value belongs in the search, and which condition must be checked first?


Build an estimator you can explain


Open learner/evaluation.mjs and implement evaluate(state, player). Handle terminal values from the referee first. For nonterminal states, choose a small set of visible features that you can explain. Material and progress toward the target row are possible starting ideas. Keep your output finite and within the heuristic range. Do not read final-game labels, hidden scenario names or future moves.


Changing a feature's direction when the player changes needs care. Player 0 advances toward larger row numbers; player 1 advances toward smaller ones. Raw row number therefore does not mean the same progress for both players. A useful representation converts geometry into a player's distance or advancement before combining features. Check the interpretation on one pawn near each player's target edge.


An all-zero nonterminal evaluation is a meaningful reference: it expresses no preference before a terminal result is found. It can support exact search when the whole relevant tree is explored, but it is weak guidance when search stops early. You may compare against it; do not call it a trained value or claim it understands positions.

2.2 Search adversarial replies under a node budget


A move wins a pawn immediately but lets the opponent reach the far edge next turn. Looking at only your move rewards the wrong consequence. In this lesson you will implement bounded adversarial search that chooses a move by accounting for the opponent's reply.


You need lesson 2.1, recursion and the difference between a maximum and a minimum. Allow approximately 5–7 minutes to read and 45–75 minutes to implement and repair; these are design estimates.


Back up the consequence the opponent can force


Keep every value in one named player's perspective—the root player for this decision. At a state where that player acts, it chooses the largest child value. At a state where its opponent acts, the opponent can choose the smallest value for the root player. Propagating these choices back through the tree is minimax search.


Consider a worked sibling tree. You choose between north and south. After north, the opponent can force values -0.2 or +0.7; after south, it can force +0.1 or +0.3. The backed-up value of north is -0.2, because the opponent need not cooperate. The backed-up value of south is +0.1. You select south. Selecting the largest leaf anywhere in the tree would assume the opponent chooses the outcome you want.


This calculation depends on the player's identity at each state. The ordinary game alternates turns, but the interface tells you currentPlayer explicitly. Use that fact. A generic tree or a later rule change can give the same player consecutive decisions; the backup should follow the actor, not the recursion level's parity.

Stop a branch for the right reason


At each state, first ask whether it is terminal. If so, use the requested player's exact return. Otherwise, if the declared depth is exhausted, use context.evaluate(state, player). A depth counts simulated transition edges: depth one examines the states after one move; it does not mean one complete pair of turns.


For a nonterminal state below the limit, inspect its legal actions, simulate children and combine their values according to the actual actor. The supplied oracle exposes terminal, returns, currentPlayer, legal and next. The search implementation owns traversal and choice. It does not own game rules. In particular, context.oracle.next(state, action) returns the hypothetical child State; it does not apply an action to the actual match.


Commit item 2.2-p2: A root move leads to another decision by the root player. Its two possible children have values -0.6 and +0.25 from that player's perspective. What value should this intermediate state back up? Explain why “always minimize on the second level” gives the wrong answer.


A budget is part of the algorithm's contract


context.oracle.remaining reports unused simulation credits, and used reports consumed credits. Every call to next consumes a credit. Asking for an extra child after the budget is exhausted violates the contract even if your code catches the resulting error. Choosing a legal move afterward does not undo that extra work.


Select a legal fallback before expanding children. With no simulation credits, a policy still has to return a legal action from context.legalActions. When there are credits, avoid claiming an unfinished branch's partial result as if every relevant reply had been examined. A partial opponent node can look unusually strong simply because its dangerous reply has not yet been visited.


A clear initial policy can restrict itself to work it can finish at its chosen depth, or use a documented safe result from an earlier completed search. More sophisticated methods are welcome, but their treatment of incomplete work must be explicit. The next lesson develops iterative deepening as one way to retain a complete earlier result.

2.3 Use deeper search without changing the experiment


Your revised policy wins more often after you add pruning and raise its budget fourfold. The result is real, but it does not tell you which change helped. In this lesson you will compare search changes under matched conditions and preserve a defensible result when deeper search runs out of work.


You need lesson 2.2 and the distinction between a code change and an experiment change. Allow approximately 5–7 minutes of reading and 35–60 minutes of coding and comparison; these are targets awaiting trials.


Count work, not the label on the algorithm


A depth limit and a compute budget answer different questions. The depth limit restricts how many transitions a branch may contain. The budget restricts the total number of simulated transitions across the whole decision. Two searches with the same depth can use very different numbers of transitions because positions have different legal actions or because one algorithm prunes branches.


For a worked tree with branching factor three, a complete depth-one expansion uses three transitions. Extending every branch one more edge adds nine, for 12 in total. Extending to depth three adds another 27, for 39. These numbers count edges actually simulated, including the root's outgoing edges. A large depth setting does not promise that the budget can complete that tree.

Keep a completed answer while looking deeper


Iterative deepening runs a shallow search, retains its completed result, then attempts a deeper one. If the new iteration finishes, its result replaces the earlier result. If it cannot finish under the remaining credits, the previous complete result remains available. The repeated shallow work has a cost; it buys a well-defined answer at interruption points.


For example, a policy completes depth one, then depth two, and begins depth three. When the credit limit is reached during the third iteration, it should not silently label a partially explored move as a depth-three optimum. It can return the depth-two result and report the completed depth honestly. That choice may be weaker than an unlimited search, but it is a comprehensible bounded policy.


Other safe partial-search schemes are possible. The requirement is not “use this exact loop.” It is to preserve the meaning of the returned result, respect the budget, and avoid treating a missing hostile reply as evidence of safety. All work through the supplied oracle counts, including repeated expansions between iterations.


Commit item 2.3-p2: A policy completed depth two and selected move C. Its depth-three iteration saw a promising move D before exhausting its credits halfway through D's opponent replies. What result can it safely describe as a completed search result, and which claim about D remains unsupported?


Pruning changes the work, not perfect minimax's answer


Alpha-beta pruning avoids exploring branches that cannot change the minimax choice given bounds already established elsewhere. The bounds describe what the maximizing player can already guarantee and what the minimizing player can already enforce. A cutoff is justified by those bounds—not by a branch merely looking unattractive.


Consider a root maximizing player with one completed option worth 0.3. In another option, the minimizing opponent already has a reply worth 0.1. 6.2 Distinguish measured exploitability from a proof


Your responder found no winning strategy, and the report calls the champion “unexploitable.” You will compute a precisely defined gap on a finite matrix and limit larger-game claims to the response space actually tested.


Define the game and the normalization


Let matrix A contain the row player's payoff. A row distribution x and column distribution y describe mixtures over the listed strategies. Their probabilities are nonnegative and sum to one. The column player's payoff is the negative of A because this is a zero-sum game.


Holding y fixed, the best listed pure row response obtains max_i (A y)_i. Holding x fixed, the column player wants the smallest row payoff, min_j (x^T A)_j. Their difference is the Nash gap:


gap(x,y) = max_i (A y)_i - min_j (x^T A)_j.


The current value x^T A y cancels when you add the two players' unilateral improvement opportunities. Some conventions report two-player exploitability as half this gap. Neither label is useful without stating its normalization.


As a worked sibling, the matching-pennies payoff matrix has rows [1,-1] and [-1,1]. Uniform x and y make every listed response worth zero, so the gap is zero. This certifies the specified finite matrix calculation. It says nothing about an unlisted action that changes the game.

“This frozen policy scored higher on these sixteen scenarios” is a different claim from “this training method produces stronger policies.” The first concerns one set of code and parameters. The second concerns a distribution over training runs. Replaying many games from one trained policy does not create independent training runs.


Name the subject, comparison and domain. Include the game/rule version, opponent pool, scenario-generation process, training replicas, evaluation replicas and compute budget. The final report can be concise because those details live in linked manifests. It cannot omit them from the evidence entirely.


As a worked audit, consider a new checkpoint compared with an older checkpoint at the same rules and scenario roster. The new checkpoint receives twice as many simulation calls per decision. A higher score supports a comparison between those two deployed configurations. It does not isolate the contribution of training. To investigate learning, compare them at a matched budget or report the combined configuration change explicitly.

Check identity, coverage and independence


First verify identity. The policy source, parameter file and rule hashes in the report must match the executed records. Second verify coverage. Every expected game has one qualified result or a visible unresolved failure. Third inspect independence and selection. Did the reported final scenarios influence feature choice, training duration, opponent weights or checkpoint selection?


If they did, the run is useful exploratory evidence. It is no longer untouched confirmation of the final choice. Preserve it, label it and use a fresh confirmation set for a new confirmatory claim. Rewriting filenames or reseeding the same disclosed tiny roster does not necessarily create a genuinely new test.


The same care applies to intervals. Show the resampling unit and count. Correlated moves are not independent samples. A narrow interval produced by resampling thousands of moves from a few games can be very precise about the wrong experiment. Repeatedly checking an ordinary interval and stopping when it looks favorable also changes its interpretation.

Search for a reason your interpretation could fail


An audit is stronger when it contains a counterexample. Inspect the policy's worst measured matchup, a failed or low-performing training run, and a scenario where the apparent improvement reverses. Ask whether the mechanism in your explanation predicts these cases too.


If you claim lower exploitability, identify the responder family and its search/training budget. A responder finding no profitable deviation does not prove that none exists. For a tiny game you can enumerate, exact best-response evidence can support an exact gap. For the larger league, your result normally remains empirical vulnerability to tested responders.


Include a valid alternative explanation. Perhaps a value model improved tactical ordering rather than its numerical accuracy. Perhaps a population helped because it retained a particular counter, not because more opponents are always better. An ablation can distinguish these explanations. If it was not run, record the uncertainty rather than inventing a mechanism from the outcome alone.

8.1 Freeze a prediction before the patch


Your league is about to receive a rule change, and you want to know whether its design transfers. Commit a prediction and evaluation plan before learning the exact change.


Prediction creates a comparison with your earlier understanding


A useful prediction names an assumption and a consequence. “Something might break” cannot distinguish insight from hindsight. “My route planner's proof needs every edge cost to be nonnegative, so I expect its greedy search can return a wrong route once a change makes an edge negative” can be checked. It also names what would show it wrong: the greedy route still matching an exhaustive search on every test map built around a negative edge. The worked example below develops this case.


Your prediction is not a scored guess of a secret answer. It records what your current model of the system implies. If it is wrong, retain it and explain why. Editing the prediction after seeing the patch removes the evidence of that change in understanding.


As a worked example from another domain, a route planner assumes all edges have nonnegative cost. A new discount can introduce a negative edge. Before seeing the map, the author predicts that a greedy shortest-path implementation may fail and names the condition needed by its proof. The value lies in connecting the algorithm's premise to its behavior, not in guessing the exact discounted road.

8.2 Adapt under the original compute budget


This lesson uses a hypothetical rule change to practise diagnosis. No patched game simulator ships in this package. Answer the three analysis items using the worked examples below. The executable adaptation steps apply after an instructor supplies a versioned challenge.


Read the new contract before changing the code


The base game alternates players, but your search interface exposes the actual current player. Those facts were deliberately separate. If a new rule sometimes gives the same player another move, a recursion that simply negates every returned value may apply the wrong perspective. A recursion that asks who acts next has a chance to remain correct without a structural rewrite.


When an instructor supplies a challenge, do not infer its rules from an animation. Read the instructor's written rules, inspect the supplied conformance examples and check the state fields. Keep the rule version and challenge identity with your work. New counters can matter to future legal moves. Two equal boards with different remaining privileges are different states and need different cache identities.


As a worked diagnostic on a generic tree, suppose the root and its child are both controlled by the maximizing player. At the child, the player can select between two outcomes. Treating that child as an opponent turn predicts the wrong choice. The mistake concerns who owns the decision, not the arithmetic sign of the terminal reward. Use an explicit actor trace to identify where your implementation's assumption diverges.

8.3 Defend what transferred and what did not


Suppose your adapted policy wins more often under the changed rules but regresses on ordinary play. These gains and regressions are hypothetical until an instructor-supplied challenge produces actual results. Defend a conclusion that preserves both results and the limits of the experiment.


Compare the prediction with the actual mechanism


Retrieve your pre-patch prediction without rewriting it. Identify the assumptions that survived, the ones that failed and the evidence supporting each judgment. If you predicted a search bug but the real problem was a value feature, explain the distinction. A revised mental model is useful evidence of learning; a retroactively perfect prediction is not.


Use a causal explanation proportional to the evidence. If changing one cache key fixes the minimal witness and several fresh structurally similar positions, that supports the cache hypothesis. It does not prove that every remaining loss has the same cause. If you changed search, features and training budget at once, the result describes that combined configuration. An ablation is needed to separate their contributions.
