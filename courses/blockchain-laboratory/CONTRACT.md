# Laboratory protocol v1

This is a deliberately small account-state protocol, not an implementation of a public chain.

## Shared values

`ctx = {network, publicKeys}` uses network `classroom-v1` and a Map from fixed account names `a,b,c,d` to ephemeral Ed25519 public keys. Genesis is `{a:{balance:100,nonce:0},b:{balance:40,nonce:0},c:{balance:0,nonce:0},d:{balance:0,nonce:0}}`. Counters never have financial value. There is no issuance or reward operation.

A transaction has exactly `network, from, to, amount, nonce, signature`. `from` and `to` must name known accounts, amount is a positive safe integer, nonce a nonnegative safe integer, signature exactly 128 lowercase hexadecimal characters. Network must match. Use supplied `txBytes(tx)`: UTF-8 JSON array `["LAB:TX:1",network,from,to,amount,nonce]`. Object property order is irrelevant. The signature covers the network and nonce as well as the value. No strings-to-numbers coercion, unknown fields or unsafe integers are accepted.

Failures return `{ok:false,code}`. Codes are `SHAPE`, `NETWORK`, `ACCOUNT`, `AMOUNT`, `NONCE`, `SIGNATURE`, `FUNDS`, `OVERFLOW`, `PARENT`, `HEIGHT`, `ROOT`, `TRANSACTIONS`. Successful validation returns `{ok:true}`; transition returns `{ok:true,state}`. No function may mutate its arguments.

## Learner functions

* `validateEnvelope(tx,ctx)`: structural/type checks before signature verification. Use supplied `verifyTx`. State validity is a later layer.
* `applyTx(state,tx,ctx)`: validate envelope; require sender nonce exactly equal to transaction nonce, sufficient funds, safe resulting balance and safe incremented nonce. Copy state, debit/credit and increment sender nonce exactly once. A self-transfer keeps its balance but still requires sufficient funds and consumes the nonce. Reject atomically.
* `stateRoot(state)`: sort account names by JavaScript's default string order. Hash each `accountBytes(name,record)` with `leafHash`. Pair adjacent nodes with `branchHash`, duplicating the last node at each odd level. Wrap the result with `rootHash(count,top)`; the empty top is `sha256(empty bytes)`. This custom count-bound tree uses RFC-inspired domain separation but is not RFC 9162's tree construction.
* `verifyProof(root,name,record,proof)`: proof is `{index,count,siblings}` where siblings are 64-character lowercase hex hashes from bottom to top. Check integer bounds, exact path length, shape and odd-level duplicated sibling consistency. Rebuild left/right by index parity and halve the index with floor each level. Root must match the count-bound commitment. This verifies membership at a position, not nonmembership or sortedness of all unseen leaves. A trusted root is a prerequisite.
* `selectMempool(state,txs,ctx,limit)`: limit is a nonnegative safe integer. Use repeated passes over input arrival order; append each first eligible valid transaction and advance a private state. Skip duplicates by supplied `txId`. Revisit future-nonce or not-yet-funded candidates after other transactions make progress. Stop at limit or a pass with no progress. Conflicting ready spends use first eligible arrival order. Do not mutate input. This is local policy; valid blocks need not use it.
* `validateBlock(block,parent,ctx)`: block has exactly `parent,height,transactions,stateRoot`; transactions is an array of at most 16. Parent is a supplied validated record `{id,height,state}`. Require exact parent ID, height `parent.height+1`, valid sequential transactions and an exact recomputed root. Return `{ok:true,id:blockId(block),height,state,block}`. The outer runtime handles duplicate and unknown-parent buffering. No claimed height or root is trusted before validation.
* `chooseHead(records)`: records are already validated candidates. Return the ID with largest height, then lexicographically smallest ID. Empty input returns `null`. This synthetic rule has no Sybil resistance, weight, real-time notion or finality.
* `verifyCertificate(votes,height,id,ctx)`: validators are the four keys in ctx. Require an array of votes, nonnegative safe integer target height and a 64-character lowercase hex target ID; otherwise return false. Each vote has exactly `voter,height,blockId,signature`; require a valid supplied `verifyVote` for the exact requested height and block ID. Ignore invalid/foreign/mismatched votes and duplicates. Reserve a voter identity only after all shape, membership, target and signature checks succeed: a forged, malformed or wrong-target packet must not suppress a later valid matching vote from that identity, regardless of arrival order. Valid duplicates still count once. Return true for at least 3 distinct valid validators. This is a fixed-height certificate checker, not a complete Byzantine consensus protocol. It does not choose a head or establish validity of the block.
* `reconcile(oldPath,newPath,pending,ctx)`: paths are supplied arrays of validated records beginning with genesis and ending at the old/new heads. Gather transactions from old path blocks in order, then pending; exclude all transaction IDs included anywhere on the new path; pass remaining candidates through `selectMempool` at the new head's state with limit 16. Return `{head:newTip.id,state:copyOfNewTipState,mempool}`. This drops currently ineligible transactions by design; a production pool might quarantine them separately. No undo arithmetic or copied old-head balances.

## Optional module 09

The core protocol below retains its original assumptions. Module 09 adds a separate `planVote(journal,request)` interface in `work/vote-guard.mjs`, fully specified in [lesson 09](lessons/09-restart.md). Its supplied model adds atomic journal persistence and serial requests across simulated crashes; the rollback incident deliberately violates persistence. It does not alter `verifyCertificate`, `chooseHead`, `reconcile` or the core simulation.

## Assumptions (modules 01–08)

The scheduler can delay, duplicate and reorder messages and model a complete cut. All nodes run the same protocol and share genesis/key membership. Honest participants retain their fixed-height vote and never sign a competing value for that height. At most one of four validators equivocates for the certificate safety argument. Signatures/hashes are treated as ideal for the model. Eventual complete delivery and a finite set of proposed blocks imply convergence of the synthetic fork rule, but indefinite delay or endless adversarial extensions defeat this liveness argument. There is no modeled durable restart, timeout protocol, view change, authenticated peer channel, stake, mining or deployment security.
