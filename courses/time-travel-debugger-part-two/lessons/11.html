11 · Question a recording

Lesson 10's lastWrite searches backward one snapshot at a time, so a byte last written long ago, on a page other code writes all the time, costs about as much as a replay from the start. And a single last write rarely explains a wrong value, because that write copied a value computed from other values. By the end of this lesson your query.mjs will build an index of a recording in one replay and then tell you, without replaying, who last wrote this byte before this tick, and which stores, answers and arguments the value stored at this tick was computed from.

Last writers, indexed

Build the index during one replay. For every byte of memory, keep the list of ticks at which an instruction wrote it, in increasing order. Keep, beside each tick, what you need to report: the instruction's function and at, and where the write started and its size.

lastWriter(address, beforeTick) is then a binary search in that byte's list for the greatest tick below beforeTick. A byte written a thousand times is answered in about ten comparisons.

The lists hold one entry per byte written, so a 4-byte store adds four entries. Lesson 09's recording makes 65,859 of them. Typed arrays that grow by doubling hold that many numbers in a few megabytes, while arrays of objects would hold the same in far more.

Keep every write

In project/query.mjs, replace the keep-writes region:

The replay calls keepWrites after every instruction with the instruction's event and tick. Each write goes into five lists at the same position, so write number w is wTick[w], wFunc[w], wAt[w], wAddress[w] and wSize[w]. The replay runs in tick order, so the lists are in tick order without any sorting. writer is different: it holds, for every byte, only the latest store that wrote it. lastWriter doesn't use it. The chains later in this lesson do, because a load needs to know which store wrote each byte it reads at the moment it reads it.

Group the writes by byte

After the replay, makeIndex turns the writes into one list per byte. Replace the by-byte region:

All the per-byte lists live in one Int32Array, byteWrites, one after another, and byteStart[a] is where byte a's list begins. The first loop counts how many writes cover each byte, the second turns the counts into starting places, and the third puts each write's number at the next free place of every byte it covers. Writes are placed in tick order, so each byte's list is in tick order too, which is what the binary search needs.

Binary search one byte's list

Replace the last-writer region:

The loop narrows lo and hi to the first write at or after beforeTick, so the write just before it, at lo - 1, is the answer. If there is none, nothing wrote the byte before that tick. The answer is the whole write, its start and size, even when the byte is inside a wider store. The debugger's lastWrite at position p is lastWriter(address, p + 1), because the instruction at tick p has already run at position p.

Where a value came from

When a stored value is wrong, the question is why. The store copied a value off the stack, and that value was computed by an earlier instruction from its operands. Those came from loads, constants, locals or calls, and each load read bytes some earlier store had written. Following those links backward from a store gives the chain of the stored value.

sources(tick) takes the tick of a store and returns the chain's ends and joints:

  • stores: every earlier store on the chain, by tick
  • answers: every import answer on the chain, by its index in recording.answers
  • args: every argument of a call into the game on the chain, as [call, index], the call's index in recording.calls and the argument's index
  • initial: every byte on the chain that was loaded before any store had written it, from the data segment or the zeros memory starts with.

The chain follows values, not addresses. A load depends on the bytes it read, not on the address it read them from, and a store passes on the value it stored, not its address. Otherwise every value in Lob would depend on the pointer g, and every chain would hold the same few hundred stores. The rules, from API.md:

  • a value depends on every operand of the instruction that produced it, except the address of a load or store
  • local.get, local.set, local.tee, global.get and global.set pass a value along unchanged, and so does a call to a defined function, whose arguments become its parameters and whose result comes back
  • an import's result depends only on that answer
  • a constant depends on nothing.

API.md settles the cases that could go either way: select depends on its condition as well as both values, a one-byte store on the whole value it was given, and a load of bytes written by several stores on all of them.

How to follow a value

Replay once and give every value a producer, the tick of the instruction that made it. Keep a producer beside every entry of the value stack, every local of every frame, every global and every byte of memory, and update them as each instruction runs:

  • an arithmetic instruction pops its operands' producers and pushes its own tick
  • a constant pushes its own tick, with no inputs
  • local.get pushes the producer stored with the local, and local.set stores the popped producer with the local
  • a load pushes its own tick and records, as its inputs, the producers of the bytes it read, which are the stores that last wrote them
  • a store records its value operand's producer as its input and becomes the producer of the bytes it wrote
  • an import call pushes its own tick, recorded as answer number k
  • a call to a defined function moves the producers of its arguments into the new frame's locals, and its return moves the result's producer back
  • an argument of a call into the game gets a producer of its own, reported as [call, index]. The other locals, and each global's starting value, have none.

Branches cut the stack back, so cut the producers back with it, keeping a block's result.

Record, for each tick, the producers it took as inputs. sources(tick) then walks backward from the store's input. Visit a tick, add its inputs to the walk, note each store, answer and argument met, and never visit a tick twice. The walk only touches the chain, so most questions finish in a few thousand steps whatever the recording's length.

The seven listings below build that procedure. Three of their choices save memory without changing any answer: a constant gets the producer "nothing" instead of its own tick, since nothing can be on its chain; a value computed from a single producer takes that producer instead of a tick of its own, since its chain is the same; and an import call's value takes its answer's producer directly.

Number the leaves

A producer has to fit in one slot of an Int32Array. Replace the leaves region:

The leaves are the producers a chain ends at: an answer, an argument of a call into the game, or an initial byte. Ticks are positive, so the leaves take the negative numbers, one range after another: answer a is -1 - a, then every argument of every call, in call order, then every byte of memory by address. argBase[k] is where call k's arguments start in that range, and argCall and argPos turn an argument's number back into [call, index] when sources reports it. The number 0 is left for nothing.

Producers beside the machine's values

Replace the producers region:

depStart, deps and isStore are what the index keeps for the questions. Tick t's inputs are deps[depStart[t]] up to deps[depStart[t + 1]], so every tick costs one number in depStart and one byte in isStore, however many inputs it has. P and sp mirror the machine's value stack, one producer per value, G mirrors the globals, and each frame will hold one producer per local. These last only as long as the replay.

add and made make a computed value's producer. add collects the operands' producers, leaving out nothing (0) and repeats. made(t) returns 0 if none was collected, the one producer if only one was, and otherwise records them all as tick t's inputs and returns t. An i32.add of a loaded value and a constant therefore passes on the load's producer, and its chain is the load's chain, as the rules ask.

Branches, returns and calls

Replace the frames region:

These three follow lesson 08's branch and return. A label remembers the stack's height when its block began and how many results the block leaves. branch copies those results' producers down to that height and cuts sp there, so the values a branch drops take their producers with them. A branch to a loop keeps the loop's label, because the loop can be branched to again. leave does the same for a function's results, and enter starts a frame whose first locals are the producers of the call's arguments and whose other locals are nothing.

Move the producers instruction by instruction

Replace the follow region:

follow runs just before the machine runs the instruction, while the operands are still on the machine's stack, and does to P what the instruction is about to do to the stack. Most cases are one line. br_if drops its condition's producer without recording it anywhere, which is "decisions are not followed" in code; it reads the condition's value from the machine's stack only to know whether the branch will be taken. An import call drops its arguments' producers and pushes the leaf of the answer the machine is about to use. A call to a defined function moves its arguments' producers into the new frame. Loads and stores go to the next region.

Loads and stores: bytes, not addresses

Replace the memory region:

A load reads its address from the machine's stack and looks up, in writer, the store that last wrote each byte it is about to read. A byte no store has written gives its initial leaf. The load's result replaces the address's producer on top of P, so the address is never an input. A store pops its value's producer and records it as its only input, then drops the address's producer. After the machine runs it, keepWrites makes this tick the writer of every byte it wrote, so the next load of those bytes depends on this store.

Replay once

Replace the replay region:

Each call begins with a frame whose locals are the call's argument leaves. Then, for every instruction, the loop records where its inputs start, moves the producers with follow, lets your machine run it and keeps its writes. After each instruction it compares the producers with the machine: the same stack height, the same number of frames, one answer used by an import call and none otherwise, and writes exactly when the instruction was a store. A mistake in follow then stops the replay at the first tick where the two part, instead of giving wrong chains later. After each call, the result must be the recorded one, as in lesson 09.

Walk back from a store

Replace the sources region:

The walk starts from the store's inputs, its value's producer, and keeps a list of producers still to visit. A tick is visited once: it is noted if it was a store, and its own inputs join the list. A leaf goes into its list according to its range. seenTick and seenLeaf mark what this question has visited with the number epoch, which goes up by one for every question, so nothing has to be cleared between questions. The store asked about is never in its own list, because the walk starts from its inputs.

Here is one chain, worked through. In project/run42.json the first shot is fired by call 19, and on the first game frame of its flight, call 20, the shell's new position is stored at g + 40 at tick 89,345. sources(89345) holds 16 stores and 2 answers:

  • the position and the horizontal speed that firing stored, at ticks 88,529 and 88,553 in call 19, because this game frame's position is the last position plus the speed times the game frame's length, plus the wind's push
  • the speed was the power times a constant times the cosine of the angle, so the chain holds the 11 stores of the power made by the presses of up in calls 2 to 12, and before them the store at tick 69,170 in game_init that set the starting power of 60 (an 8-byte store that wrote the angle and the power together)
  • the key at g + 92, stored at tick 69,157, because the game keeps the power XORed with it, as it keeps the flag's position in lesson 08's r_target_x, and with mode 4 off the key is 0
  • the cannon's position at g + 20, stored at tick 69,167, from which the shell's first position was computed
  • answer 1, the cosine of the barrel's angle, and answer 3, this game frame's wind.

By rule, the angle isn't on the chain, because it reached the outside world only as the argument of cos, and an import's arguments aren't followed. Nor is the pointer g, because it was only ever an address.

Decisions are not followed

Decisions aren't on a chain. A br_if pops a condition and branches, and the branch decides which instructions run, but no value flows from the condition into what those instructions compute.

A store of a constant has an empty chain even when it ran only because of a long computation before it. When a store's chain is empty or doesn't explain a wrong value, the cause may be a decision, so look at the branch that led to the store, with back and listing (listing FUNC:AT N prints the instructions from N before AT to N after it).

Use it on a new case: where a value in memory came from

sources answers for a store at a tick. When you look at memory in the debugger, you see a value at a position instead, with no store in sight. Write valueSources(index, { address, size, position }) in project/value-sources.mjs, which both route commands created. If you didn't use them, copy starter/value-sources.mjs to project/value-sources.mjs first. No finished version is supplied, and none of the listings above does this. Its contract:

  • It returns { stores, answers, args, initial }, in the same form as sources, for the value held by the size bytes at address at position position, the moment after position instructions.
  • For each byte, if a store wrote it at or before that position, the last such store and everything on that store's chain belong to the answer. A byte no store had written by then is an initial byte itself.
  • So the stores that last wrote the bytes are in stores themselves, unlike sources, which leaves out the store it was asked about. Bytes written by different stores bring the chains of all of them, as a load of those bytes would.
  • Each list is sorted in increasing order without repeats, and args by call, then argument index.
  • Refuse with an error: an address, size or position that isn't a whole number, a size below 1, bytes outside memory, or a position outside 0 to index.end.
  • Memory is 131,072 bytes in every recording of Lob and Lob II, two WebAssembly pages of 64 KiB (API.md, "Memory"), so bytes outside memory are any below address 0 or at 131,072 and above. The index doesn't report memory's size, and API.md doesn't say what lastWriter does with an address outside memory, so test the bytes against 131,072 yourself before you ask it anything.
  • Use only index.end, index.lastWriter, index.sources and that fixed size of memory, so your function works with any index that meets API.md.

The budget holds for every question, whatever the bytes or the position, a refused one included: valueSources may run no instruction, because lastWriter and sources answer from the index without replaying. The checker counts your machine's step calls while each call to valueSources runs. Building the two indexes it asks is not counted, and the whole check must finish within 120 seconds.
