## Where names live

`targets/lob.wasm` was linked with its names stripped, left out of the file, because Sightline asks its learners to work out what each unnamed function does. For this lesson the course built the same C file again, with the same compiler, and kept its names, in `targets/lob-names.wasm`. Its code is byte for byte the code of `lob.wasm`, so `programs/lob.json` describes it too. The extra bytes are a **custom section** at the end of the file.

A WebAssembly file is 8 fixed bytes followed by **sections**. Each section is an id byte, its size in bytes, then that many bytes. Custom sections have id 0, and their contents start with a name: a length, then that many bytes of text (UTF-8, which for these names is plain ASCII). The section named `name` holds the names.

Sizes and lengths are **LEB128** numbers, in which each byte carries 7 bits of the number, lowest first, and its top bit says whether another byte follows. `1D` is 29. `B8 02` is two bytes. `B8` has its top bit set and carries 56, and `02` carries 2, worth 2 × 128. Together, 312. (Sightline teaches LEB128 and the rest of the file format in depth.)

Inside the `name` section are **subsections**, each an id byte, a size and contents. Subsection 1 holds function names: a count, then for each function its index and its name. Skip any other subsection by its size. Here are the first bytes of the `name` section in `lob-names.wasm`, after its own name:

```
00 0F              subsection 0, 15 bytes: the module's own name
0E 6C 6F 62 2D ... a name of 14 bytes: lob-names.wasm
01 B8 02           subsection 1, 312 bytes: function names
1D                 29 names follow
00                 function 0
0C 73 65 72 76 65 72 5F 72 6F 75 6E 64
                   a name of 12 bytes: server_round
01 06 6A 73 5F 63 6F 73
```

The 29 names are Lob's 4 imports and its 25 functions.

### Read numbers and names

The supplied `Reader` at the top of `names.mjs` keeps a position in the file, `pos`, and `byte()` returns the byte there and moves past it, refusing to read past the end. In `project/names.mjs`, replace the `leb128` region, which adds the two reads everything else is made of:

<!-- code-example {"file":"examples/names-checkpoint.mjs","region":"leb128","language":"js","title":"LEB128 numbers and names","change":"Replace the leb128 region."} -->
```js {"file":"examples/names-checkpoint.mjs","region":"leb128","title":"LEB128 numbers and names","change":"Replace the leb128 region."}
  // Unsigned LEB128: 7 bits per byte, lowest first. A byte with its top bit
  // set says another byte follows.
  u32() {
    let value = 0;
    let shift = 0;
    let b;
    do {
      b = this.byte();
      value += (b & 0x7f) * 2 ** shift;
      shift += 7;
    } while (b & 0x80);
    return value;
  }

  // A length, then that many bytes of UTF-8 text.
  name() {
    const length = this.u32();
    const end = this.pos + length;
    if (end > this.bytes.length)
      throw Error('functionNames: a name runs past the end of the file');
    const text = new globalThis.TextDecoder().decode(
      this.bytes.subarray(this.pos, end),
    );
    this.pos = end;
    return text;
  }
```
<!-- /code-example -->

`u32` adds each byte's low 7 bits at the place `shift` gives them, 0, then 7, then 14, and goes on while the byte's top bit, `0x80`, is set. Take `B8 02`: `B8 & 0x7f` is 56, added at shift 0, and the top bit is set; `02` adds 2 at shift 7, which is 256, and its top bit is clear, so the number is 312. Multiplying by `2 ** shift` keeps the arithmetic in ordinary numbers. JavaScript's `<<` works on 32-bit signed integers, so in a fifth byte, at shift 28, it could turn a large number negative. `name()` reads a length with `u32` and decodes that many bytes as text, so every name in the file costs one call.

### Walk the sections

Replace the `sections` region:

<!-- code-example {"file":"examples/names-checkpoint.mjs","region":"sections","language":"js","title":"functionNames: find the name section","change":"Replace the sections region."} -->
```js {"file":"examples/names-checkpoint.mjs","region":"sections","title":"functionNames: find the name section","change":"Replace the sections region."}
// { [index]: name } for every function the "name" section names; {} without one.
export function functionNames(bytes) {
  const magic = [0x00, 0x61, 0x73, 0x6d];
  if (!magic.every((b, i) => bytes[i] === b))
    throw Error('functionNames: not a WebAssembly file');
  const r = new Reader(bytes, 8);
  while (r.pos < bytes.length) {
    const id = r.byte();
    const size = r.u32();
    const end = r.pos + size;
    if (id === 0 && r.name() === 'name') return functionSubsection(r, end);
    r.pos = end;
  }
  return {};
}
```
<!-- /code-example -->

After the 8 fixed bytes, each section starts with its id and size, so `end` is where the next section begins. A section that isn't custom, or a custom section with another name, is skipped by setting `pos` to `end` without reading its contents. Only custom sections have a name to read, which is why the test reads it only when `id === 0`. A file without a name section runs out of sections and gets `{}`.

### Read subsection 1

Replace the `subsections` region:

<!-- code-example {"file":"examples/names-checkpoint.mjs","region":"subsections","language":"js","title":"Every function's index and name","change":"Replace the subsections region."} -->
```js {"file":"examples/names-checkpoint.mjs","region":"subsections","title":"Every function's index and name","change":"Replace the subsections region."}
// Inside the name section: subsections, each an id byte, a size and contents.
// Subsection 1 is a count, then each function's index and name; skip the rest.
function functionSubsection(r, end) {
  const names = {};
  while (r.pos < end) {
    const id = r.byte();
    const size = r.u32();
    const next = r.pos + size;
    if (id === 1) {
      for (let n = r.u32(); n > 0; n--) {
        const index = r.u32();
        names[index] = r.name();
      }
    }
    r.pos = next;
  }
  return names;
}
```
<!-- /code-example -->

Each subsection is found the way sections were, by its id and size, and `next` is where the following one begins. Subsection 1 is read entry by entry: an index, then a name. Every other subsection, the module's name in subsection 0 among them, is skipped by jumping to `next`. Setting `pos` to `next` after subsection 1 too means the next subsection is read from where it really starts, even if subsection 1 held more than its entries. The order of subsections doesn't matter, which is what the check's small file tests.

## The call stack

Your machine already keeps the call stack in `state.frames`, outermost first, each with the function it's running and the `at` of its next instruction. `stack()` returns `[{ func, at }]` for those frames at the debugger's current position, or `[]` between calls. A call to an import pushes no frame, because the import runs outside the machine and returns at once.

In `debug.mjs`, `stack` prints the frames with names, and `where` names the instruction that runs next.

Question 12b: you stop where `update_hud`, function 6, begins during a call to `game_tick`. How many entries does `stack()` return? Commit:

```
node lab.mjs predict project 12b YOUR_ANSWER
```

A stop where `update_hud` begins comes after `game_tick`'s `call` instruction has pushed `update_hud`'s frame, so that frame counts. A call that comes from outside the game, from the recording rather than from another function, works differently. It begins between calls, so at a stop where it begins, its instruction 0 runs next but no function is running yet, and `stack()` is `[]`.

## Stopping at a function

A **function stop** fires at a position where a call to that function begins, meaning the next instruction is the function's instruction 0. ### Test for a function stop

Tour the supplied `nextInstruction` again, just above `where` in your `debugger.mjs`. During a call it answers the innermost frame's next instruction, and between calls the first instruction of the next call, `{ func: this.callFunc[calls], at: 0 }`. So the instruction a call begins with is visible at the position before it runs, whether the call comes from another function or from the recording.

Replace the `stops` region. Only the marked lines differ from lesson 10's:

<!-- code-example {"file":"examples/stack-checkpoint.mjs","region":"stops","language":"js","title":"stopHere with function stops","change":"Replace the stops region; the marked lines are new.","focus":[1,10,11,12]} -->
```js {"file":"examples/stack-checkpoint.mjs","region":"stops","title":"stopHere with function stops","change":"Replace the stops region; the marked lines are new.","focus":[1,10,11,12]}
  stopHere({ breakpoints = [], watches = [], functions = [] }, event) {
    if (event && event.writes.some((w) => changesWatched(w, watches)))
      return 'watchpoint';
    const next = this.nextInstruction();
    if (
      next &&
      breakpoints.some((b) => b.func === next.func && b.at === next.at)
    )
      return 'breakpoint';
    // A function's instruction 0 runs next only where a call to it begins.
    if (next && next.at === 0 && functions.includes(next.func))
      return 'function';
    return null;
  }

  continue(stops = {}) {
    while (this.tick < this.end) {
      const event = this.forward();
      const reason = this.stopHere(stops, event);
      if (reason) return { reason, tick: this.tick };
    }
    return { reason: 'end', tick: this.tick };
  }
```
<!-- /code-example -->

`stopHere` now takes `functions`, defaulting to none, so every caller from lesson 10 still works. The function test looks forward, like the breakpoint test, at the instruction that runs next. Both halves of its condition matter: the function must be one of the stopped ones, and its instruction 0 must be next. Instruction 0 of a function runs next only where a call to it begins, because a branch inside a function goes either forward to the end of a block or back to the first instruction inside a `loop`, after the `loop` instruction itself, and neither is instruction 0. `continue` is unchanged: it already asks `stopHere` after every instruction.

Then replace the `search-back` region. Only the marked line differs from lesson 10's:

<!-- code-example {"file":"examples/stack-checkpoint.mjs","region":"search-back","language":"js","title":"continueBack skips stretches only when every stop is a watch","change":"Replace the search-back region; the marked line is changed.","focus":[7]} -->
```js {"file":"examples/stack-checkpoint.mjs","region":"search-back","title":"continueBack skips stretches only when every stop is a watch","change":"Replace the search-back region; the marked line is changed.","focus":[7]}
  continueBack(stops = {}) {
    const here = this.tick;
    if (here === 0) return { reason: 'start', tick: 0 };
    const pages = (stops.watches ?? []).flatMap((w) =>
      pagesOf(w.address, w.size ?? 1, this.pageSize),
    );
    const watchesOnly = !stops.breakpoints?.length && !stops.functions?.length;
    const found = this.searchBack(
      here - 1,
      (event) => {
        const reason = this.stopHere(stops, event);
        return reason ? { reason, tick: this.tick } : null;
      },
      (i) => !watchesOnly || this.mayHaveWritten(i, pages),
    );
    if (found) {
      this.moveTo(found.tick);
      return found;
    }
    this.moveTo(0);
    return { reason: this.stopHere(stops, null) ?? 'start', tick: 0 };
  }

  searchBack(last, test, mayMatch = () => true) {
    for (let i = Math.ceil(last / this.every) - 1; i >= 0; i--) {
      if (!mayMatch(i)) continue;
      const snapshot = this.snapshots[i];
      const stop = Math.min(last, snapshot.tick + this.every);
      this.restore(snapshot);
      let found = null;
      while (this.tick < stop) {
        const finding = test(this.forward());
        if (finding) found = finding;
      }
      if (found) return found;
    }
    return null;
  }

  mayHaveWritten(i, pages) {
    const a = this.snapshots[i];
    const b = this.snapshots[i + 1];
    return !b || pages.some((p) => a.pages[p] !== b.pages[p]);
  }
```
<!-- /code-example -->

`watchesOnly` decides whether `continueBack` may skip a stretch whose watched pages stayed shared. With a function stop present it is now false, so every stretch going back is replayed until one holds a stop, as with a breakpoint. The cost is about the distance to the stop plus up to two stretches, lesson 10's cost for a breakpoint.

### Run to the end of the function

`stepOut()` runs forward until the function running now has returned to its caller, that is, until the call stack is shorter than it is now. In `debug.mjs` it's `finish`. Between calls there is no function running. Define what `stepOut()` does there and say so in a comment.

Find the `step-out` region, which holds the stub of `stepOut()` that throws "stepOut: not written yet (lesson 12)". Replace everything between `// region: step-out` and `// endregion: step-out` with the listing below, or, in a file without those markers, replace your `stepOut()` stub and add the two marker lines around it:

<!-- code-example {"file":"examples/stack-checkpoint.mjs","region":"step-out","language":"js","title":"stepOut: forward until there are fewer frames","change":"Replace the step-out region, which holds the stepOut() stub."} -->
```js {"file":"examples/stack-checkpoint.mjs","region":"step-out","title":"stepOut: forward until there are fewer frames","change":"Replace the step-out region, which holds the stepOut() stub."}
  // Forward to the first position with fewer frames than now. Between calls no
  // function is running, so stepOut runs the whole next call and stops where it
  // has returned, at the next position between calls. At the end it stays.
  stepOut() {
    const depth = this.machine.state.frames.length;
    if (depth === 0) {
      if (this.tick < this.end) {
        do {
          this.forward();
        } while (this.machine.running);
      }
    } else {
      while (this.machine.state.frames.length >= depth) this.forward();
    }
    return this.tick;
  }
```
<!-- /code-example -->

Inside a call, `stepOut` counts the frames now and runs instructions until there are fewer. A deeper call made on the way pushes a frame and pops it again without stopping it, so the stop comes when the current function's own `return` or final `end` pops its frame. The first position with fewer frames is where the caller carries on, or, for the outermost function of a call, the position between calls after it. Between calls, this checkpoint runs the whole next call, the one `where()` names, and stops where it has returned. Another choice would do, such as refusing or not moving, as long as the comment says which. `forward()` is lesson 10's: between calls it begins the next call first. Moving forward replays only the distance moved, so `stepOut` costs the instructions it runs.

## Lines

The compiler can also write a **line table**, which gives, for each stretch of code, the line of the C source it came from. It lives in `.debug_line`, one of the sections of DWARF, the standard format for debugging information, which only a build with debugging information carries. No file this course ships carries DWARF, because DWARF also records the layout of every C struct, which is what Sightline asks its learners to work out. The course decoded the line table of a debugging build when it built the targets and saved its rows in `lines/lob.json`: `{ offset, line, column }`, sorted by `offset`. DWARF counts a WebAssembly address from the start of the code section's contents, after its id byte and size (the code section holds the functions' instructions, and the listing records that start as `codeSectionStart`). The course added that start, so `offset` is a file offset like the listing's `offsets`, where `offsets[k]` is the file offset of instruction k.

An instruction belongs to the last row at or before its offset. `lineAt(lines, offset)` finds that row with a binary search and returns `{ line, column }`, or `null` before the first row.

Some rows say line 0. That is DWARF's way of saying the compiler made this code without a line of its own, and 561 of Lob's 2,806 instructions fall on such rows, among them instructions of loop bodies the compiler unrolled, writing the body out several times in a row. In lesson 08's clearing loop, the `local.get` and `i32.const` that begin each copy after the first fall on line 0. `debug.mjs` prints "no line" for any instruction on a line-0 row. DWARF also marks the end of each function's rows with an end-of-sequence row. The course kept those as rows of line 0 at the end of each function's code, so the last line of one function never covers the start of the next.

The C source isn't given, so a line number is a label rather than a place you can read. It still groups instructions into statements. An assignment compiled to eight instructions gives all eight one line, and comparing lines is how a debugger steps by line.

### Find the row

Replace the `line-at` region of `project/names.mjs`:

<!-- code-example {"file":"examples/names-checkpoint.mjs","region":"line-at","language":"js","title":"lineAt: the last row at or before an offset","change":"Replace the line-at region."} -->
```js {"file":"examples/names-checkpoint.mjs","region":"line-at","title":"lineAt: the last row at or before an offset","change":"Replace the line-at region."}
// { line, column } of the last row at or before `offset`, or null when every
// row comes after it. Rows are sorted by offset.
export function lineAt(lines, offset) {
  let lo = 0;
  let hi = lines.length;
  // Rows before lo are at or before offset; rows from hi on come after it.
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (lines[mid].offset <= offset) lo = mid + 1;
    else hi = mid;
  }
  if (lo === 0) return null;
  return { line: lines[lo - 1].line, column: lines[lo - 1].column };
}
```
<!-- /code-example -->

The search keeps one rule true as `lo` and `hi` close in: every row before `lo` is at or before `offset`, and every row from `hi` on comes after it. When they meet, `lo` is the first row past `offset`, so the row just before it is the answer. When `lo` is still 0, every row comes after the offset and there is no line. Lob's table has 1,050 rows, so a question takes at most 11 comparisons. A row of line 0 is returned like any other; deciding what it means is left to the caller, as `debug.mjs` does.

## Use it on a new case: step by line

`step` moves one instruction, and `finish` a whole function. A person reading C wants a step between the two: run to the next line of the function they're in, stepping over any function it calls, as gdb's `next` does. Write `nextLine(debugger, program, lines)` in `project/next-line.mjs`, which both route commands created. If you didn't use them, copy `starter/next-line.mjs` to `project/next-line.mjs` first. No finished version is supplied, and none of the listings above does this. Its contract:

- `program` is the listing the debugger replays and `lines` the rows of `lines/lob.json`. The line of a position is the line `lineAt` gives the instruction that runs next there. A row of line 0, or no row at all, counts as no line.
- From the current position, run forward to the first later position where there are fewer frames than at the start, because the current function has returned, or where there are as many frames as at the start and there is a line, different from the start's line. Leave the debugger standing there and return that position.
- Positions with more frames than at the start are inside functions the current line called, and never end the step, whatever their lines.
- Between calls, the end of the run included, no function is running and there's no line to step over: throw an error, without moving and without running anything.
- Use only the Debugger's public surface (`tick`, `end`, `step`, `seek`, `stack`, `where`), the listing's `offsets` and your own `lineAt`, so your function works with any debugger that meets `API.md`.

The budget holds for every question the checker asks: a step may run at most the number of instructions it moves forward, plus 2,000. Moving forward one instruction at a time costs exactly the distance, and the 2,000 leave room for one restore from a snapshot and a short replay. A step that replays from position 0, or from far behind, for each instruction doesn't fit.
