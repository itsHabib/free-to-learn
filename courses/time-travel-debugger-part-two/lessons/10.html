10 · Run backwards

Lesson 08's wall measured part one's debugger on Lob. Every step copied the whole state, and one backward question at the end of a run would take hours. By the end of this lesson your debugger.mjs will step back one instruction, run backward to the last time a breakpoint (a stop before a chosen instruction) or a watch (a stop after chosen bytes change) fired, and say who last wrote any byte, each by replaying from a snapshot, so an answer a few thousand instructions back costs a few thousand instructions. Its snapshots will copy only the parts of memory written since the previous one.

The tool this lesson mirrors is rr's reverse execution, behind reverse-stepi (one instruction back) and reverse-continue in gdb, the standard debugger for compiled programs. rr answers both the same way, by restoring a saved moment and replaying forward from it.

Positions

The debugger works on one recording. A position is a moment between instructions. Position t is the state after t instructions of the run, counted across all its calls, so position 0 is before game_init runs anything and position end is after the last call returns. Between two calls no function is running. The next instruction is the first one of the next call, and where() names it with that call's index.

Everything the debugger answers is a position. seek(t) moves to position t. step(n) and stepBack(n) move by n instructions. continue(stops) and continueBack(stops) move to the nearest position after or before this one where a stop fires. At the current position, read(address, size) returns memory and state() a structuredClone of the whole machine state. debug.mjs, the course's command line for your debugger (you try it later in this lesson), uses state() to call the game's getters and, in lesson 13, to name your answer. Check 10.state compares both with a replay from tick 0.

Tour the supplied nextInstruction and where in your debugger.mjs now. During a call, the instruction that runs next is the innermost frame's at. Between calls the machine has no frames, so nextInstruction looks up the function the next call starts in, which the constructor keeps in this.callFunc, and answers its instruction 0. Breakpoints use the same method, which is how a breakpoint on a call's first instruction fires at the position between calls.

The obvious way, and its cost

The simplest debugger replays the recording from tick 0 every time it moves. seek(t) then costs t instructions, and so does every stepBack. On lesson 09's recording, 652,927 instructions long, stepping back once from near the end replays more than 650,000 instructions to move one.

Part one fixed half of this with checkpoints, replaying from the nearest saved state instead of from 0. The other half was what a checkpoint cost. Part one's checkpoint was a full copy of the state, and on Lob the state is 131,072 bytes of memory.

Snapshots that share pages

Cut memory into pages of equal size, say 4,096 bytes, which makes 32 pages for Lob's 131,072 bytes. These are your debugger's pages, not WebAssembly's 64 KiB pages, and you choose their size. A snapshot is the state at one position with its memory kept as a list of pages. Take one every K instructions during a first pass over the recording.

Between two snapshots most pages aren't written at all. So when you take a snapshot, copy only the pages written since the previous snapshot, and for every other page put the previous snapshot's page object itself in the list. Two snapshots then share every page that no instruction wrote between them, and each shared page is the same Uint8Array, held once.

To know which pages were written, read the events. Each write names its address and size, and its page is Math.floor(address / 4096). A write can cross into the next page, so mark both.

The rest of the state is small: the frames with their locals and open blocks, the value stack, the globals, the tick, the call count, and how many recorded answers the run has used so far, so that a replay from this snapshot answers the next import with the right one. Copy all of that with structuredClone.

Share what wasn't written

Replace the capture region:

Each page is either the previous snapshot's page object, when nothing wrote it, or a fresh slice, which copies those bytes. The rest of the state goes through structuredClone without its memory, and answered saves the position in the recording's answers. Called with no previous snapshot, capture copies every page; the first snapshot and lastWrite call it that way.

Restoring a snapshot means building a Uint8Array of 131,072 bytes from its pages, copying the small state back, and pointing the machine at both. Never let the machine write into a snapshot's pages. Copy them into a fresh memory first, or the next replay would change the past.

Restore without sharing

Replace the restore region:

memory.set copies each page into the new memory, so a later store changes only the machine's memory. The small state is cloned for the same reason: the machine pushes and pops its frames and stack in place. Replacing this.answers makes the next import answer from where the snapshot's run had got to. Lesson 08's rule pays off again: assigning machine.state is all it takes to put the machine at that moment.

Check 10.page-sharing takes your snapshots after a first pass and counts the bytes they hold, counting a page shared by several snapshots once. It also checks that each snapshot's pages, laid end to end, are exactly the memory at its tick.

Going back

continue(stops) and continueBack(stops) take stops = { breakpoints: [{ func, at }], watches: [{ address, size }] } and return { reason, tick }. A breakpoint { func, at } fires at a position whose next instruction is that one, so the debugger stops before it runs. A watch fires right after an instruction that changed one of its bytes, and the debugger stops after the write. Both continue and continueBack move at least one instruction, so from a position where a breakpoint fires, continue finds the next time it fires, not this one.

With snapshots, every backward move is a restore and a short replay:

  • stepBack(n) from position t: restore the last snapshot at or before t - n, then replay forward to t - n.
  • seek(t) the same way, forward or back.
  • continueBack(stops): the answer is the latest position before t where a stop fires. Restore the snapshot just before t and replay the stretch up to t, noting every position where a stop fires. If there were any, the last one is the answer. If not, go one snapshot further back and replay that stretch, and so on. Stop at the first stretch, going back, that holds a match.
  • lastWrite(address): the same search, where the stop is "this instruction wrote the byte at address", changed or not.

Shared pages buy one more saving. If the page holding a watched byte is the very same object in two neighbouring snapshots, no instruction wrote that page between them, so the stretch between them can't hold a match and doesn't need to be replayed. For a byte on a page nothing has written for a long time, lastWrite then skips most of the run. How often that happens depends on the page size. A page is skipped only if none of its bytes was written, so smaller pages are skipped more often, and each snapshot then holds more page objects.

Move by restoring and replaying

Replace the move region:

forward runs the run's next instruction. Between calls it first begins the next call, which is why a position between calls has no frames: the call starts only when its first instruction runs. moveTo restores a snapshot only when it has to, when the target lies behind the current position or before the snapshot it would use. Moving forward a little from where the machine stands replays only the distance. seek, step and stepBack check their argument and clamp at 0 and end, then all go through moveTo.

Stop before or after

Search backward one stretch at a time

Replace the search-back region:

searchBack(last, test, mayMatch) is the procedure the bullet list described, written once for both backward searches. Stretch i is the instructions after snapshot i, up to snapshot i + 1 or last. It restores the snapshot, replays the stretch once and keeps the latest finding, because the answer is the latest match, not the first. The first stretch, going back, that holds a finding has the answer, so the cost is about the distance to the match plus up to two stretches.

mayHaveWritten(i, pages) is the shared-page saving: it answers no when snapshot i + 1 holds the same page objects as snapshot i. continueBack uses it only when every stop is a watch, because a breakpoint can fire in a stretch that writes nothing. When nothing matches, continueBack goes to 0 and reports 'start', unless a breakpoint fires at position 0 itself.

Ask who last wrote a byte

Replace the last-write region:

lastWrite counts any write to the byte, changed or not, as the contract asks, and findLast picks the last write of an instruction that wrote the byte twice. It starts by capturing the current position, with every page copied, and restores it at the end: the method answers without moving the debugger. Only the page holding the byte matters, so every stretch in which that page stayed shared is skipped.

Budgets

The checks count every instruction your machine runs, by counting calls to its step. They ask questions near the end of a long recording and give each kind a budget, a few times what a snapshot every few thousand instructions needs, and far less than a replay from tick 0.

Each check makes its own debugger, moves it, and compares what it finds with a replay from tick 0 or with a scan of the recording. What each one moves to, and so which snapshots your debugger restores on the way, and what it compares:

  • 10.seek seeks to positions spread over the run, among them the start and the end, and after each seek compares the position, where() and all of memory with a replay from tick 0. Its targets are far apart, so no two of its seeks restore the same snapshot.
  • 10.step-back seeks to a position, then steps back by one instruction or by a few hundred, or forward by a few, and compares where it lands the same way. A step back restores the snapshot at or before the new position, often the one the seek has just restored.
  • 10.continue seeks to a position and calls continue, which only runs forward, so nothing is restored after the seek. It compares each stop with a scan of every instruction.
  • 10.continue-back seeks to a position and calls continueBack, which restores the snapshot of the stretch it stands in, often the one the seek has just restored, and then earlier ones. It compares each stop with a scan of every instruction.
  • 10.last-write seeks to a position and calls lastWrite, which searches back the same way, stretch by stretch from the one it stands in, and then puts the debugger back. It compares the write found with a scan of every write, and checks that the debugger did not move.
  • 10.state seeks to a position inside a call and then to the next position between calls, and at each compares state()'s memory and frames with a replay from tick 0. Then it changes the copy and checks that the debugger's memory did not change.
  • 10.page-sharing seeks to the end, which restores the snapshot before the end and replays to it, and then reads snapshots. It counts the bytes their pages hold, and compares the pages of a sample of them with a replay. It compares no position.
  • 10.budget opens a debugger, seeks near the end and asks a series of backward questions in a row, which restore some snapshots more than once. It counts the instructions each question replays and fails a debugger that replays from the start for any of them. It compares no position, memory or answer with a replay.
  • 10.lob2 does the same kinds of move on a Lob II recording: at a few positions it seeks, steps back one instruction, seeks there again, asks lastWrite and calls continueBack, and compares each result with a replay or a scan.

What you should have seen: with this lesson's debugger, last-write costs 113,351 instructions, the search and then the move to the write it found, far more than the few thousand the earlier questions cost. Your debugger isn't broken; this question is the busy-page case. g + 40 is on page 16, one of the pages written on almost every game frame, which the snapshot listing above shows as copied by the last snapshot itself. Each snapshot holds a new object for that page, so mayHaveWritten can't rule out any stretch, and lastWrite replays every stretch between here and the write, about one instruction for each instruction it goes back. A byte on a page nobody writes, like g itself, is found in about a thousand.

Use it on a new case: find a value backward

Lesson 08's wall timed part one's reverseFind, a search for the latest earlier tick at which a byte held a given value, and estimated hours for a question near the end of the run. Write it again on your snapshots: reverseFind(debugger, { address, size, equals }) in project/reverse-find.mjs, which both route commands created. If you didn't use them, copy starter/reverse-find.mjs to project/reverse-find.mjs first. No finished version is supplied, and none of the listings above does this. Its contract:

  • equals is an array of size byte values. Return the greatest position before the debugger's current one at which the size bytes at address equal equals, and leave the debugger standing there. Position 0 counts.
  • When no earlier position holds that value, return null and leave the debugger where it started.
  • Refuse, with an error and before moving: bytes outside memory, a size below 1, or an equals that isn't size whole numbers from 0 to 255.
  • The budgets hold for the bytes the checker asks about, not for any bytes. It asks, near the end of a long run, about a byte whose value changed a few thousand instructions back, and about bytes on a page nothing has written since game_init, such as g at 78,112. For those, a question may replay at most 20,000 instructions, even when the answer lies in game_init. A value the bytes never held may replay at most 80,000. Bytes on a page written on almost every game frame, in Lob page 15 and the two pages after it, are different: that page is a new object in every snapshot, so no stretch can be skipped soundly, and a value they never held costs a replay of the whole run. The checker doesn't ask that.
  • Use only the Debugger's public methods (tick, seek, step, read) and its snapshots, each with its tick and pages, so your function works with any debugger that meets API.md.
