# 13 · The ladder

Six later builds of the game each misbehave in one way, five of Lob and one of Lob II, and each comes with a recording of a run that went wrong. By the end of this lesson you will have named, for each build, the **first bad write**, the earliest store in the run that leaves a byte of memory holding a value a correct build wouldn't hold there at the same point of the run (`API.md` defines it under "investigations/N.txt"). Each answer comes from a script of debugger commands that your own tool runs inside a replay budget.

`node lab.mjs ladder` lists the six builds, what is wrong at the end of each recording, and each budget.

## What you have and what you don't

For each build you get its `.wasm` file (with function names), its listing in `programs/ladder/`, and its recording in `recordings/ladder/`. You don't get its C source, and its memory is laid out differently from `lob.wasm`. The game's state sits elsewhere and its fields are in another order. So you can't find the change by comparing memory with `lob.wasm`, and a listing compared line by line with `lob.wasm`'s differs almost everywhere.

What you can compare is behaviour. `lob.wasm` is the last good build of Lob, and `lob2.wasm` is the last good build of Lob II, the good build for build 6. Their getters, `r_px`, `r_result` (the kind of landing) and the rest (`getters` prints them all), or `g0` to `g7` for Lob II, mean the same in every build of the same game. `debug.mjs` runs both builds on the recording's calls in Node's own engine:

- `diverge` names the first call after which a getter of this build differs from the good build's (this is `debug.mjs`'s `diverge`, not the lab's from lesson 09)
- `compare` shows every getter of both builds side by side after the calls so far, and for a build of Lob each build's status line, message line and help text too.

Neither command uses your machine or counts towards the budget. They tell you where to look, and your debugger finds the write.

## The method

Work backward from the first visible difference to the first bad write.

1. Find the first visible difference. Start from the build's symptom, or run `diverge`. Note the call and the getter.
2. Find the address. A getter reads memory, so run it in your head from the listing, or stand between calls and `read` the bytes it reads. In Lob, `r_px` reads the pointer at 78,112 and then the 4 bytes at an offset from it. In a ladder build the pointer's address and the offset can both differ (build 1's pointer is at 72,992), and the listing gives both. Read the pointer at the call you are investigating. In mode 2 the game moves its state to a new address at every new round (API.md, "public/sessions.mjs"), so an address read in round 2 may hold something else in round 1.
3. Find who wrote it. Stand at the start of the call after the one where the getter first differs (`call 238` after a difference in call 237). There `last-write ADDR` (your Debugger) or `who ADDR` (your index) takes you to the last store to that byte.
4. Judge that store. Read its value and ask `sources` which stores, answers and arguments it was computed from. If one of its inputs was already wrong, that input's store is earlier on the chain, so go back to step 3 with it. If all its inputs hold the values a correct build would have, and its result is still wrong, the planted change acts here.
5. Look just before it. The code that made one wrong store often made others a few instructions earlier, from the same wrong decision. Step back a little (`back 30`) and list what the next instructions write (`writes 30`). The earliest store in that stretch with a wrong value is your new candidate, even if it isn't the one your symptom led you to. If the stretch's first store is already wrong, step back further.
6. List every change. A wrong byte's last writer may not be the store that first made it wrong. Remove earlier stops with `clear`, then set `watch ADDR` on the byte, `seek 0` and `continue` again and again. Each stop is right after a store that changed the byte, so the stops list every change to it from the start of the run.
7. Name it. Stand right after the first bad write (`last-write`, `who` and a watch's stop leave you there, and after `writes`, `seek` the tick it printed for that store) and run `answer`.

Judging a store needs a notion of right, which you can take from the help text (angle 5 to 85, power 10 to 100, land within 12 paces to score), what the good build shows through its getters on the same calls, and arithmetic you can redo from the listing. Lob II's getters don't say what they hold, so for build 6 your notion of right comes from `compare` against `lob2.wasm` and from the build's symptom in `node lab.mjs ladder`.

The store your symptom leads to may not be the first wrong one. Step 5 exists because a wrong decision usually makes several stores. The last writer of a wrong value isn't always the first bad write either. The same wrong store may have run earlier, and its earlier result may since have been overwritten, which step 6 shows. And a store can write a right value to the wrong address. Then every input `sources` lists is right, because the chain doesn't follow addresses, so look at how the address was computed.

## A worked investigation: build 1

Build 1's symptom: the second shell lands 10 paces short of the flag and the message reads SHORT BY 10, although the help says a shell within 12 paces scores. `lob.wasm` shows HIT! on the same calls. Here is the investigation, as `project/investigations/1.txt` could hold it, with what each step shows.

```
diverge
```

`after call 237 (game_tick): r_result is 2 here, 1 in lob.wasm.` Call 237 is the game frame in which the second shell lands, and `r_result` is the kind of landing: 1 a hit, 2 short.

```
listing r_result:0 4
call 238
read 72992 4 i32
```

The getter loads the pointer at 72,992 and reads 4 bytes at offset 0 from it. Between calls the pointer holds 65,928, so the result lives at 65,928.

```
last-write 65928
```

`tick 261685: function 8 (game_tick), instruction 304: i32.store wrote 4 bytes at 65928.` The landing code stored 2. Its inputs were right. The shell's position and the flag's agree with `lob.wasm`'s getters. So the decision it stored is wrong, and step 5 of the method applies. Did the same decision make other stores just before?

```
back 12
writes 12
```

Two stores: at tick 261,676, instruction 295 stored 10 at 66,540, and at tick 261,685 the result. 10 is the miss distance the message prints, and a hit stores 0 there. Both stores are wrong, and the miss distance came first.

```
seek 261676
answer
```

`answer: function 8 (game_tick), instruction 295 (i32.store), address 66540, tick 261676.` Run it with `node lab.mjs investigate project 1`. With the course's worked solution it replays about 280,000 instructions, most of them the debugger's first pass, against a budget of 856,000.

The symptom you start from decides which wrong store you meet first. Starting from the message text, SHORT BY 10, found through the getter `r_msg_ptr` at the pointer held at 72,996, `last-write` on the digit 1 finds the store that wrote it, and `sources` on that store lists the miss distance's store, tick 261,676, among the newest on its chain. The route from `r_result`, as above, leads to the result, nine instructions too late. Step 5 is what turns the second route into the right answer.

## Your investigations

To explore a build, open it in your debugger by its number. `node debug.mjs project N` loads build N's recording and listing and knows its good build, so `diverge` and `compare` work. Try commands there, then copy the ones that lead to the answer into a script.

Write each investigation in `project/investigations/N.txt`, one command per line, and run it:

```
node lab.mjs investigate project N
```

The lab prints every command's output, the answer, and how many instructions your machine replayed. The budget counts everything your debugger and index run, from opening the recording to the answer. It leaves room for one index build, a first pass of your debugger and a few dozen backward questions. Replaying from the start for each question doesn't fit.

The builds rise in difficulty. Builds 1 and 2 are a short way back from the symptom. Build 3 makes a run of stores in one call that shouldn't have happened at all, and you need the first of them that left a byte different from a correct build's. Builds 4 to 6 hide the first bad write behind later writes, so either the symptom's last writer isn't the answer or the corrupted value travels through other stores before anything visible goes wrong. In every build here the run first goes wrong at a store the build makes, never by leaving out a store a correct build makes (`API.md` says so under "investigations/N.txt"). So a store that finds its byte already wrong can't be the first bad write, which came earlier.

Checks `13.build-1`, `13.build-2`, `13.build-3`, `13.build-4`, `13.build-5` and `13.build-6` run your scripts the same way and compare your answers with the first bad writes. A wrong answer says only that it's wrong. The checks keep each answer only as a slow salted hash, a fingerprint the checks can compare your answer with but can't read the answer from, so they can't show it to you.
