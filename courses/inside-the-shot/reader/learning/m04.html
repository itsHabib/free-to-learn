M4 preparation — preserve the failure, then explain it

Your next project asks you to repair a parser that rejects valid files. A useful repair explains a particular contradiction: the file satisfies the format, yet a particular executed guard rejects it. This preparation gives you a way to reduce that contradiction and trace its cause. It does not identify the mistaken expression in the project.

Bring your M3 field map, exact-size rule, and ability to read Python functions, loops and ValueError. A guard is a condition checked before work proceeds. A reproducer is an input together with the command that produces an observed failure. A smaller input helps only if it still reaches the failure you are investigating.

The examples below are scratch practice. They add no project submission. Keep the original project's first prediction unsullied: do not run its parser, open its hints, or inspect feedback until M4 START-HERE tells you to do so after saving.

Reduce a valid failure, not any exception

Consider a separate text format for a gardening list. A line has a decimal count, a |, then that many comma-separated plant names. Counts are 0..4; names contain 1..4 lowercase letters. 0| is the empty list. Repeated names are allowed. Thus 4|oak,elm,elm,ash is valid.

Suppose this invented parser passes the syntax and count checks, then fails on that line:

seen = set()
for index, name in enumerate(names):
    if name in seen:
        raise ValueError("repeated name")
    seen.add(name)

Its failure predicate is precise: a format-valid list is rejected at the repeated-name guard. “Returns a nonzero status” is broader and would include missing files, malformed counts and unrelated exceptions.

Reduce by removing a name and regenerating the count. 3|elm,elm,ash still fails at the repeated-name guard. 2|elm,elm does too. Reducing to 1|elm passes, so it no longer reproduces the failure. Keeping the old count as 4|elm,elm gives a count mismatch before the loop; it is a different failure. The two-name result is minimal by number of names: a repeat needs at least two occurrences, and a one-name valid control does not fail. This does not prove the shortest possible spelling in bytes; that is a different minimality claim.

For a binary format, removing a record may require changing count or size fields together. An owned writer can preserve those relations. Save each candidate under a new name and ask two separate questions: does a validity control accept it, and does the faulty program still reject it at the same stage? Retain candidates that fail differently as evidence about your reduction, without calling them minimal reproducers.

Find the first contradiction in actual values

Here is the complete relevant trace for the reduced gardening input. The count check has already established two names.

Before guardnameseen before this iterationname in seenResult
index 0elmempty setfalseAdd elm
index 1elm{elm}trueRaise ValueError

The first iteration is consistent with the contract. The second guard is the first contradiction: it excludes a repetition the format explicitly permits. “The list length is wrong” does not explain this trace. The count check passed, there are two parsed names, and the exception comes from the later membership test. A competing explanation such as “the comma split lost a name” would predict different names or a count failure. These observed values reject that explanation for this case.

A causal trace connects an input fact, an operation, a condition and its consequence. It is stronger than merely quoting the final exception. For your project, predict locals before observing them; afterward, record the actual values at the executed guard. Distinguish a value the code computes from a value you believe it ought to compute. If the two differ, name the first operation that makes them differ. The final exception may be several operations downstream.

Put units and origins on numbers

A parser uses several kinds of numbers. A count may mean records; a length may mean bytes in a region; an offset means a position measured from a named origin. A number alone does not tell you which one it is.

For a separate 18-byte buffer, suppose a region starts at file offset 6 and contains 5 bytes. Its file coordinates are [6,11): offsets 6 through 10. The notation is half-open: include the start, exclude the end. Region-relative offset 0 denotes file offset 6. Region-relative offset 4 denotes file offset 10. File offset 11 is immediately after the region even though it is still inside the larger buffer.

To inspect a proposed operation, write the interval it would access and compare intervals with the same origin. A three-byte read starting at file offset 9 covers [9,12). Two of those bytes belong to the region and one does not. The whole-file length being 18 cannot establish that the operation stays inside this region. Conversely, a zero-byte window at offset 11 accesses no byte; it is not the same as a one-byte read there.

Use a trace table with columns for name, actual value, unit, origin and producer. For example, “5 bytes, length of the region, decoded from a header” and “6 bytes from the beginning of the buffer, start chosen by the caller” are different claims. Only after labeling them should you decide which comparisons are meaningful. Apply this method to the project's variables yourself; this example supplies no project values or replacement expression.

Make a repair earn its explanation

A minimal valid reproducer focuses a repair, but does not establish its full scope. The gardening parser also needs an empty list and distinct-name list to remain accepted, plus count mismatches and illegal names to remain rejected. A workaround that returns an empty list for every error would suppress the symptom while erasing valid names. A test that obtains its expected value by calling the same parser a second time would repeat its mistake.

Choose expected output from the format and your saved prediction. Preserve the original program, the failing input, actual trace and failure output before editing. Afterward, test both the newly accepted valid case and nearby malformed cases. Explain which validation rule each negative control protects. A finite regression set supports those cases; it does not prove the parser correct for every byte sequence.

Enter the original parser project

Open M4 START-HERE and follow its order from section 1. Preserve parser-original.py, write the predictions for the supplied fixtures, and successfully save before the first parser run. Then use the project's native reader as its validity control, its writer for consistent smaller candidates, and trace.py for actual local values. The preparation's gardening list is not a replacement file format or a repair template.

If a candidate fails, first classify the failure. A missing-file diagnostic calls for checking the working directory and filename. A malformed-size refusal calls for checking the candidate against your M3 map. A valid-input parser refusal calls for following the actual guard. Different exit messages can share a status, so retain stderr and the exact command. If the native validity control refuses an allegedly original fixture, use the hash/re-extraction procedure in the project's setup instead of changing your format model to accommodate damaged bytes.

Carry forward the artifacts the project already requests: original failure, minimal valid bytes, predicted and actual traces, narrow patch explanation, regression tests, and the saved revision history. Together they let another person distinguish “this input now works” from “this change addresses the traced cause while retaining the tested refusals.” M5 will reuse your distinction between the size of a region and its position in a larger byte stream.
