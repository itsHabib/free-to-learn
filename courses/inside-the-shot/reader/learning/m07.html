M7 preparation — build an investigation someone can challenge

The reservation capstone combines earlier work: infer a bounded file format, connect bytes to native calls, model state changes, compare compiled forms and defend a fresh prediction. The useful outcome is a reproducible argument with preserved counterevidence. It is not a collection of outputs that happen to match.

Bring your byte-order and bounds notes, M4's cause tracing, M5's distinction between observations and inferred events, and M6's value/flag correspondence method. You need Python functions and exceptions, state traces and caller/callee notation. A state is the set of values needed to predict subsequent behavior. An invariant is a stated relation that should hold over a specified kind of state under stated assumptions.

This preparation works a separate lift-display example. Its layout and rules are supplied solely to make the method visible. They say nothing about the reservation program's operation codes, fields or transition rules. Separate syntax from an operation's acceptance

The toy lift file begins with magic byte 45, then an unsigned one-byte count 0..4. Each entry has two bytes: direction 55 (U) or 44 (D), then amount 0..6. Its exact size is 2 + 2*count. Validate the entire file before replay. Thus 45 01 55 03 is one well-formed upward entry of amount 3. Removing its last byte makes the file malformed, so no operation is attempted. Appending a byte also violates the exact-size rule.

Toy state has floor f in 0..6 and total accepted travel t. An accepted U amount a sets f=f+a and t=t+a; an accepted D sets f=f-a and t=t+a. A move whose proposed floor lies outside 0..6 is rejected and leaves this toy state unchanged. A well-formed D entry can therefore be rejected at floor zero. That is a replay result, not a file-parser error. These are supplied toy rules, not discoveries about the capstone.

For a real probe, retain separate columns for file validity, process exit, operation acceptance, event state and published final state. If the process refuses malformed bytes before producing events, do not describe that as a rejected operation in a valid replay. If the process succeeds and reports an event as rejected, do not infer that its file was invalid.

Draw three layouts before tracing a call

The same logical entry can have different representations on disk, in an argument and in mutable state. Here are declared layouts for the toy; their addresses are illustrative, not addresses from the capstone.

RepresentationToy factsExample for U amount 3
File bytesMagic at file offset 0, count at 1, first two-byte entry at 245 01 55 03; entry bytes 55 03
By-value call argumentEntry packed as direction + 256*amount in low 32 bits of x1 (w1)0x0355 = 853; not an address
Mutable statex0 points to an eight-byte object: four-byte floor at state offset 0, four-byte travel at state offset 4At address 0x9000, floor 2 and travel 0 before the move

If the file buffer begins at 0x7000, the first entry's address is 0x7002. Decoding reads its two bytes and produces integer 853. A later call receives state address x0=0x9000 and record bits w1=853. For the accepted U3 move, state becomes floor 5, travel 3. The file offset 2, entry address 0x7002, packed integer 853 and state address 0x9000 have four distinct roles.

Follow each pointer through saves and reloads rather than treating every load as a fresh input. A stack displacement locates temporary storage relative to that function's stack/frame reference. It is neither a file offset nor automatically an object-field offset. A callee's [sp,#8] is not the caller's [sp,#8]. Likewise, a four-byte load establishes an access width, not the source-level name of the value.

Choose an input on which hypotheses disagree

Suppose the toy move rule is known, but how a sequence is processed and published is not. Three plausible runners are:

  • Continue after a rejected move and publish the resulting state.

  • Stop at the first rejected move and publish the state reached so far.

  • Continue using a working copy, record every event, but publish the original state if any move was rejected.

A working, or speculative, state is what the runner uses while evaluating a sequence. The published state is the one it exposes as final. They can differ. Do not decide publication merely from an intermediate event.

Start the toy at floor 1, travel 0 and choose U2, D4, U1. This is discriminating: it includes a rejection, a later move, and a net change from the initial state.

Entry under continued evaluationProposed floorAccepted?Working floor, travel after entry
U23yes3, 2
D4-1no3, 2
U14yes4, 3

The first runner predicts three events and final (4,3). The stop runner predicts two events and final (3,2). The working-copy runner predicts three events with the table's snapshots, but final (1,0) and unsuccessful publication. If a hypothetical observation has those three snapshots and final (1,0), it rejects the first two hypotheses on this input and supports the third. It does not establish that every detail of the third runner is correct.

An all-accepted control U2, D1 from the same start reaches (2,3) under all three candidates. It cannot distinguish their rejection policies, but it can refute a model that always resets final state. An empty sequence checks initialization. A sequence whose net change is zero may conceal publication differences; calculate both predictions before selecting the input.

For the original program, write your own two competing hypotheses before the first run and choose observations that can disagree. “Maybe it works differently” is not a predictive hypothesis. State what each candidate expects for event count, acceptance, snapshots and final state. Keep observations that fit neither; they are reasons to revise, not discard the input.

Use an invariant as a diagnostic, with its limits

For the toy, let u be the sum of accepted upward amounts and d the sum of accepted downward amounts in a particular state history. Starting at floor f0, travel zero, the exact ledger equations are:

f = f0 + u - d
t = u + d

For the worked continued evaluation, u=3 and d=0: rejected D4 contributes nothing under the supplied toy rule. Thus f=1+3=4 and t=3. The equations imply t >= abs(f-f0) and that t-(f-f0) is even. These weaker consequences can flag an impossible state, but they cannot establish the exact history. From start 1, (f=4,t=3) fits U3; (f=4,t=5) fits U4 followed by D1. Both satisfy the inequalities and parity, despite different paths.

Name the state version to which an invariant applies. The speculative ledger for the three-entry example ends at (4,3). If the runner publishes its initial state instead, the published ledger has no committed movement and ends at (1,0). Plugging speculative u and d into a published-state equation would manufacture a contradiction by mixing histories.

Your capstone needs an invariant justified from its own inferred operations. Label any quantity entering or leaving the modeled system and each separately indexed state component. Do not copy the lift's equation or collapse multiple slots into one aggregate unless the evidence justifies that abstraction. A violated invariant points to a false assumption, bad trace, lost component or wrong state version; a satisfied invariant is a consistency check, not a proof of the entire model.

Give each claim evidence at the right boundary

Keep four kinds of claim separate: supplied interface facts, byte-field interpretations, instruction-derived transitions, and behavior observed on specific probes. A dictionary with the required keys and bounded values can have its field labels attached to the wrong bytes. Even end-to-end output agreement can hide two compensating mistakes: a decoder swaps two meanings and a replay function swaps them back. Shape checks and native result comparisons do not independently validate every isolated decoded field.

Support a field claim with byte offsets, width, byte order, controlled changes and the actual extraction or call trace. Support a transition with pre-state, input, guard, stores or lack of stores, returned acceptance and post-state. Support publication with the relation between event snapshots and final state, plus the relevant caller/return/selection path. Use actual addresses from the supplied listings; a plausible source reconstruction is not address evidence.

Enter the reservation investigation

Follow M7 START-HERE from setup and the separate count example. Save that practice before its feedback, then save two target hypotheses before the first target run. Use the original route's supplied specimens and required small probe set; preserve each raw input, prediction, command and output. Establish file bounds and field claims before treating a replay model as an explanation of the file.

Do not run the transfer binary until its original prediction is saved. Compare speculative events with published state, test controls that distinguish candidate policies, and preserve any counterexample before repair. If your first model agrees with the public checks, challenge a plausible alternative rather than inventing a failure. Public agreement supports the checked behaviors and shape constraints; it cannot independently certify all decoded fields or the argument you wrote.

Diagnose a malformed probe by checking your proposed exact-size relation and reversible hex bytes first. A writer helper's success confirms that it created bytes, not that the target accepts their format. A hash mismatch or launch error belongs to setup recovery, not a new state-rule hypothesis. If outputs disagree, locate the first layer that differs: file decoding, argument packing, operation acceptance, state update, event capture, or final publication. Preserve that version and input before changing the smallest supported part.

Carry forward the original investigation.py, field/call/state diagrams, discriminating probe corpus, invariant with assumptions, instruction evidence, fresh combined-case prediction and exported records. These are parts of the original capstone handoff, not a new project. Another person should be able to rerun a claim and see what could disprove it, including the limits of finite checks and supplied facts.
