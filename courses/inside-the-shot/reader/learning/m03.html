Preparation 3: validate the envelope before decoding entries

M2 gave you a way to explain fields in one record. A file can repeat records and declare how much data follows. M3 asks you to recover that relationship and build an inspector that rejects incomplete or inconsistent input while preserving bytes whose meaning remains unknown.

You need M2's offsets, widths, byte order and signedness, plus Python lists, loops and ValueError. A header is a fixed prefix carrying declarations about the file. A payload is the data after that prefix. An envelope is the relationship between header declarations and the actual bytes. A count of entries, their width in bytes, payload length and total file length are different quantities.

Keep the project's existing two-reading badge and its save-before-feedback exercise. The new queue below adds multiple declarations and preserved unknown bytes. It is a completely declared teaching format, not the trail layout.

A complete example: a queue of sensor readings

For this invented queue format, the header is seven bytes:

Byte rangeDeclared meaning
[0:2]Signature 51 54, the ASCII letters QT
[2:3]Unsigned one-byte entry count, at most four
[3:4]Unsigned one-byte entry width, always three
[4:6]Unsigned two-byte little-endian payload length
[6:7]One byte of unknown meaning, retained as raw hex

Each three-byte entry contains a two-byte signed little-endian reading, followed by one byte of unknown meaning. Unknown means that we can locate and retain the byte without claiming what it does. This contract permits any value there.

Consider:

51 54 02 03 06 00 a5  fe ff 7c  01 02 90

The count is 2, width is 3 and declared payload length is 6 + 0 × 256 = 6. The expected payload is 2 × 3 = 6 bytes. Total length must be 7 + 6 = 13. The actual sample has 13 bytes, so the declarations agree with the bytes.

Only now interpret the entries. The first starts at offset 7 + 0 × 3 = 7: reading fe ff is 65534 - 65536 = -2 and its unknown byte is 7c. The second starts at 7 + 1 × 3 = 10: 01 02 is 513 and its unknown byte is 90. The header's unknown byte remains a5.

The count does not say “read two payload bytes.” It says to read two entries, each three bytes wide. Nor is 6 an absolute end offset: the payload ends at offset 13 because the header occupies the first seven bytes.

Check each declaration before using it

These are three separate checks for this example:

  1. Count is within the supplied limit and width is exactly three.

  2. Declared payload length equals count × width.

  3. Actual total length equals header length + declared payload length.

The first prevents an unsupported loop or interpretation. The second catches contradictory declarations even when the physical file happens to have a plausible size. The third catches missing bytes and extra trailing bytes. An empty queue is valid only with count 0, width 3, payload 0 and total length 7.

Complete the last two guards before looking at feedback.

A near miss decodes entries first and notices truncation afterward. Python slices can return fewer bytes than requested without raising, and int.from_bytes(b"", "little") returns 0. A missing field can therefore become a plausible zero. Another near miss checks len(raw) >= expected: it rejects short data but silently accepts trailing bytes outside the declared envelope.

Here is a complete inspector for the declared queue format:

QUEUE_LIMIT = 19  # 7 header bytes + at most 4 entries of 3 bytes

def decode_queue(raw):
    if not isinstance(raw, bytes):
        raise ValueError("queue must be bytes")
    if len(raw) > QUEUE_LIMIT:
        raise ValueError("queue exceeds size limit")
    if len(raw) < 7:
        raise ValueError("queue header is incomplete")
    if raw[0:2] != b"QT":
        raise ValueError("queue signature")

    count = raw[2]
    width = raw[3]
    declared = int.from_bytes(raw[4:6], "little", signed=False)
    if count > 4:
        raise ValueError("queue count exceeds limit")
    if width != 3:
        raise ValueError("queue entry width")
    if declared != count * width:
        raise ValueError("queue payload declaration")
    if len(raw) != 7 + declared:
        raise ValueError("queue total length")

    entries = []
    for i in range(count):
        start = 7 + i * width
        entries.append({
            "reading": int.from_bytes(
                raw[start:start + 2], "little", signed=True
            ),
            "unknown_hex": raw[start + 2:start + 3].hex(),
        })
    return {
        "count": count,
        "entry_size": width,
        "payload_bytes": declared,
        "header_unknown_hex": raw[6:7].hex(),
        "entries": entries,
    }

Every operation that indexes header fields follows the minimum-header check. The entry loop follows all envelope checks, so it cannot quietly decode a partial entry. The output contains the sample readings −2 and 513, the raw unknown entry bytes 7c and 90, and header byte a5. None has been renamed a flag, checksum or padding.

Preserve observations without inventing meaning

The header byte a5 and entry byte 7c occupy known positions. If we change them and the readings still decode identically, we have evidence that the reading calculation does not consume them. We do not thereby know why a producer writes them or whether another program uses them.

Keep two claims separate in your format note: “this byte is retained from offset 6” and “this byte controls a mode.” The first can be checked by comparing raw bytes and output. The second needs an experiment about behavior. A run of zero bytes is compatible with many explanations, including a currently unused field or a value that simply happened to be zero. Deleting them would discard the evidence that could later distinguish those explanations.

Test the inspector's decisions, not only its happy path

A validation test needs a reason that one implementation would accept an input while a more careful one would reject it. Start with one valid queue and change one property at a time:

Candidate inputWhat its decision checks
Fewer than seven bytesNo header field is read before it exists
A valid empty queueZero count is allowed without inventing an entry
Count 2, width 3, declared payload 5Contradictory declarations are rejected
Correct declarations, one entry byte missingA short slice cannot conceal missing data
Correct declarations, one extra byte appendedExact total length is enforced
Correct shape with nonzero unknown bytesUnknown values survive without new semantics
Count above four, or input above 19 bytesSupplied limits are applied before iteration

Predict each result before checking your own example code. If an inspector accepts an invalid input, identify the specific missing guard. If it rejects a valid nonzero unknown byte, find the unsupported rule it imposed. Do not fix either by adding the particular sample's filename to a condition.

The byte decoder's length check bounds interpretation. A file wrapper also needs to bound how much it reads into memory:

from pathlib import Path

def read_queue(path):
    with Path(path).open("rb") as stream:
        raw = stream.read(QUEUE_LIMIT + 1)
    return decode_queue(raw)

Reading at most one byte beyond the limit lets the decoder reject an oversized file without first reading all of it. If the result contains 20 bytes, it is too large whether the file ends there or continues. This input bound is a supplied safety policy; it is not evidence for a particular field offset.

Recover the original bounded file

Open M3: read an unfamiliar file. Follow its original setup, badge example, saved predictions and one-variable comparisons. The queue's seven-byte header and three-byte entries are teaching choices; they provide no trail offsets or size constants.

For your own format-note.md, distinguish supplied domains and limits from inferred fields. For each proposed range, record its width, interpretation, supporting probe and a competing explanation the probe rejects. Use empty, one-entry and two-entry files to check the count/width/payload/total relationship. Preserve unexplained bytes in the original inspector's required output.

Keep the starter's bounded file read. Build inspector.py in the project's stated order: minimum input, declarations, limits and exact size, then entries. Save your implementation and note before invoking feedback. Predict how malformed inputs should fail as well as what valid files should return. A checker pass supports its finite cases; it cannot supply your format explanation.

If an error names a file that does not exist, check the terminal directory and filename before changing offsets. If the writer refuses an existing output, choose a fresh name so that the earlier probe survives. If your inspector prints plausible zeros from a short file, inspect the envelope guards before changing signedness. If an otherwise valid high-byte value becomes negative, inspect the field's signedness and domain. Use setup for platform errors and preserve the actual message.

Carry onward your own inspector.py, format-note.md and the exported saved evidence, including original predictions, raw reproducer bytes and any feedback-assisted repairs.
