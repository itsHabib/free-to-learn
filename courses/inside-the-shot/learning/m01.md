# Preparation 1: follow a value from input to stored state

The first project asks you to explain one cart tick, then decide what transfers to two related targets. Before investigating those targets, practise the smaller task underneath: keep an old state, a calculated value, a stored value and a return value distinct. This lets you support a Python model with a trace rather than with matching outputs alone.

You need Python variables, integer addition, functions and an `if` statement. A **state** is the information retained between updates. An input can affect an update without becoming part of the retained state. A function's return value reports something to its caller; it need not equal the state left in memory. You do not need to memorize assembly.

This preparation uses a completely declared receipt counter. Its rule and instructions are unrelated to the cart. Keep the project's existing [marker trace](../m01/START-HERE.md), [probe and tracing method](../m01/methods.md) and [follow-along checkpoints](../m01/follow-along.md): they remain part of the original route, including saving the marker answer before opening its feedback.

## Read number notation

A **bit** is one binary digit, 0 or 1; a **byte** contains eight bits. A 32-bit pattern therefore occupies four bytes. **Unsigned** interpretation treats the pattern as zero or a positive number. Hexadecimal writes four bits per digit, using 0–9 and a–f; the prefix `0x` marks that notation, so `0x0a` is decimal 10 and a full 32-bit pattern uses eight hexadecimal digits. The **low** bits are the least-significant positions; the **upper** bits are the more-significant positions. Python's `**` means exponentiation: `2**32` counts the possible 32-bit patterns.

## A complete example: update a counter, return a receipt

A delivery counter retains one unsigned 32-bit count. Its function adds the delivered quantity to that count and returns the **old** count as a receipt. Use small nonnegative values here, so no arithmetic wraps.

```python
def receive(count, delivered):
    old = count
    count = old + delivered
    return count, old
```

The first component is the new state; the second is the receipt. With count 14 and delivery 3, the new count is 17 and the receipt is 14.

Here is a short ARM64 version written for this example. It is not a listing from a course target. Let **P** name the memory address of the count. On entry `x0 = P`, memory at P holds 14, and `w1 = 3`. An address tells you where a value lives; it is not the value itself.

```asm
ldr w8, [x0]
add w9, w8, w1
str w9, [x0]
mov w0, w8
ret
```

The destination comes first. `ldr` loads from memory, `add` computes into a register, `str` stores to memory, `mov` copies, and `ret` returns. Brackets mean “memory at this address.” A register is a processor's working storage. The caller reads this function's receipt from `w0` after the return.

| Instruction | Values read | Result | Count in memory at P |
| --- | --- | --- | ---: |
| `ldr w8, [x0]` | Address P, then its four-byte count | `w8 = 14` | 14 |
| `add w9, w8, w1` | 14 and 3 | `w9 = 17` | 14 |
| `str w9, [x0]` | 17 and address P | Four bytes at P become 17 | 17 |
| `mov w0, w8` | The still-retained 14 | Receipt register `w0 = 14` | 17 |
| `ret` | Return address | Caller receives 14 | 17 |

Addition does not change memory: there are no brackets on its destination. Nor does it replace `w8`: its destination is `w9`. The store is the point at which the retained state changes. The final copy still reads the old count. This chain of “which produced value does the next operation read?” is **dataflow**.

A near miss translates the last two lines as “return the new count because the store already happened.” It predicts receipt 17. The store changed memory at P, not `w8`, so it cannot justify that prediction. Another near miss changes memory in the addition row and then treats the store as a second addition. A store copies bits; it does no addition.

Complete this same trace with a new starting count and delivery. Track the memory column separately from the register columns before checking.

## Width belongs to the operation; signedness belongs to the interpretation

ARM64's `x8` and `w8` are two names for parts of the same register, not independent boxes. `x8` names all 64 bits. `w8` names the low 32 bits. Writing `w8` also makes the upper 32 bits of `x8` zero. Reading `w8` reads only its low 32 bits. The same relationship holds for `x0/w0` and the other numbered pairs.

In the example, `ldr w8, [x0]` reads **four** bytes from the address held in the 64-bit `x0`. The address width does not make that a load of eight bytes. `str w9, [x0]` likewise writes four bytes. Writing the receipt to `w0` replaces the address previously held in `x0` with the zero-extended receipt bits. This is safe in the example because no later instruction needs that address. In a longer trace, using `x0` as P after that write would be an error.

For a separate width example, if `x8` holds `0x0000000100000007` and `mov w8, #2` runs, `x8` becomes 2. `#2` is the literal number 2. It does not mean “memory at address 2,” and the instruction has not stored anything to memory.

A 32-bit register holds one of `2**32` bit patterns. Unsigned interpretation gives 0 through 4294967295. Under signed two's-complement interpretation, patterns from `0x80000000` upward represent negative values: subtract `2**32` from the unsigned reading. Thus `0xfffffffe` has unsigned value 4294967294 and signed value −2. A load into a `w` register alone does not choose which interpretation your Python model needs.

A 32-bit addition retains the low 32 result bits. For example, the bit pattern for −2 plus 5 becomes `0x00000003`. Python integers do not have that fixed width automatically. This explains the notation; it is not a request to add overflow behavior outside the original project's input and output contract. In the cart project, use its signed values, supported domains and observed instructions to justify your model.

## Carry the returned state into the next update

Run the receipt counter twice, starting at count 2 and delivering 5 each time. The first call returns new state 7 and receipt 2. The second call starts from **7**, so it returns state 12 and receipt 7. Feeding 2 to both calls would model two separate deliveries to a reset counter. Keeping the receipt as the next state would also be wrong: the receipt reports the old value.

This distinction is useful when one tick works but a later tick fails. Compare the first differing row, then check which returned component became the next input. You cannot diagnose the cause by looking only at the final number.

## Choose an observation that distinguishes the explanations

Suppose you had not been told whether this receipt function returns the old or new count. With delivery zero, both explanations return the same number. Agreement there leaves the ambiguity intact. Starting at count 9 and delivering 2 predicts receipt 9 under the old-count explanation and 11 under the new-count explanation. Observing the receipt now separates them; inspecting the final count alone does not, because both explanations update it to 11.

Before probing an unfamiliar program, write down both predictions. Name the output field on which they disagree. This gives a matching result a purpose and gives a mismatch somewhere to lead.

## Apply the method to the original cart project

Open [Milestone 1: explain one tick](../m01/START-HERE.md). Follow its original order: setup, marker trace, saved first prediction, native probes, instruction trace, model and the two transfer investigations. The receipt example has supplied its own rule; it supplies no cart rule.

For your cart instruction trace, keep a row for the instruction, the values it reads, the destination and what that value supports. Label an address P or Q until you have evidence for what is stored there. When an arithmetic destination overwrites a register, cross out its old value. When a store occurs, update the memory state. When a branch is taken, follow the instruction address selected by the actual comparison; do not keep tracing the untaken path as if it also ran.

If Python reports a syntax error, use the named line and `python3 -m py_compile model.py` to check the file before comparing behavior. If the native program cannot execute, use [setup](../m01/setup.md) and the [follow-along troubleshooting](../m01/follow-along.md); a platform or working-directory failure is not a counterexample to your rule. If output runs but disagrees with your model, preserve it, find the first different value in the trace, and only then revise the model. A checker result cannot identify which instruction you misunderstood.

Your carried artifact is your own `model.py` together with saved predictions, native observations and the instruction evidence that explains it. Keep `transfer_model.py` and `crossing_model.py` as separate revisions for the related targets, following the project's save-before-feedback procedure. M2 uses this same retained evidence and dataflow habit to connect memory bytes to a function call; the models remain your record of what was learned about these particular targets.
