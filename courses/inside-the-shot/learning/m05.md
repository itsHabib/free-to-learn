# M5 preparation — follow bytes across boundaries

M5 asks you to explain a real exchange between two supplied local processes and build an incremental decoder. The useful result is a timeline that separates bytes arriving from messages becoming complete. Bring Python loops, lists, bytes and object state, plus M4's habit of labeling a number's unit and origin. A **process** is a running program with its own memory; a **pipe** carries ordered bytes from a writer to a reader.

This preparation uses a separate display protocol. Its examples and checks are scratch practice, not additional project deliverables. The original printer completion, baseline exchange and changed-request exercise still require their own saved predictions. Do not inspect the project's implementation scripts or run its exchange before the saves required by [M5 START-HERE](../m05/START-HERE.md).

## Four boundaries that answer different questions

A writer may intend to send a complete frame, but the pipe does not preserve that intention as a message boundary. An OS `read` asks for up to some number of bytes; a positive result may be shorter than requested. The receiving application can accumulate several reads before passing a chosen group to a decoder. The decoder then finds frames according to the wire format.

| Boundary | What it establishes | What it does not establish |
| --- | --- | --- |
| Write intent / write-loop return | Bytes the sender intends to send / completion of its write loop | One OS call or the peer's receive time |
| Positive OS read result | Bytes returned by that particular read | A complete frame or a repeatable future read size |
| Application delivery | Bytes the application groups for one decoder call | The original write or OS read boundaries |
| Decoded frame | A complete header and body meeting the protocol rules | That the next delivery or the whole stream has ended |

The project's prescribed application delivery sizes make decoder inputs reproducible. They do not control OS packetization; pipes are byte streams, and these delivery groups are not packets. A saved cumulative trace is fixed data about one recorded run. Its read intervals should be reported as observations from that run, not promises about the next run.

For practice, consider this invented capture of a nine-byte stream. These intervals are supplied example data, not measurements from your machine. An interval `[a,b)` includes a and excludes b.

| Layer | Successive byte intervals in this one capture |
| --- | --- |
| Sender's write intents | `[0,3)`, `[3,9)` |
| Receiver's actual read results | `[0,2)`, `[2,3)`, `[3,9)` |
| Application's decoder deliveries | `[0,1)`, `[1,4)`, `[4,9)` |

The first write's three bytes reached the application through two read results. The second decoder delivery includes bytes from both write intents: offsets 1 and 2 from the first, offset 3 from the second. It need not be one of the three OS reads. All three rows cover `[0,9)` in order without losing bytes; their boundaries answer different questions.

## Work a complete framed stream

The display protocol has a one-byte unsigned length from 1..3, followed by that many printable ASCII bytes. One byte `02` means length 2; the hex pairs `4f 4b` spell `OK`. There is no separator or implied newline. This is deliberately different from the original project's two-byte header.

The stream below contains three frames. Offsets are positions in this direction of the stream, not times.

```text
bytes:    02 4f 4b | 01 3f | 03 52 55 4e
payload:     OK   |   ?   |    RUN
interval: [0,3)   | [3,5) | [5,9)
```

Use the invented capture's application deliveries: one byte, then three, then five. A **pending buffer** retains the incomplete suffix between decoder calls.

| Delivery | Bytes added | Reasoning | Returned messages | Pending bytes |
| --- | --- | --- | --- | --- |
| `[0,1)` | `02` | Length is known, but neither body byte is present. | none | `02` |
| `[1,4)` | `4f 4b 01` | Finish the first frame and remove exactly three bytes. The next header remains. | `OK` | `01` |
| `[4,9)` | `3f 03 52 55 4e` | Finish `?`, remove its two bytes, then finish `RUN` and remove its four bytes. | `?`, `RUN` | empty |

The middle delivery finishes an old frame and begins another. The last finishes two frames, so a decoder must loop rather than check for only one message per call. At each step, pending bytes plus newly added bytes are the unconsumed suffix; removing anything beyond the complete frame would lose the next header. Keeping an already consumed prefix would emit the same message again.

The framing calculation is separate from character decoding. First find a complete body using byte counts; only then validate its allowed byte values and decode ASCII. Three body bytes are six displayed hex characters. Counting the spaces or hex digits would produce a different, incorrect size.

Complete the same stream under a new delivery grouping before checking the explanation.

With a wider header there is an earlier waiting stage. In a two-byte big-endian variant, `00 03` means `0*256+3=3`. Receiving only `00` has not declared zero: the header is incomplete, and its missing second byte could change the length. Wait for the whole header before interpreting or bounding its value, then separately wait for the body. These are two different reasons to retain pending bytes.

## Waiting, refusal and EOF are distinct

A correct incremental decoder needs enough memory to distinguish “not enough bytes yet” from “these bytes cannot form an allowed frame.” In the toy display protocol, pending `02 41` promises two body bytes but has only `A`: wait for another delivery. Pending `04` already declares a forbidden length: reject immediately instead of waiting for four bytes. A complete body with a disallowed character is invalid when that body is available for validation.

EOF means no later bytes will arrive. On the project's blocking pipe, a zero-byte OS read signals EOF after the sending side has closed and buffered bytes are exhausted. A decoder's `feed(b"")` is an API call with no new bytes; it does not announce EOF. The project uses a separate `finish()` call to do that. If bytes are still pending at `finish()`, the stream is truncated, even if its earlier frames were valid. If nothing is pending, EOF is clean. Closing the request pipe and closing the response pipe are also separate events: label the direction.

For example, feed toy bytes `01 41 02 42`. The decoder returns `A` and retains `02 42`. An empty feed changes neither the buffer nor the open lifecycle. A subsequent `43` would complete `BC`. Calling `finish()` before that byte arrives must refuse the incomplete suffix. Calling it after that byte arrives can close successfully.

The original project's lifecycle contract adds another distinction: failed, open and successfully closed decoders allow different calls. Read those exact rules when implementing. Do not use one boolean “buffer empty” as a substitute for lifecycle state; an empty open decoder can accept more bytes, whereas a closed one cannot. A raised `feed` returns no list from that call, even if its internal loop had encountered a complete frame first; events already returned by earlier successful calls remain earlier events.

## Explain order without inventing timings

Suppose a writer logs intent, enters its write loop, and later logs its return. The reader can receive bytes and log a read while the writer is waiting to run its return-logging statement. A sorted timestamp list may therefore place the read before the write return. That does not reverse the byte flow.

Use each process's sequence numbers for its local order and stream offsets for byte order. A monotonic timestamp difference is elapsed time between recorded observations on this host; it includes scheduling, buffering, Python work and logging. It does not isolate transport latency. Actual PIDs, read grouping and timing may differ between repeats even when prescribed decoder deliveries match. If a particular pair of runs has the same reads, report that observation without generalizing it into an OS guarantee.

## Enter the original exchange

Follow [M5 START-HERE](../m05/START-HERE.md) from its first save, then do its separate printer example in the stated order. The original wire contract has two big-endian length bytes, bounded printable ASCII bodies, and explicit failure/lifecycle rules. Use those rules rather than copying the toy display format. Compute the original baseline's frame intervals and messages per application delivery yourself, save successfully, then run the supervisor and inspect the saved trace.

If a live run fails, inspect the named child logs before interpreting a partial trace as a complete exchange. Keep a refused existing output folder and choose a new run path. If your decoder disagrees, first identify the layer: missing or changed trace bytes, incorrect pending-suffix arithmetic, premature ASCII decoding, header bounds, or EOF/lifecycle handling. A `finish()` failure with pending bytes is a different diagnosis from a refused length during `feed`.

Carry forward the existing project's own decoder, interval timeline, raw trace, saved first attempt, feedback and revisions. For each claim, cite the direction, interval and event that supplies its evidence. Preserve the changed-request prediction before the transfer run. These artifacts support a bounded explanation of how this exchange was decoded; neither repeatable deliveries nor a finite decoder check establishes universal correctness.
