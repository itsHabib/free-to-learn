## A complete unrelated correspondence example

A display computes `3*n + bonus`, where `n` is in 0..20 and `bonus` is 2 when `enabled` equals zero, otherwise 5. A negative `enabled` is nonzero. This tiny rule is supplied, so the task is to explain its representations rather than infer its rule.

Here are two **schematic** ARM64 fragments for that rule. They illustrate value flow; they are authored examples, not captured compiler listings or runnable project files. Inputs enter `w0=n`, `w1=enabled`, and the integer result leaves `w0`. `mul d,a,b` multiplies its two source values. `madd d,a,b,c` multiplies a and b and adds c. All example arithmetic fits in signed 32 bits, so overflow is not involved.

```text
Branch form                       Selected-value form
mov w8, #3                        mov w8, #2
mul w8, w0, w8                    mov w9, #5
cbz w1, off                       cmp w1, #0
add w8, w8, #5                    csel w8, w8, w9, eq
b done                            mov w9, #3
off: add w8, w8, #2                madd w0, w0, w9, w8
done: mov w0, w8                   ret
ret
```

`cbz` branches only when its tested register is zero. `cmp a,b` records flags from a-b. The **zero flag**, Z, is 1 when that result is zero. The condition `eq` tests Z=1; `ne` tests Z=0. `csel d,a,b,condition` writes a when the condition is true, otherwise b. It chooses a value without jumping to another instruction address. Source values are read before the destination is overwritten, even when the register names overlap.

For `n=4, enabled=-2`, the branch form calculates `3*4=12`. Its `cbz` is not taken because -2 is not zero. Adding 5 gives 17, which moves to the return register. The selected form first prepares candidate bonuses 2 and 5. Comparing -2 with zero gives Z=0, so `eq` is false and `csel` writes the second candidate, 5, into `w8`. It next overwrites `w9` with multiplier 3; the previously selected 5 remains in `w8`. `madd` reads old `w0=4`, `w9=3`, `w8=5`, then writes `w0=4*3+5=17`.

| Role | Branch form for this input | Selected-value form for this input |
| --- | --- | --- |
| Input n | Entry `w0=4` | Entry `w0=4`, retained until `madd` |
| Conditional fact | `cbz` sees -2 and falls through | `cmp` sets Z=0; `csel ... eq` chooses 5 |
| Running arithmetic | `w8=12`, then `w8=17` | Bonus `w8=5`, combined with multiplication in `madd` |
| Return value | Move 17 to `w0` | `madd` writes 17 directly to `w0` |

Matching `w8` to `w8` would equate 12 with 5 at the arithmetic stage. Match their roles and consumers instead. A destination register is reusable storage, not a permanent source variable. Likewise, the selected form still has conditional behavior despite having no conditional branch.

Complete another trace before checking it.

## Trace the flag producer separately from value producers

Flags are state too. A later conditional instruction reads the most recent flags, not the old value of its destination. Ordinary `mov`, `ldr`, `str` and `add` without the `s` suffix do not set arithmetic flags. `cmp`, `subs` and `adds` do. If a flag-setting instruction intervenes, the consumer uses those newer flags. On the original listings, write down the instruction address that produced the flags used at each `csel`, branch or conditional comparison.

For example, `cmp w1,#0; mov w9,#99; csel w8,w2,w3,eq` still selects using the comparison with zero. The move makes `w9=99` but does not replace Z. Do not read `eq` as “the two source registers are equal”; `csel` does not compare them. It consumes a condition already represented in flags.

Signed and unsigned conditions also answer different questions. `gt` means signed greater; `lo` means unsigned lower. A negative 32-bit value has a large unsigned interpretation. Use the specific condition and its flag producer; establish nonnegativity before replacing an unsigned comparison with a signed one in your model.

## Conditional comparison can combine questions

A **conditional comparison**, `ccmp`, either performs a comparison or supplies literal fallback flags. That lets later code test a combined condition without a separate branch for each question.

Consider another supplied toy question: “Is n greater than 3, and is flag nonzero?”

```text
cmp  w0, #3
ccmp w1, #0, #4, gt
cset w8, ne
```

`cset` writes 1 when its condition is true, otherwise 0. Here `ccmp` compares `w1` with zero only if the preceding flags say signed greater. Otherwise it sets NZCV to the fallback integer 4, binary `0100`: N=0, Z=1, C=0, V=0. N, Z, C and V are the negative, zero, carry and signed-overflow flags. The fallback therefore makes the final `ne` false.

With n=6, flag=0, the first comparison makes `gt` true, so the second comparison runs. Zero minus zero gives Z=1, and `cset ... ne` writes 0. With n=6, flag=-2, the second comparison instead gives Z=0 and the result is 1. With n not greater than 3, the second input is not compared at all: the fallback Z=1 forces result 0. Reading only the last comparison would lose the first question's gate.

## Choose probes that can separate explanations

Two equal outputs can hide unequal intermediate values. Suppose a separate indicator displays `min(raw,30)`. Candidate A computes `raw=4*n`; candidate B computes `raw=4*n+2`. At n=8, raw values are 32 and 34, but both displays are 30. This observation cannot tell you which raw rule ran. At n=5, displays are 20 and 22, so that input separates the candidates.

The **limit** is where an intermediate becomes capped; a **boundary probe** chooses an input around a suspected condition. A good probe has predictions that differ under the competing models. Pair one changed input with two otherwise identical inputs to isolate a condition, and inspect the listing when a final cap conceals earlier changes. Agreement in sampled outputs supports those cases; it does not establish source identity or prove a rule for every input.
