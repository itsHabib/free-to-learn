## Slots and candidates

Numbers in Lob's memory take 4 bytes each. A **slot** is 4 bytes at an address that is a multiple of 4, so slot `s` starts at address `4 * s`, and 131,072 bytes of memory hold 32,768 slots. The same 4 bytes can be read as a 32-bit float (`'f32'`) or as a signed 32-bit integer (`'i32'`), both little-endian, which means the lowest byte comes first. A 32-bit float holds numbers with a fraction, such as a wind of 3.6662, to about seven significant digits, so float arithmetic is rounded. An i32 holds whole numbers only, exactly.

JavaScript reads slots with **typed arrays**. `new Float32Array(bytes.buffer)` and `new Int32Array(bytes.buffer)` are two views of the same bytes, and element `s` of each view is slot `s`. `viewsOf(bytes)` returns both. The two views read the same bytes as very different numbers. The angle 45 stored as a float is the bytes `00 00 34 42`, which the f32 view reads as 45 and the i32 view reads as 1110704128. The integer 45 is the bytes `2D 00 00 00`.

The **candidates** are the slots that might hold a value, written `{ f32, i32 }`. Each half is a `Uint32Array` of slot numbers in increasing order, or `null` when that type isn't being searched. At the start every slot is a candidate in both views, so `allSlots(bytes)` gives 32,768 slot numbers and you begin with 65,536 candidates for the angle. `count(cands)` adds up both halves, and `list(cands)` turns them into `[{ type, slot, addr }]`, the f32 candidates first.

### Write the views and the candidates

A view needs the buffer under `bytes` and where `bytes` starts in it. A snapshot made with `slice()` starts at 0, but a `Uint8Array` can also be a window into a larger buffer, and `byteOffset` says where. A view counts whole slots only, so the length is the byte length divided by 4, rounded down. In `work/scan.mjs`, replace the `views-of` region:

```js {"file":"examples/scan-checkpoint-02.mjs","region":"views-of","title":"Two views of the same bytes","change":"Replace the views-of region of work/scan.mjs."}
export function viewsOf(bytes) {
  // Two views of one buffer: element s of each is slot s. No copy.
  const { buffer, byteOffset } = bytes;
  const n = Math.floor(bytes.byteLength / 4);
  return {
    f32: new Float32Array(buffer, byteOffset, n),
    i32: new Int32Array(buffer, byteOffset, n),
  };
}
```

## Filtering by change

A filter keeps the candidates that behaved the way the value should have. Here is `filterDelta` worked on eight slots read as integers, before and after a RIGHT press:

```
slot     0   1   2    3   4   5   6   7
before   0  45   7  120   0  60  45   3
after    0  46   7  122   0  60  46   3
```

Slots 1 and 6 rose by exactly 1, so `filterDelta(cands, before, after, 1)` keeps them. Slot 3 rose by 2, like a frame counter after two frames, and goes. Every other slot stayed the same and goes.

The filters' rules:

- `filterDelta(cands, before, after, delta)` keeps f32 slots whose value rose by `delta` within 0.001 (float arithmetic is rounded, so an exact test could miss a real rise), and i32 slots whose value rose by exactly `delta`.
- `filterUnchanged` keeps slots whose 32 bits are the same in both snapshots, and `filterChanged` keeps slots whose bits differ.
- A `null` half stays `null`.

You need both views because the game stores the angle as a float and the power as an integer, and a scan of one type misses the other. Each key press tests every value at once. An angle press should raise the angle by 1 and leave the power alone, so it narrows the angle with `filterDelta` and the power with `filterUnchanged`.

The unchanged and changed filters compare bits, never float values. In a fresh game, the slot that counts the frames since the last landing holds −1, because nothing has landed yet. The 32 bits of −1 are `FF FF FF FF`, which the f32 view reads as NaN, "not a number". NaN is never equal to anything, itself included, so a float compare reports that slot as changed when nothing touched it. Compare the slots as `Uint32Array` or `Int32Array` values instead.

### Write the three filters

All three filters walk one half of the candidates and keep the slots that pass a test. `keep` does that walk once for all of them. It fills a new array no longer than the half, then cuts it to the slots that passed, and it gives `null` back for a half that is `null`. `filterDelta` reads both snapshots through both views, so each half is tested in the type it stands for. Replace the `filter-delta` region:

<!-- code-example {"file":"examples/scan-checkpoint-02.mjs","region":"filter-delta","language":"js","title":"Keep the slots that rose by delta","change":"Replace the filter-delta region of work/scan.mjs."} -->
```js {"file":"examples/scan-checkpoint-02.mjs","region":"filter-delta","title":"Keep the slots that rose by delta","change":"Replace the filter-delta region of work/scan.mjs."}
// The slots of one half that pass test, as a new Uint32Array.
// A half that is null was not searched, and stays null.
function keep(slots, test) {
  if (!slots) return null;
  const out = new Uint32Array(slots.length);
  let n = 0;
  for (const slot of slots) if (test(slot)) out[n++] = slot;
  return out.slice(0, n);
}

export function filterDelta(cands, before, after, delta) {
  const b = viewsOf(before);
  const a = viewsOf(after);
  // Float arithmetic is rounded, so a float rise counts within 0.001.
  const roseF = (s) => Math.abs(a.f32[s] - b.f32[s] - delta) < 1e-3;
  const roseI = (s) => a.i32[s] - b.i32[s] === delta;
  return { f32: keep(cands.f32, roseF), i32: keep(cands.i32, roseI) };
}
```
<!-- /code-example -->

The other two filters read both halves through the i32 view, because an integer compare is a compare of the 32 bits, which is what the rule asks: the NaN slot's bits are equal to themselves as integers. Replace the `filter-unchanged` and `filter-changed` regions:

<!-- code-example {"file":"examples/scan-checkpoint-02.mjs","region":"filter-unchanged","language":"js","title":"Keep the slots whose bits stayed","change":"Replace the filter-unchanged region of work/scan.mjs."} -->
```js {"file":"examples/scan-checkpoint-02.mjs","region":"filter-unchanged","title":"Keep the slots whose bits stayed","change":"Replace the filter-unchanged region of work/scan.mjs."}
export function filterUnchanged(cands, before, after) {
  // Compare bits, never floats: as a float, NaN !== NaN.
  const b = viewsOf(before).i32;
  const a = viewsOf(after).i32;
  const same = (s) => a[s] === b[s];
  return { f32: keep(cands.f32, same), i32: keep(cands.i32, same) };
}
```

```js {"file":"examples/scan-checkpoint-02.mjs","region":"filter-changed","title":"Keep the slots whose bits changed","change":"Replace the filter-changed region of work/scan.mjs."}
export function filterChanged(cands, before, after) {
  const b = viewsOf(before).i32;
  const a = viewsOf(after).i32;
  const moved = (s) => a[s] !== b[s];
  return { f32: keep(cands.f32, moved), i32: keep(cands.i32, moved) };
}
```

## Which copy is real

Of the two candidates left, only one is the variable the game uses. The way to tell is to change each one and see whether the change lasts.

{{practice:p02b}}

{{gate:p02b}}

Write 53 into each candidate in turn, and one write holds. Written into the real angle, 53 is still there after two frames and the status line now reads `ANGLE 53`. Written into the copy, 53 lasts until the next frame, when the game rebuilds the copy from the real angle and it reads 46 again.

`writeTest(host, cands)` makes that test for each candidate in turn. The lessons call it the write-test.

1. Write the slot's value plus 7, or minus 7 when the value is 50 or more. The written value is the **probe**, and choosing it this way keeps it inside the game's limits, 5 to 85 for the angle and 10 to 100 for the power.
2. Tick 2 frames, so the game has had a chance to overwrite it.
3. Read the slot back. `held` is true when the probe is still there.
4. Restore the original value, then tick 2 frames again before the next candidate. Without that tick, a copy the game hasn't rebuilt yet still holds your probe, and the next test starts from the wrong value.

### Write the write-test

The listing is the four steps above. The probe is rounded to a whole number, so it is a value the angle or the power could really take, whichever type the slot is. `held` allows a difference of a millionth. A whole number comes back exactly from either type, so this is a margin, not something the game needs. The second `tick(2)` is the one the fourth step asks for. <!-- code-example {"file":"examples/find-checkpoint.mjs","region":"write-test","language":"js","title":"Write, wait, read back, restore","change":"Replace the write-test region of work/find.mjs."} -->
```js {"file":"examples/find-checkpoint.mjs","region":"write-test","title":"Write, wait, read back, restore","change":"Replace the write-test region of work/find.mjs."}
export function writeTest(host, cands) {
  const results = [];
  for (const { type, addr } of S.list(cands)) {
    const was = read(host, addr, type);
    // 7 up below 50 and 7 down from 50: inside 5 to 85 and 10 to 100.
    const probe = Math.round(was) + (was < 50 ? 7 : -7);
    host.write(addr, type, probe);
    host.tick(2); // time for the game to rebuild a copy
    const held = Math.abs(read(host, addr, type) - probe) < 1e-6;
    host.write(addr, type, was);
    host.tick(2); // and time to rebuild it from the restored value
    results.push({ type, addr, held });
  }
  return results;
}
```

```js {"file":"examples/find-checkpoint.mjs","region":"try-write","title":"Take the slot that held","change":"Replace the try-write region of work/find.mjs."}
// A write-test on one value. The f32 slot that held wins, else the
// first; when none held, the candidates were wrong: start again.
function tryWrite(host, s, name) {
  const held = writeTest(host, s[name]).filter((r) => r.held);
  const best = held.find((r) => r.type === 'f32') ?? held[0];
  if (best) s.found[name] = { addr: best.addr, type: best.type };
  else s[name] = { f32: s.all, i32: s.all };
}
```

## The wind and the flag

The wind and the flag can't be moved with a key, so they need other tests.

The status line shows the wind rounded to one decimal, as in `WIND +3.7`, so the exact wind is within 0.05 of the number shown. `scanNear(bytes, 3.7, tol)` returns the f32 slots within `tol` of 3.7. Use a tolerance slightly over 0.05, such as 0.051, so that a wind exactly halfway between two shown values still matches after float rounding. With seed 1 the exact wind is 3.6662, and the first scan finds one slot, at address 65848, 8 bytes past the angle. When a new round changes the wind, `filterNear(cands, bytes, value, tol)` keeps the candidates near the new number. Both look at f32 slots only, so `filterNear` returns `{ f32, i32: null }`.

The flag's position appears on screen and nowhere in text. `host.screen()` returns the current frame as `{ width: 960, height: 540, data }`, with four bytes of red, green, blue and alpha per pixel. The rows run from the top of the screen down, so the pixel in column `x` of row `y` starts at `data[(y * width + x) * 4]`. The flag's cloth is the only part with red above 190 and green and blue below 120. `findRed(screen)` returns `{ x, pixels }`, where `x` is the middle of the leftmost and rightmost columns that hold a cloth pixel, and `pixels` is how many cloth pixels it found. It returns `null` when no pixel is red. The cloth hangs from a pole at the flag's position and runs 20 pixels to the right, so its middle sits about 10.5 pixels right of the flag. Over the next four rounds with seed 1, the flag stood at 688.84, 726.86, 509.15 and 791.12, and the cloth's middle was at 699.5, 737.5, 519.5 and 801.5.

One pixel is one pace, so the flag's slot follows the pixel position on a straight line with slope 1. The **line test** collects each candidate's value and the pixel position over at least four new rounds and fits a line `y = slope × x + intercept` through those points with `lineFit(xs, ys)`, the pixel positions as `xs` and the candidate's values as `ys`.

The line is the **least-squares** line, the one with the smallest sum of squared gaps between each `y` and the line. Write `mx` for the average of the `xs` and `my` for the average of the `ys`. Then:

```
slope     = sum of (x - mx) * (y - my)  /  sum of (x - mx)^2
intercept = my - slope * mx
```

A point's **residual** is its gap from the line, `y − (slope × x + intercept)`. `lineFit` returns `{ slope, intercept, worst }`, where `worst` is the largest residual with its sign dropped, called the worst residual. The test keeps a candidate only when the slope is above 0.25 and below 4 and the worst residual is at most 1.5 paces. Here is the sum for the four seed 1 rounds above, with the cloth's middle as `x` and the flag's own slot as `y`. The averages are `mx` = 689.5 and `my` = 678.99. The four products `(x − mx) × (y − my)` add up to 43,827.62 and the four squares `(x − mx)²` to 43,848, so the slope is 43,827.62 / 43,848 = 0.99954, which prints as 1.00, and the intercept is 678.99 − 0.99954 × 689.5 = −10.19. The four residuals are −0.15, −0.11, 0.08 and 0.18, so the worst residual is 0.18.

Two points always lie on a line, so two rounds prove nothing, and each extra round is a fresh test that a wrong slot must also pass. So the flag counts as found only after four rounds of the test, even when one candidate is left sooner. The slope bound stops two kinds of wrong slot. A slot that hardly moves fits an almost flat line with tiny residuals. A copy of the flag kept in other units, such as a marker on a small map of the field drawn at one-eighth scale, moves in perfect step but fits a line with slope 1/8. Between rounds the flag's slot must change (`filterChanged`), and during key presses it must stay the same (`filterUnchanged`). A good place to start the flag's candidates is the f32 slots whose bits changed at the first new round and that hold a finite number between 0.001 and 100,000 in size.

On seed 1 that start, narrowed by four new rounds, leaves three candidates: the flag, the wind and the drifting cloud's position, which moves a little every frame. The figure draws each one's line through the same four rounds.

`lineFit` is the two formulas above, then one more pass for the worst residual. When every `x` is the same, the sum of squares is 0 and no slope can be worked out, so the listing gives a slope of 0, which the slope bound then turns down. Replace the `line-fit` region:

<!-- code-example {"file":"examples/scan-checkpoint-02.mjs","region":"line-fit","language":"js","title":"The least-squares line and its worst residual","change":"Replace the line-fit region of work/scan.mjs."} -->
```js {"file":"examples/scan-checkpoint-02.mjs","region":"line-fit","title":"The least-squares line and its worst residual","change":"Replace the line-fit region of work/scan.mjs."}
export function lineFit(xs, ys) {
  const n = xs.length;
  const mx = xs.reduce((sum, x) => sum + x, 0) / n;
  const my = ys.reduce((sum, y) => sum + y, 0) / n;
  let sxy = 0; // the sum of (x - mx) * (y - my)
  let sxx = 0; // the sum of (x - mx)^2
  for (let i = 0; i < n; i++) {
    sxy += (xs[i] - mx) * (ys[i] - my);
    sxx += (xs[i] - mx) ** 2;
  }
  const slope = sxx ? sxy / sxx : 0; // every x the same: no slope
  const intercept = my - slope * mx;
  let worst = 0; // the largest residual, its sign dropped
  for (let i = 0; i < n; i++) {
    const residual = ys[i] - (slope * xs[i] + intercept);
    worst = Math.max(worst, Math.abs(residual));
  }
  return { slope, intercept, worst };
}
```

## The wind and the flag in the search

The search runs the line test once per new round, keeping its state in the object `newSearch` made. `movedFloats` gives the starting candidates, by the rule above. `lineTest` narrows the flag's candidates to those that changed in the round, adds each one's new value to its history, and records the cloth's middle. A new `Map` replaces the old one each round, so a candidate that was filtered away takes its history with it. From the fourth round on it keeps only the candidates whose history fits a line by the test's bounds. Replace the `line-test` region:

<!-- code-example {"file":"examples/find-checkpoint.mjs","region":"line-test","language":"js","title":"The line test, one round at a time","change":"Replace the line-test region of work/find.mjs."} -->
```js {"file":"examples/find-checkpoint.mjs","region":"line-test","title":"The line test, one round at a time","change":"Replace the line-test region of work/find.mjs."}
// Where the flag's candidates start: f32 slots whose bits changed in
// the round and that hold a finite number between 0.001 and 100,000
// in size.
function movedFloats(before, after) {
  const all = { f32: S.allSlots(after), i32: null };
  const f = S.viewsOf(after).f32;
  const sized = (s) => Math.abs(f[s]) > 1e-3 && Math.abs(f[s]) < 1e5;
  const moved = S.filterChanged(all, before, after).f32;
  return moved.filter((s) => Number.isFinite(f[s]) && sized(s));
}

function lineTest(s, before, after, x) {
  s.flag = s.flag
    ? S.filterChanged(s.flag, before, after)
    : { f32: movedFloats(before, after), i32: null };
  const values = S.viewsOf(after).f32;
  const history = new Map();
  for (const slot of s.flag.f32) {
    history.set(slot, [...(s.history.get(slot) ?? []), values[slot]]);
  }
  s.history = history;
  s.pixels.push(x);
  if (s.pixels.length < 4) return; // two points always fit a line
  const onLine = (slot) => {
    const ys = history.get(slot);
    if (ys.length !== s.pixels.length) return false;
    const { slope, worst } = S.lineFit(s.pixels, ys);
    return slope > 0.25 && slope < 4 && worst <= 1.5;
  };
  s.flag = { f32: s.flag.f32.filter(onLine), i32: null };
}
```

## Experiments from a menu

`findValues` runs experiments one after another: a key press followed by filters, a write-test, or a new round. Something has to choose the next one, and that is a job for a menu. `experimentMenu(state)` writes it, and it offers only experiments that can narrow something:

- A press of an angle or power key, while that value has more than two candidates, has none, or hasn't been scanned. The up key and the down key are two options of their own, so a value in this state puts two presses on the menu.
- A write-test, once a value is down to one or two candidates.
- The new-round key, once the status line is found and while the wind or the flag isn't found.

It offers nothing else, and never more than 5 options. A menu that kept offering presses with two candidates left would let a picker press keys without end and learn nothing, because a press can't tell the real angle from its copy.

`state` is `{ angle, power, wind, flag, lineFound }`. `angle`, `power`, `wind` and `flag` are each a candidate count, `'found'`, or `null` for not scanned yet, and `lineFound` is true once the status line's address is known. A count of 0 means every candidate was filtered away. The menu treats it like `null`, and `findValues` starts that value again from every slot. Each option is `{ kind, target, label }`. For a press, `kind` is `'press'` and `target` is a control name: `'angle_up'`, `'angle_down'`, `'power_up'`, `'power_down'` or `'new_round'`. A down key lowers its value by 1, so the filter after it is `filterDelta` with −1. For a write-test, `kind` is `'write'` and `target` is `'angle'` or `'power'`. The label is the sentence a picker reads, such as `Press the angle up key: angle should go up by 1`.

`findValues(host, controls, { decide })` takes a function, `decide(text, labels)`, that returns the index of the option to run. `text` is one line describing the state, such as `angle: 2, power: 65524, wind: not scanned, flag: not scanned`, and `labels` are the options' labels. A picker can take time to answer, so `decide` may return a promise, and `findValues` is `async` and awaits it. When no `decide` is passed, `findValues` takes option 0 every time, and an index outside the menu also falls back to option 0. `findValues` must work on any seed. Each seed puts the game's state at a different address, 65840 with seed 1 and 65936 with seed 7, so search every time and never reuse an address from an earlier run.

`findValues` runs at most 30 experiments. If a value still isn't found then, it throws an error whose message contains `could not find` and names what is missing, the status line and the message included. On the plain game the search finishes in far fewer, and on a game that moves or scrambles its values the cap is what makes it stop.

### Write the menu

The listing walks the angle and then the power, so the options come in a fixed order: option 0 is the angle's first experiment while the angle isn't found, and the power's after that. A value with 0 candidates gets presses again, the same as one not scanned. The new-round key goes last. The `slice` at the end is the rule's cap of 5, which these rules never go past: two values with two presses each and the new-round key make 5 at most.
```js {"file":"examples/find-checkpoint.mjs","region":"experiment-menu","title":"Only experiments that can narrow something","change":"Replace the experiment-menu region of work/find.mjs."}
export function experimentMenu(state) {
  const options = [];
  for (const name of ['angle', 'power']) {
    const n = state[name];
    if (n === 'found') continue;
    if (n === null || n === 0 || n > 2) {
      // Either key narrows the value, so each is an option.
      for (const way of ['up', 'down']) {
        const target = `${name}_${way}`;
        const effect = `${name} should go ${way} by 1`;
        const label = `Press the ${name} ${way} key: ${effect}`;
        options.push({ kind: 'press', target, label });
      }
    } else {
      // One or two left: a press can't tell them apart.
      const label =
        `Write-test the ${n} ${name} candidates` +
        ' to see which one the game uses';
      options.push({ kind: 'write', target: name, label });
    }
  }
  const outside = state.wind !== 'found' || state.flag !== 'found';
  if (state.lineFound && outside) {
    const label = 'Press the new-round key: the wind and the flag move';
    options.push({ kind: 'press', target: 'new_round', label });
  }
  return options.slice(0, 5);
}
```

## One run, step by step

Here is what the walkthrough's `findValues`, which you write in this section, does on seed 1, taking option 0 every time. Yours can take the steps in another order. The figure gives the number of candidates left after each experiment.

{{figure:search-run}}

1. Press the angle-up key and tick 2 frames. The status line is the changed string on which `changedLabel` names `angle`, so its address is now known. With seed 1 it's the only string that changed. With seed 24 another string changes too and comes first, which is why the label decides and the order doesn't. `filterDelta` with +1 narrows the angle, and `filterUnchanged` the power.
2. Write-test the 2 angle candidates. One holds, and the angle is found.
3. Press the power-up key. `filterDelta` with +1 narrows the power to 2.
4. Write-test the 2 power candidates. The power is found.
5. Press the new-round key. The message is the changed string, other than the status line, that starts with a capital letter and has no lower-case letter, which gives its address. Read the wind the status line shows, and `scanNear` finds 1 slot, so the wind is found. For the flag, start from the f32 slots whose bits changed in this round and that hold a finite number of the size given above. Record each candidate's value beside the cloth's pixel position from `findRed`.
6. Press the new-round key a second and a third time. After each round, keep the flag candidates that changed and add their new values and the new pixel position to the record.
7. Press it a fourth time. The record now holds four points for each candidate, so the line test runs, and only the flag passes.

That is 8 experiments, 4 of them new rounds, and the same counts hold for seeds 7, 24 and 42. `findValues` returns both counts, as `experiments` and `rounds`. Every key press also runs `filterUnchanged` on the values it shouldn't move: an angle press on the power, a power press on the angle, both of them on any wind or flag candidates, and a press of the new-round key on the angle's and the power's candidates while those values aren't found. If a value's candidates ever fall to 0, start that value again from every slot.

### Write the search

`afterPress` is what the search does after any key press, the new-round key included. The status line is looked for only after an angle or power press, by the label rule from lesson 01, and the message only after a new round, by its capitals. Then each value that isn't found is narrowed: `filterDelta` for the key that should move it, `filterUnchanged` for every other key. The wind and the flag are filtered only after the angle and power keys, since a new round is meant to move them. Replace the `after-press` region:

<!-- code-example {"file":"examples/find-checkpoint.mjs","region":"after-press","language":"js","title":"What one key press tells the search","change":"Replace the after-press region of work/find.mjs."} -->
```js {"file":"examples/find-checkpoint.mjs","region":"after-press","title":"What one key press tells the search","change":"Replace the after-press region of work/find.mjs."}
// Narrow every value by what one key press should have done to it.
function afterPress(s, target, before, after) {
  const changed = S.changedStrings(before, after);
  const was = (t) => S.readCString(before, t.addr);
  const label = (t) => S.changedLabel(was(t), t.text);
  const round = target === 'new_round';
  if (!round && s.statusLine === null) {
    const keyed = (t) => ['angle', 'power'].includes(label(t));
    const line = changed.find(keyed);
    s.statusLine = line ? line.addr : null;
  }
  if (round && s.message === null) {
    const caps = (t) => /^[A-Z][^a-z]*$/.test(t.text);
    const msg = changed.find((t) => t.addr !== s.statusLine && caps(t));
    s.message = msg ? msg.addr : null;
  }
  for (const name of ['angle', 'power']) {
    if (s.found[name]) continue;
    const v = s[name];
    if (target === `${name}_up`) {
      s[name] = S.filterDelta(v, before, after, 1);
    } else if (target === `${name}_down`) {
      s[name] = S.filterDelta(v, before, after, -1);
    } else s[name] = S.filterUnchanged(v, before, after);
  }
  if (round) return;
  // No key moves the wind or the flag.
  for (const name of ['wind', 'flag']) {
    if (s[name] && !s.found[name]) {
      s[name] = S.filterUnchanged(s[name], before, after);
    }
  }
}
```

<!-- code-example {"file":"examples/find-checkpoint.mjs","region":"find-values","language":"js","title":"The search: menu, pick, experiment","change":"Replace the find-values region of work/find.mjs."} -->
```js {"file":"examples/find-checkpoint.mjs","region":"find-values","title":"The search: menu, pick, experiment","change":"Replace the find-values region of work/find.mjs."}
export async function findValues(host, controls, options = {}) {
  const decide = options.decide ?? (() => 0);
  const s = newSearch(S.snapshot(host.memory()));
  const names = ['angle', 'power', 'wind', 'flag'];
  while (s.experiments < BUDGET && !names.every((n) => s.found[n])) {
    const state = stateOf(s);
    const menu = experimentMenu(state);
    if (!menu.length) break;
    const labels = menu.map((o) => o.label);
    let pick = await decide(describe(state), labels);
    // An answer that is not an index on the menu counts as option 0.
    const onMenu = pick >= 0 && pick < labels.length;
    if (!(Number.isInteger(pick) && onMenu)) pick = 0;
    const { kind, target } = menu[pick];
    s.experiments++;
    if (kind === 'write') tryWrite(host, s, target);
    else {
      const before = S.snapshot(host.memory());
      host.press(controls[target]);
      host.tick(2);
      const after = S.snapshot(host.memory());
      afterPress(s, target, before, after);
      if (target === 'new_round') afterRound(host, s, before, after);
    }
    settle(s);
  }
  const missing = names.filter((n) => !s.found[n]);
  if (s.statusLine === null) missing.push('status line');
  if (s.message === null) missing.push('message');
  if (missing.length) {
    throw new Error(`could not find ${missing.join(', ')}`);
  }
  const { found, statusLine, message, rounds, experiments } = s;
  return { ...found, statusLine, message, rounds, experiments };
}
```

## Asking the picker

`findValues` takes its `decide` as a plain function and doesn't know who answers. The engine's side is `choose(env, what, text, options)`, the one place where your engine asks the picker anything. Every later menu in the course goes through it: which repair to try for a broken kit in module 03 and module 06, and whether to fire now in module 07.

`choose` returns the index of one option, and it always returns one:

- `options` is a list of strings, or of objects that each have a `label`. `text` is the line that describes the state, and `what` is a few words for the log, such as `'the next experiment'`.
- With one option, or none, there is nothing to decide. `choose` returns 0 and makes no call.
- Otherwise it calls `await env.models.decide(text, labels, options)`, which returns `{ choice, ms, model }`. The labels are what a decision model reads. The options go along as a third argument for the pickers that aren't models, such as your heuristic, which reads them in module 06.
- It returns `choice` only when `choice` is a whole number from 0 to `options.length - 1`. For any other answer it returns 0: an index past the end of the menu, a number with a fraction, the text `"1"`, or nothing at all.
- When the call throws, because the decision model isn't running, it returns 0.
- It logs a line with `rung` set to `'decision'` and the step `pick ` followed by `what`, saying the label that was picked or why option 0 was taken.

### Write choose

The listing follows the rules in order. `answer?.choice` reads nothing from an answer that is missing, so a picker that returns nothing ends up at option 0 like any other answer that isn't on the menu. One error is passed on rather than turned into option 0: `OutOfBudget`, defined in the given top of `engine.mjs`, which module 03 uses to stop a level whose budget is spent. A spent budget has to stop the level, and must not be mistaken for a missing picker. `say` is lesson 01's given helper for the log. In `work/engine.mjs`, replace the `choose` region:

<!-- code-example {"file":"examples/engine-checkpoint-02.mjs","region":"choose","language":"js","title":"The one place the engine asks the picker","change":"Replace the choose region of work/engine.mjs."} -->
```js {"file":"examples/engine-checkpoint-02.mjs","region":"choose","title":"The one place the engine asks the picker","change":"Replace the choose region of work/engine.mjs."}
export async function choose(env, what, text, options) {
  if (options.length <= 1) return 0; // nothing to decide: no call
  const labelOf = (o) => (typeof o === 'string' ? o : o.label);
  const labels = options.map(labelOf);
  const step = `pick ${what}`;
  try {
    const answer = await env.models.decide(text, labels, options);
    const choice = answer?.choice;
    const onMenu = choice >= 0 && choice < labels.length;
    if (Number.isInteger(choice) && onMenu) {
      say(env, 'decision', step, labels[choice]);
      return choice;
    }
    const shown = JSON.stringify(choice);
    const why = `answered ${shown}, which is not on the menu`;
    say(env, 'decision', step, `${why}; taking option 0`);
  } catch (error) {
    if (error instanceof OutOfBudget) throw error; // the level is over
    const why = `unavailable (${error.message})`;
    say(env, 'decision', step, `${why}; taking option 0`);
  }
  return 0;
}
```

## When a pick can matter

The menu offers only experiments that narrow something, so whatever is picked, the search makes progress. The open question is what a pick changes.
