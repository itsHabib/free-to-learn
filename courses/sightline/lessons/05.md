# 05 · Lift the code

Level 2, Bullseye, is level 1's game with a target of 3 paces, and 9 of its 10 shots must land that close. By the end of this module your `lift.mjs` will turn the game's key handler and frame function into expressions. Your `flight.mjs` will find in them the code that launches a shell and the code that flies it, and build from those a simulator that works out where any shot lands, to the bit and to the frame. Your engine will fire three shots to test that simulator before it aims with it.

## Why no model writes the physics

{{practice:p05a}}

{{gate:p05a}}

Your kit arrives from level 1 with a fit. On 20 seeds of the plain game, the fit module 03 builds landed all 200 of its shots within 12 paces but only 91 within 3, between 1 and 7 in each ten, and on level 2 the fit that level 1 left landed 6 of its 10 within 3 (module 03, "Judging the fit"). Level 2 needs nine. A tighter judge wouldn't make the fit better, because its five terms are a guess at the form of the motion, made from a few landings, and the game's code holds the motion itself. A fit with more terms can do better. In the course's tests a six-term fit, whose sixth term is the wind times the power, landed between 5 and 10 of each ten shots within 3 paces on the same 20 seeds, so it would sometimes pass level 2. We keep five terms so that level 2 needs the code.

The first version of this course had a model read that code. A large hosted language model was handed the listings of the key handler and the frame function, wrote the physics as code, and the engine tested it with shots. On one game it needed a number that the game sets once at start-up, in a function the model was never handed, so it assumed one. Its code said so in a comment: "Its value is not shown in the disassembly, so this default is assumed." Every landing it predicted was off by the same distance. Then a trial asked a local model, `qwen2.5:7b`, to write the fit, the physics and the state reader inside the same loop. It made 12 tries and none was accepted: code that wouldn't load, functions JavaScript doesn't have, landings off by thousands of paces.

From here on no model writes code. You write **passes**, analyses that read the decoded code and work out what it does, the way the game would run it. Where the code doesn't say what a number is, a pass leaves it unknown instead of guessing, and the engine reads it from the game's memory when it needs it, as the game itself does.

## Following the stack with expressions

To run code you follow its stack with numbers. To read it, follow the stack instead with **expressions**, objects that say how a value is computed. `i32.const 0` pushes the constant 0. `i32.load offset=78112` takes that constant as an address and pushes a load, the 4 bytes at 0 + 78112, whatever they hold when the code runs. `i32.xor` takes two expressions and pushes the XOR of them. A local keeps whatever expression it was given, and nothing is computed, so every value becomes a recipe in terms of the function's parameter, constants, the results of calls, and memory as it was when the function began. Following a whole function this way is called **lifting** it.

Here is the start of `game_key`, the key handler. The page calls it once for each key press, with the key's code as its one parameter, `param0`. Beside each instruction is the expression it pushes or keeps:

```
i32.const 0            0
i32.load offset=78112  i[0x13120]
local.tee 1            local 1 = i[0x13120]
i32.load offset=36     i*0x13120+36
local.set 2            local 2 = i*0x13120+36
```

`i[0x13120]` is the i32 at the fixed address 0x13120. `i*0x13120+36` is the i32 36 bytes past the address held at 0x13120, a field of the game's state. A **struct** is a group of values kept side by side in memory and reached through one address, its base. A **field** is one of them, named by its offset from the base, such as +36, and a word that holds an address, as the word at 0x13120 does, is a **pointer**. The field at +36 holds 1 while a shell is in the air and 0 otherwise, and the lessons call it the **flying flag**. A few instructions later the handler loads two more fields, writing `k` for `i*0x13120+92` and `a` for `i*0x13120`, field +0:

```
local.get 1            i[0x13120]
i32.load offset=92     k
local.tee 2            local 2 = k
local.get 1            i[0x13120]
i32.load               a
i32.xor                (k ^ a)
f32.reinterpret_i32    asfloat((k ^ a))
local.set 4            local 4 = asfloat((k ^ a))
```

When the left key is pressed (code 1), the handler takes 1 off the angle and stores it back:

```
local.get 1            i[0x13120], the address
local.get 2            k
local.get 4            asfloat((k ^ a))
f32.const -1           -1
f32.add                (asfloat((k ^ a)) + -1)
i32.reinterpret_f32    asbits((asfloat((k ^ a)) + -1))
i32.xor                (k ^ asbits((asfloat((k ^ a)) + -1)))
i32.store              store to field +0 of the struct at i[0x13120]
```

A store takes the value off the stack, then the address, and pushes nothing. `lift` records it as `{ addr, offset, type, value, guard, at }`: the address expression, the instruction's offset, its name, the expression written, the conditions under which it runs (the next sections), and `at`, the index of the store's instruction in `decode(mod, index)`, 47 for this one. In words, the angle is kept XORed with the word at +92, and this store decodes it, takes 1 off, encodes it the same way and puts it back.

{{figure:lifted-store}}

Each kind of instruction does one thing to the expression stack:

- A constant pushes `{ op: 'const', type, value }`, with type `i32`, `i64`, `f32` or `f64`. A local not yet set is the constant 0, which is what WebAssembly starts it at, and parameter n is `{ op: 'param', index: n }`.
- `local.get`, `local.set` and `local.tee` move expressions between the stack and the locals. `global.get` pushes `{ op: 'global', index }`, and `global.set` and `drop` take one off.
- A load takes its address and pushes `{ op: 'load', type, addr, offset }`, with the instruction's name as `type`, such as `'f32.load'`.
- An arithmetic, comparison or conversion instruction takes one or two expressions and pushes `{ op, args }` with the instruction's name as `op`. `UNARY` in `opcodes.mjs` lists the opcodes that take one, and the saturating conversions take one too. Fold an `i32.add` of two constants into one constant, and an add of the constant 0 into its other part, as the course's lifter does.
- `select` takes three, the condition on top, and pushes `{ op: 'select', args }`.
- `call` takes one argument for each parameter of the function it calls, the first parameter deepest, and makes `{ op: 'call', name, args }` with the name `funcName` gives. It records `{ call, guard }` in `calls`, and pushes the call when the function has a result. `return` records `{ guard, value }` in `returns`, and so does the function's own last `end` when the function has a result, because what's left on the stack there is what it returns, which is how a getter such as `r_angle` gives its value.

`show(e)` in `lift.mjs` (given) prints an expression the way these listings do, and `showStore(st)` prints a store.

## One object per expression

`make(e)` in `lift.mjs` (given) returns the one object for an expression. The first time it sees an expression it keeps it, and after that it returns the kept object for any equal expression. Two expressions are equal when they have the same `op`, the same type, value, offset or name, and the same parts, which must already be made objects. So build every expression with `make`, parts first. `constant(type, value)` and `UNKNOWN` (both given) are made the same way.

That's what lets the passes compare expressions with `===` and use them as `Map` keys. In `game_key` the launch, which runs when the fire key is pressed, loads the pointer at 0x13120 again, into local 0:

```
i32.const 0
i32.load offset=78112
local.tee 0
i32.const 0
i32.store offset=88
```

The second load of 0x13120 is the same expression as the first, so `make` returns the same object, and every store the launch makes through local 0 lands on the same places as the stores made through local 1. A **place** is an address expression and an offset, and `placeKey(addr, offset)` (given) names one in a `Map` by the address object's id and the offset. Without `make`, field +4 would be two places, one under each load of the pointer, and the passes later in this module, such as `xrefs`, which lists every place the functions touch, couldn't see that the launch reads what the earlier stores wrote.

`make` also puts the two parts of an operation whose order doesn't matter (an add, a multiply, an i32 XOR, AND or OR, or an i32 test for equal or not equal) in one order, by id, so `(a + b)` and `(b + a)` are one object. Ids follow the order expressions were made in, so your printouts may show the two sides of `+`, `*` or `^` the other way round from this lesson's.

## Places

A load's address is itself an expression, and three kinds of place matter:

- A fixed address. `i[0x13120]` is the i32 at 0x13120, a constant address. The letter in front says how the access reads: `i` for an i32, `f` for an f32, `b` for a byte.
- A field of a struct reached through a pointer. Module 02's search found the game's state at an address that changes with the seed. The code finds it the same way every time, because the word at 0x13120 holds the state's address, and `i*0x13120+36` is the i32 36 bytes past it. An offset of 0 isn't printed, so `i*0x13120` is field +0, where the angle is kept.
- A pointer chain. A field can hold the address of another struct, and then a place goes through two pointers. `i*0x2000+4+16`, in a made-up game, is the i32 at field +16 of the struct whose address is in field +4 of the struct whose address is at 0x2000. Every `+N` but the last is a field that holds an address.

{{figure:pointer-struct}}

In this notation the figure's rows are the places `*0x13120` (the angle), `*0x13120+4` (the power), `*0x13120+8` (the wind) and `*0x13120+16` (the flag the shells aim at). The flying flag, `*0x13120+36`, is one of the fields that follow.

With seed 1 the word at 0x13120 holds 65840, so `i*0x13120+36`, the flying flag, is the word at 65876. With another seed the address changes and the place doesn't, because the place says how the code finds the word, whatever the seed. `place(addr, offset)` (given) prints a place this way.

## Stores and their guards

A store runs only on the paths that reach it. Its **guard** is the list of branch conditions that must all hold for it to run, each written `{ cond, holds }`: a condition expression, and whether it must hold (be non-zero) or fail (be 0). Two instructions add conditions:

- `br_if N` takes a condition and leaves the block N levels out when the condition holds. The path that leaves gets `{ cond, holds: true }`. The code after the `br_if` runs on the other path, which gets `{ cond, holds: false }`.
- `if` takes a condition. Its first branch gets `{ cond, holds: true }` and its `else` branch `{ cond, holds: false }`.

The store that takes 1 off the angle sits behind these instructions:

```
block
  local.get 0
  i32.const 1
  i32.ne
  br_if 0          leaves the block when param0 != 1
  local.get 4
  f32.const 5
  f32.gt
  i32.eqz
  br_if 0          leaves the block when not (angle > 5)
  ...the store...
```

So its guard ends with `not (param0 != 1)` and `(asfloat((k ^ a)) > 5)`, meaning the key code is 1 and the angle is above 5. `showStore` prints a condition that must fail as `not` and the condition, and a condition that is itself `not x` (an `i32.eqz`) and must fail as plain `x`. `node lab.mjs lift game_key ./work` prints the whole guard after `when`. Here it is, with `k` and `a` written for the two loads:

```
i*0x13120 = (k ^ asbits((asfloat((k ^ a)) + -1)))   when
  ((param0 != 6)) and not i*0x13120+36 and not (param0 != 1)
  and (asfloat((k ^ a)) > 5)
```

`not i*0x13120+36` comes from an earlier `local.get 2` and `br_if 0`, because the handler changes nothing while the flying flag is set. The first condition, `((param0 != 6))`, comes from the rule in Code after an early exit.

When both ways out of a `br_if` meet at the same `end`, the conditions cancel. The code after that `end` runs either way, and its guard is the guard the block opened with. `lift` keeps a record for each open block: the stack's height, the guard and the locals when it opened, and the paths that left for its end. Code after a `br` or a `return` runs on no path until the block ends, so skip it.

Lob's `game_key` lifts to 13 stores: four that step the angle and the power, and nine that launch a shell.

## Phis

A local can be set differently on different paths. Where the paths meet, at a block's `end`, the local holds a **phi**, an expression whose value depends on the path taken. A phi is a list of `{ when, value }`, each `when` a list of conditions like a guard, tried in order, and `show` prints it as `(when: value; when: value)`. Where every arriving path brings the same expression, there is no phi, only that expression. A block whose type says it leaves a value merges that value the same way.

In the moving-flag build, met in module 07, the flag slides along the ground and turns round at the ends of its range, 420 and 900. Here is how `game_tick`, the frame function the page calls 60 times a second, does it, with `x` for the flag's next position:

```
f32.const 420
local.set 3
block
  block
    (x is worked out, kept in local 6 and left on the stack)
    f32.const 420
    f32.lt
    br_if 0          leaves the inner block when x < 420
    f32.const 900
    local.set 3
    local.get 6
    f32.const 900
    f32.gt
    i32.eqz
    br_if 1          leaves the outer block when not (x > 900)
  end
  (a store: +96 = neg(+96), the flag's speed turned round)
  local.get 3
  local.set 6
end
(a store: +16 = the flag's new position, from local 6)
```

At the inner block's end two paths arrive: the one that left by `br_if 0` with local 3 still 420, and the one that fell through with local 3 set to 900. So after that end local 3 is

```
((x < 420): 420; not (x < 420) and (x > 900): 900)
```

At the outer block's end, the path that left by `br_if 1`, with local 6 still x, meets the paths that came through the inner block, with local 6 set from local 3. So the position stored at +16 is a phi too: x when it's between 420 and 900, 420 below and 900 above.

`select` is different. It's one instruction that picks one of two values by a condition, with no paths, and it lifts to a `select` expression.

## Code after an early exit

{{practice:p05b}}

{{gate:p05b}}

The store that turns the flag's speed round sits after the inner block's end, and three paths start at the top of the bounce. The one with x below 420 leaves the inner block by `br_if 0` and arrives at its end. The one with x above 900 falls through and arrives too. The one with x between 420 and 900 leaves by `br_if 1` for the outer block's end and never reaches the store. So the store runs when one of the arriving paths' conditions holds, and only then. `+84` holds the build's mode, a number whose bits say which defences are on, and the bit worth 8 marks the moving-flag build:

```
f*0x13120+96 = neg(f*0x13120+96)   when (i*0x13120+84 & 8)
  and ((x < 420) or not (x < 420) and (x > 900))
```

{{figure:early-exit}}

The rule: when a path left a block early, for a block further out, the code after the block's `end` runs only when one of the arriving paths' conditions holds. `br` and `br_if` leave every block inside the one they name, and `return`, `br_table` and `unreachable` leave every block around them. All but `br_if` end the path. The lifter adds one condition to the guard after the end, a phi that is 1 on each arriving path and 0 otherwise, which must hold. `show` prints such a phi as the arriving paths' conditions joined by `or`. When no path left early, every path arrives, and the guard after the end is the one the block opened with.

The first condition of every guard in `game_key` comes from the same rule. The handler's first block deals with key code 6, a new round, and every path through it with code 6 returns or leaves for the outer block. The only path that arrives at its end is the one where `param0 != 6`, so everything after it runs under `((param0 != 6))`.

Give the speed's store the guard its block opened with instead, `(i*0x13120+84 & 8)`, and in the moving-flag build the store runs in every frame. The flag's speed changes sign every frame, and a prediction built from these stores has the flag jump back and forth between two places while the game's flag slides and bounces. Module 07 builds the flag's motion from these stores.

## A load after a store

A function can store to a place and load it again later, and the game reads back what it wrote, so the lifter must too. A load sees the last store to the same place made earlier in the function, which is called **forwarding**:

- If that store's guard is the start of the current guard, the store ran on this path, and the load is the stored expression.
- If the store's guard has conditions the current path doesn't, the store may not have run, and the load is a phi, giving the stored expression when the store's extra conditions hold and otherwise what the load would have seen without it.

The launch loads the power again after the two stores that step it, which run on other paths, for key codes 3 and 4. So the power in the launch is a phi. Here it is, writing `p` for the power as the game sees it, `(i*0x13120+4 ^ k)`:

```
(k ^ (not (param0 != 4) and not (p < 11): (k ^ (p + -1));
      otherwise: (not (param0 != 3) and not (p > 99):
          (k ^ (1 + p)); otherwise: i*0x13120+4)))
```

On the launch's path `param0` is 5, so neither stepping store's conditions hold, and the phi gives the word in memory, `i*0x13120+4`. The lifter doesn't work out that the stepping stores' paths returned, because the phi's conditions carry that. Evaluate the same phi with `param0` given as 3 instead, with the power below 100, and it gives the stepped word, the power plus 1.

Only 4-byte loads and stores, `i32.load`, `f32.load`, `i32.store` and `f32.store`, forward, and only between the same address object and offset. A store whose address is computed, neither a constant nor a load, is taken not to touch any other place. An f32 stored and loaded back as an i32, or the other way round, goes through a reinterpret, `asbits` or `asfloat`.

{{practice:r05-forward}}

## Loops

`lift` doesn't follow a `loop`. Following one would mean knowing how many times it runs, and that depends on values the function computes as it goes. When it meets a `loop` it skips to the loop's `end`. Every local set inside the loop is `UNKNOWN` after it, and every store inside is kept with `inLoop: true`, an unknown address and an unknown value. A loop whose type says it leaves a value leaves `UNKNOWN`. The passes skip stores inside loops.

In `game_tick` the stores inside loops write the message's letters and digits, one byte at a time, and none of them is part of a shot. `node lab.mjs lift game_tick ./work` ends `26 stores lifted from game_tick, and 7 inside loops left as unknown.` `slice`, one of the passes later in this module (Slices), collects the stores that decide some places.

## What the compiler did to gravity

{{practice:p05c}}

{{gate:p05c}}

The game's code holds gravity as numbers per frame. Here are two of `game_tick`'s stores and the moment of landing, with the places renamed: `py` for the shell's height, `f*0x13120+44`, `vy` for its upward speed, `+52`, and `t` for the part of a frame at which the height reaches 0:

```
vy = (vy + -5.00000048)
py = (((0.0166666675 * vy) + py) + -0.0416666716)
t  = ((neg(vy) - sqrt(((vy * vy) + (py * 600)))) / -300)
```

Lob's gravity is 300 paces per second squared and a frame lasts 1/60 of a second. The compiler multiplied out what it could:

- −5.00000048 is −300 × 1/60, the upward speed gravity takes away in one frame. 1/60 as a 4-byte float is 0.0166666675, a little more than 1/60, and the product rounded to the nearest 4-byte float is −5.00000048.
- −0.0416666716 is ½ × (−300) × (1/60)², the height gravity takes away in one frame.
- 600 and −300 are 2 × 300 and −300 in the formula for `t`.

Gravity's 300 never appears on its own. It's −300 in the divisor, and it's multiplied into −5.00000048, −0.0416666716 and 600. Someone writing the physics down by hand has to divide the frame time back out of each constant, and taking the 5 for gravity would make the shell fall sixty times too slowly. Lifting has no such step. Your simulator adds −5.00000048 to the upward speed once a frame because the lifted store says so, rounded as the game rounds it, and it never needs to know that gravity is 300.

## The game's arithmetic

`evaluate(e, env)` works out the value of an expression, or `null` where it can't be known. To give the game's own answers it must do the game's arithmetic, which isn't JavaScript's:

- **f32.** A 4-byte float operation rounds its result to the nearest 4-byte float, every time, and `Math.fround` does that rounding. In f32, 0.1 + 0.2 is 0.300000012, where JavaScript's numbers give 0.30000000000000004. The game rounds after every operation, so the evaluator must too, or its landings stop being the game's, bit for bit.
- **i32.** Integers are 32 bits and wrap: `i32.add` of 2147483647 and 1 is −2147483648, which `(a + b) | 0` gives. `i32.mul` needs `Math.imul`, because a product can need more bits than a JavaScript number holds exactly.
- **Unsigned.** The `_u` comparisons and `i32.shr_u` read the 32 bits as a number from 0 to 4294967295, which `a >>> 0` gives. As unsigned, −1 is 4294967295, so `i32.lt_u` of −1 and 1 is 0.
- **Reinterpret.** `f32.reinterpret_i32` reads an integer's 32 bits as a float, and `i32.reinterpret_f32` does the reverse. A `DataView` does both. The integer 1110704128 read as a float is 45, which is how a float such as Lob's angle sits in a word.
- Comparisons give 1 or 0, and `env.sin` and `env.cos` are the page's own `Math.sin` and `Math.cos`.

`OPS` in `lift.mjs` (given) has the rule for every instruction the games use. Your `evaluate` handles the kinds of expression around it:

- `const` gives its value. An i64 constant, a BigInt, gives `null`.
- `param`, `global` and `unknown` give `null`.
- `load` works out its address, adds the offset, and asks `env.load(type, address)`, which gives `null` for memory it doesn't have.
- `call` works out its arguments and asks `env.call(name, args)`.
- `phi` tries its paths in order and gives the value of the first whose conditions all hold. A path with a condition that fails is passed over. A path with a condition that can't be known makes the phi `null`, because the path it would have taken can't be known either. If no path holds, the phi is `null`.
- Any other op works out its arguments and applies `OPS`. An argument that is `null` makes the result `null`.

`env` also holds `given` and `memo`, and both come before all that. `given` is a `Map` from expression to the value to use in its place, and `evaluate` looks there first. The simulator gives the key handler's parameter this way. `memo` is a `Map` that keeps every value worked out in one round of evaluation, because expressions share parts. The landing's value uses `t` three times, and without the memo it would be worked out three times, and each of its parts again.

`holds(when, env)` says whether all of a guard's conditions hold: `true`, `false`, or `null` when one of them can't be known. It takes the conditions in order and stops at the first that can't be known, giving `null`, or at the first that fails, giving `false`. So a condition that can't be known followed by one that fails gives `null`, and the same two the other way round give `false`.

## Memory the engine can write

{{practice:p05d}}

{{gate:p05d}}

`overlay(bytes)` is memory the engine can write without touching the game. Reads fall through to the bytes you hand it, the game's own memory read while the game isn't running. Writes go into a `Map` of words and never reach the game:

- `load('i32.load', a)` gives the word at `a`, `load('f32.load', a)` the same word read as a float, and `load('i32.load8_u', a)` one byte. A word past the end of the bytes is `null`.
- `store('i32.store', a, v)` and `store('f32.store', a, v)` keep a word in the `Map`. Any other store, an address that isn't a multiple of 4, and a `null` value change nothing.

`apply(list, m, { call, given })` runs a list of lifted stores once against such a memory. Every expression in a lifted store is in terms of memory as it was when the function began, because forwarding has already accounted for what the function wrote before. So `apply` works out every guard, address and value first, all from memory as it is, and only then writes the stores whose guards hold, in their order. It skips stores inside loops, stores whose guard doesn't hold for certain, and stores whose address is unknown, and it returns how many it wrote.

This is why `apply` works out every value before it writes any. In `game_tick` the sideways speed, `+48`, is stored before the position across, `+40`, and the position's value uses the sideways speed as it was when the frame began. Stored one at a time, with memory read afresh for each store, the position would use the new speed, and in any wind every frame would move the shell by the wrong amount.

## Cross-references and constants

The rest of this module is passes over lifted code. `liftAll(mod)` lifts every function the file defines and returns a `Map` from name to lifted function. The first pass, `xrefs(lifted)`, lists every place those functions touch, with the functions that read it and the stores that write it. A function reads a place when a load of it appears in one of its stores (value, address or guard), in the arguments of one of its calls, or in a value it returns. A store at a computed address is left out, and so are stores inside loops. `node lab.mjs xrefs ./work` prints yours for each struct the code reaches through a pointer. Three of the lines for Lob:

```
The struct at *0x13120:
  +8    read by func6, game_tick; written by no store through
        this pointer
  +20   read by game_key, r_cannon_x; written by no store through
        this pointer
  +36   read by game_key, game_tick, r_flying; written by game_key,
        game_tick
```

A pass called **constant tracking** uses the cross-references. A float the launch reads that no store writes is set once, when the game starts. On Lob that's `+20`, which holds 80, the cannon's position across and the place every shell starts from. `game_init` writes it, once, through the address it works out for the state at start-up, a computed address that the cross-references leave out. It's exactly the kind of number the model of the first version had to assume.

The same table shows the pass's limit. `+8`, the wind, is also written by "no store through this pointer", yet the wind changes every round. `func5`, which starts each round, writes it through a pointer that depends on whether it moved the state that round, and the cross-references leave that store out with the other computed addresses. So the line means only that no store the lifter can place writes it. A finding like that is a hypothesis, something a pass found that hasn't been tested against the game. Your simulator doesn't rest on this one, because it reads `+20` from memory each time it runs, as the game does. The pass tells you where the launch depends on a number set outside the code you read, and the engine names that number when it describes the physics.

## Slices

A **slice** is the set of stores that decide some places. `slice(list, targets)` takes a list of stores and a list of place keys. It keeps the stores to the target places, then adds as targets the places their values, addresses and guards read, and goes round again with those, until a round adds nothing. It returns the kept stores in their order in the list.

The shell's flight is a slice of `game_tick`. The targets are the places the launch sets: the shell's position and speed, `+40`, `+44`, `+48` and `+52`, and the flying flag, `+36`. `game_tick` has five stores to them: `+36 = 0` when the shell lands, and the steps of the position and the speed. Their values and guards read those five places, the build's mode at `+84`, the word at `+92` and the wind at `+8`. `game_tick` stores to none of the last three, so the second round adds nothing, and the slice is those 5 stores. `game_tick`'s other 21 stores, the frame counter, the cloud, the flag, the score and the message among them, aren't in it. One of them, the landing, comes back in the section "The flight and the landing".

A slice for the flag's word, `+16`, grows for longer. The store to `+16` reads the flag's speed at `+96`, so the next round keeps the two stores to `+96`. One of them sets a new speed from the random generator's state at `+80`, and its guard reads the timer at `+100`, so the round after keeps the stores to `+80` and `+100`. Their values read `+80` and `+100` again, and nothing more is added. The slice is 6 stores, the whole of the flag's motion, which module 07 uses.

## Steppers

The passes that remain recognise shapes, with no game-specific code. Nothing in them names an offset, a constant or a key code of Lob's. The first finds the **steppers**, the key handler's stores that put a value back plus or minus 1, within a bound, under a key code. `steppers(keyFn)` takes the lifted key handler and returns `{ code, delta, value, bound, store }` for every store that has all three of these:

- A key code. `codeOf(guard)` finds a condition on the handler's parameter, either `(param0 != k)` that must fail or `(param0 == k)` that must hold, which gives the key code `k`.
- A bound. The last condition in the guard that orders a value against a constant, with `lt`, `gt`, `le` or `ge` of any type, signed or unsigned, after an `i32.eqz` around it is unwrapped, gives the stepper's `value` and `bound`: the side that isn't a constant, and the constant. A test for equal or not equal is never the bound, so the key-code test `(param0 != k)` is passed over, though it compares with a constant too.
- A step. An add of the constant 1 or −1 somewhere in the stored value gives `delta`.

On Lob the four steppers are:

```
code 1, delta -1, bound 5     the angle, asfloat((k ^ a))
code 2, delta  1, bound 85    the angle
code 3, delta  1, bound 99    the power, (i*0x13120+4 ^ k)
code 4, delta -1, bound 11    the power
```

The bounds are the constants the compiled tests use. "Power below 100" became "not above 99", so the bound is 99, and "power above 10" became "not below 11".

Take the value from the bound test, not from the stored expression. The bound test compares the value as the game sees it, decoded. The stored expression need not show that value at all. In another build a stepper's store can be the stored word plus 1, with nothing decoded in it, because the compiler can fold the decoding away. The bound test still has to compare the decoded value with its limit.

## The decode step

The steppers' values show how the game keeps the angle and the power. `decoding(value, rawKey)` reads the shape and returns `{ raw, key, op, float }`:

- An `asfloat(...)` around the rest means the value is a float kept as its bits: `float: true`.
- A plain i32 load means the value is stored as it is: `op: 'plain'`, with that load as `raw` and no key.
- An XOR of two i32 loads means one is the stored word and the other a key: `op: 'xor'`. An XOR doesn't say which part is which, and `make` puts its parts in id order, so `rawKey`, the `placeKey` of the place the stepper writes, tells them apart, since `raw` is the load of that place.
- A subtraction of two i32 loads, the stored word less the key, means the value is stored with the key added: `op: 'add'`.

On Lob the angle decodes to `{ raw: i*0x13120, key: i*0x13120+92, op: 'xor', float: true }`, and the power to the same with `raw: i*0x13120+4` and `float: false`.

These functions also use what `decoding` finds:

- `decoder(d, raw)` builds the expression that decodes another word the same way, a load of `raw`'s place, XORed with `d.key` or less `d.key`, inside an `asfloat` when `d.float` is true. Module 06 decodes the flag's word with it.
- `resolve(m, addr)` works out where an address expression points now, in memory `m` from `overlay`. A constant gives its value. An i32 load with address `A` and offset `o` gives the word in `m` at `resolve(m, A) + o`. So it follows every pointer the address goes through. Anything else gives `null`.
- `encode(m, d, value)` is decoding run backwards, the word the game would store for a value. It takes the value's 32 bits (a float's bits when `d.float` is true), then XORs them with the key or adds the key, the key read from `m` at its place through `resolve`.

On a build that doesn't scramble its values the key is 0, and the angle 45 is stored as 1110704128, the bits of 45. Module 06 meets builds where the key changes every round.

{{practice:r05-decode}}

## The launch

The **launch** is what the key handler does when the fire key is pressed. `launchOf(keyFn)` finds it by its trigonometry, the stores whose values call `env.sin` or `env.cos`. It takes the key code from the first such store's guard and gathers every store under that code. The shell's fields, the places the trigonometric stores write, are its position and its speed, and the store of the constant 1 among the launch's stores marks the flying flag. It returns `{ code, stores, trig, fields, flying, flyingStore }`, with `fields` and `flying` as place keys.

On Lob, key code 5 has 9 stores. These 4 use `sin` and `cos`, with `A` for the angle, `asfloat((k ^ a))`, and `P` for the power (`float(P)` turns it from an integer into a float):

```
f*0x13120+44 = ((sin((A * 0.0174532924)) * 22) + 18)
f*0x13120+40 = ((22 * cos((A * 0.0174532924))) + f*0x13120+20)
f*0x13120+52 = (sin((A * 0.0174532924)) * (float(P) * 6))
f*0x13120+48 = (cos((A * 0.0174532924)) * (float(P) * 6))
```

0.0174532924 is π/180, which turns degrees into radians. The shell starts at the tip of a barrel 22 paces long, at height 18 + 22 sin A and across at `+20` + 22 cos A, and leaves at 6 paces a second for each unit of power. `+36 = 1` sets the flying flag, and the other four stores clear the trail and the result, count the shot and empty the message.

`aimValues(keyFn, launch)` names two of the steppers. The angle is the stepped value that appears inside the `sin` and `cos` calls, and the power is the other stepped value the trigonometric stores use. It returns `{ angle, power }`, each `{ value, raw, codes }`, with `raw` the stepping store and `codes` its key codes and deltas, `[[1, -1], [2, 1]]` for Lob's angle.

{{practice:r05-launch}}

## The flight and the landing

The **flight** is the slice of `game_tick` for the launch's fields and the flying flag, together with the landing. `flightOf(tickFn, launch)` takes that slice, finds the flying flag's reset (the store of 0 to its place), and then the **landing**, the f32 store whose guard is exactly the reset's, made through the same struct pointer, to a place that isn't one of the launch's fields. On Lob the landing is `+56`, and the flight is 6 stores in all. `flightOf` returns `{ stores, landing, landingKey, wind }`.

The flight's guards say what a frame does. Write `ny` for the next height, `(((0.0166666675 * vy) + py) + -0.0416666716)`. Under `i*0x13120+36 and (ny <= 0)` the shell comes down in this frame, and `game_tick` resets the flying flag and writes the landing, the position across plus the distance covered in the part `t` of the frame. Under `i*0x13120+36 and not (ny <= 0)` it steps the position and the speed instead.

`flightOf` also finds the wind, which is the factor, other than constants and the shell's own fields, that the sideways speed gains each frame. It isn't handed the aim, so it finds the sideways speed from the launch alone. Among the launch's trigonometric stores, the first `f32.store` whose value calls `cos` and turns an integer into a float, the power (`float(P)` in the printouts), writes the sideways speed, `+48` on Lob. The flight's store to that place is the speed's step. Going through the step's value in the order `parts(e)` gives (every expression inside `e` once, `e` first), the first `f32.mul` by a constant whose other side isn't a constant and reads none of the launch's fields holds the wind, and taking off any further multiplications by constants leaves it. Lob's step is `vx = (vx + (0.0166666675 * (W * 12)))`. The first such multiplication is by 0.0166666675, taking the 12 off its other side leaves `W`, and the wind `W` is

```
((1 & i*0x13120+84): server_wind();
 (not (1 & i*0x13120+84)): asfloat((i*0x13120+92 ^ i*0x13120+8)))
```

On a build whose mode has the bit worth 1 set, the wind comes from a call to the page's `server_wind`, and the game's memory never holds it. Module 06 meets those builds. Otherwise the wind is decoded from `+8` with the key. 12 is the wind's push, so each unit of wind adds 12 paces a second to the sideways speed every second.

{{practice:r05-flight}}

## The simulator

`simulator(launch, aim, flight)` returns a function, `simulate(bytes, { angle, power, wind })`, that works out where a shot lands from a copy of the game's memory and nothing else. Each call:

1. Makes `m = overlay(bytes)`.
2. Sets the barrel the way the game keeps it. For the angle and the power, `resolve(m, raw.addr)` follows the pointers the stored word's place goes through, to where it is now, and `encode` gives the word to write there. The barrel can be set to any setting, not only the one the game is set to.
3. Runs the launch's stores once with `apply`, with the key handler's parameter given as the launch's key code, and `call` answering `env.sin` and `env.cos` with `Math.sin` and `Math.cos`.
4. Runs the flight's stores with `apply`, once a frame, until the flying flag's word is 0, then reads the landing's place as a float.

It returns `{ x, frames }`, the landing and how many frames the flight took. It returns `null` when a place can't be found, when the flying flag isn't reset within 2000 frames, or when the landing isn't a finite number. Given a `wind`, the flight's wind expression is given that value, rounded to a 4-byte float, and `server_wind` answers it too. Without one, the wind in memory is used.

The simulator does the game's arithmetic on the game's own expressions. Built this way, the course's own simulator gave the game's landing bit for bit, and the same number of frames, on every build the course has. Nothing in it was fitted, and no constant was copied out of the code by hand.

## Check shots

Everything the passes found is a hypothesis. The decoder could have a bug, a shape could match the wrong store, or the code read could belong to another game. So the engine tests the physics against the game before relying on it, with three **check shots**, and installs it only when all three confirm it. The check shots are the physics' judge.

`learnPhysics(host, kit, env)`:

1. Gets the passes' findings from `analyse(host)`, described in the next section. If they include no simulator, it logs `read the physics` with `the code shows no launch and flight` and returns `null`.
2. Looks at the state. If the wind isn't a number, no check shot can be compared with a simulation, so it logs `check the physics` with `the exact wind is not on the client, so no check shot can be compared here` and returns `null`.
3. Logs `read the physics` with what `sayPhysics(code, host)` says, where `code` is what `analyse(host)` returned in step 1.
4. For each setting in `CHECK_SHOTS`, 30° at power 70, 55° at 80 and 40° at 85, starts a new round, sets the barrel, simulates the shot from memory as it is at that moment, and then presses the fire key and waits for the message, counting the frames. `SHORT BY 37` means the shell came down 37 paces before the flag, and `LONG BY 37` 37 paces past it. With the flag's position read when the shell has landed, that gives the landing. A shot that ends in `HIT` says only "within 12 paces", so the same angle is fired again, in a new round, with 7 more power, and if that hits too, with 7 less.
5. Confirms the physics when all three settings gave a landing, each within 1 pace of the simulated landing and after exactly the simulated number of frames. The message rounds the miss to the nearest pace, so the true landing can be half a pace from the measured one, and a pace allows for that. The frame count is a whole number nothing rounded, so it must match exactly.
6. Logs `check the physics` with `3 check shots each landed within a pace of the simulated landing, after the same number of frames`, or with `refuted:` and the shots that disagreed. It sets `kit.physics` to `{ game: gameId(host), says: sayPhysics(code, host) }` when the physics is confirmed and to `null` when it's refuted, and returns it.

The kit records what was confirmed and on which game, not the simulator itself, because the engine rebuilds that from the game's file whenever it needs it. A physics confirmed on one game is no evidence about another, and when the code read isn't the game being played, the check shots refute it.

## Level 2 with your engine

`analyse(host)` runs the passes once per game and keeps the result, keyed by `gameId(host)`. It parses the file, runs `liftAll`, takes the two functions the page calls by their export names, `game_key` and `game_tick`, and runs `launchOf`, `aimValues`, `flightOf`, `decoding` on the angle, `simulator`, and constant tracking. It returns `{ lifted, launch, aim, flight, decode, simulate, constants, flag, readers }`. For now `flag` is `null` and `readers` is empty, and module 06 fills them in.

`sayPhysics(code, host)` puts the hypothesis in one sentence, for the log and for the menu. With a host it adds each constant's value now. On Lob:

```
A shot starts on key code 5: game_key writes +44 +40 +52 +48 from
the angle, the power and +20 (no store through the pointer writes
it; 80 now), and sets +36; game_tick moves the shell with 5 stores
while +36 is set and writes the landing to +56.
```

Each constant reads `+C (no store through the pointer writes it; V now)`, and without a host the `; V now` is left out. Several constants follow `the power and` one after another, separated by commas, as in `the power and +C (…), +D (…), and sets +36`. With none, the sentence reads `from the angle, the power, and sets +36`. `API.md` gives the whole sentence with its parts named.

Your engine takes the physics in through `checkKit` and `aimFor`:

- `checkKit`. A level whose radius is under 12 adds the evidence `'exact'`. A kit whose physics is for this game has no aim problem. On a level that needs the exact aim, a fit doesn't settle the aim problem and isn't offered, and the problem's reason is `this level needs the exact physics`. The menu offers the physics whenever `analyse` found a simulator. The option costs 3 rounds and 3 shots, and its limits are `['arrows']`, the evidence that rules the option out (module 06 gives every option its limits), since check shots can't be compared on a build whose screen shows only wind arrows. Its label is `Test what the code says about a shot with 3 check shots (3 rounds, 3 shots): ` followed by `sayPhysics(code)`, and it runs `learnPhysics`.

The physics names the game it was made on, as the fit does, so `checkKit` never takes it for another game's physics. Module 08 adds the step that empties a kit carried to a new game.

- `05-lift`: a count other than 13 usually means code after a `return` or a `br` was lifted as if it ran, or a store took its value and its address in the wrong order. A guard unlike the lesson's usually means a `br_if`'s two paths got the wrong `holds`. The path that leaves gets the condition holding.
- `05-guards`: the code after a block kept the guard the block opened with although a path left early, or a path that left early was counted among the arriving ones.
- `05-forward`: a load after a store gave the load from memory, or a store on another path was taken as if it had run, with no phi.
- `05-evaluate`: a float operation without `Math.fround`, an integer that doesn't wrap, an unsigned comparison done as signed, `given` looked at after anything else, or a `null` argument that didn't make the result `null`.
- `05-apply`: a store written before the next store's value was worked out, or a write that reached the game's own memory.
- `05-xrefs`: a store at a computed address was counted as writing a place, or loads in guards weren't counted as reads.
- `05-slice`: the slice stopped after the first round, or didn't follow the loads in guards.
- `05-steppers`: the value was taken from the stored expression instead of the bound test.
- `05-decoding`: the raw word and the key were swapped in an XOR. The stepper's place says which is raw.
- `05-launch`: the launch was taken as the trigonometric stores alone. It's every store under their key code.
- `05-flight`: the landing was taken as any f32 store under the reset's guard. It must be through the same pointer and not one of the launch's fields.
- `05-simulate`: a landing off by a little usually means a missing `Math.fround` somewhere or an `apply` that writes as it goes. `null` usually means the launch's parameter wasn't given, or the wind wasn't given on a build that keeps it on the server.

- `05-level-2`: the physics is never offered on level 2, or `aimFor` still aims with the fit.

## What module 06 needs

Module 06 meets builds where the game moves its state to a new address every round and scrambles its values with a key that changes every round, so the addresses a search finds stop working. Its reader of the state is built from what your passes found. The steppers' values, evaluated on the game's memory as it is, give the angle and the power through any key, because they decode them the way the game does. The landing leads to the hit test, which compares the landing less the flag's position with a constant, and so to the flag. The wind expression says where the wind comes from. Module 06 also adds `windWord` to `flight.mjs`. The physics in the kit stays as it is, because those defences hide the game's values and leave how a shell flies alone.
