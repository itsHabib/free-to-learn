## How a shell flies

A shell leaves the tip of the barrel with some speed in some direction. Gravity pulls it down at a constant rate and the wind pushes it sideways at a constant rate. When something speeds up at a constant rate `a`, then after `t` seconds its speed has changed by `a·t` and it has moved `v·t + ½·a·t²`, where `v` is the speed it started with. That one fact, used twice, describes the whole flight.

- The shell starts at the barrel's tip: `x0 = cannonX + barrel·cos(angle)` across and `y0 = height + barrel·sin(angle)` up (`cannonX` is the cannon's position, `barrel` the barrel's length and `height` the launch height, three of the six numbers of the physics named below). The game's angle is in degrees and JavaScript's `Math.cos` and `Math.sin` take radians, so pass them `angle × Math.PI / 180`.
- Its speed is `speedPerPower·power`, split into `vx = speed·cos(angle)` across and `vy = speed·sin(angle)` up.
- After `t` seconds its height is `y0 + vy·t − ½·g·t²`, where `g` is gravity, and its distance across is `x0 + vx·t + ½·k·wind·t²`, where `k` is how hard one unit of wind pushes.
- It lands when the height reaches 0, at `t = (vy + √(vy² + 2·g·y0)) / g`.

{{figure:shell-flight}}

Lob's physics comes down to six numbers: the speed per power, gravity, the wind's push per unit, the cannon's position, the barrel's length and the launch height. Your engine doesn't know any of them. In module 05 it reads the game's own arithmetic out of its code. In this module it fits a formula to shots it has fired, and these equations give the formula its shape.

Fired from the ground at the same speed, shells at 30° and 60° land at the same place. A shell that starts on the ground has `y0 = 0`, so it lands at `t = 2·vy / g` and comes down `vx·t = 2·vx·vy / g` past where it started. With speed `v`, `vx·vy = v²·cos(angle)·sin(angle)`, which is `½·v²·sin(2·angle)`, so the shell lands `v²·sin(2·angle) / g` away. This is the **vacuum range formula**, the range of a shell fired from the ground with nothing but gravity acting on it. sin 60° and sin 120° are equal, so 30° and 60° land at the same place, and 45°, where sin 90° = 1, lands furthest.

Lob's shell doesn't start on the ground. At power 70 with the wind written as 0, a shot at 30° landed at 654.34 and one at 60° at 620.78, about 34 paces apart. The shell starts at the barrel's tip, above the ground and in front of the cannon, and the tip sits in a different place at each angle.

## Five numbers for a shot

The fit starts from the vacuum range formula and adds what Lob's shell does differently. Write `a` for the angle, `p` for the power and `w` for the wind, and let the speed be `s·p`, where `s` is the unknown speed per power. Fired from the ground at the cannon, the shell would land at

```
x = cannonX + (s²/g)·p²·sin(2a) + (2·k·s²/g²)·w·(p·sin a)²
```

The last term is the wind's push, `½·k·w·t²`, with `t = 2·s·p·sin(a) / g`, the flight time of a shell fired from the ground. Each way Lob's shell differs from it adds a term:

- It starts at the barrel's tip, `barrel·cos(a)` further across than the cannon. That is a term in `cos(a)`.
- It starts above the ground, so it stays in the air a little longer than a shell fired from the ground, and in that extra time it keeps moving across at `s·p·cos(a)`. That is a term in `p·cos(a)`. The extra time isn't the same for every shot, so this term is close, not exact.

So the fit predicts a landing as a sum of five terms, each a coefficient times a number worked out from the shot:

```
x = c0 + c1·cos(a) + c2·p²·sin(2a) + c3·w·(p·sin a)² + c4·p·cos(a)
```

The five numbers the coefficients multiply are the shot's **features**: 1, `cos(a)`, `p²·sin(2a)`, `w·(p·sin a)²` and `p·cos(a)`. `features(angle, power, wind)` returns them as a list, with the angle turned into radians first. `predictFit(coef, angle, power, wind)`, later in this lesson, multiplies each feature by its coefficient in `coef` and adds them up.

```js {"file":"examples/learn-checkpoint.mjs","region":"features","title":"The five numbers the fit multiplies","change":"Replace the features region of work/learn.mjs."}
export function features(angle, power, wind) {
  // Math.cos and Math.sin take radians.
  const a = (angle * Math.PI) / 180;
  const p = power;
  const rise = p * Math.sin(a);
  return [
    1,
    Math.cos(a),
    p * p * Math.sin(2 * a),
    wind * rise ** 2,
    p * Math.cos(a),
  ];
}
```

## Measuring a shot

`testShot(host, found, controls, angle, power)` fires one shot and measures it. `found` is what `findValues` returned. It presses the angle and power keys until the slots you found read the angle and power you asked for, at most 200 presses for each, reads the flag and the wind, presses fire, and ticks one frame at a time until the message isn't empty. Pressing fire clears the message at once, so the next text to appear at `found.message` is the result: `HIT!`, `SHORT BY 149` or `LONG BY 95`, with the miss rounded to a whole pace. It ticks at most 1,500 frames and throws `the shot never landed` if no text came by then, so a mistake elsewhere can't leave it ticking without end.

The exact landing spot is a float in memory, and a miss leads you to it. In a fresh game with seed 1, a shot at 45° and power 60 came down while the flag stood at 780.33, and the message said `SHORT BY 149`, so the shell landed near 780.33 − 149 = 631.33. The slot that holds the landing is within 0.6 of that number, half a pace for the message's rounding and a little more for the rounding of floats. `scanNear` with a tolerance of 0.6 finds it, holding 631.71.

One scan doesn't always settle it, because more than one slot can be that close. The shell's own position on its last frame in the air can be within 0.6 of where it comes down. A first shot at 45° and power 60 left more than one such slot on 72 of 300 seeds. So `testShot` narrows the candidates over misses:

1. After a miss, scan for the f32 slots within 0.6 of the landing the message gives.
2. If `found.landingCandidates` holds slots from an earlier miss, keep only the slots that are in both lists.
3. If one slot is left, keep it as `found.landing`, as `{ addr, type: 'f32' }`, and drop the candidates. If several are left, keep them as `found.landingCandidates` for the next miss.

Once `found.landing` is set, `testShot` reads every later landing straight from it. Until then, the landing of a miss comes from the message, which is within half a pace. A hit before the slot is known is worse off. `HIT!` carries no distance and says only "within 12 paces of the flag", so all `testShot` can return as the landing is the flag's position, and that can be 12 paces from the truth. Your engine keeps that from mattering by finding the slot before it fires any shot whose landing it will use, with the sighting shots that the section "Practice shots, some held back" describes.

`testShot` returns `{ angle, power, wind, target_x, impact_x, frames }`, where `target_x` is the flag's position and `impact_x` is the landing spot. The wind comes from the wind slot, never from the status line. The status line's rounding can be off by 0.05, and the same shot at 45° and power 60 landed 19.9 paces further with the wind written as 1 than as 0, so the rounding alone can cost another pace. `frames` is the number of ticks from the fire key until the message appeared, which is the flight time on the game's own clock, 110 frames for that shot. The fit doesn't use it, and module 05 does.

```js {"file":"examples/learn-checkpoint.mjs","region":"set-aim","title":"Press the keys until the slots read the setting","change":"Replace the set-aim region of work/learn.mjs."}
// The number at addr, read as 'f32' or 'i32', from the live memory.
function read(host, addr, type) {
  const m = host.memory();
  const view = new DataView(m.buffer, m.byteOffset, m.byteLength);
  if (type === 'f32') return view.getFloat32(addr, true);
  return view.getInt32(addr, true);
}

// Press one value's keys until its slot, rounded, reads want.
function setValue(host, slot, up, down, want) {
  for (let presses = 0; presses < 200; presses++) {
    const now = read(host, slot.addr, slot.type);
    if (Math.round(now) === want) return;
    host.press(now < want ? up : down);
  }
}

function setAim(host, found, controls, angle, power) {
  const c = controls;
  setValue(host, found.angle, c.angle_up, c.angle_down, angle);
  setValue(host, found.power, c.power_up, c.power_down, power);
}
```

```js {"file":"examples/learn-checkpoint.mjs","region":"wait-for-message","title":"Tick until the message shows the result","change":"Replace the wait-for-message region of work/learn.mjs."}
// Tick one frame at a time until the message slot holds text.
function waitForMessage(host, message) {
  let text = '';
  let frames = 0;
  while (frames < 1500 && !text) {
    host.tick(1);
    frames++;
    text = S.readCString(host.memory(), message);
  }
  if (!text) throw new Error('the shot never landed');
  return { text, frames };
}
```

```js {"file":"examples/learn-checkpoint.mjs","region":"narrow-landing","title":"Narrow the landing slot over misses","change":"Replace the narrow-landing region of work/learn.mjs."}
// After a miss: the floats within 0.6 of where the message puts the
// landing, kept only if an earlier miss had them too. One slot left is
// the landing slot. None left keeps the earlier list as it was.
function narrowLanding(host, found, landed) {
  let near = Array.from(S.scanNear(host.memory(), landed, 0.6));
  const earlier = found.landingCandidates;
  if (earlier) near = near.filter((slot) => earlier.includes(slot));
  if (near.length === 1) {
    found.landing = { addr: near[0] * 4, type: 'f32' };
    delete found.landingCandidates;
  } else if (near.length) found.landingCandidates = near;
}
```

```js {"file":"examples/learn-checkpoint.mjs","region":"test-shot","title":"Fire one shot and measure where it landed","change":"Replace the test-shot region of work/learn.mjs."}
export function testShot(host, found, controls, angle, power) {
  setAim(host, found, controls, angle, power);
  const target_x = read(host, found.flag.addr, 'f32');
  const wind = read(host, found.wind.addr, 'f32');
  host.press(controls.fire);
  const { text, frames } = waitForMessage(host, found.message);
  const shot = (impact_x) => {
    return { angle, power, wind, target_x, impact_x, frames };
  };
  if (!found.landing) {
    const miss = text.match(/(SHORT|LONG) BY (\d+)/);
    // HIT! says only "within 12 paces": the flag is the best guess.
    if (!miss) return shot(target_x);
    const by = Number(miss[2]);
    const landed = miss[1] === 'SHORT' ? target_x - by : target_x + by;
    narrowLanding(host, found, landed);
    if (!found.landing) return shot(landed);
  }
  return shot(read(host, found.landing.addr, 'f32'));
}
```

## A fit by least squares

Module 02's `lineFit` chose two numbers, a slope and an intercept, so that the sum of the squared residuals came out as small as it can be. The fit chooses five coefficients by the same rule. The least-squares coefficients make the sum over the shots of (prediction − landing)² as small as it can be.

Write the shots' features as the rows of a table `A`, one row per shot, and their landings as a list `b`. The best coefficients `c` solve the **normal equations**, `(AᵀA)·c = Aᵀb`, one equation per coefficient, so five equations in five unknowns. Entry (i, j) of `AᵀA` is the sum over the shots of feature i times feature j, and entry i of `Aᵀb` is the sum over the shots of feature i times the landing. These are the right equations because at the smallest sum, nudging any one coefficient up or down can't lower it, and that holds exactly when, for every feature, the sum over the shots of that feature times the residual is 0. Written out, that condition for feature i is equation i.

Here they are for the three points (0, 1), (1, 3) and (2, 4) and a line with the features 1 and `x`:

```
A = [[1, 0], [1, 1], [1, 2]]        b = [1, 3, 4]
AᵀA = [[3, 3], [3, 5]]              Aᵀb = [8, 11]
```

Entry (0, 1) of `AᵀA` is 1·0 + 1·1 + 1·2 = 3, entry (1, 1) is 0·0 + 1·1 + 2·2 = 5, and entry 1 of `Aᵀb` is 0·1 + 1·3 + 2·4 = 11.

`leastSquares(A, b)` builds the normal equations and solves them by **elimination**. Write each equation as a row with its right side at the end, here `[3, 3 | 8]` and `[3, 5 | 11]`. Before you start, note the largest number on the diagonal, ignoring its sign, which here is 5. Then, for each column in turn:

1. Of this row and the rows below it, take the one with the largest number in this column, ignoring its sign, as the **pivot** row, and swap it into this row's place. A tie keeps the row that comes first.
2. If the pivot isn't bigger in size than 1e-12 times that largest diagonal number (a millionth of a millionth of it), return `null`.
3. From every other row, subtract the multiple of the pivot row that makes that row's number in this column 0.

When every column is done, each row has one number left on the diagonal, and each coefficient is its row's right side divided by that number. On the example, both rows hold 3 in column 0, so row 0 stays the pivot row, and row 1 minus 1 × row 0 is `[0, 2 | 3]`. In column 1 the pivot is that 2, and row 0 minus 1.5 × row 1 is `[3, 0 | 3.5]`. So `c0` = 3.5 / 3 = 1.1667 and `c1` = 3 / 2 = 1.5, the line `y = 1.5·x + 1.1667`, which is the line `lineFit` gives for the same three points.

Taking the largest pivot keeps the arithmetic accurate, because dividing by a small number magnifies every rounding error in its row. A pivot of almost nothing means the equations have no single answer. Three points that all have `x = 2` are such a case, since any slope fits them as well as any other. Fewer shots than coefficients is another, so `fitShots` on 4 shots returns `null`. So is a set of shots all fired at one angle. Then `cos(a)` is the same for every shot, so its column is a multiple of the first and the two can trade off without limit. Rounding leaves that pivot near 1e-12 rather than 0, which is why the test is against the size of the numbers in play and not against a fixed number.

`fitShots(shots)` calls `leastSquares` with one row of features per shot and the shots' `impact_x` as `b`. On the 14 practice shots the course recorded with seed 7, the fit on all 14 predicts every one of them within 7.05 paces.

### Write the fit

`normalEquations` builds the rows: for each pair of features the sum over the shots of their product, then the sum of feature times landing as the right side. In `work/learn.mjs`, replace the `normal-equations` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"normal-equations","language":"js","title":"The normal equations as rows","change":"Replace the normal-equations region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"normal-equations","title":"The normal equations as rows","change":"Replace the normal-equations region of work/learn.mjs."}
// (AᵀA) c = Aᵀb as rows [entries of AᵀA | entry of Aᵀb].
function normalEquations(A, b) {
  const n = A[0].length;
  const rows = [];
  for (let i = 0; i < n; i++) {
    const row = [];
    for (let j = 0; j < n; j++) {
      row.push(A.reduce((sum, r) => sum + r[i] * r[j], 0));
    }
    row.push(A.reduce((sum, r, k) => sum + r[i] * b[k], 0));
    rows.push(row);
  }
  return rows;
}
```
<!-- /code-example -->

`leastSquares` is the elimination, step for step. `scale` is the largest diagonal number, taken before any row changes. The test is written `!(… > …)` rather than `… <= …` so that a pivot that is `NaN`, which no comparison holds for, also gives `null`. The inner loop starts at column `c`, because the columns before it are already 0 in every row but their own. Replace the `least-squares` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"least-squares","language":"js","title":"Elimination with the largest pivot","change":"Replace the least-squares region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"least-squares","title":"Elimination with the largest pivot","change":"Replace the least-squares region of work/learn.mjs."}
export function leastSquares(A, b) {
  const M = normalEquations(A, b);
  const n = M.length;
  // The largest number on the diagonal, its sign dropped.
  const scale = Math.max(...M.map((row, i) => Math.abs(row[i])));
  for (let c = 0; c < n; c++) {
    // The pivot row: the largest number in this column, the first of
    // equals, from this row down.
    let p = c;
    for (let r = c + 1; r < n; r++) {
      if (Math.abs(M[r][c]) > Math.abs(M[p][c])) p = r;
    }
    [M[c], M[p]] = [M[p], M[c]];
    // A pivot this small means the equations have no single answer.
    if (!(Math.abs(M[c][c]) > 1e-12 * scale)) return null;
    for (let r = 0; r < n; r++) {
      if (r === c) continue;
      const f = M[r][c] / M[c][c]; // makes row r's number here 0
      for (let k = c; k <= n; k++) M[r][k] -= f * M[c][k];
    }
  }
  return M.map((row, i) => row[n] / row[i]);
}
```

```js {"file":"examples/learn-checkpoint.mjs","region":"fit-shots","title":"Fit the shots, and predict with the fit","change":"Replace the fit-shots region of work/learn.mjs."}
    A,
    shots.map((s) => s.impact_x),
  );
}

export function predictFit(coef, angle, power, wind) {
  const f = features(angle, power, wind);
  return f.reduce((sum, x, i) => sum + x * coef[i], 0);
}
```

## Judging the fit

A fit can be wrong, and the engine has to find out before it relies on one.

{{practice:p03c}}

{{gate:p03c}}

A fit's coefficients are chosen to match the shots it was given, so how well it matches them says little about a setting it never saw. So the engine fits on most of its practice shots and keeps a few back. A **held-back** shot is one the fit never saw, and the shots the fit was made from are the **fitted** shots.

A **judge** is a test that decides whether a part goes into the kit. The fit's judge is `judgeFit(coef, { fitOn, heldOut }, within = ACCEPT_WITHIN)`:

1. If `coef` is `null`, the verdict is `'send back'`, and both worst misses are `Infinity`.
2. `fitWorst` is the worst miss, the largest distance between prediction and landing, over the fitted shots `fitOn`, and `heldWorst` is the worst over the held-back shots `heldOut`.
3. The verdict is `'accept'` when both are at most `within` paces, and `'send back'` otherwise.

It returns `{ verdict, fitWorst, heldWorst }`. `ACCEPT_WITHIN`, given in `learn.mjs`, is 12, the radius of level 1, because a fit that misses one of the engine's own shots by more than the radius can miss the flag by as much.

Both groups count, because each catches a fault the other misses. Here are fits on the 14 recorded shots of seed 7, with the 4th, 8th and 12th held back. On the other 11, the fit that `learnFit` (next section) makes misses its fitted shots by at most 6.9 paces and its held-back shots by at most 1.5, and the judge accepts it. Two other fits show what each group is for:

- A fit with the `p·cos(a)` term left out misses one of its fitted shots by 12.4 paces and its held-back shots by at most 6.5. Only the fitted shots catch it. A formula that lacks a term the shells need can't match even the shots it was made from.
- A five-term fit made from only five of the fitted shots passes through all five, with a worst fitted miss of less than a billionth of a pace, because five coefficients can be chosen to match any five shots. Its fitted shots say nothing about it. On the three held-back shots it misses by up to 10.6 paces, inside the limit, so the judge accepts it, on evidence that only shots the fit never saw could give.

Held-back shots have a limit of their own. A held-back shot tests only what is new about it, the conditions no fitted shot shares. In `learnFit` each held-back shot is the last shot of its round, so its angle and power are new to the fit and its wind isn't, because the fit saw three other shots in that same wind. The judge's verdict says the fit handles new settings in winds it has seen. Whether it handles a new wind is settled later, on fresh rounds, by the referee.

A fit the judge accepts is good enough for level 1 and not for level 2. On 20 seeds of the plain game, a fit from 14 practice shots, aimed with the search later in this module, landed all 200 of its shots within 12 paces, and 91 of them within 3 paces, between 1 and 7 in each ten. Level 2 needs 9 of 10 within 3 paces. On level 2 itself, the fit that level 1 left landed 6 of its 10 within 3 paces. Five terms come close to the game's arithmetic without being it, and module 05 reads that arithmetic from the code.

### Write the judge

`miss` is one shot's distance between prediction and landing, and `worst` the largest over a list. `Math.max(0, …)` gives 0 for an empty list, where `Math.max()` alone would give `-Infinity`. In `work/learn.mjs`, replace the `judge-fit` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"judge-fit","language":"js","title":"Accept only a fit within the limit on both groups","change":"Replace the judge-fit region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"judge-fit","title":"Accept only a fit within the limit on both groups","change":"Replace the judge-fit region of work/learn.mjs."}
export function judgeFit(coef, sets, within = ACCEPT_WITHIN) {
  const { fitOn, heldOut } = sets;
  if (!coef) {
    const fitWorst = Infinity;
    return { verdict: 'send back', fitWorst, heldWorst: Infinity };
  }
  const miss = (s) =>
    Math.abs(predictFit(coef, s.angle, s.power, s.wind) - s.impact_x);
  // The worst miss on a list; 0 for an empty list.
  const worst = (shots) => Math.max(0, ...shots.map(miss));
  const fitWorst = worst(fitOn);
  const heldWorst = worst(heldOut);
  const ok = fitWorst <= within && heldWorst <= within;
  return { verdict: ok ? 'accept' : 'send back', fitWorst, heldWorst };
}
```

```js {"file":"examples/engine-checkpoint-03.mjs","region":"learn-fit","title":"Sighting shots, practice shots, a fit and its verdict","change":"Replace the learn-fit region of work/engine.mjs."}
  // Sighting shots first: fired flat, each lands far short of any flag,
  // so its message gives a distance that narrows the landing slot.
  for (const power of SIGHTERS) {
    if (kit.found.landing) break;
    newRound(host, kit);
    testShot(host, kit.found, kit.controls, LIMITS.angle_min, power);
  }
  const shots = [];
  for (let i = 0; i < PRACTICE.length; i++) {
    if (i % 4 === 0) newRound(host, kit); // before shots 1, 5, 9 and 13
    shots.push(testShot(host, kit.found, kit.controls, ...PRACTICE[i]));

  const heldOut = shots.filter((_, i) => i % 4 === 3);

    `${v.heldWorst.toFixed(1)} on the held-back ones`;
  const accepted = v.verdict === 'accept';
  const verdict = accepted ? 'accepted' : 'not good enough';
  const step = 'fit the practice shots';
  say(env, 'code', step, `${sizes}; ${worst}: ${verdict}`);
  kit.fit = accepted ? { coef, game: gameId(host) } : null;
  return kit.fit;
```

```js {"file":"examples/learn-checkpoint.mjs","region":"nearest","title":"The closest practice shot","change":"Replace the nearest region of work/learn.mjs."}
export function nearest(shots, state) {
  let best = null;
  for (const s of shots) {
    const miss = Math.abs(s.impact_x - state.target_x);
    // Strictly closer, so the first of equals stays.
    if (!best || miss < best.miss) {
      best = { angle: s.angle, power: s.power, miss };
    }
  }
  return best ? { angle: best.angle, power: best.power } : null;
}
```

### Search the whole-number settings

Better aim needs the landing of settings nobody fired, and a fit predicts one for any setting. What's left is to find the setting that lands on the flag. The controls move in whole steps, so the answer is a whole-number angle from 5 to 85 and a whole-number power from 10 to 100, as `LIMITS` gives them, one of 81 × 91 = 7,371 settings. Rounding a smooth answer to whole numbers isn't safe, because one step moves the landing by very different amounts in different places. At angle 15 and power 100, one degree moves the landing 32.6 paces. At angle 45 and power 70 it moves it 1.4. Rounding near the first setting can throw away 16 paces, more than the 12-pace radius.

{{practice:r03-round}}

`search(predict, at, { enough = 0.5, order = 'middle' })` tries whole-number settings themselves, without trying all 7,371. `predict(angle, power)` returns `{ x, frames }`, the predicted landing and the flight time in frames, or `null` for `frames` when the predictor can't say, as a fit can't. `at(frames)` returns where the flag will be when a shot of that flight time comes down. For a flag that stands still, `at` ignores its argument and returns `state.target_x`. Module 07 hands in an `at` that follows a moving flag. The search:

1. Tries the angles in `order`: `'middle'` starts at 45 and goes outwards, 44, 46, 43, 47 and so on, the lower of each pair first, and `'low'` starts at 5 and goes up.
2. At each angle, predicts the powers 10, 20 and so on up to 100.
3. For each pair of neighbouring powers whose landings fall on opposite sides of the flag, one short and one long, halves the gap. It predicts the middle power, rounded down, and keeps the half in which the sides still differ, until the two powers are neighbours.
4. Keeps the setting with the smallest miss so far, and stops after the first angle that leaves it within `enough` paces of the flag.

It remembers each prediction at an angle, so no power is predicted twice, and it treats a prediction that is `null` or not a finite number, or an `at` that gives no number, as no setting at all. It returns `{ angle, power, x, frames, miss }`, or `null` when no setting could be predicted.

`anglesIn` is step 1: nearer 45 first, and the lower of two angles as far from it. In `work/learn.mjs`, replace the `search-order` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"search-order","language":"js","title":"The order of the angles","change":"Replace the search-order region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"search-order","title":"The order of the angles","change":"Replace the search-order region of work/learn.mjs."}
// The angles in the order search tries them.
function anglesIn(order) {
  const angles = [];
  const { angle_min, angle_max } = LIMITS;
  for (let a = angle_min; a <= angle_max; a++) angles.push(a);
  if (order !== 'middle') return angles;
  // 45 first, then outwards, the lower of each pair first.
  const away = (a) => Math.abs(a - 45);
  return angles.sort((a, b) => away(a) - away(b) || a - b);
}
```

`setting` gives one prediction's miss and `side`, −1 short of the flag and +1 beyond it, or `null`. Replace the `setting` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"setting","language":"js","title":"One setting, its miss and its side","change":"Replace the setting region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"setting","title":"One setting, its miss and its side","change":"Replace the setting region of work/learn.mjs."}
// One setting as search compares it, or null when it can't be: no
// prediction, a landing that is not a finite number, or no flag.
function setting(predict, at, angle, power) {
  const r = predict(angle, power);
  const t = r ? at(r.frames) : null;
  if (!r || typeof t !== 'number' || !Number.isFinite(r.x)) return null;
  const { x, frames } = r;
  // side: -1 short of where the flag will be, +1 beyond it.
  const side = Math.sign(x - t);
  return { angle, power, x, frames, miss: Math.abs(x - t), side };
}
```

`settingsAt` is steps 2 and 3. `row` predicts each power once, into `seen`, a `Map`, which keeps its order. The flag stays between `lo` and `hi`. Replace the `settings-at` region:

<!-- code-example {"file":"examples/learn-checkpoint.mjs","region":"settings-at","language":"js","title":"The powers tried at one angle","change":"Replace the settings-at region of work/learn.mjs."} -->
```js {"file":"examples/learn-checkpoint.mjs","region":"settings-at","title":"The powers tried at one angle","change":"Replace the settings-at region of work/learn.mjs."}
// Every setting predicted at one angle, in the order predicted: the
// powers every 10, then the halving of each gap of 10 whose ends fall
// on opposite sides of the flag. Each power is predicted once.
function settingsAt(predict, at, angle) {
  const seen = new Map();
  const row = (power) => {
    if (seen.has(power)) return seen.get(power);
    const s = setting(predict, at, angle, power);
    seen.set(power, s);
    return s;
  };
  const { power_min, power_max } = LIMITS;
  for (let p = power_min; p <= power_max; p += 10) row(p);
  for (let p = power_min; p < power_max; p += 10) {
    let lo = p;
    let hi = p + 10;
    if (!row(lo) || !row(hi) || row(lo).side === row(hi).side) continue;
    while (hi - lo > 1) {
      const mid = (lo + hi) >> 1; // the middle power, rounded down
      if (row(mid) && row(mid).side === row(lo).side) lo = mid;
      else hi = mid;
    }
  }
  return [...seen.values()];
}
```

```js {"file":"examples/learn-checkpoint.mjs","region":"search","title":"Stop at the first angle close enough","change":"Replace the search region of work/learn.mjs."}
export function search(predict, at, options = {}) {
  const { enough = 0.5, order = 'middle' } = options;
  let best = null;
  for (const angle of anglesIn(order)) {
    for (const s of settingsAt(predict, at, angle)) {
      if (s && (!best || s.miss < best.miss)) best = s;

    if (best && best.miss <= enough) break; // the first good angle
  }
  if (!best) return null;
  const { angle, power, x, frames, miss } = best;
  return { angle, power, x, frames, miss };
}
```

`metered(host, kit, left)` returns `{ host, spent }`. Its `host` is the host your engine learns with. Every call passes through to the game, and every key press is counted by key name. `spent()` returns `{ rounds, shots }`, the presses so far of the kit's new-round key and of its fire key. Once `kit.controls` is known, the metered host refuses a press of the new-round key when `left.rounds` rounds are already spent, and a press of the fire key when `left.shots` shots are, by throwing `OutOfBudget` instead of pressing. Before the kit knows its keys it refuses nothing, since it can't tell which key starts a round. It still counts every press, so the new-round presses made while the controls were being worked out count as soon as the controls are known.

<!-- code-example {"file":"examples/engine-checkpoint-03.mjs","region":"given-metered","language":"js","title":"Given: the host that counts and refuses presses","change":"Study; this part of work/engine.mjs is given."} -->
```js {"file":"examples/engine-checkpoint-03.mjs","region":"given-metered","title":"Given: the host that counts and refuses presses","change":"Study; this part of work/engine.mjs is given."}
export function metered(host, kit, left) {
  const presses = {};
  const spent = () => ({
    rounds: presses[kit.controls?.new_round] ?? 0,
    shots: presses[kit.controls?.fire] ?? 0,
  });
  const wrapped = {
    binary: () => host.binary(),
    memory: () => host.memory(),
    screen: () => host.screen(),
    write: (addr, type, value) => host.write(addr, type, value),
    tick: (frames) => host.tick(frames),
    press(key) {
      if (kit.controls) {
        const s = spent();
        if (key === kit.controls.new_round && s.rounds >= left.rounds)
          throw new OutOfBudget(
            `out of rounds: ${left.rounds} were left for learning`,
          );
        if (key === kit.controls.fire && s.shots >= left.shots)
          throw new OutOfBudget(
            `out of shots: ${left.shots} were left for learning`,
          );
      }
      presses[key] = (presses[key] ?? 0) + 1;
      host.press(key);
    },
  };
  return { host: Object.freeze(wrapped), spent };
}
```

Read the tour with three things in mind. `spent` looks up the kit's keys each time it is called, not once, which is why presses made before the controls were known still count once they are. `OutOfBudget` is an `Error` class, given above `allowance`. ## The engine's loop

Now the loop of module 01 can be written, in a first version that knows three problems. `checkKit(host, kit, level, env)` returns the first problem it finds, most basic first, as `{ part, why, evidence, options }`, or `null` when the kit is ready for the level. `part` names what the problem is about, `why` says what the engine saw, `evidence` is a list that stays empty in this module, and `options` is the menu of what could fix it. The tests, in order:

1. The controls. If `controlsHold(host, kit)` is false, the problem is `{ part: 'controls', why: 'the controls are not known on this game' }`, with its evidence and options.
2. The state. If the kit holds addresses from a search, test them by starting a new round, reading the angle, the power and the wind at those addresses, and comparing them with `parseStatus` on the status line. They hold when the angle is within 0.5 of the one shown, the power rounds to the one shown, and the wind is within 0.051 of the one shown. If they don't hold, or the line shows no number to compare with, delete `kit.found` and keep the reason, such as `a round later the addresses found by searching no longer hold what the screen shows (angle 0 there, 45 on screen)`. With no `kit.found`, the problem is `{ part: 'state', why }`, where `why` is that reason or `'nothing reads the state yet'`.
3. The aim. If `kit.fit` was made on this game, `kit.fit.game === gameId(host)`, the kit is ready, so return `null`. Otherwise the problem is `{ part: 'aim', why: 'nothing in the kit aims yet' }`.

The state test starts a round because a build that moves its state does so when a round starts, as level 3's does. It also catches level 2, which is the same game with another seed, where the addresses that level 1 found hold other numbers from the start. It costs one round each time `checkKit` runs with searched addresses in the kit.

Each problem comes with its menu. An option is `{ kind, which, key, label, cost, run }`. `kind` is a short name, `key` tells options apart so the loop can avoid trying one twice on a level, and `label` is a sentence for a picker to read, saying what the option does and what it costs. `cost` is `{ rounds, shots }`, an estimate of what the option will spend, and `run(host, kit, env)` carries it out. `which` is 0 for every option in this module; module 06 puts several options of one kind on a menu and tells them apart by it. `key` is always the kind, a colon and `which`, such as `search:0`, the form API.md gives and module 06 relies on. This first version has one option for each problem, with these labels, word for word:

- For the controls, kind `'controls'`, cost 2 rounds and 0 shots, label `Press each key and watch the status line`. It runs `learnControls`.
- For the state, kind `'search'`, cost 6 rounds and 0 shots, label `Search memory for the values (about 6 rounds; what it finds stops working if the state moves or is scrambled, and it needs the wind on the screen)`. It runs `findValues` with `choose` as its `decide`, sets `kit.found` and logs the step `search memory for the values` with the result `found angle, power, wind and flag in N experiments`. When the search throws any error but an `OutOfBudget`, it sets `kit.found` to `null` and logs the same step with the result `failed: ` and the error's message.
- For the aim, kind `'fit'`, cost 7 rounds and 17 shots, label `Fire 14 practice shots and fit an aim to them (about 7 rounds and 17 shots; good to about 10 paces)`. It runs `learnFit`. Its cost is the most it can spend: three sighting shots, each in a round of its own, then four rounds of practice shots.

Running an option is a repair, and the log calls it that.

## Playing the scored rounds

`playRounds(host, level, kit, env)` plays `level.rounds` rounds. In each it starts a new round with `newRound`, looks at the state, asks `aimFor` for a plan, ticks one frame and fires it, counting the hits. The shot leaves one frame after its plan, the 1 frame `aimFor`'s `delay` counts by default. When looking throws, because nothing in the kit reads the state, it logs an entry with the step `round N` and the result `cannot play: ` followed by the error's message and `; firing nothing`, and returns at once. The lab prints that entry as `round N: cannot play: …; firing nothing`, the step before the colon. When `aimFor` returns `null`, it logs the step `round N` with the result `nothing in the kit can aim` and goes on to the next round. N counts the scored rounds from 1, and the rung of both entries is `code`. It returns `{ hits, rounds }`. That count is the engine's own, and the level's result is the referee's. These small functions turn the kit into a shell in the air:

- `look(host, kit, env)` returns the game's state now, `{ angle, power, wind, wind_arrows: null, target_x }`, read from the addresses in `kit.found`. With no `kit.found` it throws an error that says nothing in the kit reads the state. Module 06 gives it a second way to read.
- `aimFor(host, kit, state, env, delay = 1)` returns the shot to fire, which the lessons call a **plan**. With a fit in the kit and a number for `state.wind`, it's `search` with a `predict` that returns `{ x: predictFit(kit.fit.coef, angle, power, state.wind), frames: null }` and an `at` that returns `state.target_x`. With no fit it's `nearest(kit.shots, state)`, and with no shots either it's `null`. Modules 05 and 07 add to it, and `delay` isn't used until module 07.
- `fire(host, kit, env, plan)` sets the barrel and fires. It looks at the state, presses the angle keys until the angle equals `plan.angle`, at most 200 presses, does the same for the power, presses the fire key, and ticks one frame at a time until the message at `kit.message` isn't empty, at most 1,500 frames. A key press takes no frame, because the game handles each press at once and only `host.tick` lets frames pass, so `fire` ticks nothing between presses. It returns `{ text, frames, hit }`, where `hit` is true when the text starts with `HIT`.

```js {"file":"examples/engine-checkpoint-03.mjs","region":"fire","title":"Set the barrel, fire, and read the result","change":"Replace the fire region of work/engine.mjs."}
// Set the barrel to the plan, counting press by press from the angle
// and power look reads. A press takes no frame, so none is ticked.
function setBarrel(host, kit, env, plan) {
  const { controls } = kit;
  const state = look(host, kit, env);
  let a = Math.round(state.angle);
  let p = Math.round(state.power);
  for (let n = 0; n < 200 && a !== plan.angle; n++) {
    const up = a < plan.angle;
    host.press(up ? controls.angle_up : controls.angle_down);
    a += up ? 1 : -1;
  }
  for (let n = 0; n < 200 && p !== plan.power; n++) {
    const up = p < plan.power;
    host.press(up ? controls.power_up : controls.power_down);
    p += up ? 1 : -1;
  }
}

// Fire, and tick one frame at a time until the message shows text.
function release(host, kit) {
  host.press(kit.controls.fire);
  let text = '';
  let frames = 0;
  while (frames < 1500 && !text) {
    host.tick(1);
    frames++;
    text = S.readCString(host.memory(), kit.message);
  }
  return { text, frames, hit: text.startsWith('HIT') };
}

export function fire(host, kit, env, plan) {
  setBarrel(host, kit, env, plan);
  return release(host, kit);
}
```

```js {"file":"examples/engine-checkpoint-03.mjs","region":"play-rounds","title":"Ten scored rounds with the kit's aim","change":"Replace the play-rounds region of work/engine.mjs."}
  for (let n = 1; n <= level.rounds; n++) {
    newRound(host, kit);

    try {
```

## Running the loop

`playLevel(host, level, kit, env)` runs the loop:

1. Work out `left = allowance(level)`, make `meter = metered(host, kit, left)`, and start an empty set of tried keys.
2. Ask `checkKit(meter.host, kit, level, env)` for the first problem. If it's `null`, stop repairing.
3. Work out what is left: `left` less `meter.spent()`. Keep the options not tried on this level whose cost fits in what is left. If none is left, log the step `repair` with the result `nothing left to try that fits the budget (R rounds and S shots left) for the PART: WHY`, where `round` and `shot` are singular for 1 (check 03-budget looks for the words up to `budget`), and stop repairing.
4. Ask `choose(env, 'what to try next', text, options)` for one of them. `text` is one line, such as `Level 1, Open range: The plain build. Find the controls and the values, and get an aim. Problem: nothing reads the state yet. Left for learning: 16 rounds and 20 shots.` Hand each option in as `{ ...option, problem }`, so the heuristic of module 06 can see the problem it's for.
5. Add the pick's key to the tried set, log the step `repair` with the result `WHY: LABEL`, run the option on the metered host, and log the step `spent` with the result `KIND: R rounds and S shots`, what this repair spent.
6. Go back to step 2, at most 10 times in all.

If the metered host throws `OutOfBudget`, stop repairing. During a repair, in step 5, log the step `repair` with the result `stopped: ` and the error's message, such as `stopped: out of rounds: 8 were left for learning`. During `checkKit`, in step 2, log the step `check the kit` with the error's message as the result. Out of `choose`, in step 4, log nothing more. These are the forms the walkthrough's listings log. Then return what `playRounds(host, level, kit, env)` returns, played on the plain host.

The tried set stops the loop from running the same repair twice on one level. The cost test keeps an option off the menu when its estimate says it won't fit. The cap of 10 ends the loop even if `checkKit` keeps finding problems, and the meter stops a repair whose estimate was wrong.

API.md describes the whole of `playLevel` as it is at the end of the course. Its first step, which empties a kit that was learned on another game, is module 08's, and setting `kit.decider` before the rounds is module 07's. This lesson walks through the loop and the rounds only.

```js {"file":"examples/engine-checkpoint-03.mjs","region":"what-fits","title":"What is left, and the options that fit in it","change":"Replace the what-fits region of work/engine.mjs."}
// What is left of the allowance, and the options not yet tried on
// this level whose estimated cost fits in it.
function whatFits(problem, left, spent, tried) {
  const rounds = left.rounds - spent.rounds;
  const shots = left.shots - spent.shots;
  const fits = (o) => o.cost.rounds <= rounds && o.cost.shots <= shots;
  const untried = problem.options.filter((o) => !tried.has(o.key));
  const room = `${count(rounds, 'round')} and ${count(shots, 'shot')}`;
  return { options: untried.filter(fits), room };
}
```

```js {"file":"examples/engine-checkpoint-03.mjs","region":"pick-repair","title":"The first problem, and the repair to try","change":"Replace the pick-repair region of work/engine.mjs."}
// fit. null when the kit is ready or nothing that fits is left.
async function pickRepair(at) {
  const { meter, level, kit, env, left, tried } = at;
  let problem;
  try {
    problem = await checkKit(meter.host, kit, level, env);
  } catch (error) {
    if (!(error instanceof OutOfBudget)) throw error;
    say(env, 'code', 'check the kit', error.message);
    return null;

    return { why, option: options[pick] };
```

```js {"file":"examples/engine-checkpoint-03.mjs","region":"play-level","title":"Repair at most ten times, then play","change":"Replace the play-level region of work/engine.mjs."}
  const meter = metered(host, kit, left);
  const tried = new Set(); // keys of the options run on this level
  const at = { meter, level, kit, env, left, tried };
  for (let n = 0; n < 10; n++) {
    if (!(await repairOnce(at))) break;
  }
  // The scored rounds, on the plain host: the allowance left room.
  return playRounds(host, level, kit, env);
}
```

Module 03 has 11 checks. A failure on `03-test-shot` means a landing or a frame count that differs from the game's own, candidates that weren't narrowed across misses, or a hit before the slot was known that didn't give the flag's position. `03-features` usually fails on an angle passed to `Math.sin` in degrees. `03-least-squares` fails on a wrong solution, a noisy line fitted badly, or a singular system that didn't give `null`, and `03-fit` when `fitShots` misses a recorded practice shot by more than 12 paces. `03-judge` fails when a fit that misses a fitted or a held-back shot by more than 12 paces is accepted, or one within 12 on both is sent back. `03-nearest` fails when `nearest` picks any shot but the one that landed closest, often because it used the wind. `03-search` fails when the search doesn't get within 0.5 paces for a smooth predictor, doesn't stop at the first angle that does, tries angles in the wrong order, or takes the flag's position from anywhere but `at(frames)`.
