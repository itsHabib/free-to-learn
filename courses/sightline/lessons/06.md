# 06 · The game fights back

Levels 3, 4 and 5 each turn on a defence against tools that search memory, and the addresses your search found stop working on the first of them. By the end of this module your engine reads the game's state through expressions lifted from the game's own code, confirms them against the screen, aims when only the wind arrows are on the client, and, when a level breaks its kit, lists the options that could fix it with what each costs and picks with a rule you write, the rule the decision model is measured against.

## Three defences

Each of the three levels adds one defence, of a kind games use against tools like your module 02 search:

- **Moving state** (level 3). At every new round the game moves its state to a new address. An address a search found in one round isn't where the game keeps the value in the next.
- **Scrambled values** (level 4, with the state still moving). The angle, the power, the wind and the flag are stored scrambled with a key, a word that changes every round, so the words that hold them no longer look like the numbers on the screen.
- **Server wind** (level 5, with both of the others). The exact wind is kept on a **server**, outside the game's memory. The **client**, the copy of the game that runs in the host, keeps only the number of wind arrows it draws, and the status line shows `WIND >>` where it used to show a number such as `WIND +2.7`.

Levels 1 to 7 all run the same file, `lob.wasm`. The code decides which defences are on by testing bits of the word at field +84 of its state. You can see one of those tests in the wind expression your module 05 passes found, further down this page.

Your kit arrives at level 3 holding the controls, the addresses a search found on level 2, a fit and the physics. The angle's stepper from module 05 is in your analysis too, and its value is the decoded angle:

```
asfloat((i*0x13120 ^ i*0x13120+92))
```

## The code's own decoder

An expression lifted from the code gets past two of the three defences, the moving state and the scrambled values, and no reading of memory gets past the server wind.

Here are the two values the key handler's steppers test against their bounds, as your passes found them in module 05. As in module 05, `i*0x13120+92` is the 32-bit word at field +92 of the struct whose address is held at 0x13120, `i*0x13120` is field +0 of it, `^` is XOR and `asfloat` reads 32 bits as a float:

```
angle  asfloat((i*0x13120 ^ i*0x13120+92))
power  (i*0x13120+4 ^ i*0x13120+92)
```

These expressions are the game's own decoder, and the code computes exactly this every time it needs the angle, for instance to keep it between 5 and 85. Evaluate the angle's expression with module 05's `evaluate`, with a `load` that reads the game's memory as it is now, and the expression gets past both defences:

- Every load goes through the pointer. To read `i*0x13120`, the evaluator first evaluates its address, the word at 0x13120, which holds the struct's address in this round, and then reads field +0 there. On level 3 the pointer holds a new address after every new round, and the expression follows it, because the game's code has to find its state on every frame and finds it the same way.
- The key comes from the same struct at the same moment. XOR gives a 1 in each bit where two words differ, and XORing twice with the same key gives back the word you started from. So the game stores the value XORed with the key and gets the value back with a second XOR. On level 4 the key changes every round and the values are stored with the key of that round, so the expression decodes whatever the round holds.

Here is one evaluation on made-up memory. The word at 0x13120 is 0x10A40 in this round, so field +0 is at 0x10A40 and field +92 at 0x10A9C:

```
i*0x13120      word at 0x10A40     0x973ECFB5
i*0x13120+92   word at 0x10A9C     0xD506CFB5
XOR                                0x42380000
asfloat                            46
```

46 is the angle the status line would show. Read straight as a float, the stored word 0x973ECFB5 is about −6.2 × 10⁻²⁵, which is what a search comparing memory with the screen meets on this build. The power is an integer, so the XOR alone decodes it, with no `asfloat`.

So one reader made of these expressions reads Lob's state on every build so far, plain, moving or scrambled, without knowing which one it's on. It needs no knowledge of either defence, because it does what the code does. On these games, whatever the code must reach and decode while it runs, an expression lifted from that code reaches and decodes too, because the code that undoes a defence inside the client ships with the client. A decoder written as a loop would need more than this lifter, which leaves loops unknown. The server wind is the other kind of defence, and two sections from here deal with it.

## The flag, found by the hit test

The angle and the power came from steppers, because a key changes them. Nothing the player presses moves the flag, so no stepper says where it's kept. One piece of code must read it all the same, the **hit test**, where the frame function decides whether a shell that has just landed counts. Here is one of the stores the frame function makes only when a shell lands close enough to count, from `node lab.mjs lift game_tick ./work`. The landing's long expression is written as LAND, and the flag's expression is written out on the lines below as FLAG and WORD:

```
i*0x13120+64 = 1   when … and
  ((((LAND - FLAG) < 0) ? neg((LAND - FLAG)) : (LAND - FLAG)) <= 12)
FLAG = asfloat((i*0x13120+92 ^ WORD))
WORD = ((i*0x13120+84 & 8): NEW; otherwise: i*0x13120+16)
```

The guard compares the distance between the landing and the flag with 12, the hit radius. LAND is the value of the landing store, the store your `flightOf` found in module 05, and FLAG is decoded the way the angle is. WORD is a phi. On a build where the bit worth 8 in field +84 is set, which is module 07's moving flag, the frame function has already stored a new word at +16 earlier in the same frame, and NEW stands for that stored value. On every other build it's the word loaded from +16.

`flagOf(tickFn, flight, key)` finds that shape with no address written into it:

1. Take `land`, the value of `flight.landing`.
2. For each store of the frame function, for each condition in its guard, look at every expression inside the condition (module 05's `parts`). You want an `f32.le` or `f32.lt` whose right side is a constant, with an `f32.sub` inside its left side whose first argument is `land`. Because equal expressions are one object, "is `land`" is a test with `===`.
3. The subtraction's second argument is the flag's value. The constant is the radius.
4. Undo the decoding to reach the stored word. Remove an `asfloat` (`f32.reinterpret_i32`). Then, if what's left is an XOR with `key`, take its other argument. If it's an `i32.sub` with `key` second, take its first argument.
5. If the word is a phi, take the value on each of its paths, and otherwise take the word itself. For each one, an `i32.load` gives its place. Any other expression is a value the frame function stored, so find the store, not inside a loop and at an address that is a load or a constant, whose value is that expression, and take the store's place.
6. Return `{ value, radius, raws }`, where `raws` holds one `i32.load` for each place found, with no place twice.

`key` is the key of the angle's decoding (`decoding(...).key`), or `null` when the game stores its values plainly. Step 4's second case is for a game whose decoding module 05 calls `add`, which subtracts the key. On Lob, `flagOf` returns a radius of 12 and one place, `*0x13120+16`, on the still and the moving builds alike, because both paths of the phi lead there.

The hit test is the right place to look because it's the one place the code compares the flag with something the engine has already found. The comparison names the flag's expression and the radius in one go.

## A reader made of the code's expressions

A **reader** is a part made of four expressions, one each for the angle, the power, the wind and the flag, evaluated against the game's memory whenever the engine needs the state. `readerFrom(aim, flight, flagRaw)` builds one from findings your engine already has:

- `angle` is `aim.angle.value` and `power` is `aim.power.value`, the decoded values of the steppers.
- `wind` is `flight.wind`, the wind expression module 05's `flightOf` found.
- `flag` is the flag's word decoded the way the angle is. Work out the angle's decoding with `decoding(aim.angle.value, placeKey(aim.angle.raw.addr, aim.angle.raw.offset))`, then build the flag's expression with `decoder({ ...d, float: true }, flagRaw)`. `float: true` because the flag is a float whatever the angle's decoding said.

On Lob the four are:

```
angle  asfloat((i*0x13120 ^ i*0x13120+92))
power  (i*0x13120+4 ^ i*0x13120+92)
wind   ((1 & i*0x13120+84): server_wind();
       (not (1 & i*0x13120+84)): asfloat((i*0x13120+92 ^ i*0x13120+8)))
flag   asfloat((i*0x13120+92 ^ i*0x13120+16))
```

`readState(host, reader, lineAddr)` evaluates them on the game's memory now and returns `{ angle, power, wind, wind_arrows, target_x }`:

- Evaluate each expression with `evaluate` and an `env` of three fields. `load(type, address)` reads `host.memory()`: `i32.load` the little-endian signed word, `f32.load` the float, `i32.load8_u` the byte, and `null` for an address outside memory. `call` answers `null` for every import. `memo` is one `new Map()` shared by the four expressions.
- `target_x` is the flag's value.
- When the wind comes out `null`, `wind_arrows` is the arrow count that `parseStatus` reads from the status line at `lineAddr` (module 01). Otherwise it's `null`.

On level 5 the wind comes out `null`. Its expression is a phi, and on a build with the bit worth 1 in field +84 set, its value is a call of the import `server_wind`. The engine has no server to ask and never runs the game, so `call` answers `null`, and the phi's value is `null`. Nothing in your reader says "level 5".

## The screen check

A reader built from findings is still a hypothesis. The screen is the one thing a defence inside the client can't falsify, because the player has to read it, so the reader's judge compares it with the screen. The lessons call it the **screen check**.

`checkReader(host, look, { lineAddr, rounds = 3, newRound = 'KeyN' })` starts `rounds` new rounds. In each round it presses `newRound`, ticks 2 frames so the status line is drawn, and calls `look()`, which returns the state through the reader under test. A throw is a problem, `round 1: the reader failed:` and the error's message, and the check ends at the first round with no state. Then it compares the state with the status line at `lineAddr`, read with `parseStatus`, and with the flag's cloth, found with `findRed(host.screen())` from module 02:

1. If the line shows no angle and power, that is a problem. A check that compares only when the screen shows numbers would pass a reader the screen never tested.
2. The angle must be within 0.5 of the line's angle, which the line rounds to a whole number. The power, rounded, must equal the line's power.
3. When the line shows a number for the wind, the reader's wind must be a number within 0.051 of it. The line rounds the wind to one decimal place, which can move it by 0.05.
4. When the line shows arrows and the reader returns a number for the wind, that is a problem. The exact wind isn't on the client, so the number was made up.
5. When `findRed` finds the cloth, `target_x` must be within 12 of its `x`. `findRed` gives the middle of the red cloth, which the host draws from 1 to 20 pixels right of the pole, so a correct reader's flag is 10.5 paces left of it. One pixel is one pace on this screen.

It returns `{ ok, rows, problems }`. `rows` keeps what was compared in each round: the state, what the line showed and where the cloth was. Each problem is a sentence that starts with its round, such as `round 1: angle 46 but the screen shows 45`, `round 2: wind 0 but the screen shows 2.7`, `round 1: wind -3 but the screen shows only arrows: the exact wind is not on the client` or `round 3: the flag at 598.0 but the screen shows it near 621`. `ok` is true only when there are no problems and every round was compared.

Each round of the check is a round of the game, so the screen check costs 3 rounds of a level's budget.

## Wind the client never sees

On level 5 no word in the game's memory holds the exact wind. Your reader says so with `wind: null`, and the status line shows only arrows. Each arrow stands for 1.5 units of wind, the count is rounded, and the wind itself stays between −5 and 5, so two arrows mean a wind from 2.25 to 3.75. The count says the wind is somewhere in a range, which the lessons call its **band**:

- `windBand(arrows)` returns `[lowest, highest]`: `[1.5 × (arrows − 0.5), 1.5 × (arrows + 0.5)]`, with the lower end raised to −5 and the higher end lowered to 5 where they pass them.
- `windBand(2)` is `[2.25, 3.75]`, and `windBand(0)` is `[-0.75, 0.75]`.
- `windBand(-3)` is `[-5, -3.75]`: −5.25 would be past the end of the range.

A band is 1.5 wide except at the ends of the range, so the middle of the band is never more than 0.75 from the true wind.

When the status line shows arrows, `checkKit`, later in this module, records the evidence `arrows`. It rules out every option that needs the exact wind. The search pins the wind by comparing memory with the number on the screen, the fit's practice shots are fitted with their wind, and the physics' check shots are compared with landings simulated in the wind. Your `learnPhysics` from module 05 already refuses on such a build, without firing a shot: `the exact wind is not on the client, so no check shot can be compared here`.

## Aiming inside the band

Of the settings that land on the flag at the band's middle wind, the one with the shorter flight is safer, by a factor of the flight time squared.

The wind accelerates the shell sideways. Module 05's flight stores add `0.0166666675 * (wind * 12)` to the sideways speed every frame, where 0.0166666675 is a sixtieth of a second, one frame, and the position gains half of that acceleration times the frame time squared on top of the speed. Over a flight of t seconds the wind's push adds up to ½ × 12 × wind × t², which is 6 × wind × t² paces. Only the middle of the band is known, and the true wind can be up to 0.75 from it, so a shot aimed at the middle can land up to 6 × 0.75 × t² = 4.5 × t² paces from where it was aimed:

- A flight of 1 second can be off by 4.5 paces.
- A flight of 2.5 seconds can be off by 28.1 paces, more than twice the 12-pace radius.

Doubling the flight time multiplies the push by four. So among the settings that land on the flag at the middle wind, the quickest is the safest.

`aimBand(state, predict)` is that rule. `predict(angle, power, wind)` is the physics, giving `{ x, frames }`:

1. Take the band for `state.wind_arrows` (an arrow count of `null` counts as 0) and plan for its middle, halfway between the two ends.
2. Return module 03's `search` for that wind, with `() => state.target_x` as where the flag will be and the options `{ enough: 2, order: 'low' }`.

`order: 'low'` tries the angles from 5 upward, and `enough: 2` stops the search at the first angle whose best setting lands within 2 paces of the flag. For a given distance a lower angle flies flatter and lands sooner, so the first angle that can land within 2 paces gives about the shortest flight. The 2 paces trade a little planned miss for a shorter flight. A wider margin admits shorter flights that start further off the flag, and a narrower one leaves fewer to choose from.

`aimFor`, from modules 03 and 05, now has two cases when the kit holds the physics: `aimBand` when `state.wind` isn't a number, and module 03's search for the exact wind when it is. Module 07 adds a third, a flag that moves. On level 5 this aim hit 10 of 10.

## Learning the reader

`learnReader(host, kit, env, which)` tests one reader the code suggests and, if the screen agrees, puts it in the kit. `which` picks the reader from `analyse(host).readers`:

1. Log `read the state out of the code`, with the sentence from `sayReader(code, cand)`, where `cand` is `code.readers[which]`.
2. Run `checkReader` with a `look` that returns `readState(host, cand.reader, kit.statusLine)`, with `lineAddr: kit.statusLine`, `newRound: kit.controls.new_round` and `rounds: 3`.
3. Log `check the reader against the screen`: `it agreed with the screen in 3 rounds`, or `refuted:` followed by the first two problems joined by `; `.
4. If the check failed, return `null` and leave the kit as it was.
5. Otherwise set `kit.reader = { game: gameId(host), which, says }`, delete `kit.found`, and return `kit.reader`.

The kit keeps `which`, not the expressions, because the kit is plain data that the lab saves as JSON. Whenever the engine needs the reader, it rebuilds it from `analyse(host).readers[kit.reader.which]`, which costs nothing after the first analysis of a game. The searched addresses go because the confirmed reader replaces them. Two ways of reading the state would sooner or later disagree, and only one of them has passed the screen check.

`analyse(host)` lists the readers the code suggests. Module 05 left its `flag` as `null` and its `readers` empty, and now it fills them in. After the physics, it sets `code.flag` to `flagOf(tickFn, flight, decode.key)` when the flight and the decoding were found, and adds one entry to `code.readers` for each place in `code.flag.raws`: `{ raw, reader: readerFrom(aim, flight, raw), mover }`. `mover` is module 07's, and stays `null` until then.

`sayReader(code, cand)` is the sentence the log, the menu and the decision model read. For Lob it is:

```
The state is the struct at *0x13120, values stored XORed with the
word at +92: angle at +0, power at +4, flag at +16, wind at +8, or
from the server in builds that take it from there.
```

The struct is `place(d.raw.addr)` for the angle's decoding `d`. The middle part reads `values stored as they are`, `values stored XORed with the word at +K` or `values stored with the word at +K added`, for decodings `plain`, `xor` and `add`. Then come the offsets of the angle, the power and the flag. Last comes the wind, as `wind at +N` with the offset of `windWord(flight, d)`, or as plain `wind` when that finds no stored word, followed by `, or from the server in builds that take it from there` when the wind expression calls `server_wind`. When the flight has no wind, that part reads `the wind is not used`.

`windWord(flight, d)`, which you add to `flight.mjs`, finds the stored word the wind is decoded from. It goes through `flight.wind` in the order `parts` gives, looking for an `asfloat` (`f32.reinterpret_i32`). When the `asfloat` holds an `i32.load`, that load is the word. When it holds an XOR or a subtraction with `d.key`, the word is the side that isn't the key. `windWord` returns that load expression, or `null` when the code keeps no wind word. On Lob it returns the load of `*0x13120+8`, so the sentence says `wind at +8`.

`look(host, kit, env)` gets its reader branch, before the others. With a reader in the kit, it returns `readState(host, readerOf(host, kit).reader, kit.statusLine)`, where `readerOf` rebuilds the reader as described above. Without one it reads the addresses in `kit.found`, as before, and with neither it throws `nothing in the kit reads the state`. `checkKit`, in the next section, tests a reader already in the kit against the screen with no new round.

## The engine checks its kit

From level 3 on, a level can break something the kit holds, and the engine can't know which thing in advance. Module 03's `checkKit` knew the controls, the state and the aim, and module 05 gave it the evidence `exact`. This module gives it the rest: a test of a reader, more kinds of evidence, and a fourth problem, a flag that moves. It still answers with the first problem it finds, most basic first, or `null` when the kit is ready for the level. A problem is `{ part, why, evidence, options }`:

- `part` names what the problem is about: `'controls'`, `'state'`, `'flag'` or `'aim'`.
- `why` is a sentence for the log and for the decision model.
- `evidence` lists what the engine has seen on this level that rules options out.
- `options` is the menu, the next section's subject.

Here is `checkKit` in full, as this module leaves it. Steps 3, 4 and 7 are new, and step 5 now records evidence. It runs the steps in order and returns at the first problem:

1. Start `evidence` empty. If `level.radius` is under 12, add `exact`, because a target that small needs the exact physics. Level 2's target is 3 paces.
2. The controls. If `controlsHold(host, kit)` from module 01 is false, the problem is `controls`, with the why `the controls are not known on this game` and one option, pressing each key. `controlsHold` presses the angle and power keys one way and back and starts no round.
3. If the status line shows wind arrows, add `arrows`.
4. The state. If the kit has a reader, test it against the screen now, with no new round, through `look`. The angle must be within 0.5 of the line's, the power equal, the wind within 0.051 when the line shows a number, and the flag within 12 of the cloth. A reader that fails is deleted from the kit, and the sentence saying how it failed becomes the why: `the reader in the kit fails here` when `look` throws, `the reader in the kit reads angle A and power P; the screen shows S and T` when the angle or the power disagrees, or the line shows no number for them, `the reader in the kit reads wind W; the screen shows S` for the wind, and `the reader in the kit puts the flag where the screen does not` for the flag.
5. If nothing reads the state yet and the kit has found addresses, test them by starting a new round and comparing the angle, power and wind at those addresses with the status line. A new round brings a new wind, so addresses that point at an old copy of the state fail on the wind even when the angle and the power there still match the barrel. If the line shows no angle and power, the why is `the status line shows no angle and power to compare with`, with no evidence. If the angle or the power is wrong, the why is `a round later the addresses found by searching no longer hold what the screen shows (angle A there, S on screen)` and the evidence `moves`. It names the angle even when only the power is wrong, with A the angle read at the found address and S the angle on the line. If the line shows arrows, the why is `the screen shows only wind arrows, so an address for the wind is no use` and the evidence `arrows`. If the wind is wrong, the why is `the address found for the wind holds W; the screen shows S` and the evidence `moves`. Addresses that fail are deleted from the kit. This test costs one round.
6. If nothing reads the state, the problem is `state`, with the why `nothing reads the state yet` unless step 4 or 5 gave one.
7. The flag. If the kit has no flag motion, find out whether the flag moves on its own by reading `target_x` through `look`, ticking 20 frames, reading it again, ticking 20 more and reading it a third time. If either change is more than 0.001 paces, add `flag-moves`, and the problem is `flag`, with the why `the flag moves while nothing is happening, and nothing in the kit says how`. Twenty frames is a third of a second, long enough for a moving flag to show it, and the second wait covers a flag that stood still during the first. If the kit has a flag motion, add `flag-moves` and go on.
8. The aim. If the kit holds the physics for this game, `kit.physics.game` equal to `gameId(host)`, the kit is ready, so return `null`. If no evidence is `exact`, `arrows` or `flag-moves`, a fit for this game will do as well. Otherwise the problem is `aim`, with the why `this level needs the exact physics` when there is such evidence and `nothing in the kit aims yet` when there isn't.

The order is the order in which each thing depends on the one before. The state can't be compared with the screen without the status line and the keys. The flag is read through the state. The aim needs the state, and on a moving flag it needs the motion too.

The kinds of evidence, when each is recorded, and what each rules out:

- `moves`: found addresses fail a round later. It rules out the search.
- `arrows`: the status line shows wind arrows. It rules out the search, the fit and the physics.
- `exact`: the level's radius is under 12 paces. It rules out the fit.
- `flag-moves`: the flag moves while nothing happens. It rules out the fit.

The fit is ruled out by `flag-moves` because it aims at where the flag is when the shot is planned and has no way to say where the flag will be.

## The menu: options, costs and limits

Each option on the menu is a hypothesis about what will fix the problem. It carries an estimate of what testing it costs, in rounds and shots, and its limits, the evidence that would rule it out. Here are the kinds, each with its estimate, its limits and what it runs:

- `controls` costs 2 rounds, has no limits and runs `learnControls`.
- `search` costs 6 rounds, has the limits `moves` and `arrows`, and runs the search of module 02.
- `reader`, one for each reader the code suggests, costs 3 rounds, has no limits and runs `learnReader`.
- `fit` costs 7 rounds and 17 shots, has the limits `exact`, `arrows` and `flag-moves`, and runs `learnFit`.
- `physics` costs 3 rounds and 3 shots, has the limit `arrows` and runs `learnPhysics`.
- `motion`, one for each reader that has a mover, costs 2 rounds, has no limits and runs module 07's `learnMotion`.

The fit's estimate counts every sighting shot `learnFit` may fire before its 14 practice shots, 3 rounds and 3 shots on top of 4 rounds and 14 shots. On level 1 at module 03 it spent 5 rounds and 15 shots.

The search runs `findValues` with `choose(env, 'the next experiment', text, labels)` as its decider, as in module 02. On success it sets `kit.found` and logs `search memory for the values: found angle, power, wind and flag in N experiments`. When it fails it sets `kit.found` to `null` and logs `search memory for the values: failed:` and the error. An `OutOfBudget` error isn't a failure of the search, so let it through.

Module 03 built each option as `{ kind, key, label, cost, run }`, and module 05 gave the physics its `limits`. Every option now has all of these: `{ kind, which, key, label, cost, limits, run }`. `which` is the reader it belongs to, or 0. `key` is the kind and `which` joined by a colon, such as `reader:0`, and names the option within a level. `cost` is `{ rounds, shots }` and `limits` a list of evidence kinds. `run(host, kit, env)` runs the option's function, passing `which` on to `learnReader`. `label` is all a decision model knows about the option, so it says the cost and the limits in words:

- `controls`: `Press each key and watch the status line`
- `search`: `Search memory for the values (about 6 rounds; what it finds stops working if the state moves or is scrambled, and it needs the wind on the screen)`
- `reader`: `Test what the code says about the state (3 rounds against the screen): ` followed by `sayReader`'s sentence for that reader
- `fit`: `Fire 14 practice shots and fit an aim to them (about 7 rounds and 17 shots; good to about 10 paces)`
- `physics`: `Test what the code says about a shot with 3 check shots (3 rounds, 3 shots): ` followed by module 05's `sayPhysics(code)`

The menu for each problem:

- `controls`: the `controls` option.
- `state`: the `search` first, then one `reader` option for each entry of `code.readers`.
- `flag`: one `motion` option for each reader that has a mover. Until module 07 no reader has one, so on a level whose flag moves this menu is empty.
- `aim`: the `fit`, but only when no evidence calls for the exact physics and the kit has found addresses, because practice shots are measured at found addresses, and then the `physics` if `code.simulate` exists.

The menus keep the course's order: first the way that needs no reading of the code, then what the code says. Option 0 follows that order, not the costs. By the estimates, the code's way is the cheaper one on Lob, 3 rounds against 6 for the state, and 3 rounds and 3 shots against 7 and 17 for the aim.

The search stays on every state menu, even when the evidence rules it out, while the fit is left off a menu it can't serve. "Budgets make the order matter", below, gives the reason.

## A rule to measure the decision model against

The picker, as module 01 put it, is whoever answers a menu: your heuristic, option 0, random picks or a decision model. To say whether a decision model's picks are any good, the course needs a rule to compare it with, written in code you can read. `heuristic(problem, options)` is that rule. It picks the cheapest option that no evidence rules out.

1. Skip every option whose `limits` include any kind in `problem.evidence`.
2. Among the rest, compare costs as `rounds × 100 + shots`. No option costs 100 shots, so shots never outweigh a round. Rounds count first, and shots decide only between equal rounds. Rounds come first because every option spends them and only some spend shots.
3. Return the index of the cheapest. Of equals, keep the first, replacing the best only with one that is cheaper.
4. If every option is ruled out, return 0, and the menu's own order decides.

On level 3 from the kit level 2 left, the evidence is `moves`, the search is ruled out, and the rule returns 1, the reader. On level 1 from an empty kit there is no evidence, and the rule still returns 1, the reader's 300 against the search's 600.

On Lob's menus the cheapest option is never one the evidence rules out, so your rule would pick the same with the evidence left out. The evidence matters to the pickers that don't compare costs. Option 0 ignores both. A decision model gets the evidence in words, in the problem's why and the options' labels, and the measurement asks whether it reads them.

In the lab, `--picker rule`, the default, answers with your `heuristic` on every menu for a problem and with option 0 on any other menu, such as module 02's experiment menu. `--picker first` always answers 0 and `--picker random` picks at random.

## Budgets make the order matter

`playLevel(host, level, kit, env)` keeps the loop you wrote in module 03. It learns only through the metered host, which throws `OutOfBudget` rather than spend past the allowance. In each pass it asks `checkKit` for the first problem, keeps the options not yet tried on this level whose cost fits the room left, the allowance less what has been spent, and picks one with `choose(env, 'what to try next', text, options)`. It adds the pick's `key` to the tried set, runs it on the metered host, and logs what it spent. It stops when the kit is ready, when nothing left fits the budget, after 10 passes, or when the metered host refuses a press, and then plays the scored rounds with `playRounds` on the host itself. The figure shows the first two of those stops.

{{figure:engine-loop}}

What changes in this module is what reaches the picker. Menus now have more than one option, so the pick decides what runs and what the level spends. Each option goes to `choose` as `{ ...option, problem }`, as module 03 set out, so a picker that is code, such as your heuristic, can read the problem's evidence. A decision model is sent only the text, `Level N, NAME: ABOUT Problem: WHY. Left for learning: R rounds and S shots.`, and the labels. The log entries keep their module 03 form: `repair` with the why and the picked option's label, `spent` with the option's kind and what it used, `nothing left to try that fits the budget (R rounds and S shots left) for the PART: WHY` when no option fits, and `repair`: `stopped:` with the message when the metered host refuses a press.

When the loop ends with a problem still standing, the engine plays with whatever the kit holds. If nothing reads the state, `playRounds` logs `round 1: cannot play: nothing in the kit reads the state; firing nothing` and returns at once. Module 07 adds a step between the loop and the rounds, and module 08 sets out the step in front of the loop that empties a kit from another game.

Level 3 has a budget of 18 rounds and 12 shots, and the 10 scored rounds take 10 of each, so the allowance is 8 rounds and 2 shots.

- `06-flag`: usually the decoding wasn't undone, so the place found is the key's, or the phi of a moving flag wasn't followed to the store's place.
- `06-read-state`: a value disagreed with the game. If it's the wind on a server-wind build, your `call` returned something other than `null` for the import, or `wind_arrows` wasn't read from the status line.
- `06-check-reader`: your check accepted a wrong angle, a wrong flag or a made-up wind, or failed a correct reader. Compare your tolerances with the five rules.
- `06-wind-band`: a band wasn't cut at −5 and 5, or the arrows were read as a wind.
- `06-aim-band`: `aimBand` planned for a wind other than the middle of the band, returned a setting more than 2 paces off, or passed over a lower angle with a setting that lands within 2 paces.
- `06-learn-reader`: the reader wasn't confirmed in 3 rounds on level 3, or the searched addresses were left in the kit.
- `06-check-kit`: the problems came in another order, or a kind of evidence was missing: `moves` once found addresses fail a round later, `arrows` under server wind, `exact` at a radius of 3, `flag-moves` for a flag that moves.
- `06-menu`: the state menu didn't start with the search followed by each reader, or an option lacked its cost or its limits.
- `06-heuristic`: an option the evidence rules out was picked, shots were compared before rounds, or a later option of equal cost replaced the first.
- `06-picks`: your engine didn't do what the picker picked. On level 3 from a searched kit, picking the reader must mean no search runs, and picking the search must mean it runs once and isn't offered again on that level.
- `06-budget`: the engine went over a level's budget, or kept repairing after the allowance ran out instead of playing.
- `06-stuck`: with nothing to read the state, your engine threw or let a shot land. It has to log why and fire nothing.
- `06-level-3`, `06-level-4`, `06-level-5`: the level wasn't passed within its budget. The steps that `node lab.mjs level N ./work` prints show what your engine did.
