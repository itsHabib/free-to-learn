## A flag that moves

The fourth defence is a moving flag. Level 6 adds it to the moving state and scrambled values of level 4, and level 7 has every defence at once, the server wind included. Your reader from module 06 reads the flag's position on these builds as it did before, through the decoded word at `*0x13120+16`. What it can't say is where the flag will be when a shell lands, a second or more later.

The engine notices without being told. At the start of level 6 your `checkKit` finds the keys working and the reader agreeing with the screen, and then reads the flag three times, 20 frames apart. The flag has moved while nothing was happening. It adds the evidence `flag-moves` and reports the `flag` problem, whose menu offers one option for each reader that has a mover. In module 06 no reader had one, so the menu was empty. This module gives each reader its mover.

Time now matters. A shell flies for a second or more before it lands (the 14 practice shots of module 03 flew from 71 to 211 frames), and between the engine's look at the game and the shot leaving, some frames pass. The lessons call that number of frames the **delay**. For code the delay is about a frame. For a decision model it's the time its answer takes.

In the lab, the game's clock moves only when your engine ticks it, so a model that takes half a second to answer doesn't move the flag by itself. Your engine counts that time against itself. Before a shot leaves, it ticks the frames the decision is taken to have cost. That keeps every run repeatable, and it means the count is only as true as the engine makes it.

## The flag's motion is a slice

The frame function moves the flag, and module 05's slice finds which of its stores do it, by taking the stores that decide a set of places, then the stores to every place those read, until nothing is added. `moverOf(tickFn, flagRaw)` is the slice of the frame function for the flag's place:

```
slice(tickFn.stores, [placeKey(flagRaw.addr, flagRaw.offset)])
```

On Lob it holds 6 stores. Here is what each one does, read from `node lab.mjs lift game_tick ./work`. All six run only when the bit worth 8 in field +84 is set, the moving-flag build:

- `+16`, the flag's word: the old position plus the speed times 0.0166666675, a sixtieth of a second, held between 420 and 900, then stored XORed with the key.
- `+96`, the speed in paces a second: turned round (`neg`) when the new position would pass 420 or 900. That is the bounce.
- `+100`, a timer: one less every frame.
- `+96` again: a new speed when the timer runs out. The code draws a number r from 0 to 1 from the game's random number generator and stores 140 × (2r − 1), so a speed of up to 140 paces a second either way.
- `+80`, the state of that generator: moved on by its own shifts and XORs, once for each number drawn, when the timer runs out.
- `+100` again: a new timer when the old one runs out, 120 plus a number from 0 to 179 drawn from the generator. So the flag changes speed every 120 to 299 frames.

Module 05 followed this slice as it grows. The flag's store reads the speed at +96, as well as the key at +92 and the mode at +84. A store of +96 reads the generator at +80 and the timer at +100, and the stores of +80 and +100 read nothing new. No store of the frame function writes +92 or +84, so the slice stops at six, kept in the order the function makes them.

`sayMover(cand)` is the sentence for the log and the menu: `game_tick moves the flag with N stores, to` and the places those stores write, each once, in the slice's order. For Lob it says `game_tick moves the flag with 6 stores, to +96 +16 +100 +80.` For a slice of one store, "store" has no s.

In `analyse`, each entry of `code.readers` gets its mover, `moverOf(tickFn, raw)` for that reader's flag place.

```js {"file":"examples/engine-checkpoint-07.mjs","region":"analyse","title":"The findings, with each reader's mover","change":"Replace the analyse region of work/engine.mjs."}
// The findings, worked out once per game: look and aimFor ask for them
// every round, and the same file always gives the same findings.
const analyses = new Map();

export function analyse(host) {
  const id = gameId(host);
  if (analyses.has(id)) return analyses.get(id);
  const lifted = liftAll(parseModule(host.binary()));
  const keyFn = lifted.get('game_key');
  const tickFn = lifted.get('game_tick');
  const launch = keyFn ? launchOf(keyFn) : null;
  const aim = launch ? aimValues(keyFn, launch) : null;
  const flight = launch && tickFn ? flightOf(tickFn, launch) : null;
  const raw = aim?.angle.raw;
  const rawKey = raw ? placeKey(raw.addr, raw.offset) : null;
  const decode = aim ? decoding(aim.angle.value, rawKey) : null;
  const all = launch && aim && flight;
  const simulate = all ? simulator(launch, aim, flight) : null;
  const code = {
    ...{ lifted, launch, aim, flight, decode, flag: null, simulate },
    ...{ readers: [], constants: [] },
  };
  if (launch) code.constants = constantsOf(lifted, launch);
  // The flag, by the hit test, and a reader for each place it may be
  // kept in, with the flag's motion for that place.
  if (flight && decode) {
    code.flag = later(() => flagOf(tickFn, flight, decode.key));
  }
  for (const raw of code.flag?.raws ?? []) {
    const reader = later(() => readerFrom(aim, flight, raw));
    const mover = later(() => moverOf(tickFn, raw));
    if (reader) code.readers.push({ raw, reader, mover });
  }
  analyses.set(id, code);
  return code;
}

// The value of f(), or null while f needs a function that is not
// written yet, so analyse works before reader.mjs and race.mjs do.
function later(f) {
  try {
    return f();
  } catch (error) {
    if (/not written yet/.test(error.message)) return null;
    throw error;
  }
}
```

## Running the slice on a copy of memory

The slice predicts the flag exactly, past every change of speed. The random generator's state is a field of the game's own struct, +80, and the store that moves it on is in the slice. Run the slice on a copy of memory and the copy draws the same numbers the game will draw, from the same state, at the same frame. Random numbers made on the client aren't random to code that reads the client.

`flagPath(bytes, mover, flag, frames)` says where the flag will be:

1. Make `m = overlay(bytes)`, module 05's memory that reads the game's bytes and keeps its own writes in a map, never touching the game.
2. The flag's position is `evaluate(flag, { load: m.load, call, memo: new Map() })`, where `flag` is the reader's flag expression. `call` answers imports the way your simulator from module 05 does for `sin` and `cos`, with `Math.sin` and `Math.cos` for imports whose names end in `.sin` and `.cos`, as the page supplies them, and `null` for any other.
3. `path[0]` is the position now.
4. For each of the next `frames` frames: if the entry before is `null`, push `null`. Otherwise run the mover once with module 05's `apply(mover, m, { call })` and push the position.
5. Return the path, `frames + 1` entries.

Once one entry is `null`, every later one is too, because a position the code can't work out at one frame leaves nothing to work the next from.

The path is exact because nothing in it is an approximation of the game. The evaluator does the game's own arithmetic, with `f32` rounding after every float operation and 32-bit integers. `apply` works out every value of a frame from memory as it was before the frame's first store, then writes them, which is what the lifted values mean. The generator's state is written on the copy as it is in the game. The game's frame function also moves the cloud, counts frames and flies the shell, and none of that is in the slice, because none of it decides the flag.

The engine runs only six stores it found, can read and will test in the next section. Running a copy of the whole game file would predict everything and explain nothing, and module 08 makes it a rule you can check.

```js {"file":"examples/race-checkpoint.mjs","region":"flag-path","title":"Where the flag will be, frame by frame","change":"Replace the flag-path region of work/race.mjs."}
// The page's sin and cos, as the simulator answers them; null for any
// other import.
function call(name, args) {
  if (name.endsWith('.sin')) return Math.sin(args[0]);
  if (name.endsWith('.cos')) return Math.cos(args[0]);
  return null;
}

export function flagPath(bytes, mover, flag, frames) {
  const m = overlay(bytes); // writes stay in the copy
  const env = () => ({ load: m.load, call, memo: new Map() });
  const at = () => evaluate(flag, env());
  const path = [at()];
  for (let k = 1; k <= frames; k++) {
    // Once the flag can't be worked out, nothing after it can be.
    if (path[k - 1] === null) {
      path.push(null);
      continue;
    }
    apply(mover, m, { call });
    path.push(at());
  }
  return path;
}
```

## The motion judge

A path from the slice is still a hypothesis. The **motion judge** tests it against the frames that follow. `judgeMotion(host, look, pathNow, { newRound = 'KeyN', rounds = 3, frames = 300 })` asks for a prediction and then watches the game:

1. For each round, numbered from 1, while no problem has been found, press `newRound` and tick 2 frames plus 7 times the round's number, so the rounds are caught at different moments.
2. Ask `pathNow(frames)` for the path from memory as it is now. A throw is a problem, `round 1: the path failed:` and the message. So is a result that isn't a list of `frames + 1` entries: `round 1: a path for 300 frames must have 301 entries, got 12`.
3. For each entry from 0 to `frames`: tick one frame first, except for entry 0. A `null` ends this round's comparison without a problem. Otherwise compare the entry with `look().target_x`. More than 0.05 paces apart is a problem, such as `round 1: the path said the flag would be at 685.00 after 182 frames; it was at 684.74`, and judging ends. Count each entry after 0 that matched as predicted.
4. If there is no problem and fewer than 20 frames were predicted over all the rounds, that is a problem too: `the path predicted only 14 frames over 2 rounds; it gives null too early to plan a shot`. A path that says "can't know" almost everywhere is no use for planning.
5. Return `{ ok, problems, predicted }`.

The number of frames the judge watches in each round is how far ahead the path is tested. A path that ignores the bounce, or the changes of speed, is right until the first bounce or change and wrong after it, so a short watch can pass it. 300 frames is longer than the longest timer the frame function sets, 299 frames.

`learnMotion(host, kit, env, which)` tests one reader's mover and, if the flag agrees, puts it in the kit:

1. Take `cand = analyse(host).readers[which]`. Log `read the flag's motion out of the code` with `sayMover(cand)`.
2. Run `judgeMotion` with a `look` of `() => look(host, kit, env)`, with `pathNow = (frames) => flagPath(host.memory(), cand.mover, cand.reader.flag, frames)`, and with `newRound: kit.controls.new_round`, `rounds: 2` and `frames: 300`.
3. Log `watch the flag`: `the path held for N frames over 2 rounds`, or `refuted:` and the first problem.
4. If the judge refuted the path, return `null`. Otherwise set `kit.mover = { game: gameId(host), which, says }` and return it.

The `motion` option on the flag menu runs `learnMotion` for its reader. Its estimate is 2 rounds, it has no limits, and its label is `Test what the code says about the flag by watching it for 2 rounds: ` followed by `sayMover`'s sentence.

```js {"file":"examples/race-checkpoint.mjs","region":"judge-round","title":"One round of the motion judge","change":"Replace the judge-round region of work/race.mjs."}
// One round of the judge: { predicted, problem }. predicted counts the
// frames after the first that matched; a null entry ends the round.
function judgeRound(host, look, pathNow, frames, r) {
  let path;
  try {
    path = pathNow(frames);
  } catch (error) {
    const why = String(error?.message ?? error);
    const problem = `round ${r}: the path failed: ${why}`;
    return { predicted: 0, problem };
  }
  if (!Array.isArray(path) || path.length !== frames + 1) {
    const got = Array.isArray(path) ? path.length : typeof path;
    const want = `must have ${frames + 1} entries, got ${got}`;
    const problem = `round ${r}: a path for ${frames} frames ${want}`;
    return { predicted: 0, problem };
  }
  let predicted = 0;
  for (let k = 0; k <= frames; k++) {
    if (k > 0) host.tick(1);
    if (path[k] === null) break;
    const x = look().target_x;
    if (!(Math.abs(path[k] - x) <= 0.05)) {
      const said = `${Number(path[k]).toFixed(2)} after ${k} frames`;
      const was = `it was at ${x.toFixed(2)}`;
      const would = 'the path said the flag would be at';
      const problem = `round ${r}: ${would} ${said}; ${was}`;
      return { predicted, problem };
    }
    if (k > 0) predicted++;
  }
  return { predicted };
}
```

```js {"file":"examples/race-checkpoint.mjs","region":"judge-motion","title":"The motion judge","change":"Replace the judge-motion region of work/race.mjs."}
export function judgeMotion(host, look, pathNow, opts = {}) {
  const { newRound = 'KeyN', rounds = 3, frames = 300 } = opts;
  const problems = [];
  let predicted = 0;
  for (let r = 1; r <= rounds && !problems.length; r++) {
    host.press(newRound);
    host.tick(2 + 7 * r); // each round caught at another moment
    const round = judgeRound(host, look, pathNow, frames, r);
    predicted += round.predicted;
    if (round.problem) problems.push(round.problem);
  }
  if (!problems.length && predicted < 20) {
    const few = `the path predicted only ${predicted} frames`;
    const late = 'it gives null too early to plan a shot';
    problems.push(`${few} over ${rounds} rounds; ${late}`);
  }
  return { ok: problems.length === 0, problems, predicted };
}
```

## Leading the flag

Aiming at where the flag will be is called **leading** it. `lead(state, predict, path, delay = 1)` finds the shot, with `predict(angle, power, wind)` the physics and `path[k]` where the flag will be after `k` frames:

1. With an exact wind, plan for that wind. With only the arrows, plan for the middle of their band, as `aimBand` does.
2. A setting that flies `frames` frames, fired after `delay` frames, lands when the flag is at `path[delay + frames]`. That is where it must land. Past the end of the path, or where the path is `null`, it can't be planned.
3. Return module 03's `search` with `at(frames)` giving that position, `{ enough: 0.5, order: 'middle' }` with an exact wind, and `{ enough: 2, order: 'low' }` with only the arrows.

The delay moves every landing frame by the same number of frames, which is why it has to be in the sum. A slower shell has to be aimed further ahead.

Here it is on made-up numbers. The flag is at 700 and moves left half a pace a frame, so `path[k]` is 700 − 0.5 × k. The wind is exact and the delay is 10. Some of the settings the search tries:

- One that flies 62 frames lands at frame 72, when the flag is at 664. Its x is 666, so it misses by 2.
- One that flies 104 frames lands at frame 114, when the flag is at 643. Its x is 643, a miss of 0.
- One that flies 133 frames lands at frame 143, when the flag is at 628.5. Its x is 632, a miss of 3.5.

Of the three, only the second is within the 0.5 paces the search wants with an exact wind.

`ready(plan)` says whether a plan is good enough to fire at a moving flag. It's true when the plan isn't `null` and its `miss` is at most 2. Settings are whole numbers, so the best setting can land a few paces from where the flag will be. A frame later the flag is somewhere else and another setting may fit.

`aimFor` gets its third case. When the kit has the physics and a flag motion, take the reader the motion belongs to, `analyse(host).readers[kit.mover.which]`, and get the path for the next 700 frames with `flagPath`. If the path isn't all one value, return `lead(state, predict, path, delay)` with `moving: true` added to the plan. If it's all one value, the flag stands still, and `aimFor` goes on to its cases from module 06.

## Fire or wait

`kit.decider` says who decides when to fire and what a decision costs: `{ who, frames }`, where `who` is `'code'` or `'model'`, or code at 1 frame when the kit has none. `playRounds` uses it. For each round:

1. Start a new round.
2. Look, and plan with `aimFor(host, kit, state, env, delay)`, where `delay` is the decider's `plan` when it has one and its `frames` otherwise. Only the sweep, below, sets `plan`. If nothing reads the state, log `cannot play` and return, as before. If there is no plan, stop looking.
3. If the frames this round has let pass while looking, the waits included, add up to 600 or more, stop looking. The engine fires the plan it has just made, ready or not, without asking.
4. If the plan is for a moving flag and isn't ready, tick one frame and go back to step 2.
5. If code decides, go to step 6. If the model decides, ask it with `choose(env, 'fire or wait', text, ['Fire now', 'Wait and look again'])`, where `text` is `The planned shot lands in F frames, M paces from where the flag will be.`, with the miss to one decimal place. On `Fire now`, go to step 6. On `Wait and look again`, tick the decider's `frames`, since asking took that long, and go back to step 2.
6. If there is no plan, log `round N`: `nothing in the kit can aim`, and go to the next round. Otherwise tick the decider's `frames`, the delay the plan was made for, and fire the plan.

The clock is read in step 3, right after a plan is made, so the plan that is fired always comes from what the engine has just seen. Had the engine read the clock after a wait instead, a round that ran out of time there would fire the plan made before the wait, aimed for a moment that had already passed.

A plan for a flag that stands still is fired at once whatever its miss. Waiting changes nothing, because the same settings land in the same places a frame later.

Both options on this menu are safe. The model is asked only once the plan is ready, so `Fire now` fires a plan that lands within 2 paces of where the flag will be. `Wait and look again` costs the decider's frames, and the engine plans again from what it sees then. A model that isn't there, or answers off the menu, gets option 0 from `choose`, which fires.

### Write the fire-or-wait loop

```js {"file":"examples/engine-checkpoint-07.mjs","region":"play-rounds","title":"Wait for a ready plan, and ask the decider","change":"Replace the play-rounds region of work/engine.mjs."}
// Ask the decider whether to fire a plan that is ready.
async function fireNow(env, plan) {
  const miss = plan.miss.toFixed(1);
  const text =
    `The planned shot lands in ${plan.frames} frames, ${miss} paces` +
    ' from where the flag will be.';
  const options = ['Fire now', 'Wait and look again'];
  return (await choose(env, 'fire or wait', text, options)) === 0;
}

// Look and plan until the plan can be fired: { plan }, with plan null
// when nothing can aim, or { cannot } when nothing reads the state.
async function planToFire(host, kit, env, who) {
  const delay = who.plan ?? who.frames;
  // waited: the frames this round has spent looking, waits included.
  for (let waited = 0; ;) {
    let state;
    try {
      state = look(host, kit, env);
    } catch (error) {
      return { cannot: error.message };
    }
    const plan = aimFor(host, kit, state, env, delay);
    // At 600 frames, fire the plan just made, ready or not.
    if (!plan || waited >= 600) return { plan };
    if (plan.moving && !ready(plan)) {
      host.tick(1); // a frame later another setting may fit
      waited += 1;
      continue;
    }
    if (who.who !== 'model') return { plan };
    if (await fireNow(env, plan)) return { plan };
    host.tick(who.frames); // asking took the decider's frames
    waited += who.frames;
  }
}

export async function playRounds(host, level, kit, env) {
  const who = kit.decider ?? { who: 'code', frames: 1 };
  let hits = 0;
  for (let n = 1; n <= level.rounds; n++) {
    newRound(host, kit);
    const { plan, cannot } = await planToFire(host, kit, env, who);
    if (cannot) {
      const why = `cannot play: ${cannot}; firing nothing`;
      say(env, 'code', `round ${n}`, why);
      return { hits, rounds: level.rounds };
    }
    if (!plan) {
      say(env, 'code', `round ${n}`, 'nothing in the kit can aim');
      continue;
    }
    host.tick(who.frames); // the delay the plan was made for
    if (fire(host, kit, env, plan).hit) hits++;
  }
  return { hits, rounds: level.rounds };
}
```

## Planned and unplanned delay

The engine counts the delay into its plan. What happens when the count is wrong?

`sweep(newHost, level, kit, env, latencies)` measures it. Each entry of `latencies` is a delay to try, in frames. For each delay the sweep plays the level's rounds twice, each time with `playRounds` on a fresh host from `newHost()`, so both runs meet the same rounds:

- **Planned**: with `kit.decider = { who: 'code', frames: latency }`. The plan is made for the delay, and the shot leaves after it.
- **Unplanned**: with `kit.decider = { who: 'code', frames: latency, plan: 1 }`. The plan is made for a delay of 1 frame, and the shot still leaves after the whole delay. The frames of delay the plan didn't count are the **surprise**, here the delay less 1.

It keeps the `hits` each run returns, returns `[{ latency, planned, unplanned }]`, with `latency` the delay tried, and puts `kit.decider` back as it was. A lab command, which you will run after the next prediction, runs it on level 6 with the kit level 6 left. It prints that prediction's answer. Its delays are 1, 2, 3, 4, 6, 9, 12, 18, 30 and 54 frames.

## The frame budget

Your sweep gives the number the engine needs. `FRAME_BUDGET` in `work/race.mjs` is the longest surprise, in frames, at which your sweep still hit at least 9 of 10. Read it from the unplanned column by taking the largest delay in it that hit at least 9 of 10, even if a shorter delay hit fewer, and subtracting the 1 frame the plan already counts. On level 6 that is 6 less 1, which is 5. The check `07-sweep` runs your own sweep on level 6 and fails unless `FRAME_BUDGET` is the number this rule gives.

Level 7's sweep, `node lab.mjs sweep ./work --level 7`, gives the same answer, since its unplanned column held 9 of 10 at a delay of 6 and fell to 8 at 9.

The sweep counts in frames, never in milliseconds. Time measured in real seconds depends on how busy the computer is, and the same seed would give different results on different runs. Counted in frames, the same seed gives the same hits every time.

## When the decision model may decide

The decision model's answer time is its delay. The part of that time that is the same on every call can be planned for, and the part that varies is surprise.

`pickDecider(env, budget = FRAME_BUDGET)` measures both:

1. Ask `env.models.decide` three practice questions, with the options `['Fire now', 'Wait and look again']`, and keep each answer's `ms`. The course's own engine asks `The planned shot lands in 96 frames, 0.4 paces from where the flag will be.`, then 106 frames and 0.5 paces, then 116 and 0.6. If a call throws, log `time the decision model`: `unavailable; code decides`, and return `{ who: 'code', frames: 1 }`.
2. Sort the three times. The middle one, in frames, is the delay to plan for: `Math.round(ms × 60 ÷ 1000)`, and at least 1.
3. The **spread** is the slowest time minus the fastest, turned into frames after the subtraction: `Math.round((slowest − fastest) × 60 ÷ 1000)`.
4. If the spread is at most the budget, the model decides, and the result is `{ who: 'model', frames }`. Otherwise it's `{ who: 'code', frames: 1 }`.
5. Log `time the decision model`: `answers took T1, T2, T3 ms: F frames to plan for, and a spread of S frames against a budget of N, so the model decides when to fire`, ending `code decides when to fire` instead when code decides. T1 to T3 are the three times sorted from fastest to slowest, rounded to whole milliseconds. A count of 1 takes the singular, `1 frame`, here and in every log line that counts rounds, shots or frames.

These are the course's words, and the logs printed in this lesson use them. As with every log entry except module 03's budget line, the words of the steps and results are yours: `07-decider` checks what `pickDecider` returns, not what it logs.

The engine plans for the middle answer, so an answer can stray from the plan by up to the spread, and the budget is the surprise your sweep showed the engine can take. Three timings are a small sample. They stand in for the surprise a real clock would bring, and they can understate it.

`playLevel` gets its step between the loop and the rounds. Set `kit.decider = { who: 'code', frames: 1 }`. Then, if the kit has a reader, the physics and a flag motion, get the flag's path for the next 120 frames, and if it isn't all one value, set `kit.decider = await pickDecider(env)`. On a level whose flag stands still the decision model is never timed and never asked, because code loses nothing by deciding alone.

```js {"file":"examples/engine-checkpoint-07.mjs","region":"pick-decider","title":"Who decides when to fire","change":"Replace the pick-decider region of work/engine.mjs."}
// The decider's three timing answers in ms, or null if it is not there.
async function timeAnswers(env) {
  const times = [];
  for (let i = 0; i < 3; i++) {
    const text =
      `The planned shot lands in ${96 + 10 * i} frames,` +
      ` 0.${4 + i} paces from where the flag will be.`;
    try {
      const options = ['Fire now', 'Wait and look again'];
      times.push((await env.models.decide(text, options)).ms);
    } catch {
      return null;
    }
  }
  return times.sort((a, b) => a - b);
}

export async function pickDecider(env, budget = FRAME_BUDGET) {
  const step = 'time the decision model';
  const times = await timeAnswers(env);
  if (!times) {
    say(env, 'decision', step, 'unavailable; code decides');
    return { who: 'code', frames: 1 };
  }
  const toFrames = (ms) => Math.round((ms * 60) / 1000);
  const frames = Math.max(1, toFrames(times[1])); // the middle answer
  const spread = toFrames(times[2] - times[0]); // after the subtraction
  const who = spread <= budget ? 'model' : 'code';
  const took = times.map((t) => Math.round(t)).join(', ');
  const plan = `${count(frames, 'frame')} to plan for`;
  const gap = `a spread of ${count(spread, 'frame')}`;
  const against = `${gap} against a budget of ${budget}`;
  const so = who === 'model' ? 'the model decides' : 'code decides';
  const result = `answers took ${took} ms: ${plan}, and ${against}`;
  say(env, 'code', step, `${result}, so ${so} when to fire`);
  return who === 'model' ? { who, frames } : { who, frames: 1 };
}
```

## What the live models did

The course recorded two small models on Ollama, one climb each at temperature 0, the setting that makes a model give the same answer to the same question, with the course's own engine: `llama3.2:1b` and the larger `qwen2.5:7b`. The 1b and 7b in their names are their sizes, about 1 billion and 7 billion parameters, the numbers a model learns in training. The recordings are in `fixtures/recorded/live-llama3-2-1b.json` and `fixtures/recorded/live-qwen2-5-7b.json`, every question and answer with its time. Both models passed levels 6 and 7 with 10 of 10. Only one of them was allowed to decide.

- `llama3.2:1b` was timed on level 6 at 321, 277 and 262 ms, which gives 17 frames to plan for and a spread of 4, so it decided. It answered `Fire now` in all 10 rounds. On level 7 it took 265, 264 and 269 ms, a spread of 0, and again answered `Fire now` every time.
- `qwen2.5:7b` was timed on level 6 at 695, 601 and 602 ms, which gives 36 frames to plan for and a spread of 6, over the budget of 5, so your engine left the firing to code and never asked it during a round. On level 7 its answers took 720, 601 and 611 ms, a spread of 7, and code fired again. Each time its first answer was the slowest, by about a tenth of a second, and that alone put it over the budget. It answered `Wait and look again` to all six timing questions.

Neither model's answers helped. The model is asked only about a plan that is ready, so `Fire now` is a good answer every time, and it's what code would do. Waiting only spends the decider's frames, and in a round where the model goes on waiting for 600 frames the engine fires the plan it has just made. That is one climb per model, and the two are general small models standing in for a decision model built for this job. Module 08 sets out the rest of their record, with a level where the larger model did decide.

## A new case: when the flag turns

The walkthrough predicts where the flag will be. Use that on a question the lesson didn't ask: when will the flag next turn round? In `work/turn.mjs`, which the start command added (`node examples/start-07.mjs ./work new-case` adds it alone), write `framesToTurn(host)`. It returns the number of frames from now after which the flag first moves the other way: the smallest k of 1 or more for which its move from frame k to frame k + 1 goes the opposite way to its move from now to the next frame, or `null` if that is more than 600 frames away. Press no key, let no frame pass and write nothing to memory.

The flag turns at a bounce, and also when the timer runs out and the new speed has the other sign, and a new speed with the same sign is no turn. Decide how to count the frames before you write it, from the slice's stores and the definition above.

```
node examples/check-turn.mjs ./work --help-used "none"
```

The check asks your function about six moments of builds whose flag moves, one build that moves only the flag and two that also move and scramble the state, one of them with the wind on a server. For each, it works out the answer from a second copy of the game, set up the same way and run ahead frame by frame, and compares it with yours. Your function is handed a copy of memory, and it may not press a key, let frames pass, write to memory or read the screen. Each try is saved under `work/.attempts/` with a copy of your file, and `node lab.mjs status ./work` shows how your latest try did. No supplied file contains an answer to this case, on any route.

## Run the check

```
node lab.mjs level 6 ./work
node lab.mjs sweep ./work
node lab.mjs check 07 ./work

```

`level 6` comes first because `sweep` needs the kit level 6 left, with the flag's motion in it. `watch 6` writes `work/watch-6.html`, where you can step through the shots and see each shell come down where the flag has got to.

- `07-mover`: the slice missed a store or took one too many. Check that it grows until nothing is added, and that it follows the places read by guards as well as by values.
- `07-path`: your path drifted from the game. Check that the mover runs on an overlay and never on the game's memory, that `call` answers the imports the way your simulator does, and that a `null` is followed only by `null`s.
- `07-judge-motion`: your judge passed a path that ignores the bounce, passed one that gives `null` too early, or failed a correct path.
- `07-learn-motion`: the motion wasn't confirmed on level 6 in 2 rounds.
- `07-lead`: usually the delay was left out of the landing frame, or the aim went where the flag is now. With only the arrows, it must be the shortest flight that lands within 2 paces.
- `07-ready`: a plan more than 2 paces off was called ready, or `null` was.
- `07-decider`: the model was allowed to decide with a spread over the budget, an unavailable model wasn't left to code, or the engine planned for the fastest answer instead of the middle one.
- `07-wait`: the engine fired although the model said wait, didn't plan again after waiting, or asked again before the decider's frames had passed. The check also plays ten rounds with a model that always waits. Each round must end with one shot once its 600 frames are up, from a plan made after the last wait, and at least 9 of the 10 must hit.
- `07-sweep`: `FRAME_BUDGET` isn't the largest delay in your own unplanned column that hit at least 9 of 10, less 1. Check also that the unplanned run plans for 1 frame and still ticks the whole delay.
- `07-level-6`, `07-level-7`: the level wasn't passed within its budget. The steps `node lab.mjs level N ./work` prints show what your engine did.
