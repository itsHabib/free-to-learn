## The file's layout

`host.binary()` returns the game's `.wasm` file as bytes. A WebAssembly file starts with 8 fixed bytes, the magic number `00 61 73 6D` (the characters `\0asm`) and the version `01 00 00 00`. After that the file is a list of **sections**. Each section starts with an id byte and its size in bytes, followed by that many bytes of contents, so a reader can skip any section it doesn't need. Lob's file has these, by id:

- 1, type: 7 function signatures. A signature is the types of the values a function takes and the types of those it returns.
- 2, import: 4 functions the game calls from outside, `server_round`, `cos`, `sin` and `server_wind`.
- 3, function: the signature of each of the 25 functions defined in the file.
- 4, table: a table of functions that code can call by number. Lob's code never does.
- 5, memory: the memory's starting size, 2 pages of 64 KB.
- 6, global: 1 global variable, starting at 65536. The compiled C code keeps the address of its own scratch area of memory in it.
- 7, export: 24 names visible from outside, the memory and 23 functions.
- 10, code: the body of each defined function.
- 11, data: 281 bytes copied to address 65536 at start, the help text and the miss messages.

Sizes and counts are written as **LEB128** numbers, which take as many bytes as they need. A byte's 8 bits are numbered 0 to 7 from the lowest, and bit n is worth 2 to the power n, so the top bit, bit 7, is worth 128. Each byte of a LEB128 number carries 7 bits of the number, lowest bits first, and its top bit says whether another byte follows. A number below 128 fits in one byte, so the type section's size, 31, is the single byte `1F`. The code section's size, 5,954, takes two bytes, `C2 2E`. The first byte, `C2`, has its top bit set and carries 66. The second, `2E`, has its top bit clear and carries 46, worth 46 × 128. Together they make 66 + 5,888 = 5,954.

The figure draws the whole file from the top: each section's id byte, its size as a LEB128 number, and its contents to scale. A section's size counts its contents, the bytes after the size, so the data section's 290 hold the 281 bytes of data and the few bytes before them that say where they go.

Written in as few bytes as possible, 78112 takes three. It needs 17 bits, and each byte carries 7. Take the lowest 7 bits, 32, and set the top bit to get `A0`. Shift right by 7, which divides by 128 and drops the remainder, to get 610. Take its lowest 7 bits, 98, and set the top bit to get `E2`. Shift again to get 4, which fits with the top bit clear, giving `04`. So 78112 is `A0 E2 04`.

The number 78112 appears 29 times in the file's code, 28 of them as the offset of an instruction that reads or writes memory, and every time it's 5 bytes long, `A0 E2 84 80 00`. The figure reads both forms byte by byte. The **linker**, the tool that joins compiled code into one file, wrote every address with room for 5 bytes so that it could change an address later without moving any code. Both forms are correct LEB128, and only one rule reads both. Keep reading until a byte has its top bit clear, and never assume a width.

### Write readU32

`readU32(bytes, pos)` reads one number starting at `pos` and returns it with `next`, the position after its last byte, so the caller knows where to go on. Each byte's low 7 bits are shifted into place, `shift` going up by 7, until a byte with its top bit clear. JavaScript's `|` and `<<` work on 32-bit signed integers, so the 32nd bit would make the number negative, and `>>> 0` turns the result back into an unsigned number. `ranOff` is the error for a number that runs past the last byte. In `work/wasm.mjs`, replace the `read-u32` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"read-u32","language":"js","title":"Read an unsigned LEB128 number","change":"Replace the read-u32 region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"read-u32","title":"Read an unsigned LEB128 number","change":"Replace the read-u32 region of work/wasm.mjs."}
// A number that runs past the last byte is a broken file.
const ranOff = (pos) => new Error(`ran off the end at byte ${pos}`);

// { value, next }: an unsigned LEB128 number.
export function readU32(bytes, pos) {
  let value = 0;
  let shift = 0;
  let byte;
  do {
    if (pos >= bytes.length) throw ranOff(pos);
    byte = bytes[pos++];
    value |= (byte & 0x7f) << shift; // 7 bits, lowest first
    shift += 7;
  } while (byte & 0x80); // the top bit: another byte follows
  return { value: value >>> 0, next: pos };
}
```

## Signed numbers and the first bytes

Most LEB128 numbers in the file can't be negative: sizes, counts, indexes and offsets. An `i32.const` instruction pushes a constant onto the stack, explained under Instructions and their immediates, and that constant can be negative, so it's written as **signed LEB128**. The bytes are read the same way, and then one more rule applies. If bit 6 (value 64) of the last byte is set, the number is negative, and you subtract 2 raised to the power 7 × n, where n is the number of bytes read, so 128 for one byte and 16,384 for two. `7F` is 127 − 128 = −1. So a positive number with bit 6 set needs an extra byte. The game's `i32.const 104` is `41 E8 00`, where `E8` carries 104 and the `00` keeps it positive.

Here are the first 21 bytes of Lob's file, read by hand:

```
00 61 73 6D        magic: \0asm
01 00 00 00        version 1
01                 section id 1: type
1F                 its size: 31 bytes
07                 7 types follow
60 01 7F 01 7F     type 0: a function taking 1 i32 and returning 1 i32
60 01 7C 01 7C     type 1: a function taking 1 f64 and returning 1 f64
```

`60` marks a function type, and each list starts with its length. `7F` is i32, `7E` is i64, `7D` is f32 and `7C` is f64. Type 1 is the signature of `cos` and `sin`.

### Write readS32

`readS32` reads the bytes as `readU32` does, then applies the sign rule. Subtracting 2 to the power `shift` is the same as setting every bit from `shift` up, which `~0 << shift` does: `~0` is a number whose bits are all 1. After 5 bytes `shift` is 35 and every bit is already in place, so the fill applies only below 32. `| 0` makes the result a signed 32-bit number. Replace the `read-s32` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"read-s32","language":"js","title":"Read a signed LEB128 number","change":"Replace the read-s32 region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"read-s32","title":"Read a signed LEB128 number","change":"Replace the read-s32 region of work/wasm.mjs."}
// { value, next }: a signed LEB128 number.
export function readS32(bytes, pos) {
  let value = 0;
  let shift = 0;
  let byte;
  do {
    if (pos >= bytes.length) throw ranOff(pos);
    byte = bytes[pos++];
    value |= (byte & 0x7f) << shift;
    shift += 7;
  } while (byte & 0x80);
  // Bit 6 of the last byte set: negative. Fill the bits above with 1s,
  // which subtracts 2 to the power shift.
  if (shift < 32 && byte & 0x40) value |= ~0 << shift;
  return { value: value | 0, next: pos };
}
```

## What each section holds

`parseModule` has to read six of the sections, and each one is laid out in a few bytes. Two rules hold for all of them. The contents of a section start with a count, an unsigned LEB128 number, and that many entries follow. A **name** is written as its length in bytes, an unsigned LEB128 number, followed by that many bytes of text.

In the type section, id 1, each entry is the byte `60`, the list of parameter types and the list of result types, each list as a count and then one type byte for each. The 21 bytes above showed two entries.

In the import section, id 2, each entry is two names, the module and the field, then a kind byte, then what the kind needs. Kind 0 is a function, and it's followed by the index of its type. Lob's import section starts like this:

```
04                 4 imports follow
03 65 6E 76        a name of 3 bytes: env
0C 73 65 72 76 65 72 5F 72 6F 75 6E 64
                   a name of 12 bytes: server_round
00                 kind 0: a function
00                 its type is type 0
```

So the first import is the function `env.server_round`, of type 0. Both games import only functions. If you want your parser to read any file, the other kinds are 1 for a table (a type byte, then limits), 2 for a memory (limits) and 3 for a global (a type byte and a byte that says whether it can change). Limits are a flags byte, a smallest size and, when bit 0 of the flags is set, a largest size.

In the function section, id 3, each entry is one number, the index of a type. Entry 0 belongs to the first function the file defines, entry 1 to the next, and so on. Lob's section starts `19 03 04`, meaning 25 entries, and the first defined function has type 3.

In the global section, id 6, each entry is a type byte, a byte that is `01` when the global can change, and a short piece of code that gives its starting value, ending in `0B`. Lob's whole section is `01 7F 01 41 80 80 04 0B`: one global, an i32, changeable, starting at `i32.const 65536`. The three bytes `80 80 04` are 65536 as signed LEB128, 4 × 16,384.

In the export section, id 7, each entry is a name, a kind byte and an index. The kinds are those of the imports: 0 for a function, 1 a table, 2 a memory, 3 a global. Lob's export section starts like this:

```
18                 24 exports follow
06 6D 65 6D 6F 72 79
                   a name of 6 bytes: memory
02                 kind 2: a memory
00                 memory 0
09 67 61 6D 65 5F 69 6E 69 74
                   a name of 9 bytes: game_init
00                 kind 0: a function
04                 function 4
```

In the code section, id 10, each entry is one function body, its size in bytes and then the bytes. The section "Instructions and their immediates", below, says how to read a body. The entries are in the same order as those of the function section.

In the data section, id 11, each entry starts with a flags number. Flags 0 means a piece of code follows that gives the address in memory, ending in `0B`, as for a global. Then come a count of bytes and the bytes themselves. Lob's section starts `01 00 41 80 80 04 0B 99 02`: one entry, flags 0, the address `i32.const 65536`, then 281 bytes of data (`99 02` is 25 + 2 × 128). In other files, flags 1 means no address follows, and flags 2 means the number of a memory comes before the address.

Sections 4 and 5, the table and the memory, hold nothing your tool needs. Skip them by their size, and skip any section whose id you don't know the same way.

`parseModule(bytes)` returns what it read as one object, the **module**:

- `types`: `[{ params, results }]`, each a list of type names such as `'i32'`.
- `imports`: `[{ module, name, kind, type }]`, with `kind` the kind byte and `type` the type index of a function.
- `importedFuncs`: a number, how many of the imports are functions. Function indexes count those first.
- `funcTypes`: a list of type indexes, one for each defined function.
- `exports`: `[{ name, kind, index }]`, with `kind` the kind byte.
- `globals`: `[{ type, mutable, init }]`.
- `code`: one entry for each defined function, saying where its body is in the file. The course's own parser keeps `{ start, codeStart, end, locals }`: the position of the body after its size, the position of its first instruction, the position right after its last byte, and the locals as `[{ count, type }]`.
- `data`: `[{ offset, size, start }]`: the address in memory, the number of bytes, and the position of the first of them in the file.

The checks look at the counts, at the imports' `module` and `name`, and at the exports. The fields of a `code` or `data` entry are yours to choose. Keep the file's bytes on the module as well, for example as `mod.bytes`, because `decode(mod, index)` gets nothing else to read the body from. `funcName`, in the next section, names an imported function by its module and field joined by a dot.

### Write the cursor

Every section is a run of numbers, bytes and names read one after another, so a small object keeps the position: the **cursor**. Each of its readers reads one thing at the cursor's position and moves the position past it. `end` is where the cursor must stop, the end of the file or, in `decode`, the end of one body, so a broken body can't read into the next. `take` hands `readU32` or `readS32` the bytes up to `end` and moves on to the `next` they return. Floats are read with a `DataView` with the lowest byte first, as in module 02. Replace the `cursor` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"cursor","language":"js","title":"A position that moves past what it reads","change":"Replace the cursor region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"cursor","title":"A position that moves past what it reads","change":"Replace the cursor region of work/wasm.mjs."}
// A place in the file that moves on past each thing it reads, and
// never past end.
function cursor(bytes, pos = 0, end = bytes.length) {
  const c = { bytes, pos, end };
  const view = new DataView(bytes.buffer, bytes.byteOffset);
  const take = (read) => {
    const { value, next } = read(bytes.subarray(0, c.end), c.pos);
    c.pos = next;
    return value;
  };
  c.byte = () => {
    if (c.pos >= c.end) throw ranOff(c.pos);
    return bytes[c.pos++];
  };
  c.u32 = () => take(readU32);
  c.s32 = () => take(readS32);
  c.s64 = () => take(readS64);
  c.f32 = () => {
    c.pos += 4;
    return view.getFloat32(c.pos - 4, true);
  };
  c.f64 = () => {
    c.pos += 8;
    return view.getFloat64(c.pos - 8, true);
  };
  // A name: its length in bytes, then the text.
  c.name = () => {
    const n = c.u32();
    const text = bytes.subarray(c.pos, c.pos + n);
    c.pos += n;
    return new TextDecoder().decode(text);
  };
  // A count, then that many entries, each read by entry().
  c.vec = (entry) => {
    const n = c.u32();
    const out = [];
    for (let i = 0; i < n; i++) out.push(entry());
    return out;
  };
  return c;
}
```

A global's starting value and a data entry's address are both a short piece of code ending in `0B`. `constExpr` reads it and keeps the last constant, and `limits` reads the limits of a table or memory import. Replace the `const-expr` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"const-expr","language":"js","title":"Starting values and limits","change":"Replace the const-expr region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"const-expr","title":"Starting values and limits","change":"Replace the const-expr region of work/wasm.mjs."}
// A short piece of code that gives a starting value, ending in 0B.
function constExpr(c) {
  let value = null;
  for (;;) {
    const op = c.byte();
    if (op === 0x0b) return value;
    if (op === 0x41) value = c.s32();
    else if (op === 0x42) value = c.s64();
    else if (op === 0x43) value = c.f32();
    else if (op === 0x44) value = c.f64();
    else if (op === 0x23) value = { global: c.u32() };
    else {
      const hex = op.toString(16);
      const why = `unexpected opcode 0x${hex} in a constant expression`;
      throw new Error(why);
    }
  }
}

// Limits: a flags byte, the smallest size, and the largest when bit 0
// of the flags is set.
function limits(c) {
  const flags = c.u32();
  const min = c.u32();
  const max = flags & 1 ? c.u32() : null;
  return { min, max };
}
```

### Write the section readers

Each reader is the layout from the list above, read with the cursor's `vec`, which reads a count and then that many entries. `readImports` counts the imported functions in `mod.importedFuncs` as it goes, and reads past what the other kinds need without keeping it. Replace the `types-imports` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"types-imports","language":"js","title":"The type and import sections","change":"Replace the types-imports region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"types-imports","title":"The type and import sections","change":"Replace the types-imports region of work/wasm.mjs."}
// id 1: each entry is 60, the parameter types and the result types.
function readTypes(c) {
  return c.vec(() => {
    c.byte(); // 60, a function type
    const params = c.vec(() => VALTYPE[c.byte()]);
    const results = c.vec(() => VALTYPE[c.byte()]);
    return { params, results };
  });
}

// id 2: the module's name, the field's, a kind byte and what it needs.
function readImports(c, mod) {
  return c.vec(() => {
    const imp = { module: c.name(), name: c.name(), kind: c.byte() };
    if (imp.kind === 0) {
      imp.type = c.u32(); // a function, and the index of its type
      mod.importedFuncs++;
    } else if (imp.kind === 1) {
      c.byte(); // a table: its type, then limits
      limits(c);
    } else if (imp.kind === 2)
      limits(c); // a memory
    else if (imp.kind === 3) {
      c.byte(); // a global: its type, and whether it can change
      c.byte();
    }
    return imp;
  });
}
```

```js {"file":"examples/wasm-checkpoint.mjs","region":"code-data","title":"The code and data sections","change":"Replace the code-data region of work/wasm.mjs."}
// id 10: each body's size, then its locals; where its instructions
// start and where it ends are kept, and the body itself is skipped.
function readCode(c) {
  return c.vec(() => {
    const size = c.u32();
    const start = c.pos;
    const local = () => ({ count: c.u32(), type: VALTYPE[c.byte()] });
    const locals = c.vec(local);
    const body = { start, codeStart: c.pos, end: start + size, locals };
    c.pos = start + size;
    return body;
  });
}

// id 11: flags, the address (unless flags is 1), a count of bytes and
// the bytes, which are skipped.
function readData(c) {
  return c.vec(() => {
    const flags = c.u32();
    if (flags === 2) c.u32(); // the number of a memory
    const offset = flags === 1 ? null : constExpr(c);
    const size = c.u32();
    const segment = { offset, size, start: c.pos };
    c.pos += size;
    return segment;
  });
}
```

### Write parseModule

`parseModule` checks the first five bytes, then reads sections until the end of the file. Each section's size gives its `end`, and after the reader the cursor jumps there, which also skips the sections no reader asks for. Replace the `parse-module` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"parse-module","language":"js","title":"Read every section of the file","change":"Replace the parse-module region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"parse-module","title":"Read every section of the file","change":"Replace the parse-module region of work/wasm.mjs."}
export function parseModule(bytes) {
  const magic = [0x00, 0x61, 0x73, 0x6d, 0x01];
  if (magic.some((b, i) => bytes[i] !== b)) {
    throw new Error('not a WebAssembly module');
  }
  const mod = {
```

## Names and types of functions

Every function has an index, and calls, exports and your own code all name a function by it. Function indexes count the imports first. Lob's indexes 0 to 3 are its 4 imports, so the first function defined in the file, `game_init`, is function 4, and entry 0 of the function section belongs to it. The figure lines up the three numberings.

{{figure:function-index}}

`funcName(mod, index)` gives a function a name you can print:

- For an import, its module and field joined by a dot, such as `env.cos`.
- Otherwise, an export's name, such as `game_key`.
- Otherwise, `func` and the index, such as `func5`, for a function that is neither imported nor exported.

## Instructions and their immediates

The code section holds one body per defined function. A body starts with its size, then its **locals**, a list of pairs of a count and a type, so `01 01 7F` means one group of one i32 local. Then come the instructions, up to the body's final `end`, the byte `0B`.

WebAssembly instructions pass values to each other on a **stack**, a pile of values where an instruction takes its inputs off the top and puts its result back on top. `i32.const 5` pushes the number 5, and `i32.add` takes the top two values and pushes their sum. A function's locals are numbered variables of its own. `local.set 0` takes the top value and keeps it in local 0, `local.get 0` pushes a copy of local 0, and `local.tee 0` keeps the top value in local 0 and also leaves it on the stack. Here is the stack after each of four instructions, with the top on the right:

```
i32.const 5      stack: 5
i32.const 7      stack: 5 7
i32.add          stack: 12
local.set 0      stack: empty, and local 0 holds 12
```

Module 05 follows the stack through whole functions. In this module you only decode the instructions, and the stack explains what their immediates are for. A call takes one value off the stack for each parameter of the function it calls and pushes one for each result, which is what `funcType` tells module 05.

Each instruction is an **opcode** byte followed by its **immediates**, the fixed values written after it in the file:

- A memory access, such as `28` `i32.load`, `2A` `f32.load` or `36` `i32.store`, has two unsigned LEB128 numbers: the alignment, then the offset. The address it reads is the value it takes from the stack plus the offset. The alignment is only a hint, so it never changes the address, but you have to read past it.
- `41` `i32.const` has a signed LEB128 number. `42` `i64.const` has one of up to 64 bits, which `decode` gives as a BigInt such as `258808741888n`, because a JavaScript number can't hold every 64-bit integer. `game_init` uses several `i64.const`s. `43` `f32.const` has 4 bytes, a float stored little-endian (lowest byte first, as in module 02), and `44` `f64.const` has 8.
- `20` `local.get`, `21` `local.set` and `22` `local.tee` name a local by its index. `10` `call` names a function, and `0C` `br` and `0D` `br_if` name a block to jump out of.
- `02` `block`, `03` `loop` and `04` `if` have a block type byte. `decode` gives it as `null` when it's `40`, meaning the block returns nothing, and otherwise as the type's name, such as `'i32'`.
- `FC` is a prefix: a LEB128 number after it says which instruction this is. Lob uses `FC 00`, `i32.trunc_sat_f32_s`, which turns a float into an integer, in three functions.

An `i64.const` number is read by the same rule as an `i32.const` number, with BigInt arithmetic, because JavaScript's `<<` on numbers works on 32 bits only. For each byte add `BigInt(byte & 0x7f) << shift`, with `shift` starting at `0n` and going up by `7n`. When bit 6 of the last byte is set, subtract `1n << shift`, which is 2 to the power 7 × n, and the number is negative, as for `i32.const`. A 64-bit number takes at most 10 bytes. The first `i64.const` in `game_init` is `42 80 80 D0 91 C4 07`. The six bytes after the opcode carry 0, 0, 80, 17, 68 and 7, and the last, `07`, has bit 6 clear, so the number is 80 × 2¹⁴ + 17 × 2²¹ + 68 × 2²⁸ + 7 × 2³⁵ = 258,808,741,888, which `decode` gives as `258808741888n`. A single byte `7F` is −1n, as it's −1 for an `i32.const`.

The instructions above are the common ones. The full list of instructions that carry immediates is short:

- `02` `block`, `03` `loop`, `04` `if`: a block type.
- `0C` `br`, `0D` `br_if`: a block index. `0E` `br_table`: a list of block indexes (its length first), then a default.
- `10` `call`: a function index. `11` `call_indirect`: a type index, then a table index.
- `1C` `select` with types: a list of type bytes.
- `20` to `22`, the locals, and `23` `global.get`, `24` `global.set`: an index.
- `28` to `35`, the loads, and `36` to `3E`, the stores: alignment, then offset.
- `3F` `memory.size`, `40` `memory.grow`: one zero byte to skip.
- `41` to `44`, the constants.
- `FC`: a number that picks the instruction. 0 to 7 are the saturating conversions, with nothing after them. 8 `memory.init` has a data index and a zero byte, 9 `data.drop` a data index, 10 `memory.copy` two zero bytes and 11 `memory.fill` one.

Every other instruction is a single byte with no immediates, and there are 135 of them. You don't type their names. `work/opcodes.mjs` is given, complete. `PLAIN` maps each of those bytes to its name (`0x6A` to `'i32.add'`), `LOADS` and `STORES` name the memory accesses, and `SATURATING` lists the names for `FC 00` to `FC 07`. Import what you need with `import { PLAIN, LOADS, STORES, SATURATING } from './opcodes.mjs'`. An opcode in none of these is one your decoder doesn't know, and it should throw, naming the byte and its position. Keep each instruction's opcode byte with it as `code`, because the tables in `opcodes.mjs` are keyed by that byte, and module 05's lifter looks instructions up in them.

```js {"file":"examples/wasm-checkpoint.mjs","region":"read-s64","title":"Read a 64-bit signed LEB128 number","change":"Replace the read-s64 region of work/wasm.mjs."}
// { value, next }: a signed LEB128 number of up to 64 bits, a BigInt.
function readS64(bytes, pos) {
  let value = 0n;
  let shift = 0n;
  let byte;
  do {
    if (pos >= bytes.length) throw ranOff(pos);
    byte = bytes[pos++];
    value |= BigInt(byte & 0x7f) << shift;
    shift += 7n;
  } while (byte & 0x80);
  if (byte & 0x40) value -= 1n << shift;
  return { value, next: pos };
}
```

```js {"file":"examples/wasm-checkpoint.mjs","region":"prefixed","title":"The instructions behind the FC prefix","change":"Replace the prefixed region of work/wasm.mjs."}
  const sub = c.u32();
```

## Blocks and depth

`block`, `loop` and `if` each open a block, `end` closes the innermost one, and `else` switches an `if` to its second branch. `decode(mod, index)` gives every instruction a **depth**, the number of blocks open around it. The function body itself counts as the first block, so instructions directly inside it are at depth 1, and the body's final `end` is at depth 0. `else` and `end` are shown at the depth of the line that opened their block:

```
1   block
2     local.get 0
2     if
3       i32.const 1
3       local.set 1
2     else
3       i32.const 2
3       local.set 1
2     end
1   end
0 end
```

Lob's own code happens to contain no `else`, so the check also decodes a small function written by hand that has one. The depths are also a check on your decoder. A function whose depth doesn't come back to 0 at its last byte was decoded wrong, and a decoder that stops at the first `end` it meets would drop everything after the first closed block.

### Write decode

`decode` reads one body with a cursor that stops at the body's end. Each instruction is an opcode byte, then whichever of the four kinds it is: no immediates, a memory access, an entry of `IMMEDIATES`, or `FC`. Anything else throws, naming the byte and its position. The depth goes down before an `end` or `else` is kept and up after a block, a loop, an `if` or an `else` is kept, which puts each of them at the depth of the line that opened the block. Replace the `decode` region:

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"decode","language":"js","title":"Decode one function, with the depth of each instruction","change":"Replace the decode region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"decode","title":"Decode one function, with the depth of each instruction","change":"Replace the decode region of work/wasm.mjs."}
export function decode(mod, index) {
  const body = mod.code[index - mod.importedFuncs];
  if (!body) throw new Error(`no body for function ${index}`);
  const c = cursor(mod.bytes, body.codeStart, body.end);
  const out = [];
  let depth = 1; // the body itself is the first block
  while (c.pos < c.end) {
    const offset = c.pos;
    const code = c.byte();
    let op;
    let imm = [];
    if (PLAIN[code]) op = PLAIN[code];
    else if (LOADS[code] || STORES[code]) {
      op = LOADS[code] || STORES[code];
      imm = [c.u32(), c.u32()]; // the alignment, then the offset
    } else if (IMMEDIATES[code]) {
      const [name, read] = IMMEDIATES[code];
      op = name;
      imm = read(c);
    } else if (code === 0xfc) [op, imm] = prefixed(c, offset);
    else {
      const hex = code.toString(16);
      throw new Error(`unknown opcode 0x${hex} at byte ${offset}`);
    }
    // else and end sit at the depth of the line that opened the block.
    if (op === 'end' || op === 'else') depth--;
    out.push({ offset, code, op, imm, depth });
    if (['block', 'loop', 'if', 'else'].includes(op)) depth++;
  }
  if (depth !== 0) {
    const why = `did not close its blocks (depth ${depth})`;
    throw new Error(`function ${index} ${why}`);
  }
  return out;
}
```

## The listing

A listing is how you read what your decoder made of a function, and `node lab.mjs listing` prints yours, so its form is fixed. This is the course's own listing of `r_angle`, the function decoded by hand above:

```
(func r_angle (param -) (result f32))
  i32.const 0
  i32.load offset=78112
  local.tee 0
  i32.load offset=92
  local.get 0
  i32.load
  i32.xor
  f32.reinterpret_i32
end
```

- The first line is `(func NAME (param TYPES) (result TYPES))`, with the types separated by spaces and a `-` where there are none. `NAME` is what `funcName` returns, and the types are what `funcType` returns.
- Each instruction is indented two spaces for each level of its depth.
- A memory access shows `offset=N`, and nothing when the offset is 0. The alignment isn't shown.
- A call shows the index and the name, as in `call 5 <func5>`.
- A constant shows its value. An `f32.const` or `f64.const` is printed to 9 significant digits, `String(Number(value.toPrecision(9)))`, so 0.1 stored as a 4-byte float prints as `0.100000001`, and 25 prints as `25`.
- `block`, `loop` and `if` show `(result i32)`, with the type's name, when the block leaves a value, and nothing when it leaves none.
- `br_table` shows its block indexes and then `default=N`. Any other instruction shows its immediates as numbers separated by spaces, as in `local.get 0` and `br_if 1`.
- `notes` is a list with one entry for each instruction. When `notes[i]` isn't empty and instruction `i` isn't a call, pad the line with spaces to 44 characters and then add ` ;; ` and the note. A call line already names the function it calls, so it gets no note. Once your lifter of module 05 is written, `node lab.mjs listing` passes a note for every store, with what your lifter says the store writes.

### Write the listing

```js {"file":"examples/wasm-checkpoint.mjs","region":"imm-text","title":"What a listing shows after each name","change":"Replace the imm-text region of work/wasm.mjs."}
function immText(mod, ins) {
  const { op, imm } = ins;
  if (LOADS[ins.code] || STORES[ins.code]) {
    return imm[1] ? `offset=${imm[1]}` : ''; // no alignment, no 0
  }
  if (op === 'f32.const' || op === 'f64.const') {
    return String(Number(imm[0].toPrecision(9)));

  if (op === 'call') return `${imm[0]} <${funcName(mod, imm[0])}>`;
  if (op === 'br_table') return `${imm[0].join(' ')} default=${imm[1]}`;
  if (['block', 'loop', 'if'].includes(op)) {
    return imm[0] ? `(result ${imm[0]})` : '';
  }
  return imm.map(String).join(' ');
}
```

<!-- code-example {"file":"examples/wasm-checkpoint.mjs","region":"listing","language":"js","title":"The listing of one function","change":"Replace the listing region of work/wasm.mjs."} -->
```js {"file":"examples/wasm-checkpoint.mjs","region":"listing","title":"The listing of one function","change":"Replace the listing region of work/wasm.mjs."}
export function listing(mod, index, notes = []) {
  const t = funcType(mod, index);
  const types = (list) => list.join(' ') || '-';
  const name = funcName(mod, index);
  const head = `(func ${name} (param ${types(t.params)})`;
  const lines = decode(mod, index).map((ins, i) => {
    const imm = immText(mod, ins);
    const indent = '  '.repeat(Math.max(0, ins.depth));
    const text = `${indent}${ins.op}${imm ? ` ${imm}` : ''}`;
    // A call already names what it calls, so it gets no note.
    if (!notes[i] || ins.op === 'call') return text;
    return `${text.padEnd(44)} ;; ${notes[i]}`;
  });
  return `${head} (result ${types(t.results)}))\n${lines.join('\n')}`;
}
```

## What module 05 needs

Module 05 lifts the functions you can now decode. It walks `decode(mod, index)` instruction by instruction and keeps, in place of each number, an expression that says where the number comes from. From your decoder it needs:

- Every instruction of a function, in order, with its name and its opcode byte as `code`.
- Exact immediates: a memory access's offset becomes part of the place it reads or writes, a constant becomes a constant in an expression, a branch's index says which block it leaves, and a block's type says whether its end leaves a value.
- `funcType`, for how many values a call takes and leaves, and for the key handler's one parameter.
- `funcName`, so that a call to `env.sin` or `env.cos` can be recognised.
