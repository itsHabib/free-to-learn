1. State the promises

Goal: distinguish a useful program from a confined program, then state a boundary claim that an observation could disprove.

You need ordinary tests, arrays and the idea of a process. You do not need exploitation experience. This lab executes an original miniature instruction set inside a Rust program. It does not execute native plugins and it currently has no OS sandbox.

1.1 Assets, adversaries and exclusions

The supplied studio wants to turn a grayscale image into its negative. A pixel containing 12 should become 243. Run the demo after committing a prediction:

python3 run.py demo --attempt attempts/01-demo \
  --prediction "I expect the filter to work; that will not yet prove isolation."

Inspect the output and saved source identity. The original pixel values and transformed values are useful-behavior evidence. They say nothing about whether another program could read beyond its allowed memory, use another job's object or consume unlimited work.

The attacker in this model controls the bytecode, initial guest bytes and request fields it can express. The attacker does not control the Rust compiler, the native VM implementation, the broker, or the kernel. The protected objects are synthetic input/output tiles and synthetic data granted to a different job. No real secret is needed to test whether the boundary discriminates correctly.

An exclusion is part of a claim, not fine print. “This prevents a malicious native executable from reading my files” is outside the model. “The VM prevents this bytecode from reading a guest offset outside its declared region” is inside it. An incorrect native implementation could invalidate the latter claim; that is why the implementation and its assumptions must both be reviewed.

Practice: write two sentences in attempts/01-demo/claims.md: one about the image result you actually observed, and one proposed isolation claim that the run did not establish. Name the additional observation the second claim needs.

1.2 Follow authority across the boundary

Trace an intended read. A guest instruction selects a handle and range. The VM supplies the actual job identity to the broker. The broker selects a grant and object. Only then do bytes become available to the guest. The guest's claim about its job is data; it cannot create authority.

A worked sibling case: imagine two documents opened in an editor. Each tab labels its first local handle “1.” That label need not name the same document in both tabs. The trusted tab context decides which table is being consulted. A global lookup that ignores the tab would change the meaning of the handle. Our job tables have the same issue, even though the host application is different.

Draw four boxes: guest, VM, broker, host process. Mark which inputs each actor controls. In today's portable build, the first three live inside the same host process; drawing separate boxes does not create operating-system isolation. Module 5 explains what the additional process/kernel boundary would need.

Practice: the guest changes claimed_job from 1 to 2. Before opening learner.rs, write which component should be allowed to decide whether job 2's object is reachable and what trusted information that decision needs.

1.3 Write a falsifiable contract

A useful claim has an actor, condition, action and observable result. For example: “When a bytecode read asks for a range outside this job's grant, the broker denies it and leaves every object unchanged.” This is narrower and more testable than “the broker is secure.” It also names a positive obligation: requests inside a live read grant must still work.

Run check core in a new preserved attempt. Choose one failing line. Record its expected result, actual result and source snapshot hash. Do not patch yet. Explain how that observation contradicts one proposed promise. If the process merely failed to compile, you have no observation of guest behavior; record the setup failure instead.

Checkpoint: your report distinguishes output correctness, logical confinement and OS confinement; identifies guest-controlled versus trusted identity; and gives one falsifiable negative claim with a useful positive control. A later green check will not erase this first explanation.

Fresh application: a plugin emits an all-black tile while obeying every range and authority rule. Is that enough to declare the sandbox broken? State which product requirement may have failed and which isolation evidence would still be needed. No keyword or single yes/no answer substitutes for the distinction.

2. Admit only programs you understand

Goal: implement structural admission without confusing it with execution or termination, and explain why the admitted program cannot change underneath the VM.

Prerequisite: module 1 and reading a Rust match. Your code goes in Learner::validate. The supplied decoder and execution loop are infrastructure; do not replace them.

2.1 Bytes, instructions and canonical decoding

The capsule header identifies the format, instruction count, initial-data length and logical memory length. The supplied decoder checks the envelope and splits fixed 16-byte records. These are wire-format duties. Recognizing whether an operation and its operands belong to the language is admission policy.

In the supplied type, an unrecognized operation remains Instruction::Unknown. A known operation can still contain an invalid register or target. An enum name is not a promise that every value stored inside it is valid.

Run the wire group and inspect codec.rs. The decoder rejects a truncated capsule, trailing bytes and noncanonical reserved fields. These checks are supplied and should already pass. They do not mean your validator is correct.

Practice: commit a prediction about the admission group, then run it. For one failed case, identify whether the missing decision concerns the envelope, an instruction operand or a control-flow edge. Do not call all three “parsing.”

2.2 Validate operations and control flow

The public language contract is small. A program has 1–4,096 instructions. Registers are numbered 0 through 7. Only the nine named operations are supported. JUMP and JZ target an existing instruction index. A fallthrough edge must also lead to an existing instruction. HALT and unconditional JUMP have no fallthrough edge.

Consider a sibling program with three records: set register 0; conditionally jump to record 0; halt. Both possible edges from the conditional are inside the program. Now imagine removing the halt. If the condition is false, execution would fall off the end. The branch target is still legal, but the program is not structurally complete. Admission must consider both paths.

An unconditional jump back to itself is structurally valid. It does not promise to stop. Rejecting all loops would prevent useful image processing; allowing loops means a separate execution budget is necessary. Module 6 owns that obligation.

Repair validate using the public contract. You may use Instruction::registers() to inspect operands; writing instruction-decoding plumbing is not the task. Keep the positive cases. A validator that only allows HALT prevents many bad programs but fails the product.

python3 run.py check admission --attempt attempts/02-repair \
  --parent-attempt 02-first --prediction "Name the cases your change should now discriminate."

If a test fails, inspect the specific edge or operand named by its constructed input in checks.rs. A runtime PhysicalGuard means the supplied VM protected the lab after admission failed to do its job; it is not an admission success.

2.3 Bind validation to execution

Validation is about particular values. If another component changes those values afterwards, a correct validator has answered the wrong question for the eventual execution.

The supplied admit function clones the accepted program into an Admitted value with a private field. run_admitted uses that owned snapshot. Look at public case R06: the caller changes its original program after admission, while the admitted copy remains stable. This is a design boundary you must explain, not extra code to duplicate in the learner policy.

A printed hash helps identify a saved file. It does not itself prevent mutation or make the VM fetch from the hashed bytes. Connect the saved identity to the actual ownership/data path when writing your argument.

Checkpoint: admission cases pass, the useful demo still works, and your explanation distinguishes structural validity, immutable identity and runtime termination.

Fresh application: a proposed optimization caches “valid” under a file path and reloads the file just before execution. Describe a sequence of ordinary file edits that invalidates the argument, then specify the property a corrected cache must preserve. Do not assume the filename is content identity.

3. Keep guest memory inside its world

Goal: enforce the complete logical memory range and distinguish a logical escape from a native memory-corruption event.

Prerequisites: unsigned integers, arrays and module 2. Repair Learner::range. The physical slice checks in runtime.rs remain supplied and unchanged.

3.1 Linear memory and host memory

The guest sees offsets into one declared region. An offset is not a native pointer. The supplied runtime stores that region in a safe Rust vector followed by sixteen synthetic guard bytes, each 167. Those guard bytes are physically present but outside the guest's declared region.

This deliberate arrangement separates two questions: did Rust access allocated storage, and did the guest have permission to access that storage? A broken logical check can answer the first correctly and the second incorrectly. No out-of-bounds native access or real secret is necessary.

Before running check runtime, predict whether the one-byte guest in R05 can observe the guard. Save the prediction. Inspect the outcome and guest bytes afterwards. If 167 appears, call it a synthetic logical-isolation violation. It does not demonstrate arbitrary host-memory access, a kernel exploit or a production sandbox escape.

The WebAssembly specification makes a related boundary distinction: its memory model does not imply an unsafe program cannot corrupt its own layout inside linear memory. Our custom VM is not WebAssembly and inherits none of its implementation guarantees. WebAssembly introduction.

3.2 Check the complete range

For logical length L, offset o and count n, the entire half-open interval [o, o+n) must fit inside [0,L). A zero-byte operation may name the endpoint L; it may not name an offset beyond it. A one-byte access at L is outside the region.

Worked sibling: an eight-byte region has valid byte positions 0 through 7. A request starting at 6 for two bytes covers 6 and 7, so it fits. Starting at 6 for three bytes also reaches 8, so the whole request must fail. Copying the first two bytes and then failing would violate the all-or-nothing contract.

Integer arithmetic is part of this decision. The machine's ADD operation deliberately wraps at 32 bits. That is useful language semantics, but a wrapped range endpoint is not the mathematical endpoint used by the security contract. Your range implementation must distinguish them. Do not rely on debug-mode overflow panics as the policy.

Repair the function, preserving all valid boundaries. Use the public memory group, then rerun runtime because the same decision protects loads, stores and broker copies. Write a short argument for the entire domain, not only the examples. Explain zero length, a last-byte access, a span crossing the endpoint and a sum larger than u32 can represent.

3.3 Reset state between jobs

Isolation also has a time dimension. A new job must begin with zero registers and zero logical memory, then its own initial segment. Reusing a buffer without resetting it would let the next job observe data the previous one left behind.

The supplied runner creates a new register array and arena per run. Inspect the initialization before declaring that this property holds. The host's broker objects are different: their lifecycle is governed by grants and publication, which module 4 and module 6 address. “Everything is zeroed” would be an inaccurate description of the whole application.

Practice: propose a two-job observation that distinguishes fresh guest state from accidental reuse. Name what the first job writes, what the second is allowed to read, and the expected difference. Implement the small additional public regression if you choose; keep it separate from changing the required checks.

Checkpoint: range checks and R05 pass for the intended reason; the normal filter still works; your report identifies the logical boundary, physical backstop and next-job initialization separately.

Fresh application: a host call wants two disjoint guest spans for a header and payload. Their combined byte count is less than memory capacity. Is that sufficient to authorize both copies? State the required property of each span and of the operation as a whole, including what happens if only the second span is invalid.

4. Make authority explicit

Goal: implement a broker decision that binds a request to the correct job, live handle, right and complete object range.

Prerequisites: modules 1–3. Repair Learner::authorize; keep the actual job argument and untrusted request fields distinct.

4.1 Handles are not global object names

The guest sends a small integer handle. The broker owns grants that interpret that handle. A handle combines a 16-bit slot with a 16-bit generation. The same local handle can exist in two jobs without naming the same object.

The trusted caller supplies actual_job. The request also carries claimed_job, which the guest can influence. Choosing a grant table from the claim lets one principal ask the broker to exercise another principal's authority. That is a confused-deputy problem: the broker has access, but it is using that access on the wrong caller's behalf.

Worked sibling: a photo application gives its previewer handle 4 for a thumbnail. A backup component also has handle 4 for an archive. An incoming preview message saying “I am backup” does not become a backup request. The trusted communication context must bind the request to the previewer.

Predict the result of C02 before running authority. The correct result is defined by the trusted context; the request's self-description cannot change it. Record how this differs from simply rejecting every unusual claim.

4.2 Rights, ranges and identity over time

A matching job and slot are only part of the decision. A reused slot can belong to a new generation. A read grant does not imply write permission. An object may contain more bytes than the grant permits the guest to use. Every part must match the requested operation.

The grant's base and length define a window into its object. The request's offset is relative to that window. First establish authority for the complete relative range. The runtime's physical object-slice check is a separate safety backstop, not permission to use the entire object.

A zero-byte operation still needs a live handle and the right. It transfers no data, but skipping authority checks would make the API's semantics depend on a special size value and could create a surprising side channel or future extension hazard. This course's contract explicitly keeps those checks.

Repair authorization without keying it to fixture order or constant handle numbers. The two reference-worthy approaches you should be able to imagine are a per-job table and an explicit search constrained by the trusted job. You need not use either exact representation; the observable rule is what matters.

4.3 Do not let the broker become a deputy

The broker can access all synthetic objects because it owns the application state. That does not mean every request can use every object. Keep names, paths, claimed principals and direct object indices out of the authority decision unless the public contract deliberately grants them meaning.

The core broker reads an immutable input object and stages writes to a distinct output object. It copies a stable request's bytes as one operation. If authority is denied, no prefix of a write is allowed. Later, module 6 distinguishes this per-operation atomicity from publication of the whole job.

The capability idea is grounded in work on explicit authority and compartmentalization; our job-local grant table is an educational model, not an implementation of kernel capabilities. Capsicum primary paper.

Checkpoint: all authority cases pass, both legitimate local handles still work, and the identity/negative filters retain their expected outputs. In your report, explain why matching a slot, matching an object index and matching a live grant are three different claims.

Fresh application: a plugin receives permission to read a selected rectangle of a larger image object. A proposed shortcut checks only that the requested pixels fit somewhere in the full image. Describe the authority it has accidentally added, then design one permitted request and one forbidden request that distinguish the shortcut from the public contract. Do not use real private images.

5. Seal the operating-system boundary

Goal: state what a real restricted worker must establish, and refuse to claim native confinement from portable VM tests.

Native practical status: NOT IMPLEMENTED / NOT RUN. This page includes a runnable pure policy-model exercise. The full Linux activity requires an approved existing Linux environment, a reviewed fixed worker/adapter and explicit permission for child-only confinement. Nothing here asks you to change host settings or install a tool.

5.1 Setup and execution are different phases

Today's VM, broker and objects share a process. Their interfaces enforce model-level rules, but a native flaw in the trusted host implementation is outside the guest model. A separate worker process plus a kernel restriction would add another boundary with its own assumptions.

That worker must perform trusted setup before interpreting attacker-controlled bytes. Its executable and libraries load, bounded storage is prepared, unintended file descriptors are closed, and its environment is constrained. Only after the restriction succeeds may untrusted guest interpretation start. A failed setup cannot fall back to ordinary execution while claiming the worker is confined.

A worked sibling: a tool reads its configuration, opens a particular input pipe, then enters a restricted phase. Requiring it to open arbitrary files after the restriction would expand its authority. Conversely, allowing all of its setup operations forever would fail to describe the narrow execution phase. The phase boundary matters as much as a list of syscall names.

5.2 A syscall policy is one component

Linux seccomp filters inspect syscall metadata and arguments. They do not dereference a pathname pointer and decide whether its contents are a safe file. The kernel documentation explicitly distinguishes syscall filtering from a complete sandbox. This is why our design gives object authority to the broker instead of imagining that a filter can safely approve arbitrary guest pathnames. Linux seccomp documentation.

A policy must identify the intended ABI as well as operation numbers. On x86-64, x32 encodings require attention in addition to the ordinary architecture value. Allowing reads/writes also requires thinking about which descriptors they can use; denying new opens does not revoke an already inherited descriptor. seccomp manual.

No-new-privileges is another specific mechanism. It prevents certain exec-related gains, but is not a command to erase existing authority. Linux no-new-privileges documentation.

5.3 Evidence must name its boundary

Repair modeled_syscall and modeled_seal in learner.rs. The model admits only NativeX86_64, READ on descriptor 3, WRITE on descriptor 4, and EXIT (whose descriptor field is irrelevant). X32, other ABIs, unknown operations and other descriptor uses are denied. Guest interpretation may begin only if no-new-privileges was verified, the filter was installed, and descriptors were cleaned. Run the syscall practice group with a recorded prediction.

These are original model enums and booleans, not actual syscall numbers, BPF or kernel observations. Passing S01–S12 establishes the modeled decision behavior only. In a real worker, each precondition needs independent actual evidence; the worker cannot prove it simply by emitting true.

Run cargo run --offline -- native. It reports NOT RUN and exits with code 2. That is the correct result for this slice. It does not install a filter or inspect private machine state.

The future practical check must show both a harmless fixed probe that works without the filter and its specified denial inside the sealed child. It must also show that ordinary useful work still succeeds. A missing syscall, failed process launch or runtime panic is not proof that the intended rule blocked an operation.

Practice: annotate your current report with three columns: supported portable claim, proposed native claim, missing observation. Include exact worker/filter identity, successful seal, inherited resources and raw process outcome in the latter. Keep the proposed native claim marked unassessed.

Checkpoint: you can explain why passing modules 2–4 does not complete module 5. The practical checkpoint cannot be completed in this package. Continue the portable modules without treating this page as a native pass.

6. Bound work and make failure precise

Goal: charge for work before it happens, preserve atomic effects, and distinguish an expected refusal from broken infrastructure.

Prerequisites: modules 2–4; module 5's practical run is not needed for this portable exercise. Repair Learner::charge.

6.1 Fuel, byte budgets and termination

Every executed instruction consumes one fuel unit, including HALT and INVOKE. At zero fuel, no instruction executes. The language may admit loops, but the runtime must stop after the allowed number of steps. This separates the structural promise in module 2 from the resource promise here.

A host call additionally consumes one call and the number of bytes it transfers. Read and write budgets are separate. The maximum payload of one call is 4,096 bytes. Many small calls still count toward the cumulative budget. A zero-byte call consumes a call, because the crossing itself is work.

Worked sibling: a budget permits two calls and six read bytes. Reading four bytes leaves one call and two read bytes. A second request for three bytes must fail before any copy, even though it is below the per-call maximum. A second request for two bytes is legal. This is not a bandwidth benchmark; it is a deterministic state-transition contract.

Predict the current budget results, save the attempt, then repair the transition function. The function receives the prior state by value. On success it returns the new state; on failure it returns an error. Do not wrap a depleted unsigned counter into a huge remaining allowance.

The supplied VM also has an emergency maximum step guard. A broken learner policy cannot run forever in these fixtures, but an emergency PhysicalGuard result is evidence of a broken policy, not successful fuel accounting. Likewise, a thirty-second capture-runner deadline is an infrastructure backstop and cannot masquerade as guest budget exhaustion.

6.2 Atomic broker effects and failed jobs

Each broker operation either copies the complete authorized range or copies nothing. The runtime computes and validates the relevant ranges before the copy. That is per-operation atomicity.

The application has a second boundary: the whole job's output is staged. Several writes may succeed, then a later instruction may trap. The failed job must not publish a partly transformed image as a successful result. The supplied portable runtime clones the synthetic world for staging and replaces the original only after successful HALT.

Inspect R07. It performs an otherwise useful write and then requests an invalid memory read. The expected result combines the fault with unchanged published objects. Checking only the error message misses the publication property. Conversely, deleting every staged result would break successful jobs.

Practice: explain which state must remain unchanged after a denied call, and which additional state must remain unpublished after a failed job. Then run the integrated runtime group using your repaired policies.

6.3 Denial is not every kind of failure

Admission rejection, memory denial, authority denial and budget exhaustion are model outcomes. PhysicalGuard means a supplied lab backstop intervened after policy failure or an unexpected state. A compiler error means no model execution occurred. native returning NOT RUN means a required environment is absent. A runner deadline says the recording tool stopped waiting; it does not identify the intended security mechanism.

The capture stores raw exit status alongside output and hashes. Your report supplies the interpretation. Do not replace raw evidence with a green badge. A test passes only when the observed result matches that particular contract, including its useful positive control.

Checkpoint: budget and runtime groups pass with exact threshold behavior. You can explain why charging before a copy matters and why a failed job's staged changes remain invisible.

Fresh application: a new host operation expands compressed bytes into guest memory. Its input fits the per-call byte limit, but the expansion can be much larger. State which quantity the current accounting fails to bound and what new public contract would be needed before adding the operation. You are not asked to build a decompressor.

7. Break, repair and defend the boundary

Goal: produce a reproducible investigation that connects a specific false promise, a controlled witness and a useful repair.

Prerequisites: portable modules 1–4 and 6. Native confinement remains unassessed.

7.1 Choose a discriminating counterexample

Run check core from a fresh preserved attempt. Choose a boundary you initially got wrong and return to that first source snapshot. Name the claim, the fixture, the expected observation and the actual observation. A helpful witness is small enough that you can explain why it discriminates the flawed rule from the intended one.

Do not change the implementation and the test input simultaneously and then attribute a different outcome solely to the repair. Preserve the original witness and add new cases separately. If the witness only hits a physical backstop, state that; do not relabel it as the policy denying an operation.

Worked sibling: a validator accepts an invalid final fallthrough. The runtime then stops with PhysicalGuard. After repair, the same program is rejected before step zero, while a valid looping program is still admitted. Those two observations support an admission repair. A screenshot showing the runtime no longer crashes would be much weaker.

7.2 Keep useful behavior

The public runtime checks include identity and negative filters, an empty input and a full default tile. These prevent broad refusal from looking like a secure repair. Add a different valid program or grant layout to your own regressions. Explain why it is valid under the published contract rather than merely “something my code accepts.”

A passing public suite is evidence about those cases. It is not proof over every instruction sequence, every range or every grant table. Strengthen it with an argument about the rule itself: what remains true at admission, at a memory operation, at a broker call, after a budget transition and at publication?

Run all practice groups, including transfer only when you are ready for module 8. Keep the source, prediction, observed result and revised explanation bound together. A source hash from the first attempt must not be attached to the latest implementation's result.

7.3 Deliver an assurance dossier

Create report.md in your final attempt directory with these five parts:

  1. Model: attacker controls, trusted components and excluded claims.
  2. Violation: original false promise, smallest retained synthetic witness and actual observation.
  3. Repair: why the changed rule eliminates that violation, including boundaries and arithmetic.
  4. Useful controls: at least one independently chosen permitted case and its expected output.
  5. Limits: untested cases, assistance, physical backstops and the missing native Linux evidence.

Attach the earlier attempt ID instead of rewriting its explanation. A reviewer should be able to reproduce the current attempt from its source snapshot and inspect how your reasoning changed.

The rubric is descriptive: scope, mechanism, discrimination, useful repair and transfer are supported, need revision or are not assessed. A different correct implementation is acceptable. Matching an instructor's code shape is not a requirement.

Checkpoint: the portable suite passes for your implementation, your dossier identifies its exact source and raw results, and a second reader can tell which claims remain unsupported. This is a portable project milestone. It is not a native sandbox certification or full course completion.

Fresh application: another team hands you a report with an impressive number of passing cases but no source identity and no valid positive controls. Write the two most informative follow-up requests and explain which possible false conclusion each would address. Do not merely request “more tests.”

8. Transfer: two plugins and a delayed operation

Goal: adapt the authority argument when checking a request and applying its effect occur at different times.

This is a less-guided challenge. Modules 1–4 and 6–7 taught the necessary ideas: trusted principal context, live grant identity, rights/ranges, atomic effects and explicit claims. There is no repair walkthrough or answer key in the learner package.

8.1 The changed product

The tile studio now has two plugin principals. A plugin can submit an output operation for later execution. Between submission and commit, the application may revoke a grant, reuse a slot for another generation, or change an unrelated grant.

The required rule is precise: a revocation effective before commit prevents that operation's effect. Changes to unrelated authority must not arbitrarily stop an otherwise valid operation. A queued request cannot gain another principal's authority or silently acquire the authority of a reused handle slot.

The Queued value records the original principal, handle, grant epoch, operation and range. Current grants and the current global epoch are supplied at the decision point. Repair Learner::queued to answer whether the request may commit under the stated contract. Do not assume that every increment of the global epoch revoked this particular grant.

Generations and epochs are not globally unique grant identities. Two live grants may share a principal, generation, epoch, rights and usable range while naming different slots and objects. Revoking one must not let the other authorize a write through the revoked handle. Conversely, revoking the other slot must leave the original request usable. State which fields bind a queued request to its exact live authority before writing the predicate.

8.2 Your investigation

Before running the public transfer group, commit a prediction and draw a timeline of the events you believe matter. Name the assumption from the synchronous broker that no longer holds. Do not start from a patch you remember; start from the new claim.

The ten public Q cases are practice checks for the interface contract. They include ordinary completion, revoked authority, reused generation, an unrelated epoch change, a different principal and competing live slots with the same generation and epoch. They are inspectable and cannot be called secret or independent assessment.

After repairing the policy, propose a new schedule combining at least two changed conditions, and a second schedule in which work must still succeed. State the decision at the commit point and support it with the grant's identity and lifecycle. Do not just replace job numbers in a public case.

For each schedule, predict every object's complete final bytes. Include a live competing grant, nonzero grant windows, and an independent operation that must still succeed. Check that denial changes no bytes, permission changes exactly its intended window, and the competing object's bytes remain untouched. A vector of permission booleans alone does not establish those effects.

8.3 What your evidence can establish

The current portable slice evaluates the delayed-authorization decision and supplies a deterministic event driver in schedule.rs. Public cases Q06–Q10 queue writes, revoke an authority and commit, checking the decisions and object effects. Q08–Q10 compare every byte across three objects; they vary grant order, commit order and which slot is revoked. This is a small in-memory event model, not a production asynchronous job system. You are not responsible for building a scheduler or storage system.

An independent final assessor should derive fresh interleavings from the published requirements, without sharing their concrete instances with the lesson author or learner. The revised package still needs independent final assessment. Keep your public-practice result separate from any later fresh-case result.

Deliver: a revised threat model; your queued policy; first and revised attempt records; one forbidden and one permitted novel schedule; an explanation of why slot identity, generation, principal, rights and timing each do or do not affect your decision; and remaining limits.

Completion boundary: passing the delayed-policy checks completes this portable challenge's public checks. It does not supply the missing Linux worker, independent review, human learning evidence or live Free to Learn acceptance.
